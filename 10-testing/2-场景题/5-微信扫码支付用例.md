# 微信扫码支付用例

## 面试题：如何测试微信扫码支付功能

这是一道经典的测试设计场景题，考察系统化思维和边界场景覆盖能力。核心方法：**按支付流程分段，每个环节考虑正常+异常+边界**。

---

## 支付流程梳理

```
用户扫码 → 创建订单 → 调起支付 → 输入密码 → 支付处理 → 结果通知 → 订单状态更新
   │           │          │          │          │          │           │
   ▼           ▼          ▼          ▼          ▼          ▼           ▼
 扫码环节   订单环节   支付环节   密码环节   处理环节   回调环节    业务环节
```

---

## 一、扫码环节

| 测试点 | 正常 | 异常/边界 |
|--------|------|----------|
| 二维码类型 | 微信支付码正常识别 | 付款码（反向）能否识别？其他 App 码？ |
| 二维码时效 | 有效期内扫码成功 | 过期二维码扫码提示？ |
| 二维码状态 | 正常码扫码成功 | 已支付码重复扫码？已取消码扫码？ |
| 扫码环境 | 正常光线/距离 | 光线暗/反光/褶皱/破损？ |
| 摄像头权限 | 授权后扫码 | 未授权摄像头？ |

---

## 二、订单环节

| 测试点 | 正常 | 异常/边界 |
|--------|------|----------|
| 订单金额 | 正常金额展示 | 0 元？0.01 元？999999.99 元？ |
| 金额精度 | 1.23 元正确展示 | 1.234 元（3 位小数）？ |
| 商品信息 | 商品名/数量正确 | 超长商品名？特殊字符？ |
| 订单时效 | 15 分钟内未支付自动关闭 | 倒计时最后 1 秒支付？ |
| 重复下单 | 同一商品正常下单 | 快速连续点击创建多个订单？ |
| 库存 | 库存充足正常下单 | 库存为 0？库存为 1 时并发下单？ |

---

## 三、支付环节

### 金额相关

| 测试点 | 正常 | 异常/边界 |
|--------|------|----------|
| 余额支付 | 余额 ≥ 订单金额 | 余额不足？余额刚好等于？余额多 0.01？ |
| 银行卡支付 | 正常扣款 | 银行卡过期？限额？单笔/单日限额？ |
| 组合支付 | 余额+银行卡 | 余额为 0 全用银行卡？ |
| 优惠券/折扣 | 正常抵扣 | 优惠券过期？部分抵扣？折扣后为 0？ |
| 手续费 | 含手续费正常计算 | 手续费使总金额超出限额？ |

### 网络相关

| 测试点 | 正常 | 异常/边界 |
|--------|------|----------|
| 网络正常 | 支付成功 | 支付中断网？弱网？ |
| 请求超时 | 正常返回 | 支付请求超时后如何提示？ |
| 重复提交 | 一次请求 | 快速多次点击支付按钮？ |

---

## 四、密码/验证环节

| 测试点 | 正常 | 异常/边界 |
|--------|------|----------|
| 密码正确 | 支付成功 | 密码错误 1 次？连续错误 5 次？ |
| 免密支付 | 小额免密成功 | 免密额度边界？刚好等于免密额？ |
| 指纹/面容 | 生物识别通过 | 指纹不匹配？面容识别失败回退？ |
| 验证码 | 短信验证码正确 | 验证码过期？错误 3 次？收不到短信？ |
| 账户锁定 | 正常登录 | 密码错误多次后账户锁定？ |

---

## 五、支付处理环节

| 测试点 | 正常 | 异常/边界 |
|--------|------|----------|
| 支付成功 | 余额扣减、订单更新 | — |
| 支付失败 | 余额不扣、订单标记失败 | 银行返回失败？风控拦截？ |
| 支付处理中 | 等待结果 | 长时间处理中？最终超时？ |
| 重复扣款 | 不重复扣 | 同一笔订单支付两次？ |
| 金额校验 | 扣款金额=订单金额 | 扣款金额不匹配？ |

### 并发场景

| 场景 | 预期 |
|------|------|
| 同一订单两个设备同时支付 | 只有一笔成功，另一笔退款 |
| 同一余额多个订单同时支付 | 余额扣减正确，不超扣 |
| 库存为 1 时 10 人同时支付 | 只有一人成功，其余提示库存不足 |

---

## 六、回调/通知环节

| 测试点 | 正常 | 异常/边界 |
|--------|------|----------|
| 支付成功回调 | 商户收到通知、订单更新 | — |
| 回调延迟 | 短延迟正常处理 | 回调延迟 5 分钟？1 小时？ |
| 回调丢失 | 正常收到 | 回调丢失怎么办？商户主动查询？ |
| 重复回调 | 幂等处理 | 微信重复发送回调，只处理一次 |
| 回调签名 | 签名校验通过 | 签名被篡改？伪造回调？ |
| 回调顺序 | 按序处理 | 先收到失败回调再收到成功回调？ |

---

## 七、退款环节

| 测试点 | 正常 | 异常/边界 |
|--------|------|----------|
| 全额退款 | 退款成功、余额恢复 | — |
| 部分退款 | 部分退款成功 | 退款金额 > 支付金额？ |
| 重复退款 | 不重复退 | 同一笔退款请求发两次？ |
| 退款到原路 | 退回银行卡/余额 | 原支付方式已注销？ |
| 退款时效 | 规定时间内到账 | 退款超时？ |

---

## 八、安全测试

| 测试点 | 说明 |
|--------|------|
| 篡改金额 | 抓包修改支付金额，服务端是否校验 |
| 越权支付 | 支付他人订单 |
| 重放攻击 | 重复发送支付成功回调 |
| 敏感信息 | 密码是否掩码、Token 是否加密 |
| SQL 注入 | 订单号/金额字段是否有注入风险 |
| 并发漏洞 | 余额扣减是否有竞态条件 |

---

## 九、兼容性与性能

| 维度 | 测试点 |
|------|--------|
| 设备兼容 | iOS/Android 各主流机型 |
| 系统版本 | Android 10~14、iOS 14~17 |
| 微信版本 | 最新版 + 前 2 个大版本 |
| 网络环境 | WiFi / 4G / 5G / 弱网 |
| 性能 | 高并发支付（JMeter 模拟 500 TPS） |
| 压力 | 大促场景峰值支付 |

## 用例设计方法总结

| 方法 | 应用 |
|------|------|
| **等价类划分** | 金额边界（0/0.01/最大值）、余额状态（足/不足/刚好） |
| **边界值分析** | 支付超时时间、免密额度、密码错误次数 |
| **状态迁移** | 订单状态（待支付→支付中→已支付/已关闭） |
| **错误推测** | 断网、重复点击、篡改金额 |
| **正交实验** | 支付方式 × 网络环境 × 金额范围 |

---

## 一句话总结

> 微信扫码支付测试按流程分段覆盖（扫码→订单→支付→密码→处理→回调→退款），每段考虑正常+异常+边界+并发，重点关注金额精度、重复支付、回调幂等、并发扣款四大风险点，辅以安全测试（篡改/重放/越权）和兼容性性能测试。
