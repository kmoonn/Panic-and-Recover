# 印象最深的 Bug

## 面试题：说说你印象最深的一个 Bug

这道题考察的不是 Bug 本身有多复杂，而是你**发现问题→定位原因→推动修复→总结经验**的完整闭环能力。

---

## 回答框架（STAR 变体）

```
S 背景 ──→ 什么项目、什么功能、什么时候
T 任务 ──→ 你负责什么（发现/排查/验证）
A 行动 ──→ 怎么发现的、怎么定位的、怎么修复的
R 结果 ──→ 修复后效果、补了什么用例、改了什么流程
```

### 回答要点

| 要点 | 说明 | 加分项 |
|------|------|--------|
| **发现的场景** | 正常测试发现 / 线上反馈 / 自动化巡检 | 主动发现的比被动发现的好 |
| **现象描述** | 清晰、可量化 | "1% 的用户登录后白屏" 比 "登录有问题" 好 |
| **定位过程** | 展现排查思路和方法 | 用到抓包/日志/链路追踪等工具 |
| **根因分析** | 为什么会产生这个 Bug | 不只说"代码写错了"，要挖到设计/流程层面 |
| **修复验证** | 不只验证 Bug 本身 | 回归了关联功能 |
| **预防措施** | 如何防止同类问题再次发生 | 补自动化 / 加监控 / 改流程 |

## 示例回答

### 示例 1：并发导致的双重支付

**背景**：支付系统上线前压测，模拟 100 并发用户同时支付同一笔订单。

**现象**：同一笔订单被扣款两次，数据库出现两条支付流水。

**定位过程**：
1. 查数据库 → 发现同一 order_id 有两条状态为"已支付"的记录
2. 查代码 → 支付接口先查订单状态再扣款，但两步之间没有加锁
3. 时序分析：
   ```
   请求A: 查订单状态=未支付 → 通过
   请求B: 查订单状态=未支付 → 通过（A 还没更新状态）
   请求A: 扣款 → 成功
   请求B: 扣款 → 成功 ← 重复扣款！
   ```

**根因**：查询和更新不是原子操作，存在竞态条件（Check-Then-Act）。

**修复**：
- 方案一：数据库乐观锁 `UPDATE orders SET status='PAID' WHERE id=? AND status='UNPAID'`，更新失败说明已被支付
- 方案二：分布式锁（Redis `SETNX`），同一订单同一时刻只允许一个支付请求
- 最终选择方案一 + 幂等 Token，简洁且可靠

**预防**：
- 支付相关接口增加并发测试用例
- 加了支付流水的唯一索引（order_id + pay_round）
- 代码评审增加并发场景检查项

### 示例 2：时区导致的日报数据异常

**背景**：业务方反馈日报数据从某天起比实际少约 8 小时的量。

**现象**：日报统计的截止时间从 24:00 变成了 16:00。

**定位过程**：
1. 对比正常和异常日期的 SQL → 发现查询条件中的时间范围不同
2. 查代码 → 新版本将时间处理从 `Date` 改为 `LocalDateTime`
3. 定位根因：
   ```java
   // 旧代码（正确）
   Date endOfDay = DateUtils.endOfDay(new Date()); // 用系统时区

   // 新代码（Bug）
   LocalDateTime endOfDay = LocalDateTime.now(ZoneOffset.UTC); // 用 UTC 时区
   // 中国是 UTC+8，所以 24:00 变成了 16:00 UTC
   ```

**根因**：重构时误将时区从系统默认时区改为 UTC，导致统计时间范围少了 8 小时。

**修复**：改回系统默认时区 `ZoneId.systemDefault()`，并统一时区处理工具类。

**预防**：
- 所有时间相关代码统一使用封装好的时间工具类
- 增加日报数据的基线对比自动化巡检
- Code Review 清单增加"时区处理"检查项

## 常见 Bug 类型与加分方向

| Bug 类型 | 常见根因 | 展现深度的方向 |
|---------|---------|--------------|
| 并发 Bug | 竞态条件、锁粒度 | 分析时序图、JMeter 压测复现 |
| 数据 Bug | 时区、编码、精度 | 追踪数据流转链路、边界值分析 |
| 兼容性 Bug | 浏览器/系统差异 | 矩阵化测试策略 |
| 性能 Bug | N+1 查询、内存泄漏 | 性能分析工具（Profiler/ARMS） |
| 安全 Bug | 越权、注入 | 渗透测试方法 |
| 缓存 Bug | 缓存与 DB 不一致 | 缓存一致性方案分析 |

## 回答避坑

| ❌ 不要这样说 | ✅ 应该这样说 |
|-------------|------------|
| "开发写了个 Bug，我提了 JIRA" | "我发现现象后，通过抓包/日志定位到..." |
| "就是个小 Bug，改了一行代码" | "虽然修复很简单，但根因是设计没考虑并发场景" |
| "修好了就算了" | "补了并发测试用例，加了监控告警，改了 CR 清单" |
| "线上出了大事故"（除非你真是负责人） | 选择一个你能讲清楚完整闭环的 Bug |

---

## 一句话总结

> "印象最深的 Bug"回答核心是展现完整闭环：发现→定位→根因→修复→预防，用 STAR 框架组织，重点是定位思路和预防措施，而非 Bug 本身有多严重——能讲清楚"为什么会产生"和"如何防止再发"才是加分项。
