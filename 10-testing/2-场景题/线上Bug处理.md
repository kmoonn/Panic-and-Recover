# 线上问题发生后 QA 需要做什么

## Q: 线上出问题了，QA 的职责是什么？

线上出问题时 QA 不只是"等修复"，而是要参与到整个应急闭环里。按时间线分四个阶段：

---

## 一、止血 — 降低影响面最优先

> 线上问题最优先的是降低影响面，而不是第一时间定位根因。

| 行动 | 说明 |
|------|------|
| 确认影响范围 | 多少用户受影响？哪些核心链路？有没有资损或数据风险？ |
| 判断优先级 | 单用户偶发 / 某接口稳定复现 / 整个服务不可用 |
| 配合止血 | 回滚版本、关闭实验开关、限流降级，先把用户影响控制下来 |

**关键原则**：先止血再定位，先保核心功能可用。

## 二、协助定位 — 找出复现路径

| 行动 | 说明 |
|------|------|
| 锁定变更窗口 | 是哪个版本、哪次变更引入的？ |
| 收集现场信息 | 日志、监控告警、错误堆栈、请求参数 |
| 构造复现路径 | 结合以上信息把最小复现步骤找出来，交给开发确认 |

## 三、验证修复 — 回归而非仅验证单点

> 开发出修复方案后，QA 要做的不只是验证 bug 本身修好了。

| 行动 | 说明 |
|------|------|
| 验证 bug 本身 | 用复现路径确认问题已解决 |
| 回归关联链路 | 与该功能相关联的链路也要一起回归 |
| 灰度上线 | 验证通过后才可放行上线，避免二次事故 |

## 四、复盘与防复发 — 漏放根因分析

| 讨论方向 | 典型问题 |
|---------|---------|
| 用例覆盖 | 漏测了什么场景？用例是否需要补充？ |
| 环境差异 | 测试环境无法复现的原因？数据/配置/依赖差异？ |
| 边界 case | 是否为极端输入/并发/数据量导致？ |
| 流程改进 | 能否通过监控告警提前发现？能否加自动化巡检？ |
| 预防措施 | 补充回归用例、加监控埋点、加预发校验 |

---

## 流程一览

```
线上问题发生
    │
    ▼
 ① 止血 ←── 最优先，先控制影响面
    │        回滚 / 降级 / 关开关
    ▼
 ② 协助定位 ←── 找变更窗口 + 构造复现路径
    │
    ▼
 ③ 验证修复 ←── 不只验证 bug 本身，回归关联链路
    │             灰度上线后才放行
    ▼
 ④ 复盘 ←── 根因分析 + 补用例 + 改流程 + 防复发
```

## 一句话总结

> QA 参与线上问题全闭环：止血→定位→验证→复盘，先控制影响面再找根因，验证修复要回归关联链路，复盘要追问漏放原因并补防复发措施。
