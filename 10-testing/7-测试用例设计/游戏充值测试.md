# 游戏充值测试用例

## 面试题：如何设计游戏充值功能的测试用例

游戏充值 = 支付 + 发货（游戏币/点券/礼包），比普通支付更强调**「钱货一致」**：既不能玩家付了钱不到账，也不能没扣钱却发了道具。核心方法：**按「选择档位 → 下单 → 支付 → 回调 → 发货到账」流程分段，每段考虑正常+异常+边界+并发，重点盯充值到账一致性与幂等**。

---

## 充值流程

```
选择充值档位 → 创建订单 → 调起支付 → 支付处理 → 支付回调 → 游戏发货 → 到账展示
     │            │          │          │          │          │           │
     ▼            ▼          ▼          ▼          ▼          ▼           ▼
   档位环节     订单环节   支付环节   处理环节   回调环节   发货环节    展示环节
```

> 支付环节的通用测试点复用[微信扫码支付用例](微信扫码支付用例.md)（金额精度/密码/网络/回调幂等），本篇聚焦**充值特有的发货、首充、活动、多平台货币**。

---

## 一、充值档位与商品

| 测试点 | 正常 | 异常/边界 |
|---|---|---|
| 档位展示 | 6/30/68/128/648 等档位与对应点券正确 | 档位与到账数量不匹配？ |
| 首充翻倍 | 首充双倍正确发放 | 二次充值还给首充奖励？（首充只享一次） |
| 赠送/加赠 | 充 X 送 Y 正确到账 | 活动期外仍加赠？活动临界时间点？ |
| 自定义金额 | 支持任意金额充值 | 0 元？0.01？超大额？小数位？ |
| 限购档位 | 限购礼包按上限购买 | 超出限购次数拦截？ |
| 价格一致 | 展示价 = 下单价 = 扣款价 | 客户端篡改价格，服务端是否校验？ |

---

## 二、订单与支付环节

| 测试点 | 正常 | 异常/边界 |
|---|---|---|
| 创建订单 | 正常生成唯一订单号 | 快速连点创建多笔订单？ |
| 支付方式 | 微信/支付宝/Apple/Google/银行卡 | 各渠道限额、渠道不可用？ |
| 支付成功 | 扣款成功进入发货 | — |
| 支付失败 | 不扣款、不发货、订单标记失败 | 银行返失败？风控拦截？ |
| 支付中断 | 断网/关闭 App/切后台 | 支付中杀进程，订单状态？ |
| 订单超时 | 未支付订单自动关闭 | 超时后又支付成功怎么处理？ |
| 重复支付 | 同一订单只扣一次 | 同一订单支付两次？ |

---

## 三、回调与发货环节（充值核心）

| 测试点 | 正常 | 异常/边界 |
|---|---|---|
| 支付回调 | 收到回调后触发发货 | 回调延迟 5min/1h 才到？ |
| 发货幂等 ⭐ | 重复回调只发一次货 | 支付平台重复推送回调 → 是否重复发币？ |
| 回调丢失 | 主动查单补发货 | 回调丢失，玩家没到账怎么补？ |
| 回调验签 | 签名校验通过才发货 | 伪造/篡改回调 → 服务端拒绝？ |
| 发货失败 | 记录待发货、重试补发 | 扣钱成功但发货接口挂了？ |
| 到账数量 | 发的货 = 档位对应数量 | 发多/发少/发错道具？ |
| 玩家不存在 | 校验角色存在再发 | 充值到已注销/不存在的角色？ |

> **钱货一致是充值的生命线**：支付成功必发货（不能漏）、重复回调只发一次（不能多），核心靠**订单号做幂等 + 对账补单**。

---

## 四、并发与一致性

| 场景 | 预期 |
|---|---|
| 同一订单回调并发到达两次 | 幂等：只发一次货 |
| 玩家多设备同时对同一订单支付 | 只有一笔成功，其余关闭/退款 |
| 支付成功但服务端宕机重启 | 恢复后通过对账补发货 |
| 高并发充值（大促/开服） | 发货不丢不重，队列不积压 |

## 五、账户与到账展示

| 测试点 | 正常 | 异常/边界 |
|---|---|---|
| 余额更新 | 点券/游戏币实时增加 | 到账延迟？多端余额不一致？ |
| 充值记录 | 生成流水可查 | 流水金额/时间/档位正确？ |
| 通知提醒 | 到账弹窗/邮件通知 | 通知丢失但已到账？ |
| 跨区/跨服 | 充到正确的区服角色 | 选错区服充值？ |
| 多端一致 | iOS/Android/PC 余额同步 | 换端登录余额不同步？ |

## 六、安全测试

| 测试点 | 说明 |
|---|---|
| 篡改金额 | 抓包改低支付金额、改高到账数量，服务端是否校验 |
| 越权充值/查询 | 给他人角色充值、查他人充值记录 |
| 重放攻击 | 重复发送支付成功回调，验证幂等不重复发货 |
| 刷首充/活动 | 换角色/退款后重复领首充奖励 |
| 退款薅羊毛 ⭐ | 到账后申请退款，游戏币是否同步扣回？负余额消费？ |
| 客户端伪造 | 伪造"支付成功"跳过真实扣款直接发货 |

> **退款场景是充值特有的坑**：玩家充值到账 → 花掉游戏币 → 再退款，若不扣回会造成资损，需联动**退款回收 + 负余额/封禁**策略。

## 七、兼容性与性能

| 维度 | 测试点 |
|---|---|
| 支付渠道 | 微信/支付宝/Apple IAP/Google Play/运营商 |
| 设备/系统 | iOS/Android/PC 各主流机型与系统版本 |
| 网络 | WiFi/4G/5G/弱网/支付中断网 |
| 性能 | 大促/开服峰值并发充值 TPS、发货延迟 |
| 稳定性 | 长时间高频充值不丢单、对账无差异 |

## 用例设计方法总结

| 方法 | 应用 |
|---|---|
| **等价类划分** | 充值金额（0/最小/正常/超大）、支付渠道、玩家状态（存在/注销） |
| **边界值分析** | 首充次数、限购上限、自定义金额上下界、活动临界时间 |
| **状态迁移** | 订单状态（待支付→已支付→已发货/已退款/已关闭） |
| **错误推测** | 重复回调、回调丢失、支付成功宕机、退款薅羊毛 |
| **正交实验** | 支付渠道 × 充值档位 × 设备平台 |

---

## 一句话总结

> 游戏充值测试按「选档→下单→支付→回调→发货→到账」分段覆盖，核心是**钱货一致**——支付成功必发货（对账补单防漏）、重复回调只发一次（订单号幂等防多）；重点风险是**发货幂等、回调丢失补单、支付成功宕机对账、退款薅羊毛、篡改金额/到账数量**，辅以多渠道兼容和大促峰值性能压测。
