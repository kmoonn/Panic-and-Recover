# 接口测试怎么做

## Q：接口测试的完整流程是什么？

接口测试是测试系统组件间接口的一种测试，主要检查接口参数传递、数据交互、业务逻辑等的正确性。完整流程如下：

### 1. 需求分析

- 阅读接口文档（Swagger / API 文档 / Wiki），理解接口的功能、输入输出、业务逻辑
- 明确接口的调用方式（GET/POST/PUT/DELETE）、请求参数（路径参数、查询参数、请求体）、响应结构
- 梳理接口之间的依赖关系和调用链路
- **产出**：接口清单、疑问确认记录

### 2. 测试计划

- 确定测试范围：哪些接口需要测、哪些优先级高
- 划分优先级：P0 核心交易链路 > P1 主要功能 > P2 边缘场景
- 评估风险点：新增接口、变更接口、高并发接口
- **产出**：测试计划文档

### 3. 用例设计

按多维度覆盖，详见下方用例设计维度表格。

### 4. 环境准备

- 搭建测试环境（独立测试环境，避免污染生产数据）
- 准备测试数据：正常数据、边界数据、脏数据
- 配置鉴权信息：Token / Cookie / API Key
- 数据库初始化脚本、数据清理脚本

### 5. 执行测试

使用工具或代码发送 HTTP 请求，逐条执行用例：

```python
# requests 示例
import requests

# 正向用例：正常创建用户
resp = requests.post("http://api.example.com/users", json={
    "name": "张三",
    "age": 25,
    "email": "zhangsan@example.com"
}, headers={"Authorization": "Bearer <token>"})

assert resp.status_code == 201
assert resp.json()["name"] == "张三"
```

### 6. 结果验证

验证维度包括：

| 验证项 | 说明 | 示例 |
|--------|------|------|
| 状态码 | HTTP 状态码是否符合预期 | 创建成功返回 201，参数错误返回 400 |
| 响应体 | 字段值、数据类型、业务逻辑是否正确 | 返回的 id 非空、name 与请求一致 |
| 响应时间 | 接口是否在可接受时间内返回 | P99 < 200ms |
| 数据库 | 数据是否正确落库 | 查 DB 确认记录已插入 |
| 业务规则 | 联动逻辑是否正确 | 创建用户后是否自动创建默认配置 |

### 7. 缺陷跟踪

- 记录 Bug：标题、复现步骤、期望结果、实际结果、日志截图
- 跟进修复 → 回归验证 → 关闭
- 汇总测试报告：通过率、缺陷分布、风险点

## Q：接口测试用例设计有哪些维度？

| 维度 | 说明 | 示例 |
|------|------|------|
| **功能** | 正常业务流程能否走通 | 正确参数创建订单成功 |
| **参数** | 必填/选填、类型、长度、边界值 | name 为空、age 输入负数、email 格式错误 |
| **异常** | 异常输入、服务异常、超时 | 传入非法 JSON、服务端 DB 宕机、请求超时 |
| **安全** | 越权、注入、敏感信息泄露 | 水平越权访问他人数据、SQL 注入、密码明文返回 |
| **性能** | 并发、吞吐、响应时间 | 100 并发下单、大数据量分页查询 |
| **兼容** | 不同 Content-Type、编码 | `application/json` vs `application/x-www-form-urlencoded` |
| **依赖** | 上下游接口联动 | 上游创建成功后下游查询能获取 |

### 参数测试常用方法

```text
必填参数：缺失每个必填参数 → 应返回 400/参数错误
可选参数：全部缺失 → 应正常处理
类型校验：int 传 string、string 传 int → 应返回参数类型错误
长度边界：最小值-1、最小值、正常值、最大值、最大值+1
特殊字符：SQL 注入 `' OR 1=1 --`、XSS `<script>alert(1)</script>`
枚举值：传入非枚举范围内的值
```

## Q：常用接口测试工具有哪些？怎么选？

| 工具 | 类型 | 优势 | 劣势 | 适用场景 |
|------|------|------|------|----------|
| **Postman** | GUI 工具 | 上手快、支持环境变量、集合管理、可视化 | 并发能力有限、协作需付费 | 日常调试、小规模接口测试 |
| **JMeter** | GUI+CLI | 支持高并发压测、插件丰富、可 CI 集成 | 上手成本高、界面较丑 | 性能测试、压测、CI 集成 |
| **curl** | 命令行 | 轻量、无处不在、可脚本化 | 无 GUI、结果需手动解析 | 快速验证、CI/CD 脚本 |
| **requests+Pytest** | 代码框架 | 灵活度高、可集成 Allure 报告、数据驱动 | 编码成本、需维护框架 | 自动化回归、持续集成 |
| **RestAssured** | 代码框架(Java) | Java 生态、语法简洁、集成 TestNG | 仅 Java、需编码 | Java 项目自动化测试 |

### 选择建议

```text
快速调试/探索接口   → Postman / curl
小团队日常测试      → Postman 集合 + Newman CLI 跑回归
性能压测           → JMeter
自动化回归+CI      → requests + Pytest（Python）/ RestAssured（Java）
```

## Q：接口测试中常见的坑有哪些？

| 坑 | 说明 | 解决方案 |
|----|------|----------|
| **依赖顺序** | 用例之间有数据依赖，执行顺序敏感 | 前置脚本创建数据，后置脚本清理；或使用 mock |
| **数据污染** | 测试数据残留影响后续用例 | 每条用例后清理数据，或用随机化数据 |
| **鉴权过期** | Token 过期导致批量用例失败 | 前置 Hook 自动刷新 Token |
| **环境不一致** | 测试环境和开发/生产环境配置不同 | 统一配置管理，环境变量隔离 |
| **幂等性** | 重复调用产生多条数据 | 用例设计考虑幂等，加唯一约束 |
| **接口变更** | 接口变更后用例未同步更新 | 接口文档版本管理，变更通知机制 |

## Q：面试高频 — 你做接口测试的流程是什么？

> 回答模板：

1. **拿到需求后**，先读接口文档，理解业务逻辑和接口定义，有疑问及时和开发对齐
2. **根据接口文档设计用例**，覆盖正向、逆向、边界值、安全等维度，重点关注参数校验和业务规则
3. **准备测试环境和数据**，确保环境独立、数据可重复
4. **使用 Postman/Pytest 等工具执行用例**，验证状态码、响应体、数据库状态
5. **发现缺陷提交 Bug**，跟进修复后回归验证
6. **最终输出测试报告**，包含通过率、缺陷统计、风险评估

如果面试官追问自动化：补充"核心接口用 Pytest 做了自动化回归，集成到 CI 流水线，每次发版自动跑"。

## 一句话总结

接口测试的核心是"用例设计的全面性 + 结果验证的多维度"，流程上从需求分析到缺陷跟踪形成闭环，工具选择看场景，自动化回归是长期提效的关键。
