# Spec-Driven Testing

> 一句话：**SDT（Spec-Driven Testing，规格驱动测试）以 PRD、接口契约和设计规范为权威来源，从规格推导测试点、数据与断言，并通过“规格→用例→执行→报告→修复复测”形成可追溯闭环。**

## Q：什么是 SDT？

SDT 是一种**规格驱动的测试方法**：先明确系统应满足的规格，再据此设计和执行测试，而不是只凭个人经验罗列场景。

这里的 Spec 可以包括：

- **需求规格**：PRD、验收标准、业务规则；
- **接口契约**：IDL、OpenAPI/Swagger、字段约束、错误码；
- **技术设计**：状态流转、数据模型、时序与异常处理约束；
- **变更信息**：代码 Diff/MR，用于识别增量影响，但不能替代需求规格。

> SDT 更适合作为一种方法论或团队工作流来理解，并不存在跨行业完全统一的流程标准。

## Q：SDT 的 Spec 文档包含哪些内容？

Spec 不是简单复制 PRD，而是把需求整理成**可理解、可验证、可追溯**的测试依据。通常包括以下内容：

| 内容 | 要回答的问题 | 示例 |
|---|---|---|
| 基本信息 | 测什么、为什么测、信息从哪里来？ | 功能名称、背景、目标、状态、PRD/Meego/设计文档链接 |
| 范围与角色 | 谁使用？本次做什么、不做什么？ | 用户角色、系统边界、In Scope、Out of Scope |
| 用户故事与优先级 | 用户在什么场景下完成什么目标？ | P1/P2/P3 用户故事、业务价值 |
| 主流程与状态流转 | 功能如何触发和完成？ | 前置状态、操作步骤、状态机、上下游交互 |
| 业务规则 | 什么条件下允许、拒绝或采用特殊处理？ | 权限、配额、幂等、有效期、计算规则 |
| 功能需求 | 系统必须提供哪些可验证能力？ | 使用稳定编号的 `FR-001`、`FR-002` |
| 接口与数据契约 | 输入、输出和数据应满足什么约束？ | IDL/OpenAPI、字段类型、必填项、错误码、实体关系 |
| 验收场景 | 怎样判断每项行为正确？ | Given-When-Then、明确预期结果 |
| 异常与边界 | 系统遇到非正常输入时如何处理？ | 空值、上下界、重复请求、超时、部分失败、并发冲突 |
| 非功能要求 | 除功能正确外还要满足什么？ | 性能、可靠性、安全、兼容性、可观测性 |
| 成功标准 | 达到什么指标才算交付成功？ | 延迟、吞吐量、成功率、任务完成率 |
| 依赖与假设 | 哪些外部条件会影响验证？ | 上下游服务、环境、配置、账号、数据前置 |
| 歧义与待确认项 | 哪些问题尚无权威答案？ | 冲突规则、缺失阈值、未确认交互 |

### 最关键的写法

- 每条需求使用稳定 ID，便于建立 `FR → TC-ID → 执行结果 → 缺陷` 的映射。
- 验收标准必须**具体、可观察、可判定**，避免“体验良好”“响应较快”等模糊描述。
- 正常流程、异常流程和边界条件都要写；只写 Happy Path 不足以驱动测试。
- 冲突或缺失的信息应明确标记待确认，不能由测试人员或 AI 擅自补成业务规则。

### 哪些内容不应混入 Spec？

- 具体测试命令、执行顺序和环境部署步骤应放入 `task.md`。
- 每条用例的详细测试步骤与测试数据应放入 `case.md`。
- 实际通过率、日志和失败原因应放入 `report.md`。
- 密码、Cookie、Token 等敏感凭证不应明文写入 Spec，应使用安全引用或运行时注入。

## 核心流程

```text
规格输入
  ↓ 解析需求、约束与验收标准
测试用例（case）
  ↓ 评审用例与预期结果
执行任务（task）
  ↓ 准备环境、数据并执行测试
测试报告（report）
  ↓ 分类失败原因
修正用例 / 修复代码 / 处理环境
  ↓
重新执行，直到通过或触发安全停止
```

| 阶段 | 核心问题 | 典型产物 |
|---|---|---|
| 规格解析 | 系统应该做什么？约束是什么？ | 测试点、风险清单 |
| 用例生成 | 如何证明规格被满足？ | `case.md`、Given-When-Then 用例 |
| 用例澄清 | 预期是否准确、是否覆盖关键边界？ | 评审后的用例 |
| 执行规划 | 需要哪些环境、数据、脚本和依赖？ | `task.md` |
| 测试执行 | 实际行为是否符合规格？ | 日志、执行证据、`report.md` |
| 反馈闭环 | 失败来自用例、代码还是环境？ | 修复记录、复测结果 |

## 最重要的能力：可追溯

理想情况下，每条链路都能双向追踪：

```text
Spec 条款 ↔ 测试用例 TC-ID ↔ 执行任务 ↔ 测试结果 ↔ 缺陷
```

这样可以回答：

- 某条需求由哪些用例覆盖？
- 某个失败违反了哪条规格？
- 规格变化后，哪些用例需要重审或回归？
- 测试通过时，证据和断言依据是什么？

## 失败如何分类？

| 类型 | 含义 | 处理方式 |
|---|---|---|
| 用例问题 | 预期与已确认规格不一致、前置条件缺失 | 回到规格，澄清并修改用例 |
| 代码缺陷 | 实现违反规格，且有执行证据支持 | 最小范围修复代码并复测 |
| 环境问题 | 权限、依赖、部署、账号或外部服务异常 | 恢复环境后重跑，不误判为产品缺陷 |
| 规格歧义 | 规格不足以判断正确行为 | 停止自动修复，由产品/研发/测试共同决策 |

**原则**：不能为了让测试通过而削弱断言；根因不明确时，也不能直接修改业务代码。

## Q：SDT 与 SDD 有什么区别？

SDD 是 **Spec-Driven Development（规格驱动开发）**，SDT 是 **Spec-Driven Testing（规格驱动测试）**。两者共享同一份 Spec，但驱动的对象不同：**SDD 驱动“怎么实现”，SDT 驱动“怎么验证”**。

| 维度 | SDD | SDT |
|---|---|---|
| 全称 | Spec-Driven Development | Spec-Driven Testing |
| 核心目标 | 将规格转化为技术方案、开发任务和实现 | 将规格转化为测试点、用例、执行任务和报告 |
| 主要关注 | 功能如何设计和实现 | 如何证明实现符合规格 |
| 典型输入 | `spec.md`、架构约束、现有代码 | `spec.md`、接口契约、实现信息、执行环境 |
| 典型产物 | `plan.md`、`tasks.md`、代码变更 | `test/case.md`、`test/task.md`、`test/report.md` |
| 主要参与者 | 产品、架构师、研发 | 产品、测试开发、研发 |
| 完成标准 | 规格对应的功能已正确实现 | 规格对应的行为已有证据证明通过，或缺陷被明确暴露 |
| 反馈方向 | 实现困难可能推动规格或方案调整 | 测试失败可能推动用例澄清、代码修复或规格补充 |

### 两者如何协作？

```text
                         ┌→ SDD：plan → tasks → code ─┐
需求 → 统一 Spec ────────┤                            ├→ 对照验证 → 交付
                         └→ SDT：case → task → report ┘
```

Spec 是两条链路共同的“真相来源”：

- SDD 根据 Spec 规划并实现功能；
- SDT 独立根据 Spec 推导验收依据，验证实现是否符合预期；
- 如果代码与测试不一致，应回到 Spec 判断是代码缺陷、用例问题还是规格歧义；
- 规格发生变化时，开发计划、代码、测试用例和回归范围都应同步更新。

### 为什么不能只做 SDD？

完成代码不等于证明代码正确。若测试完全根据实现反推，容易把实现中的错误同时写进测试预期。SDT 从同一份权威 Spec 独立推导断言，可以减少“自己证明自己”的确认偏差。

### 为什么不能只做 SDT？

只有用例和报告不能交付功能。没有 SDD 的方案拆解、任务规划与实现，测试缺少被验证对象；而且可测性、日志、接口契约等能力通常需要在设计与开发阶段提前建设。

### 面试回答

> SDD 和 SDT 都以 Spec 为中心，但作用在软件生命周期的不同环节。SDD 把 Spec 转化为技术方案、开发任务和代码，回答“怎么实现”；SDT 把同一份 Spec 转化为测试用例、执行任务和报告，回答“怎么证明实现正确”。两者不是替代关系，而是并行互补：开发负责实现规格，测试独立验证规格，失败时再回到 Spec 判断是代码、用例还是规格本身的问题。

## SDT 与 TDD、BDD、SDET 的区别

| 概念 | 核心关注点 | 与 SDT 的关系 |
|---|---|---|
| SDD | 从规格推导方案、任务与实现 | 与 SDT 共享 Spec，分别驱动实现和验证 |
| SDT | 从既有规格推导测试并建立追溯闭环 | 强调测试依据和全过程一致性 |
| TDD | 先写测试，再写最小实现并重构 | 更偏开发节奏与代码设计 |
| BDD | 用业务可读的行为场景描述预期 | Given-When-Then 可作为 SDT 的用例表达方式 |
| SDET | Software Development Engineer in Test | 是岗位，不是测试方法；SDET 可以实践 SDT |

## 优势与局限

### 优势

- 测试范围与断言**有依据、可追溯**；
- 降低用例设计对个人经验的依赖；
- 规格变化时可快速定位受影响用例；
- 结构化输入和产物适合接入 AI，自动生成用例、任务和报告。

### 局限

- **Garbage in, garbage out**：规格错误或缺失会直接传导到用例；
- 不能取代探索性测试、风险经验和人工评审；
- 规格与代码、用例长期不同步时，追溯链会失效；
- AI 可以提效，但业务断言和歧义决策仍需人工把关。

## 项目实践

在字节实习中，SDT 是 AI Testing 工具链的方法论底座：

- **API Testing Agent**：把 PRD/MR、IDL 等规格转化为用例与断言，并衔接执行；
- **AI Data Gen**：根据场景与字段约束准备测试数据；
- **Skills Pulse**：观测测试与造数 Skill 的调用量、成功率、耗时和错误。

三者形成“**造数据 → 看数据 → 用数据测**”的闭环。具体经历见 [字节实习背景](../../00-resume/bytedance/00-context.md) 与 [API Testing Agent](../../00-resume/bytedance/03-api-testing-agent.md)。

## 面试回答

> SDT 是 Spec-Driven Testing，也就是规格驱动测试。核心是把 PRD、IDL 和设计规范作为测试设计的权威来源，从中推导测试点、数据和断言，再经过用例评审、任务执行、报告分析和修复复测形成闭环。它最大的价值是覆盖和断言有据可依、结果可追溯，也适合通过 AI 自动化提效。但它依赖规格质量，不能替代人工评审和探索性测试。

## 一句话总结

> SDT 不是“让 AI 自动写几个用例”，而是用 Spec 统一需求、用例、执行和结果的依据，再由自动化或 AI 加速这条可追溯的质量闭环。
