# 测试Agent落地量化指标

## Q: 测试 Agent 落地后，应该看哪些量化指标？

回答这个问题，不能只说“看提效了没有”。测试 Agent 的量化指标至少要覆盖四层：

1. **产出质量**：生成/执行的结果靠不靠谱
2. **过程效率**：节省了多少时间和人工成本
3. **落地效果**：团队到底有没有在用、敢不敢用
4. **稳定性**：是否容易失败、误报、波动大

也就是说，要同时回答“**做得对不对、快不快、有没有人用、能不能稳定跑**”。

---

## 一、指标总览

```text
                 测试 Agent 落地量化指标

        质量指标      效率指标      采用指标      稳定性指标
           │            │            │             │
    断言有效率     工时节省比例    采纳率       执行成功率
    缺陷发现率     单任务耗时      使用率       误报率
    覆盖提升       回归周期缩短    修改后采纳率  重试成功率
```

---

## 二、质量指标

### 1. 断言有效率

衡量 Agent 生成或执行的断言里，有多少是真正能验证业务预期的。

```text
断言有效率 = 有效断言数 / 总断言数
```

这里的“有效断言”一般指：
- 不只是断言 200
- 能覆盖关键业务结果
- 能发现真实缺陷
- 不属于明显幻觉字段或无意义断言

### 2. 用例/检查项覆盖提升

衡量使用 Agent 后，测试覆盖是否变得更完整。

```text
覆盖提升率 = (Agent 辅助后的覆盖点数 - 原覆盖点数) / 原覆盖点数
```

可以从这些角度看：
- 需求点覆盖率
- 异常场景覆盖率
- 边界值覆盖率
- 代码 diff 涉及分支覆盖率

### 3. 缺陷发现率

衡量 Agent 是否真的帮助发现了问题。

```text
缺陷发现率 = Agent 发现并被确认的缺陷数 / Agent 产出的总问题数
```

也可以看：

```text
Agent 贡献缺陷占比 = Agent 发现缺陷数 / 总发现缺陷数
```

### 4. 误报率 / 漏报率

#### 误报率

```text
误报率 = 被判定为无效问题数 / Agent 报出的问题总数
```

#### 漏报率

```text
漏报率 = 实际存在但 Agent 未覆盖的问题数 / 实际问题总数
```

误报率高说明：
- Agent 判断不准
- 断言设计不合理
- 上下文不足

漏报率高说明：
- 覆盖不足
- 风险识别能力弱
- 只会测主流程，不会测边界和异常

---

## 三、效率指标

### 1. 工时节省比例

这是最常见的提效指标。

```text
工时节省比例 = (传统耗时 - Agent 辅助耗时) / 传统耗时
```

例如：
- 传统准备 + 执行耗时 10 小时
- Agent 辅助后耗时 6 小时

那么：

```text
工时节省比例 = (10 - 6) / 10 = 40%
```

### 2. 单任务平均耗时

看每次任务是否更快完成。

```text
单任务平均耗时 = 总耗时 / 总任务数
```

可以拆到阶段：
- 需求分析耗时
- 用例生成耗时
- 造数耗时
- 执行耗时
- 结果分析耗时

### 3. 回归周期缩短比例

衡量从“准备回归”到“给出结果”的整体周期变化。

```text
回归周期缩短比例 = (原回归周期 - 新回归周期) / 原回归周期
```

### 4. 人工 Review 成本

Agent 不是完全替代人工，所以要看 review 成本是否可接受。

```text
人工 Review 成本 = 审核 Agent 产出耗时 / Agent 产出项数
```

如果 Agent 虽然生成很快，但 review 成本很高，实际收益会被吃掉。

---

## 四、采用指标

### 1. 采纳率

衡量 Agent 产出里有多少被团队真正接纳。

```text
采纳率 = 被采纳的产出数 / 总产出数
```

采纳可以再细分：
- **直接采纳**：几乎不用改
- **修改后采纳**：需要人工补充或修正
- **未采纳**：价值低或质量不足

### 2. 使用率

衡量团队有没有持续使用 Agent。

```text
使用率 = 使用 Agent 的任务数 / 适合使用 Agent 的总任务数
```

### 3. 复用率

衡量 Agent 产出有没有进入长期资产沉淀。

例如：
- 生成的用例是否进入回归集
- 生成的 checklist 是否进入测试模板
- 生成的造数脚本是否被重复使用

```text
复用率 = 被二次使用的产出数 / 被采纳产出总数
```

---

## 五、稳定性指标

### 1. 执行成功率

```text
执行成功率 = 成功完成的任务数 / 总任务数
```

失败可能来自：
- 环境问题
- 工具调用失败
- 页面结构变化
- 依赖数据缺失
- Agent 推理错误

### 2. 重试成功率

衡量失败后通过重试/恢复机制能救回多少。

```text
重试成功率 = 重试后成功的任务数 / 失败后触发重试的任务数
```

### 3. Flaky 比例

测试 Agent 场景很容易出现偶现失败。

```text
Flaky 比例 = 同一任务多次运行结果不一致的次数 / 总运行次数
```

### 4. 环境问题占比

```text
环境问题占比 = 因环境失败的任务数 / 总失败任务数
```

这个指标很重要，因为很多时候不是 Agent 不行，而是环境不稳定。

## 六、推荐的一套落地指标看板

| 维度 | 指标 | 推荐解释 |
|------|------|---------|
| 质量 | 断言有效率 | 生成/执行结果有没有真正验证业务 |
| 质量 | 缺陷发现率 | 是否真的发现了问题 |
| 质量 | 误报率 | 报出来的问题里有多少是噪音 |
| 效率 | 工时节省比例 | 对比传统流程省了多少时间 |
| 效率 | 回归周期缩短比例 | 从准备到结果整体缩短多少 |
| 采用 | 采纳率 | 团队是否认可 Agent 产出 |
| 采用 | 使用率 | 适合场景里是否真的在用 |
| 稳定性 | 执行成功率 | 任务能不能稳定跑完 |
| 稳定性 | 重试成功率 | 失败后能不能恢复 |
| 稳定性 | Flaky 比例 | 结果是否稳定可信 |

| 质量 | 误报率 | 12% | 判断噪音是否过高 |
| 效率 | 工时节省比例 | 40% | 判断是否真的省时 |
| 效率 | 回归周期缩短比例 | 28% | 判断整体交付效率是否提升 |

| 稳定性 | 重试成功率 | 60% | 判断失败恢复能力 |
| 稳定性 | Flaky 比例 | 7% | 判断结果是否稳定可信 |

### 一个更贴近实战的汇报方式

```text
第一层：先讲总收益
- 工时节省 40%
- 回归周期缩短 28%

第二层：再讲质量兜底
- 断言有效率 82%
- 误报率 12%

第三层：最后讲落地情况
- 采纳率 76%
- 使用率 63%
- 执行成功率 91%
```

这样汇报的好处是：
- 业务方先听到收益
- 测试负责人会关心质量
- 技术负责人会关心稳定性和长期可落地性

## 八、面试 / 汇报时的表达重点

### 1. 不要只讲一个数字

如果只说：
- “我们提效了 40%”

面试官很容易追问：
- 质量有没有下降？
- 是不是只节省了生成时间，review 反而变多？
- 长期是否稳定？

所以更稳的方式是：

> 我们不仅看工时节省，还同时看断言有效率、采纳率和执行成功率，避免只看速度不看质量。

### 2. 分清“试点成功”和“稳定落地”

试点阶段可以先看：
- 工时节省比例
- 采纳率
- 误报率

稳定落地阶段要继续补：
- 使用率
- 执行成功率
- Flaky 比例
- 长期复用率

### 3. 指标最好按阶段汇报

| 阶段 | 更关注什么 |
|------|-----------|
| PoC 阶段 | 是否能产出结果、采纳率高不高 |
| 试点阶段 | 是否真提效、误报多不多 |
| 推广阶段 | 使用率、复用率、稳定性 |
| 长期运营 | 趋势变化、边际收益、维护成本 |

## 九、怎么避免“指标看起来很好，但其实没落地”

这是面试很容易追问的点。

### 问题 1：只看速度，不看质量

如果只看“生成很快”，但：
- 断言无效
- 采纳率低
- review 很耗时

那这个提效是虚的。

### 问题 2：只看单次 Demo，不看长期使用

上线第一周指标很好，不代表长期能跑。还要看：
- 连续几周使用率
- 稳定性是否下降
- 误报是否被持续容忍

### 问题 3：没区分适用场景

测试 Agent 对：
- 标准化流程
- 高重复任务
- 有明确输入输出的场景

效果通常更好。对高不确定性探索测试，指标天然会差一些，所以要分场景看。

## 十、面试回答模板

> 我会从四类指标来看测试 Agent 的落地效果。第一类是质量指标，比如断言有效率、缺陷发现率、误报率，判断它做得对不对；第二类是效率指标，比如工时节省比例、单任务耗时、回归周期缩短比例，判断它快不快；第三类是采用指标，比如采纳率、使用率、复用率，判断团队到底有没有在用；第四类是稳定性指标，比如执行成功率、重试成功率、Flaky 比例，判断它能不能稳定落地。实际汇报时我会把这四类指标放到同一个看板里，避免只看速度不看质量，或者只看 Demo 不看长期使用。

## 一句话总结

> 测试 Agent 的量化指标不能只看提效，而要同时看质量、效率、采用度和稳定性，核心指标包括断言有效率、缺陷发现率、工时节省比例、采纳率、执行成功率和 Flaky 比例。
