# 如何判断断言有效性

## Q: 怎么判断一个测试断言是不是有效？

判断断言是否有效，核心不是看“写没写 assert”，而是看它是否**真的验证了业务预期、能否发现真实缺陷、会不会产生大量误报或漏报**。

一个有效断言至少要回答三个问题：

1. **断言的对象对不对**：是不是在校验真正重要的结果
2. **断言的强度够不够**：能不能发现关键错误
3. **断言的稳定性好不好**：会不会因为无关波动频繁失败

---

## 一、什么叫有效断言

### 弱断言

只校验“接口返回 200”“页面打开成功”“元素存在”这类表层结果。

```python
assert resp.status_code == 200
```

这类断言的问题是：
- 请求虽然成功了，但业务可能失败
- 返回结构可能错了
- 数据可能没落库
- 页面虽然打开了，但核心信息可能不对

### 强断言

不仅校验接口是否成功，还要校验**业务结果是否正确**。

```python
assert resp.status_code == 200
assert resp.json()["orderStatus"] == "SUCCESS"
assert resp.json()["payAmount"] == 100
```

如果有数据库或下游副作用，还应该继续断言：
- 订单状态是否更新
- 库存是否扣减
- 消息是否投递
- 日志/事件是否记录

> **结论**：有效断言不是“有没有断言”，而是“断言是否真正覆盖了业务预期”。

---

## 二、判断断言有效性的 5 个标准

| 标准 | 说明 | 反例 |
|------|------|------|
| **与需求一致** | 断言的内容直接对应需求或业务规则 | 只断言 HTTP 200，不断言业务字段 |
| **能发现真实缺陷** | 出现逻辑错误时，这个断言会失败 | 断言过弱，错误也能通过 |
| **不容易误报** | UI 小波动、时间戳变化等不应频繁导致失败 | 对非关键文案逐字匹配 |
| **不容易漏报** | 核心错误不能被放过 | 只检查返回码，不检查业务结果 |
| **可维护** | 断言清晰、定位明确、变更时容易修改 | 把几十个条件全塞进一条模糊断言 |

## 三、常见断言类型

### 1. 结果断言

校验接口/页面返回的数据本身是否正确。

```python
assert resp.json()["userName"] == "张三"
assert resp.json()["role"] == "admin"
```

适合：
- 查询接口
- 页面展示结果
- 配置回显

### 2. 状态断言

校验系统状态是否按预期变化。

```python
assert order.status == "PAID"
assert coupon.status == "USED"
```

适合：
- 支付成功后订单状态流转
- 优惠券领取/核销
- 用户权限变更

### 3. 副作用断言

校验主动作之外带来的联动结果。

例如下单成功后：
- 库存减少
- 积分增加
- 消息发送
- 审计日志记录

这类断言很重要，因为很多 bug 不是主接口失败，而是联动链路出问题。

### 4. 负向断言

校验“不应该发生的事”没有发生。

```python
assert "password" not in resp.text
assert db_count == 1  # 重复提交后不应插入两条数据
```

适合：
- 幂等性
- 安全性
- 去重逻辑
- 越权访问

### 5. 容错/异常断言

校验异常输入时系统给出的结果是否正确。

```python
assert resp.status_code == 400
assert resp.json()["message"] == "参数错误"
```

适合：
- 边界值
- 参数校验
- 非法输入
- 权限不足

## 四、为什么“只断言 200”不够

这是面试里很高频的追问。

### 原因 1：HTTP 成功 ≠ 业务成功

很多接口统一返回 200，但业务状态会放在 body 里。

```json
{
  "code": 5001,
  "message": "余额不足",
  "success": false
}
```

如果只断言 200，这条用例会被错误判为通过。

### 原因 2：主流程成功 ≠ 联动正确

如下单接口返回成功，但：
- 库存没扣
- 优惠券没核销
- MQ 没发出去

这类 bug 只有副作用断言才能发现。

### 原因 3：页面可打开 ≠ 用户目标达成

UI 自动化里，不能只判断“页面打开了”或“按钮存在”，还要判断：
- 信息展示对不对
- 操作结果对不对
- 页面状态是否正确变化

---

## 五、断言过弱与断言过强

### 断言过弱

表现：
- 只判断是否成功返回
- 只断言元素存在
- 只校验列表非空

问题：
- 很容易漏报
- 业务错了也测不出来

### 断言过强

表现：
- 对每个时间戳、随机字段、文案细节都严格匹配
- 对非关键 UI 像素级对比

问题：
- 容易误报
- 稍微一点无关变化就失败
- 用例稳定性差，维护成本高

### 合理做法

对**关键业务结果**做强断言，对**非关键展示细节**做适度容忍。

例如：
- 关键字段：强断言
- 时间字段：可断言“非空、格式正确、在合理区间”
- 文案：优先断言关键语义，不要对所有空格标点过度敏感

## 六、如何判断一个断言能不能发现真实问题

可以用下面这套检查清单：

```text
1. 如果功能逻辑错了，这个断言会失败吗？
2. 如果接口只是返回 200，但业务失败了，这个断言能识别吗？
3. 如果联动链路错了，这个断言能识别吗？
4. 如果页面只是展示了一个壳，但数据不对，这个断言能识别吗？
5. 这个断言会不会因为无关小变动频繁失败？
```

如果前 4 个问题大多回答“不能”，说明断言偏弱；如果第 5 个问题回答“会”，说明断言偏强。

## 七、不同测试类型里的有效断言

| 测试类型 | 有效断言示例 |
|---------|-------------|
| **接口测试** | 状态码 + 响应体关键字段 + 数据库落库 + 下游联动 |
| **UI 测试** | 页面元素 + 关键文案/数据 + 页面状态变化 + 跳转结果 |
| **数据库测试** | 插入/更新/删除结果 + 数据一致性 + 事务回滚效果 |
| **性能测试** | 响应时间、吞吐量、错误率、资源使用 |
| **安全测试** | 越权失败、注入不生效、敏感信息不泄露 |

## 八、AI 生成断言时怎么判断是否有效

AI 场景下，还要多加两层判断：

1. **有没有幻觉**：AI 是否断言了不存在的字段或规则
2. **是不是太表面**：AI 是否只写了 `200`、`success=true` 这种浅层断言

判断方法：
- 对照 PRD / 接口文档看字段是否真实存在
- 看断言是否覆盖业务预期，而不是只覆盖技术返回
- 看是否覆盖副作用与异常路径

所以 AI 生成断言通常要人工 review，重点审核：
- 字段真实性
- 业务逻辑正确性
- 断言强度是否足够

---

## 九、面试回答模板

> 我判断断言是否有效，主要看三点：第一，它是不是直接对应业务预期；第二，如果功能逻辑错了，这个断言能不能真正报错；第三，它会不会因为无关波动频繁失败。比如只断言 HTTP 200 就是典型弱断言，因为接口可能 200 但业务失败。更有效的做法是同时校验关键业务字段、数据库状态以及联动副作用。反过来如果断言过强，比如对时间戳、随机字段、非关键文案做严格匹配，又会带来很多误报，所以要在“能发现问题”和“稳定可维护”之间找到平衡。

## 一句话总结

> 判断断言是否有效，关键看它是否真正校验了业务预期、能否发现真实缺陷、是否兼顾稳定性与可维护性——既不能只断言 200 过弱，也不能对无关细节过度严格导致误报。
