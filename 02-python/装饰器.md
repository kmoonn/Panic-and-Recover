# 装饰器

## 是什么

装饰器是一个**接受函数作为参数并返回新函数**的高阶函数，用于在不修改原函数代码的前提下**增强或扩展**其行为。

语法上用 `@decorator` 糖衣语法，等价于 `func = decorator(func)`。

## 本质

装饰器的本质是**高阶函数 + 闭包**：

- **高阶函数**：接受函数作为参数，或返回函数作为结果
- **闭包**：内层函数引用了外层函数的变量，外层函数执行结束后这些变量依然存活

`@` 只是语法糖，Python 解释器在**函数定义时**就会执行这行赋值。

## 执行过程拆解

```python
def log(func):
    print(f"装饰 {func.__name__}")     # ← 第2步：装饰器函数体执行
    def wrapper(*args, **kwargs):
        print(f"调用 {func.__name__}")  # ← 第4步：每次调用 func 时执行
        return func(*args, **kwargs)
    return wrapper                      # ← 第3步：返回 wrapper 替换原函数

@log                                    # ← 第1步：函数定义时触发
def hello():
    print("hi")

hello()  # ← 第4步
```

**输出：**
```
装饰 hello    ← 定义时就执行，不是调用时
调用 hello    ← 每次调用 wrapper 时执行
hi
```

关键：**装饰器函数体在定义时执行一次**，wrapper 函数体在每次调用时执行。

## 闭包原理

wrapper 函数能访问 `func` 变量，是因为 Python 在函数对象上保存了对外层变量的引用：

```python
def log(func):
    def wrapper(*args, **kwargs):
        return func(*args, **kwargs)   # 引用外层的 func
    return wrapper

# wrapper 的闭包变量
print(wrapper.__closure__)        # (<cell at 0x...: function object at 0x...>,)
print(wrapper.__closure__[0].cell_contents)  # 原始 func 函数对象
```

`__closure__` 是一个 cell 对象元组，每个 cell 持有一个被闭包引用的外层变量。只要 wrapper 存在，`func` 就不会被垃圾回收。

## 基本用法

```python
def log(func):
    def wrapper(*args, **kwargs):
        print(f"调用 {func.__name__}")
        return func(*args, **kwargs)
    return wrapper

@log
def say_hello():
    print("hello")

say_hello()
# 输出:
# 调用 say_hello
# hello
```

等价于：

```python
say_hello = log(say_hello)
```

## 带参数的装饰器（三层嵌套原理）

需要再嵌套一层函数来接收装饰器自身的参数：

```python
def repeat(n):              # 第1层：接收装饰器参数
    def decorator(func):    # 第2层：接收被装饰函数
        def wrapper(*args, **kwargs):  # 第3层：闭包，持有 n 和 func
            for _ in range(n):
                result = func(*args, **kwargs)
            return result
        return wrapper
    return decorator

@repeat(3)
# 等价于: repeat(3) 返回 decorator → decorator(func) 返回 wrapper
def hello():
    print("hi")

hello()  # 输出 3 次 hi
```

调用 `@repeat(3)` 时：
1. `repeat(3)` 执行 → 返回 `decorator` 函数
2. `decorator(hello)` 执行 → 返回 `wrapper` 函数
3. `hello` 被替换为 `wrapper`

## functools.wraps

装饰器会覆盖原函数的 `__name__`、`__doc__` 等元信息，用 `@functools.wraps` 保留：

```python
import functools

def log(func):
    @functools.wraps(func)   # 复制 func 元信息到 wrapper
    def wrapper(*args, **kwargs):
        print(f"调用 {func.__name__}")
        return func(*args, **kwargs)
    return wrapper
```

`@functools.wraps(func)` 的原理：**把 func 的 `__name__`、`__doc__`、`__module__`、`__dict__` 等属性复制到 wrapper 上**，并更新 `__wrapped__` 指向原函数。

## 类装饰器

用类实现装饰器，利用 `__call__` 方法：

```python
class Timer:
    def __init__(self, func):   # 等同于装饰器接收 func
        self.func = func
        functools.update_wrapper(self, func)

    def __call__(self, *args, **kwargs):  # 等同于 wrapper
        import time
        start = time.time()
        result = self.func(*args, **kwargs)
        print(f"{self.func.__name__} 耗时 {time.time() - start:.4f}s")
        return result

@Timer   # 等价于 hello = Timer(hello)
def hello():
    pass

# hello 现在是 Timer 实例，hello() 触发 __call__
```

## 多个装饰器叠加

```python
@decorator_a
@decorator_b
def func():
    pass
```

等价于 `func = decorator_a(decorator_b(func))`，**自下而上装饰**。

调用时：`decorator_a.wrapper → decorator_b.wrapper → 原func`，**自外向内执行**。

## 常见应用场景

| 场景 | 示例 |
|---|---|
| 日志记录 | 记录函数调用、参数、返回值 |
| 性能计时 | 测量函数执行耗时 |
| 权限校验 | 检查用户是否登录/有权限 |
| 缓存 | `@functools.lru_cache` 自动缓存返回值 |
| 重试 | 函数失败时自动重试 N 次 |
| 事务管理 | 数据库操作自动 commit/rollback |

## 什么时候适合使用装饰器

判断标准：**多个函数是否都需要一套相似、且与核心业务相对独立的前置或后置处理**。如果答案是肯定的，就适合考虑装饰器。

例如，检索、重排和模型调用都需要记录输入、输出、耗时和异常。如果分别手写，代码会重复且容易漏埋点：

```python
def retrieve():
    start = time.time()
    try:
        return do_retrieve()
    finally:
        print(time.time() - start)

def rerank():
    start = time.time()
    try:
        return do_rerank()
    finally:
        print(time.time() - start)
```

提取成装饰器后，业务方法只关心业务本身：

```python
@trace
def retrieve():
    return do_retrieve()

@trace
def rerank():
    return do_rerank()
```

这样做的价值是：

- **解耦**：业务函数只表达“做什么”，装饰器处理“如何记录、保护或增强它”。
- **复用**：日志、计时、鉴权等逻辑只维护一份。
- **统一**：所有被装饰函数遵循相同规范，不容易漏处理。
- **易扩展**：增加采样、脱敏、指标等能力时，不需要逐个修改业务函数。

## 什么时候不建议使用

- 增强逻辑只在一个地方使用，提取后反而增加跳转成本。
- 这段逻辑本身就是核心业务流程，不应该被隐藏。
- 装饰器需要读取大量业务参数，与具体业务高度耦合。
- 装饰器层数太多且顺序敏感，调用链难以理解。
- 装饰器会悄悄修改返回值、吞掉异常或跳过原函数，行为不透明。
- 异步生成器、SSE 等生命周期复杂，却仍按普通函数“返回即结束”处理。

例如下面的代码虽然能写，但缓存、重试和事务之间的边界已经很难判断：

```python
@permission
@transaction
@retry
@cache
@trace
def create_order():
    ...
```

此时应该先梳理职责和执行顺序，而不是继续叠装饰器。

## 编写装饰器的注意事项

### 1. 不要遗漏 `functools.wraps`

具体写法见前文 `functools.wraps` 一节。否则函数名、文档和签名等信息可能变成 `wrapper`，影响日志、调试、反射和框架解析。

### 2. 记录异常后要继续抛出

```python
try:
    result = func(*args, **kwargs)
except Exception as exc:
    record_error(exc)
    raise
```

如果装饰器把异常吞掉，上层可能把失败误判为成功。

### 3. 同步函数和异步函数要分别处理

普通异步函数必须在异步包装器中 `await`：

```python
from functools import wraps

def trace_node(name):
    def decorator(func):
        @wraps(func)
        async def wrapper(*args, **kwargs):
            node = start_node(name)
            try:
                result = await func(*args, **kwargs)
                node.success(result)
                return result
            except Exception as exc:
                node.fail(exc)
                raise
            finally:
                node.close()
        return wrapper
    return decorator
```

如果漏掉 `await`，拿到的只是 coroutine 对象，真实执行耗时和异常都不能被正确记录。异步生成器、SSE 等流式返回不能直接套用这个“函数返回即关闭节点”的模板，需单独管理流的完整生命周期。

## 项目中的使用：RAG 异步全链路追踪

> 项目背景见 [`../00-resume/ceec/00-rag-platform.md`](../00-resume/ceec/00-rag-platform.md)，追踪设计见 [`../00-resume/ceec/03-rag-tracing.md`](../00-resume/ceec/03-rag-tracing.md)。仓库保存的是项目深挖笔记，没有保存 Nidus 的实际源码，所以下方代码用于说明已确认的设计，不代表真实类名和函数签名。

中国能建 RAG 项目的一次请求会经过 FastAPI SSE 入口、LangGraph 控制流、检索、Rerank、模型调用和流式返回。每个节点都要记录输入输出、耗时、状态、异常和父子关系，这属于典型的**横切关注点**，适合通过装饰器统一埋点。

概念代码可以理解为：

```python
@rag_trace_node("retrieve")
async def retrieve(query):
    return await retrieval_engine.search(query)

@rag_trace_node("rerank")
async def rerank(documents):
    return await reranker.rerank(documents)

@rag_trace_node("generate")
async def generate(context):
    return await model_router.generate(context)
```

装饰器在节点执行前后统一完成：

1. 从 `ContextVar` 取得当前追踪上下文。
2. 创建当前 `TraceNode`，以节点栈栈顶作为父节点。
3. 将当前节点压栈，记录输入和开始时间。
4. 调用真正的检索、重排或模型函数。
5. 记录输出、耗时、成功状态；异常时记录原因并重新抛出。
6. 最后弹栈并持久化追踪信息。

由此自动形成调用树：

```text
TraceRun：一次问答
├── retrieve
│   ├── intent_search
│   └── vector_search
├── rerank
└── generate
    └── llm_call
```

### 异步上下文透传

Python 版用 `contextvars.ContextVar` 保存当前 TraceRun 和节点栈。创建 `asyncio.Task` 时 ContextVar 的绑定会复制到新任务，后续重新绑定互不影响；如果绑定值本身是可变列表，仍要采用复制后再修改的方式，避免共享同一个对象。进入 `run_in_executor` 线程池时则需要使用 `copy_context()` 显式透传，否则子线程拿不到当前链路信息。

### 流式返回不能“函数返回就关 span”

普通装饰器一般在函数返回时执行 `node.close()`，但 SSE/异步生成器返回的只是**流对象**，数据还没有真正消费完。如果此时关 span，记录到的只是“创建流对象的时间”，不是完整模型调用耗时。

项目设计通过 `StreamSpan.detach()` 将 span 从当前调用栈中摘下，交给异步流在真正结束或异常时关闭，并区分：

- `LLM_TTFT`：模型自身的首包耗时。
- `USER_TTFT`：用户实际看到首字节的耗时。

这样才能判断延迟来自模型本身，还是首包探测、缓冲等中间层。

### FastAPI 中的框架装饰器

FastAPI 也大量使用装饰器注册框架行为：

```python
@app.post("/chat")
async def chat(request: ChatRequest):
    ...

@app.middleware("http")
async def add_process_time(request, call_next):
    ...

@app.exception_handler(CustomException)
async def custom_handler(request, exc):
    ...
```

- `@app.post`：把函数注册成 HTTP 路由。
- `@app.middleware`：注册统一请求/响应处理逻辑。
- `@app.exception_handler`：注册指定异常的全局处理器。

项目可以确认采用 FastAPI 和 SSE 入口，但当前仓库没有实际接口源码，因此 `/chat` 只是示意路径，不能当作真实接口名。

### Java 原版中的对应实现

RAG 的 Java 原版使用 `@RagTraceRoot` / `@RagTraceNode` 自定义注解，由 Spring AOP 在方法进出时维护 `ThreadLocal` 中的追踪上下文和节点栈；Python 重写版对应的是装饰器/上下文管理器加 `ContextVar`。两者解决相同的横切追踪问题，但机制不同。

武理工竞赛系统的数据权限也采用类似的 AOP 思想：MyBatis 拦截器在 SQL 执行前统一注入行级权限条件。笔记中只确认其**权限粒度借鉴若依 `@DataScope`**，不能表述成实际代码一定使用了 `@DataScope` 注解。详见 [`../00-resume/whut/02-contest-data-permission.md`](../00-resume/whut/02-contest-data-permission.md)。

## 与 Java 注解的区别

两者 `@` 语法相似，但本质完全不同：

| | Python 装饰器 | Java 注解 |
|---|---|---|
| **语法** | `@decorator` | `@Annotation` |
| **运行时机** | **定义时立即执行**，改写/替换原函数 | **运行时通过反射读取**，注解本身不做任何事 |
| **本质** | 高阶函数，`func = decorator(func)` | 元数据标签，附加在类/方法/字段上的信息 |
| **谁做实事** | 装饰器自身 | 框架的 AOP / 反射逻辑（如 Spring） |

> Python 装饰器**自己就是逻辑**，定义时直接改写函数；Java 注解**只是标签**，逻辑由框架在运行时通过反射读取后执行。装饰器更接近 Java 的 **AOP 切面**而非注解本身。

## 总结

| 概念 | 原理 |
|---|---|
| `@decorator` | 语法糖，等价 `func = decorator(func)` |
| 装饰时机 | 函数**定义时**执行，非调用时 |
| 闭包 | `__closure__` cell 对象持有外层变量引用 |
| 多装饰器 | 自下而上装饰，自外向内执行 |
| 带参数 | 三层嵌套：参数层 → 装饰器层 → wrapper 层 |
| `functools.wraps` | 复制 `__name__`/`__doc__` 等元信息到 wrapper |
| 类装饰器 | `__init__` 接收 func，`__call__` 充当 wrapper |

## 一句话总结

> 装饰器 = 不改原函数代码 + 增强其行为的高阶函数，本质是 `func = decorator(func)` 的语法糖，底层依赖闭包机制保存外层变量引用。
