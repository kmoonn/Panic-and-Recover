# 观察者模式

## 什么是观察者模式？

观察者模式（Observer Pattern）定义对象间一对多的依赖关系，当一个对象状态改变时，所有依赖它的对象都会收到通知并自动更新。属于行为型设计模式。

**核心思想**：Subject（主题）状态变化时，自动通知所有注册的 Observer（观察者）。

**现实类比**：报纸订阅——订阅一次后报纸每天自动送到门口，无需主动去查。出版商推送给所有订阅者，随时可取消。

**别名**：发布-订阅模式（Publish-Subscribe Pattern）、模型-视图模式（Model-View Pattern）、监听器模式（Listener Pattern）。

---

## 核心角色

| 角色 | 职责 |
|------|------|
| Subject（主题/被观察者） | 维护观察者列表，提供注册/注销/通知方法 |
| Observer（观察者） | 定义更新接口，收到通知后执行相应逻辑 |
| ConcreteSubject | 具体主题，状态变化时通知所有观察者 |
| ConcreteObserver | 具体观察者，实现更新逻辑 |

```
Subject <>-------- Observer
  |                    |
ConcreteSubject    ConcreteObserver
  | 通知                  | 更新
  +---notify()--------->|  update()
```

---

## 推模式(push) vs 拉模式(pull)

| 维度 | 推模式（Push） | 拉模式（Pull） |
|------|--------------|--------------|
| 数据传递 | Subject 主动将变化数据传给 Observer | Subject 只通知"有变化"，Observer 自己拉取数据 |
| 参数 | `update(data)` | `update(Subject)` |
| 优点 | Observer 不需要知道 Subject 细节 | Observer 按需获取数据，更灵活 |
| 缺点 | 可能传递不需要的数据 | Observer 需要持有 Subject 引用 |
| 适用 | 数据类型固定的场景 | 数据类型多变的场景 |

---

## Java 中的三种实现

| 实现 | 说明 | 推荐度 |
|------|------|--------|
| 自定义 Subject + Observer 接口 | 最灵活，推/拉模式自选 | ✅ 推荐 |
| `java.util.Observable` / `Observer` | JDK 9 已废弃——是类非接口、不支持泛型、线程不安全 | ❌ 已废弃 |
| EventObject + EventListener | Java 标准事件模型，比 Observer 更灵活 | ✅ 推荐 |

---

## 适用场景

| 场景 | 说明 | 示例 |
|------|------|------|
| 事件驱动 | 对象状态变化需要触发其他动作 | GUI 按钮点击事件 |
| 消息通知 | 一处变化多处响应 | 群聊消息、新闻推送 |
| 数据绑定 | 模型变化自动更新视图 | MVC 中的 Model→View |
| 日志审计 | 业务操作后记录日志 | 下单后记录审计日志 |

## 不适用场景

| 场景 | 原因 |
|------|------|
| 同步管线 | 处理顺序和完成很重要时，直接调用函数 |
| 事件风暴 | 太多事件难以调试，考虑批处理 |
| 循环依赖 | A 观察 B，B 观察 A → 无限循环 |
| 强顺序保证 | 观察者通知顺序不保证，需要顺序时用管道链 |

## 面试关联

### Spring 事件机制

Spring 的事件机制是观察者模式的经典应用：

| 组件 | 角色 | 说明 |
|------|------|------|
| `ApplicationEvent` | 事件 | 继承 `EventObject` |
| `ApplicationListener` | 观察者 | 继承 `EventListener` |
| `ApplicationEventPublisher` | 主题 | 发布事件 |
| `@EventListener` | 监听注解 | 声明式注册观察者，替代实现 ApplicationListener 接口 |

### Vue 的响应式原理

Vue 的响应式系统本质是观察者模式：
- **Dep（依赖收集器）**：相当于 Subject
- **Watcher（观察者）**：相当于 Observer
- 数据变化时 Dep 通知所有 Watcher，触发视图更新

Vue 2：`Object.defineProperty` 劫持 getter/setter
Vue 3：`Proxy` 劫持对象操作

### 与发布-订阅模式的区别

| 维度 | 观察者模式 | 发布-订阅模式 |
|------|-----------|-------------|
| 耦合度 | Subject 直接通知 Observer | 通过事件中心/消息总线解耦 |
| 中间层 | 无 | 有 Event Bus / Message Broker |
| 认知 | Subject 知道所有 Observer | 发布者和订阅者互不知道 |
| 同步/异步 | 通常是同步 | 通常是异步 |
| 典型实现 | Java Observer、Spring Event | Kafka、RabbitMQ、EventEmitter |

```
观察者模式：  Subject ───直接通知──→ Observer

发布-订阅模式：Publisher ─→ [Event Bus] ─→ Subscriber
```

> 面试中常将两者混称，但严格来说区别在于**是否有中间层**。

### EasyExcel 的 AnalysisEventListener

高性能 Excel 读写采用**观察者模式 + SAX 事件驱动**的生产级变体：

**观察者模式映射**：

| 观察者模式角色 | EasyExcel 对应 | 说明 |
|--------------|---------------|------|
| Subject（主题） | SAX 解析器 + `AnalysisEventManager` | 逐行解析 Excel，状态变化时触发事件 |
| Observer（观察者） | `AnalysisEventListener` | 用户实现的监听器，接收解析事件 |
| notify() | `invoke()` / `invokeHead()` / `doAfterAllAnalysed()` | 不同事件类型的回调 |
| registerObserver() | `ExcelReaderBuilder.registerReadListener()` | 注册监听器 |

**比教科书 Observer 多了什么**：

教科书 Observer 是"状态变了通知你"，EasyExcel 在此基础上做了三层增强：

```
教科书 Observer:     Subject ─notify()─→ Observer

EasyExcel 实际:
  SAX 解析器 ─invokeHead()─→ Listener    ← 表头事件
             ─invoke()─────→ Listener    ← 每行数据事件
             ─onException()→ Listener    ← 异常事件
             ─doAfterAll───→ Listener    ← 完成事件
                    ↑
              批量缓冲 + 流式解析
              (SAX 逐行读，不全量加载)
```

| 维度 | 教科书 Observer | EasyExcel 的变体 |
|------|----------------|-----------------|
| 事件类型 | 单一通知 | **多事件类型**（表头/数据/异常/完成） |
| 数据传递 | 推模式传 data | **推模式 + 行号 + 上下文** |
| 内存模型 | Subject 持有全量状态 | **SAX 流式，Subject 不持有全量数据** |
| 异常处理 | 通常不管 | `onException()` 回调，异常也是事件 |
| 批量 | 逐条通知 | `invoke()` 逐条收到，但**用户在 invoke 中攒批，到阈值批量入库** |

**为什么选 Observer + SAX 而不是全量读取**：

```
传统 POI 模式（UserModel）：
  Excel 文件 → 全部加载到 JVM 堆 → 用户处理
  10 万行 × 20 列 ≈ 数百 MB 堆内存 → OOM / 频繁 Full GC

EasyExcel 模式（SAX + Observer）：
  Excel 文件 → SAX 逐行解析 → 每行 invoke() 回调 → 用户批量入库
  内存占用 ≈ 单行数据 + 批量缓冲，与文件大小无关
```

Observer 模式的价值：解耦"解析"和"业务处理"。SAX 解析器不关心你拿数据做什么（写 DB / 写缓存 / 校验），它只管逐行通知；监听器不关心数据怎么来的（Excel / CSV），它只管收到后处理。

> EasyExcel 的 `AnalysisEventListener` = 观察者模式（事件回调解耦）+ SAX 流式解析（降内存）+ 批量缓冲（提吞吐），三者叠加实现大数据量导入的 2-3 倍效率提升。观察者模式是骨架，SAX 和批量是性能引擎。

## 缺点

| 缺点 | 说明 |
|------|------|
| 性能问题 | 观察者过多时，一次通知会遍历所有观察者，耗时增加 |
| 循环依赖 | A 通知 B，B 又通知 A，导致无限循环 |
| 内存泄漏 | 忘记注销观察者，Subject 一直持有 Observer 引用导致无法 GC |
| 更新顺序不确定 | 通知顺序取决于注册顺序，可能引发不可预期的行为 |

**最佳实践**：
- 及时 `removeObserver()` 避免内存泄漏
- 使用 `WeakReference` 持有观察者引用
- 避免在观察者回调中再次修改 Subject 状态

## 面试深度问题

**Q：通知顺序能依赖吗？**
A：多数实现按注册顺序调用，但不应依赖此顺序——该模式不保证顺序。如果观察者 B 的处理依赖观察者 A 先完成，就产生了隐式耦合，而 Observer 模式本应消除耦合。若顺序重要，应使用管道链或显式依赖声明。

**Q：一个观察者抛异常，后续观察者会怎样？**
A：简单实现中异常向上传播，后续观察者全部不执行。生产级实现用 try-catch 包裹每个监听器调用做故障隔离。Node.js EventEmitter 默认不隔离（一个坏观察者杀死后续所有），RxJS 则为每个订阅者设错误边界。关键系统应始终隔离观察者失败。

**Q：同步通知 vs 异步通知，切换会破坏什么？**
A：同步保证 emit 返回前所有观察者已处理完；切换异步会破坏"发出事件后状态立即更新"的假设——`emit('change'); readState()` 同步时能看到更新，异步时看到旧状态。Redux 的 `dispatch()` 就要求同步完成。异步性能更好（非阻塞），但要求系统处理 emit 和观察者执行之间的"最终一致性"间隙。

---

## 一句话总结

观察者模式定义一对多依赖关系，状态变化自动通知所有观察者，Spring 事件机制是其经典应用，与发布-订阅模式的本质区别在于是否有中间层解耦。
