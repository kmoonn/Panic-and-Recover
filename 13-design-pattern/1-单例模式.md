# 单例模式

## 什么是单例模式？

单例模式（Singleton Pattern）保证一个类只有一个实例，并提供一个全局访问点。属于创建型设计模式。

**核心思想**：私有构造方法 + 静态实例 + 静态获取方法。

---

## 五种实现方式（Java）

### 1. 饿汉式

类加载时就初始化实例，线程安全（由 ClassLoader 保证），但不管用不用都会创建实例，不支持延迟加载。

### 2. 懒汉式（synchronized）

延迟加载，但整个 `getInstance()` 方法加锁，每次获取实例都加锁，性能差。

### 3. 双重检查锁 DCL（推荐）

`volatile` + 两次 null 检查，仅第一次创建时加锁：

```java
private static volatile Singleton instance;       // volatile 是关键！
public static Singleton getInstance() {
    if (instance == null) {                        // 第一次检查，避免不必要的加锁
        synchronized (Singleton.class) {
            if (instance == null) {                // 第二次检查，防止重复创建
                instance = new Singleton();
            }
        }
    }
    return instance;
}
```

#### 为什么 DCL 必须加 volatile？

`new Singleton()` 不是原子操作，JVM 实际执行三步：

| 步骤 | 操作 | 说明 |
|------|------|------|
| 1 | 分配内存空间 | `memory = allocate()` |
| 2 | 初始化对象 | `ctorInstance(memory)` |
| 3 | 将引用指向内存地址 | `instance = memory` |

JVM 可能对步骤 2 和 3 **指令重排序**（先 3 后 2），此时 `instance != null` 但对象尚未初始化，其他线程拿到半初始化对象，导致 NPE。

`volatile` 禁止指令重排序，保证对象完全初始化后才对其他线程可见。

### 4. 静态内部类（推荐）

外部类加载时不加载内部类，调用 `getInstance()` 时才触发 Holder 类加载 → 延迟加载。线程安全由 ClassLoader 保证，无需 synchronized / volatile。

### 5. 枚举单例（Effective Java 推荐）

- 天然防反射破坏（JVM 禁止反射创建枚举实例）
- 天然防序列化破坏（枚举的 readResolve 由 JVM 保证）
- 写法最简洁

---

## 五种实现对比

| 实现方式 | 线程安全 | 延迟加载 | 防反射破坏 | 防序列化破坏 | 推荐度 |
|---------|---------|---------|-----------|------------|-------|
| 饿汉式 | ✅ | ❌ | ❌ | ❌ | 一般 |
| 懒汉式-synchronized | ✅ | ✅ | ❌ | ❌ | 不推荐 |
| 双重检查锁 DCL | ✅ | ✅ | ❌ | ❌ | 推荐 |
| 静态内部类 | ✅ | ✅ | ❌ | ❌ | 推荐 |
| 枚举单例 | ✅ | ❌ | ✅ | ✅ | **最推荐** |

## 使用场景

面试回答核心思路：**"一个系统只需要一个"**的东西——配置、连接池、缓存、日志、硬件接口。

### 高频场景（必答）

| 场景 | 为什么用单例 | 典型例子 |
|------|------------|---------|
| 数据库连接池 | 全局管理连接，多实例导致连接泄漏和资源浪费 | HikariCP、Druid |
| 配置管理 | 全局配置只加载一份，多处读取同一配置源 | Spring `@ConfigurationProperties` |
| 日志记录器 | 日志组件管理输出目标/格式/级别，多实例导致重复输出 | Logback、SLF4J Logger |
| 缓存 | 全局缓存保证一致性，多实例各存各的没有共享效果 | Spring Cache Manager、Guava Cache |
| 线程池 | 全局统一调度，多实例造成线程数失控 | `Executors.newFixedThreadPool()` 封装为单例 |

### 中频场景（加分项）

| 场景 | 说明 |
|------|------|
| ID 生成器 | 雪花算法需维护全局序列号/时钟，多实例生成重复 ID |
| Spring Bean 默认 scope | Spring 容器中每个 Bean 默认单例——最常见的单例使用，多数人天天用但没意识到 |

### 面试回答模板

按**类别**回答，不逐个列举类：

1. **资源管理类**：数据库连接池、线程池——全局共享，避免重复创建
2. **配置/状态类**：配置中心、缓存管理器、ID 生成器——全局唯一，保证一致性
3. **基础设施类**：日志框架、Spring 容器中的 Bean——底层组件，系统只需一个

## 单例被破坏的场景

### 1. 反射破坏

反射调用私有构造方法创建新实例。防御：构造方法中判断实例已存在时抛异常。枚举单例天然防反射。

### 2. 序列化/反序列化破坏

反序列化绕过构造方法创建新对象。防御：实现 `readResolve()` 返回已有实例。枚举单例天然防序列化。

## 面试关联

### Spring 中的单例

- Spring Bean 默认 `scope=singleton`，每个 IoC 容器中只有一个实例
- 但 Spring 的单例**不是严格单例**：
  - 每个 Spring 容器一个实例，多容器则多实例
  - 没有防反射和防序列化机制
  - 非线程安全——单例 Bean 有状态时不安全，需自行保证
- 本质是**单例注册表**模式（`SingletonBeanRegistry`）

### Python 实现单例

| 方式 | 说明 | 推荐度 |
|------|------|--------|
| 模块级别 | 模块天然单例，只加载一次 | **最 Pythonic** |
| 装饰器 | 闭包缓存实例 | 常用 |
| 元类 metaclass | `__call__` 中缓存实例 | 灵活 |
| `__new__` 方法 | 重写 `__new__` 控制创建 | 理解用 |

---

## 一句话总结

单例模式保证一个类只有一个实例，Java 推荐枚举单例（防反射/序列化破坏）或静态内部类/DCL（延迟加载），DCL 必须加 volatile 防止指令重排序，Python 最推荐模块级单例。
