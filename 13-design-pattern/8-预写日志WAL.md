# 预写日志 WAL（Write-Ahead Log）

> 一句话总结：WAL 是"先写日志再写数据"的持久化模式，通过仅追加顺序写替代随机写实现高性能，通过日志重放实现崩溃恢复，是几乎所有现代数据库的可靠性基石。

## 是什么

WAL（Write-Ahead Logging，预写日志）核心规则只有一条：

> **所有对数据文件的修改，必须在其描述变更的日志记录成功持久化到稳定存储之后，才能执行。**

即 **Log First, Write Later**——日志先行。

**现实类比**：船长日志——改变航向前先记录计划。若中途断电，船员读日志即可完成或撤销操作。日志是唯一事实来源。

## 核心运作流程

```
客户端提交事务
     │
     ▼
┌─────────────────┐
│ 1. 写 WAL 日志   │  ← 仅追加（Append-Only）顺序写
│    + fsync 刷盘  │  ← 日志持久化后才算提交成功
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ 2. 修改内存数据页 │  ← Buffer Pool 中的脏页
│    （不立即写磁盘）│
└────────┬────────┘
         │
         ▼
   返回客户端：提交成功 ✅
         │
         ▼
┌─────────────────┐
│ 3. 后台异步刷脏页 │  ← Checkpoint 时批量写入数据文件
└─────────────────┘
```

**关键点**：提交延迟 = 一次顺序写 + 一次 fsync，而非随机写数据页。脏页不必立即刷盘。

## 为什么快：顺序写 vs 随机写

| 对比项 | 直接写数据页 | WAL 模式 |
|--------|-------------|---------|
| 写入模式 | 随机写（数据页散布在磁盘各处） | 顺序追加写（WAL 文件连续增长） |
| 磁盘寻道 | 每次需寻道到不同位置 | 无需寻道，写入位置预先可知 |
| 写放大 | 改 1 行也要写整个 16KB 数据页 | 多次修改可在一次 Checkpoint 合并刷盘 |

核心思想：**将随机 I/O 转化为顺序 I/O**，这是数据库写入性能最重要的优化手段。

## 崩溃恢复

```
系统崩溃
     │
     ▼
从最后一个 Checkpoint 开始扫描 WAL
           │
     ┌─────┴─────┐
     ▼           ▼
   Redo        Undo
   重放已提交   回滚未提交
     │           │
     └─────┬─────┘
           ▼
     恢复到一致状态 ✅
```

**为什么安全**：WAL 日志 fsync 成功后才确认提交。崩溃后重放 WAL 恢复已提交事务，Undo 回滚未提交事务。即使恢复中途再次崩溃，LSN 幂等性保证安全重启。

## 关键机制

### LSN（Log Sequence Number）

- 每条 WAL 记录分配全局唯一、单调递增的 LSN
- 每个数据页头部存储 `PageLSN`（最后修改该页的日志 LSN）
- **幂等性**：Redo 时若 `PageLSN >= 日志记录 LSN`，说明该页已包含此修改，跳过重放

### Checkpoint（检查点）

WAL 不能无限增长，需要定期 Checkpoint 将脏页刷盘并截断旧日志。

| 类型 | 方式 | 采用者 |
|------|------|--------|
| Sharp | 冻结写入，刷出全部脏页 | 早期数据库 |
| Fuzzy | 后台异步渐进刷脏页 | PostgreSQL/MySQL/Oracle |

核心价值：**恢复时只需扫描最后一个 Checkpoint 之后的日志**。

### 全页写（FPW）

PostgreSQL 特有：Checkpoint 后首次修改某页时，WAL 中写**完整页面**而非差量，防止磁盘半写（torn page）导致数据页损坏后差量重放无法修复。

## 组提交（Group Commit）

fsync 是 WAL 的核心性能瓶颈。组提交是标准优化：

```
事务A ──┐
事务B ──┤  等待队列
事务C ──┘
         │
         ▼
   Leader 执行一次 fsync（刷入 A+B+C 所有日志）
         │
         ▼
   A、B、C 同时返回提交成功 ✅
```

- fsync 延迟几乎与数据量无关（刷 1 条 ≈ 刷 100 条）
- 吞吐量从 `1/fsync_latency` 提升至 `batch_size/fsync_latency`
- 并发越高收益越明显

## ARIES 算法

工业标准恢复算法（IBM 1992），整合 WAL + Checkpoint + LSN，采用三阶段恢复：

| 阶段 | 方向 | 作用 |
|------|------|------|
| Analysis | 从 Checkpoint 向前扫描 | 重建事务表 + 脏页表 |
| Redo | 从最小 RecLSN 向前重放 | 恢复到崩溃瞬间的内存状态 |
| Undo | 反向扫描 | 回滚未提交事务（写 CLR 保证幂等） |

## WAL 与 Shadow Paging 对比

| 特性 | WAL/ARIES | Shadow Paging |
|------|-----------|---------------|
| 恢复机制 | 日志重放 + 回滚 | 丢弃当前页表，恢复影子页表 |
| 写入模式 | 原地更新 | 写时复制（Copy-on-Write） |
| 并发支持 | 原生支持高并发 | 多事务页表管理复杂度急剧上升 |
| 适用场景 | 通用 OLTP | 嵌入式/只读为主 |

## 各数据库中的叫法

PostgreSQL → WAL、MySQL InnoDB → Redo Log、SQLite → WAL File、Oracle → Redo Log、Elasticsearch → Translog、etcd/raft → WAL

## 延伸价值

WAL 不仅是崩溃恢复的基础，还支撑：主从复制（流复制/binlog 复制）、时间点恢复 PITR、变更数据捕获 CDC、分布式共识（raft 日志持久化）。

## 适用与不适用场景

| ✅ 适用 | ❌ 不适用 |
|---------|----------|
| 数据库事务崩溃恢复 | 临时数据（缓存、会话） |
| 分布式共识日志（Raft/Paxos） | 可安全重推导的状态（幂等推导） |
| 消息队列持久存储（Kafka） | 同一键高频更新（WAL 膨胀快，用 LSM 更好） |
| 事件溯源 | 读密集负载（WAL 针对写优化） |

## 相关模式

| 模式 | 与 WAL 的关系 |
|------|-------------|
| Checkpoint | 截断 WAL——恢复 = 加载快照 + 重放剩余日志 |
| LSM-Tree | LSM 用 WAL 保证 memtable 刷盘前不丢数据 |
| MVCC | WAL 记录 MVCC 版本所基于的所有变更，实现崩溃恢复 |

## 面试高频问题

**Q：WAL 为什么能提升性能？**
A：将每次提交的随机写数据页转化为顺序写日志。顺序写无需寻道，且多个事务的修改可在 Checkpoint 时合并刷盘，减少磁盘写次数。

**Q：WAL 如何保证崩溃恢复？**
A：日志 fsync 成功后才确认提交。崩溃后从 Checkpoint 扫描 WAL：Redo 已提交 + Undo 未提交。LSN 幂等性保证即使恢复中途再次崩溃也能安全重启。

**Q：fsync 这么慢，怎么优化？**
A：组提交（Group Commit）——多个并发事务共享一次 fsync，吞吐量从 `1/fsync_latency` 提升至 `batch_size/fsync_latency`。

**Q：WAL 和 Shadow Paging 的区别？**
A：WAL 原地更新 + 日志重放，天然支持高并发；Shadow Paging 写时复制 + 页表切换，恢复简单但并发能力差。现代数据库几乎都选择 WAL。

**Q：WAL 运行很久日志膨胀，崩溃恢复很慢怎么办？**
A：定期做 Checkpoint（快照当前状态 + 截断旧日志）。恢复时 = 加载最近快照 + 仅重放之后的 WAL 条目。etcd 和 PostgreSQL 都这样做。

**Q：只用定期快照替代 WAL 行不行？**
A：不行。快照是异步定时的，"确认提交"和"持久化"之间存在时间差——客户端以为成功了但磁盘上没有，崩溃会丢已确认的数据。WAL 消除了这个时间差：每次提交时日志 fsync 成功才返回"提交成功"，两者原子绑定，所以零丢失。生产上两者配合：快照加速恢复，WAL 保证快照间零丢失。

## 一句话总结

WAL 是"先写日志再写数据"的持久化模式，通过仅追加顺序写替代随机写实现高性能，通过日志重放实现崩溃恢复，是几乎所有现代数据库的可靠性基石。
