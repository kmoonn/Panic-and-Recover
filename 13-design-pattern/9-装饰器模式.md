# 装饰器模式

## 什么是装饰器模式

装饰器模式（Decorator Pattern）是结构型设计模式，允许**动态地为对象添加额外职责**，而不改变原有类结构，是继承的替代方案。

**核心思想**：装饰器与被装饰对象实现相同接口，持有被装饰对象引用，在委托调用前后增加增强逻辑。

**现实类比**：穿衣服——你（Component）穿上T恤（DecoratorA），再套上外套（DecoratorB），每穿一件增加一层功能，你还是你，但能力增强了。

```
        ┌──────────────┐
        │  Component   │  ← 共同接口
        └──────┬───────┘
               │
       ┌───────┴───────┐
       ▼               ▼
┌─────────────┐  ┌─────────────┐
│ConcreteComp │  │  Decorator  │ ← 持有 Component 引用
│(被装饰对象) │  │  - component│
└─────────────┘  └──────┬──────┘
                        │
                ┌───────┴───────┐
                ▼               ▼
         ┌──────────┐  ┌──────────┐
         │DecoratorA│  │DecoratorB│  ← 可层层嵌套
         │(缓存增强)│  │(日志增强)│
         └──────────┘  └──────────┘
```

---

## 为什么用装饰器而不是继承

当对象有 n 种可选扩展功能时：
- **继承**：每种功能组合需要一个子类 → **2ⁿ 个子类爆炸**
- **装饰器**：只需 n 个装饰类，运行时自由组合 → 灵活且符合开闭原则

## 各语言/框架中的经典应用

### Java IO 流（最典型）

| 角色 | 对应类 |
|------|--------|
| 抽象组件 | `Reader` / `InputStream` |
| 具体组件 | `FileReader` / `FileInputStream` |
| 装饰器 | `BufferedReader` / `BufferedInputStream` |

```
BufferedReader br = new BufferedReader(new InputStreamReader(System.in));
                    └── 装饰器(缓存+readLine) ┘└── 适配器(字节→字符) ┘└── 基础流 ┘
```

其他 JDK 装饰器：`DataInputStream`、`PushbackInputStream`、`CipherInputStream`

### Python 装饰器

Python 的 `@decorator` 语法糖就是装饰器模式的语言级支持：

```
@log          ← 装饰器B（最外层）
@timer        ← 装饰器A（中间层）
def func():   ← 被装饰对象
    ...
# 等价于 func = log(timer(func))
```

Python 装饰器比 Java 更简洁——无需定义接口和包装类，用闭包/函数即可实现。

### Flask 请求处理

Flask 的 `before_request` / `after_request` 钩子本质是装饰器链，层层包装请求处理函数：

```
请求 → before_request1 → before_request2 → 视图函数 → after_request2 → after_request1 → 响应
```

### Django 中间件

Django Middleware 也是装饰器模式——每个中间件包装视图函数，在调用前后增加逻辑（认证、CORS、日志等）。

## 面试高频

### 装饰器 vs 代理模式（面试必问）

| 维度 | 装饰器模式 | 代理模式 |
|------|-----------|---------|
| 核心关注点 | **功能扩展**，层层增强 | **访问控制**，限制/增强访问 |
| 执行行为 | **所有装饰器都会执行** | 代理决定是否/如何委托给目标 |
| 可否中途终止 | ❌ 不可以 | ✅ 可以 |
| 典型应用 | Java IO、Python @decorator | Spring AOP、Nginx 反向代理 |

**一句话区分**：装饰器关注"加功能"，代理关注"管访问"。

### 装饰器的优缺点

| ✅ 优点 | ❌ 缺点 |
|---------|---------|
| 运行时动态扩展 | 多层装饰增加复杂度 |
| 功能自由组合，避免子类爆炸 | 多层装饰调试困难 |
| 符合开闭原则 | — |

---

## 一句话总结

装饰器模式通过包装对象动态添加职责，用组合替代继承避免子类爆炸，Java IO 流和 Python @decorator 是经典实现，与代理模式的本质区别在于装饰器关注功能扩展而代理关注访问控制。
