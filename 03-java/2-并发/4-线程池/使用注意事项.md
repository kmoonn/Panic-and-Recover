# 线程池使用注意事项

线程池配对了参数只是第一步，实际使用中的坑往往在参数之外。以下是高频踩坑点。

## 1. 异常被"吞掉"

- `execute()` 提交的任务抛异常 → 打印堆栈并终止该线程（线程池补新线程），但**不影响其他任务**。
- `submit()` 提交的任务抛异常 → 异常被**包进 Future**，不调用 `future.get()` 就**永远看不到**，问题被静默吞没。

> **对策**：任务内 `try-catch` 兜底，或自定义 `ThreadFactory` 设 `UncaughtExceptionHandler`；用 `submit` 时务必处理 `Future.get()` 的异常。

## 2. ThreadLocal 内存泄漏

线程池线程**长期复用不销毁**，`ThreadLocal` 设置的值不会随任务结束自动清理，一直挂在线程上 → 内存泄漏，还可能读到**上个任务的脏数据**。

> **对策**：任务 `finally` 里 `threadLocal.remove()`。

## 3. 必须优雅关闭

线程池不 `shutdown` 会导致线程一直存活，JVM 无法退出（非守护线程）。

| 方法 | 行为 |
|---|---|
| `shutdown()` | 不再接新任务，等已提交任务执行完 |
| `shutdownNow()` | 尝试中断正在执行的任务，返回未执行的任务列表 |

> **标准姿势**：`shutdown()` → `awaitTermination(timeout)` → 超时未完再 `shutdownNow()`。

## 4. 不同业务要资源隔离

多个业务共用一个线程池 → 一个慢任务/大批量任务**打满线程和队列**，拖垮其他业务（相互影响）。

> **对策**：核心链路与非核心链路、快任务与慢任务用**独立线程池**隔离，避免"一颗老鼠屎坏一锅汤"。

## 5. 队列与拒绝策略要匹配

- 有界队列 + `AbortPolicy`（默认）：满了直接抛异常，调用方要能处理，否则丢任务。
- 无界队列：任务堆积 → [OOM](../../3-JVM/OOM.md)（这也是不用 `Executors` 的原因）。
- 关键任务不能丢 → 用 `CallerRunsPolicy`（调用线程自己执行，反压降速）或自定义策略落库/入 MQ 重试。

## 6. 核心线程默认不预热

`corePoolSize` 的线程默认**懒创建**（来任务才建）。对延迟敏感的服务，可 `prestartAllCoreThreads()` 预热，避免首批请求慢。

## 7. 慎用 ThreadLocal + 父子线程传值

线程池场景下 `InheritableThreadLocal` 只在**线程创建时**继承一次，线程复用后不会更新，容易拿到错的上下文。跨线程传上下文用 阿里 `TransmittableThreadLocal（TTL）`。

## 一句话总结

> 线程池使用七大坑：submit 吞异常、ThreadLocal 不 remove 泄漏、忘记 shutdown、业务不隔离、无界队列 OOM、核心线程不预热、线程复用导致上下文串味——本质都源于"线程被长期复用"这一特性。
