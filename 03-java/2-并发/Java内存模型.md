# Java 内存模型（JMM）

## 先分清：JMM ≠ JVM 运行时数据区

面试最大的坑是把两者混为一谈：

| | JVM 运行时数据区 | Java 内存模型（JMM） |
|---|---|---|
| 是什么 | **物理**内存划分（堆、栈、方法区……） | 一套**抽象规范/规则** |
| 解决什么 | 内存怎么存放数据 | 多线程下变量的**可见性、有序性、原子性** |
| 关键词 | 堆、栈、Eden、老年代 | 主内存、工作内存、happens-before |

> JMM 是"游戏规则"，不是"内存条"。它定义线程如何与内存交互，屏蔽 CPU 缓存、指令重排等底层差异，保证并发程序在不同平台行为一致。详见 [JVM 内存模型](../3-JVM/内存模型.md)。

## 主内存与工作内存

```
     ┌──────────────────────────┐
     │       主内存 (共享变量)     │
     └──────────────────────────┘
        ↑ read/write     ↑ read/write
   ┌─────────┐        ┌─────────┐
   │ 工作内存 │        │ 工作内存 │   ← 每个线程私有（对应 CPU 缓存/寄存器）
   │(变量副本)│        │(变量副本)│
   └─────────┘        └─────────┘
     线程 A             线程 B
```

- 所有共享变量存在**主内存**。
- 每个线程有自己的**工作内存**，保存用到的变量**副本**。
- 线程只能操作自己工作内存的副本，**不能直接读写主内存**，也不能访问对方的工作内存。
- 副本何时同步回主内存由 JMM 规则决定 → 这正是**可见性问题**的根源：A 改了副本没刷回、B 没重新读，就看到旧值。

## 三大特性

| 特性 | 含义 | 保证手段 |
|---|---|---|
| **原子性** | 操作不可中断，要么全做要么不做 | `synchronized`、`Lock`、`Atomic` 类（`i++` 本身非原子） |
| **可见性** | 一个线程的修改，其他线程立即可见 | `volatile`、`synchronized`、`final` |
| **有序性** | 禁止（对结果有影响的）指令重排 | `volatile`、`synchronized`、happens-before |

> `volatile` 保证可见性 + 有序性，但**不保证原子性**（详见 [volatile](volatile.md)）。

## 指令重排与 happens-before

- 编译器/CPU 会为优化**重排指令**，单线程下结果不变（as-if-serial），但多线程下可能出错（如单例双检锁不加 volatile 会读到未初始化对象）。
- **happens-before** 是 JMM 判断"是否存在可见性/有序性保证"的核心准则：若 A happens-before B，则 A 的结果对 B 可见且顺序不被重排。

常用 happens-before 规则：

| 规则 | 内容 |
|---|---|
| 程序顺序 | 单线程内，前面的操作 happens-before 后面的 |
| volatile | 对 volatile 变量的写 happens-before 后续对它的读 |
| 锁 | 解锁 happens-before 后续对同一锁的加锁 |
| 传递性 | A hb B、B hb C ⟹ A hb C |
| 线程启动 | `start()` happens-before 线程内所有操作 |
| 线程终止 | 线程内所有操作 happens-before `join()` 返回 |

## 一句话总结

> JMM 是规范不是内存区：它用"主内存 + 线程私有工作内存"模型解释可见性问题，用 volatile/synchronized/final 保证可见性、有序性、原子性三大特性，并以 happens-before 作为判断并发正确性的核心准则。
