# 类加载机制

## 概述

Java 虚拟机把描述类的数据从 Class 文件加载到内存，并对数据进行校验、转换解析和初始化，最终形成可以被虚拟机直接使用的 Java 类型，这个过程称为**类加载机制**。

与编译时需连接的语言不同，Java 的类加载是**运行时**完成的，这为 Java 提供了动态扩展的能力。

## 类加载的五个阶段

```
加载(Loading) --> 验证(Verification) --> 准备(Preparation) --> 解析(Resolution) --> 初始化(Initialization)
     |                  |                    |                   |                    |
     |                  +------+-------------+                   |                    |
     |                    连接(Linking)                          |                    |
     |                                                          |                    |
     +---------------- 使用(Using) -----------------------------+                    |
     +---------------- 卸载(Unloading) ----------------------------------------------+
```

> 其中验证、准备、解析三个阶段统称为**连接（Linking）**。

### 1. 加载（Loading）

**做什么**：通过类的全限定名获取该类的二进制字节流，并将其转化为方法区的运行时数据结构，最终在内存中生成该类的 `java.lang.Class` 对象。

加载阶段 JVM 需要完成三件事：

1. 通过全限定名获取定义此类的二进制字节流（来源不限于 Class 文件，可以是 JAR/WAR/动态代理生成/网络等）
2. 将字节流所代表的静态存储结构转化为方法区的运行时数据结构
3. 在内存中（Java 堆中）生成该类的 `java.lang.Class` 对象，作为方法区数据的访问入口

```java
// 获取 Class 对象的三种方式
Class<?> clazz1 = Class.forName("com.example.MyClass");   // 全限定名
Class<?> clazz2 = MyClass.class;                          // 类名.class
Class<?> clazz3 = new MyClass().getClass();                // 对象.getClass()
```

> **数组类**不通过类加载器创建，由 JVM 直接在内存中动态构造。但数组元素类型仍然需要类加载器加载。

### 2. 验证（Verification）

**做什么**：确保 Class 文件的字节流包含的信息符合 JVM 规范，不会危害虚拟机安全。

验证阶段分为四步：

| 验证步骤 | 验证内容 | 示例 |
|---|---|---|
| **文件格式验证** | 字节流是否符合 Class 文件格式规范 | 魔数 `0xCAFEBABE`、主次版本号、常量池 Tag |
| **元数据验证** | 语义分析，确保描述信息符合 Java 规范 | 是否有父类、是否继承了 final 类、是否实现了抽象方法 |
| **字节码验证** | 数据流和控制流分析，确保程序语义合法 | 类型转换是否正确、跳转指令不会跳到方法体外 |
| **符号引用验证** | 确保符号引用转化为直接引用时能正确解析 | 类/字段/方法是否存在、访问权限是否合法 |

> 文件格式验证是基于二进制字节流的，通过后字节流才进入方法区存储；后三个验证基于方法区存储结构。

### 3. 准备（Preparation）

**做什么**：为类变量（`static` 变量）分配内存并设置**零值**（初始默认值）。

```java
public static int value = 123;   // 准备阶段：value = 0（零值）
                                 // 初始化阶段：value = 123（显式赋值）

public static final int CONSTANT = 123;  // 准备阶段：CONSTANT = 123
                                         // final static 在准备阶段就赋值
```

| 变量类型 | 准备阶段赋值 | 初始化阶段赋值 |
|---|---|---|
| `static int` | 0（零值） | 显式值 |
| `static final int`（编译期常量） | 显式值 | -- |
| `static final int`（运行期常量，如 `= Integer.valueOf(123)`） | 0（零值） | 显式值 |
| 实例变量 | 不在此阶段（对象创建时分配） | -- |

> **注意**：准备阶段只处理类变量（static），不处理实例变量。实例变量在对象实例化时随对象一起分配在 Java 堆中。

### 4. 解析（Resolution）

**做什么**：将常量池中的**符号引用**替换为**直接引用**。

| 引用类型 | 说明 | 示例 |
|---|---|---|
| **符号引用** | 以一组符号描述引用目标，与虚拟机实现的内存布局无关 | `com/example/MyClass`、`main:([Ljava/lang/String;)V` |
| **直接引用** | 直接指向目标的指针、句柄或偏移量，与虚拟机内存布局相关 | 内存地址、方法表偏移量 |

解析主要针对以下几类符号引用：

- 类或接口的解析
- 字段解析
- 方法解析
- 接口方法解析

> 解析不一定在初始化之前完成，某些情况可以在初始化后再开始（支持 Java 的运行时绑定/多态）。

### 5. 初始化（Initialization）

**做什么**：执行类的 `<clinit>()` 方法，真正执行类中定义的 Java 代码。

`<clinit>()` 方法的内容：
- 类变量的显式赋值（`static` 变量 = 值）
- 静态代码块（`static { }`）

```java
public class Demo {
    static int a = 10;                 // <clinit> 中赋值
    static final int B = 20;           // 编译期常量，不在 <clinit> 中
    static final int C = Integer.valueOf(30);  // 运行期常量，在 <clinit> 中

    static {                           // <clinit> 中执行
        a = 100;
        System.out.println("静态初始化块");
    }
}
```

`<clinit>()` 的特点：

| 特点 | 说明 |
|---|---|
| 编译器收集 | 由编译器自动收集类中所有赋值动作和静态语句块合并产生 |
| 顺序 | 按源文件中出现的顺序决定（静态语句块只能访问其之前的变量） |
| 线程安全 | JVM 保证 `<clinit>()` 在多线程下被正确地加锁和同步 |
| 无则不生成 | 如果没有静态赋值和静态代码块，则不生成 `<clinit>()` |
| 父类优先 | 先执行父类的 `<clinit>()`，再执行子类的 |
| 接口 | 接口也有 `<clinit>()`，但不需要先执行父接口的 `<clinit>()` |

> **类初始化的触发条件**（主动引用，且仅此 5 种）：
> 1. `new` / `getstatic` / `putstatic` / `invokestatic` 四条字节码指令
> 2. 反射调用 `Class.forName()`
> 3. 初始化子类时，父类未初始化则先初始化父类
> 4. 虚拟机启动时的主类（包含 main 方法的类）
> 5. JDK 7+ 动态语言支持：`MethodHandle` 解析结果为 `REF_getStatic` 等的方法句柄

## 双亲委派模型

### 类加载器的层次

```
       +--------------------------------+
       |   Bootstrap ClassLoader        |  启动类加载器
       |   (C++ 实现，非 Java 类)        |  加载 <JAVA_HOME>/lib 下的 rt.jar 等
       +---------------+----------------+
                       | parent
       +---------------+----------------+
       |   Extension ClassLoader        |  扩展类加载器
       |   (Launcher$ExtClassLoader)    |  加载 <JAVA_HOME>/lib/ext 下的类
       +---------------+----------------+
                       | parent
       +---------------+----------------+
       |   Application ClassLoader      |  应用程序类加载器
       |   (Launcher$AppClassLoader)    |  加载 classpath 下的类
       +---------------+----------------+
                       | parent
       +---------------+----------------+
       |   自定义 ClassLoader            |  用户自定义加载路径
       +--------------------------------+
```

### 类加载器分类及加载路径

| 类加载器 | 实现 | 加载路径 |
|---|---|---|
| **Bootstrap ClassLoader** | C++ 实现，不是 Java 类 | `<JAVA_HOME>/lib` 目录（`rt.jar`、`charsets.jar` 等核心类库） |
| **Extension ClassLoader** | `sun.misc.Launcher$ExtClassLoader` | `<JAVA_HOME>/lib/ext` 目录 |
| **Application ClassLoader** | `sun.misc.Launcher$AppClassLoader` | 用户 classpath（`-classpath` / `-cp` 指定的路径） |
| **自定义 ClassLoader** | 继承 `java.lang.ClassLoader` | 自定义路径 |

```java
// 查看类加载器
ClassLoader cl = String.class.getClassLoader();
System.out.println(cl);  // null（Bootstrap 加载，C++ 实现，Java 中表示为 null）

ClassLoader cl2 = Demo.class.getClassLoader();
System.out.println(cl2);  // sun.misc.Launcher$AppClassLoader@xxx
System.out.println(cl2.getParent());  // sun.misc.Launcher$ExtClassLoader@xxx
System.out.println(cl2.getParent().getParent());  // null（Bootstrap）
```

### 工作流程

双亲委派模型的工作流程：

```
自定义 ClassLoader 收到加载请求
    |
    v 委派给父加载器
Application ClassLoader 收到请求
    |
    v 委派给父加载器
Extension ClassLoader 收到请求
    |
    v 委派给父加载器
Bootstrap ClassLoader 收到请求
    |
    +-- 能加载 --> 加载并返回
    +-- 不能加载 --> 返回给子加载器
                |
                v
        Extension ClassLoader 尝试加载
            |
            +-- 能加载 --> 加载并返回
            +-- 不能加载 --> 返回给子加载器
                        |
                        v
                Application ClassLoader 尝试加载
                    |
                    +-- 能加载 --> 加载并返回
                    +-- 不能加载 --> 返回给子加载器
                                |
                                v
                        自定义 ClassLoader 尝试加载
                            |
                            +-- 能加载 --> 加载并返回
                            +-- 不能加载 --> 抛出 ClassNotFoundException
```

核心代码（`ClassLoader.loadClass()` 简化版）：

```java
protected Class<?> loadClass(String name, boolean resolve) throws ClassNotFoundException {
    synchronized (getClassLoadingLock(name)) {
        // 1. 检查是否已加载
        Class<?> c = findLoadedClass(name);
        if (c == null) {
            // 2. 委派父加载器加载
            if (parent != null) {
                c = parent.loadClass(name, false);
            } else {
                c = findBootstrapClassOrNull(name);
            }
            // 3. 父加载器加载失败，自己尝试加载
            if (c == null) {
                c = findClass(name);
            }
        }
        return c;
    }
}
```

### 双亲委派的作用

1. **保证核心类不被篡改**：无论哪个类加载器加载 `java.lang.Object`，最终都委派给 Bootstrap 加载，保证所有环境下 Object 都是同一个类
2. **避免重复加载**：父加载器已加载的类，子加载器不需要再加载

```java
// 自定义 java.lang.String 不会被加载
package java.lang;
public class String {
    // 永远不会被加载！Bootstrap 已加载了 rt.jar 中的 String
}
```

### 破坏双亲委派的场景

#### 第一次破坏：JDK 1.2 之前

JDK 1.2 引入双亲委派模型时，已有用户自定义 ClassLoader 的实现。为兼容，添加了 `findClass()` 方法，引导用户重写 `findClass()` 而非 `loadClass()`，保证双亲委派逻辑不被覆盖。

#### 第二次破坏：SPI 机制（如 JDBC）

**问题**：SPI 接口（如 `java.sql.Driver`）由 Bootstrap 加载，但实现类由第三方厂商提供，在 classpath 下，Bootstrap 无法加载。

**解决**：线程上下文类加载器（Thread Context ClassLoader）。

```
Bootstrap 加载 DriverManager（核心类）
    |
    | 需要加载第三方 Driver 实现
    | Bootstrap 无法加载 classpath 下的类
    |
    v 使用线程上下文类加载器
Application ClassLoader 加载第三方 Driver 实现
```

```java
// ServiceLoader 使用上下文类加载器加载 SPI 实现
ServiceLoader<Driver> drivers = ServiceLoader.load(Driver.class);
// 内部：ClassLoader cl = Thread.currentThread().getContextClassLoader();
```

#### 第三次破坏：Tomcat

Tomcat 需要实现 Web 应用之间的类隔离：不同应用可能依赖同一个库的不同版本。

```
      Common ClassLoader
       /            \
CatalinaClassLoader   SharedClassLoader
                          /          \
                WebApp1 ClassLoader   WebApp2 ClassLoader
                      |                    |
                JspClassLoader        JspClassLoader
```

- **WebApp ClassLoader** 打破了双亲委派：优先加载 Web 应用自己的类，再委派给父加载器
- 但 `java.*` 等核心类仍然委派给 Bootstrap 加载（有安全检查）

#### 第四次破坏：OSGi

OSGi 实现模块化热部署，每个模块（Bundle）有自己的类加载器，类加载不再是简单的树状结构，而是**网状结构**：

```
Bundle A ClassLoader <---> Bundle B ClassLoader
       |                       |
Bundle C ClassLoader <---> Bundle D ClassLoader
```

OSGi 的类加载搜索顺序：
1. 以 `java.*` 开头的类委派给父加载器
2. 否则检查是否在 Import-Package / Require-Bundle 中，若是则委派给对应 Bundle
3. 否则检查是否在 Export-Package 中，若是则在本 Bundle 内查找
4. 否则查找 Fragment Bundle
5. 否则委派给 Parent ClassLoader
6. 否则查找本 Bundle 的 ClassPath
7. 否则抛出 ClassNotFoundException

## 一句话总结

类加载分为加载、验证、准备、解析、初始化五个阶段，双亲委派模型通过自顶向下的委派机制保证核心类安全与避免重复加载，但 SPI（JDBC）、Tomcat、OSGi 等场景出于灵活性需要打破了双亲委派。
