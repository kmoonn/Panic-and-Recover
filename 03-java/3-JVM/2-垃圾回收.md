# JVM 垃圾回收（Garbage Collection）

## Q1: 如何判断对象是垃圾?

### 方法一：引用计数法（Reference Counting）

每个对象维护一个引用计数器，被引用时 +1，引用断开时 -1，计数为 0 即可回收。

| 优点 | 缺点 |
|------|------|
| 实现简单，判定效率高 | **无法处理循环引用** |
| 可即时回收 | 每次赋值需更新计数器，开销大 |

```java
// 循环引用示例：引用计数法无法回收
Object a = new Object();  // a.count = 1
Object b = new Object();  // b.count = 1
a.ref = b;  // b.count = 2
b.ref = a;  // a.count = 2
a = null;   // a.count = 1（b.ref 仍引用 a）
b = null;   // b.count = 1（a.ref 仍引用 b）
// 实际上 a、b 已不可达，但 count != 0，无法回收 → 内存泄漏！
```

> Python 使用引用计数 + 辅助分代 GC 解决循环引用；JVM **不采用**引用计数法。

### 方法二：可达性分析（Reachability Analysis）✅ JVM 采用

从 **GC Roots** 出发，沿引用链搜索，不可达的对象即为垃圾。

```
GC Roots ──→ A ──→ B ──→ C   （可达，存活）
         ──→ D ──→ E          （可达，存活）

         F ──→ G              （从 GC Roots 不可达，可回收）
```

## Q2: 什么是 GC Roots? 哪些对象可作为 GC Roots?

| GC Root 类型 | 说明 | 示例 |
|-------------|------|------|
| 栈帧中的局部变量 | 当前正在执行的方法中引用的对象 | 方法参数、局部变量 |
| 静态变量引用 | 类的 static 字段引用的对象 | `static Object obj` |
| JNI 引用 | 本地方法栈中 JNI 引用的对象 | `JavaVM*`、`jobject` |
| 同步锁引用 | `synchronized` 持有的 monitor 对象 | `synchronized(obj)` 中的 obj |
| 线程对象 | 活着的线程本身 | `Thread.currentThread()` |
| 类加载器 | 启动类加载器等核心加载器 | `BootstrapClassLoader` |
| 常量池引用 | 字符串常量池等 | `String.intern()` 结果 |

> **注意**：一个对象成为 GC Root 是**动态**的，方法执行完局部变量出栈后就不再是 Root。

## Q3: 三种基础垃圾回收算法

### 1. 标记-清除（Mark-Sweep）

```
标记阶段：从 GC Roots 遍历，标记所有可达对象
清除阶段：遍历堆，回收未标记对象
```

| 优点 | 缺点 |
|------|------|
| 实现简单 | **内存碎片**：回收后空间不连续 |
| 不需要移动对象 | 标记+清除两次遍历，效率较低 |
| | 大对象分配可能因碎片失败 |

### 2. 复制算法（Copying）

```
将内存分为两块等大小区域（From / To）
GC 时：把存活对象从 From 复制到 To，清空 From，交换角色
```

| 优点 | 缺点 |
|------|------|
| **无碎片**：复制后空间连续 | **浪费一半空间** |
| 分配快（指针碰撞） | 存活对象多时复制开销大 |
| | 适合存活率低的场景（新生代） |

### 3. 标记-压缩（Mark-Compact）

```
标记阶段：同 Mark-Sweep
压缩阶段：将存活对象向一端移动，整理边界外空间
```

| 优点 | 缺点 |
|------|------|
| **无碎片** | 移动对象需更新引用，**耗时最长** |
| 不浪费空间 | 算法最复杂 |
| | 适合存活率高的场景（老年代） |

### 算法对比

| 算法 | 碎片 | 空间利用率 | 速度 | 适用区域 |
|------|------|-----------|------|---------|
| Mark-Sweep | 有碎片 | 高 | 中等 | CMS（老年代） |
| Copying | 无碎片 | **低（50%）** | 快（存活少时） | 新生代 |
| Mark-Compact | 无碎片 | 高 | **慢（移动+更新引用）** | 老年代 |

## Q4: 分代收集理论

JVM 根据对象存活时间将堆分为**新生代**和**老年代**，不同代使用不同算法。

### 堆内存布局

```
┌─────────────────────────────────────────────────┐
│                      堆 (Heap)                   │
├────────────────────────────────┬────────────────┤
│          新生代 (Young)         │  老年代 (Old)   │
├────────┬──────────┬───────────┤                │
│  Eden  │ Survivor0│ Survivor1 │                │
│  80%   │   10%    │   10%     │                │
└────────┴──────────┴───────────┴────────────────┘
```

| 区域 | 默认比例 | 说明 |
|------|---------|------|
| Eden | 8 | 新对象优先分配在此 |
| Survivor0 (From) | 1 | 存活对象暂存区 |
| Survivor1 (To) | 1 | 存活对象暂存区 |
| Old | - | 长期存活对象 |

### GC 类型

| GC 类型 | 触发条件 | 回收区域 | 频率 | STW 时长 |
|---------|---------|---------|------|---------|
| Minor GC / Young GC | Eden 区满 | 新生代（Eden + S0 + S1） | 频繁 | 短（毫秒级） |
| Major GC / Old GC | 老年代空间不足 | 老年代 | 较少 | 较长 |
| Full GC | 整个堆满 / Metadata 满等 | 新生代 + 老年代 | 尽量避免 | 最长 |

## Q5: 对象从创建到晋升老年代的完整流程

```
1. new 对象 → 尝试分配到 Eden 区
   │
   ├── Eden 空间足够 → 直接分配（指针碰撞 / TLB）
   │
   └── Eden 空间不足 → 触发 Minor GC
       │
       ├── GC 后 Eden 仍不足 → 直接分配到老年代（空间分配担保）
       └── GC 后 Eden 足 → 分配成功

2. Minor GC 时：
   ├── Eden + From 中存活对象 → 复制到 To
   │   └── 年龄 +1
   ├── 年龄达到阈值（默认 15）→ 晋升老年代
   ├── To 区放不下 → 直接晋升老年代（动态年龄判断）
   └── 交换 From / To 角色

3. 大对象（超过 Eden 一半）→ 直接进入老年代（-XX:PretenureSizeThreshold）

4. 老年代空间不足 → Major GC / Full GC
```

| 晋升条件 | 说明 |
|---------|------|
| 年龄达到阈值 | 默认 15（`-XX:MaxTenuringThreshold`），CMS 下最大为 6 |
| 动态年龄判断 | To 区中同龄对象总大小 > To 区一半，该年龄及以上晋升 |
| 空间分配担保 | Minor GC 后 Survivor 放不下，直接进入老年代 |

## Q6: 常见垃圾回收器

### 按代分类

| 新生代 | 老年代 | 组合 | 说明 |
|-------|--------|------|------|
| Serial | Serial Old | 单线程，Client 模式默认 | 全程 STW |
| Parallel Scavenge | Parallel Old | 多线程并行，注重吞吐 | JDK 8 默认 |
| ParNew | CMS | CMS 的年轻代搭档 | 低停顿 |
| G1 | G1 | 不分代，Region 模式 | JDK 9 默认 |
| ZGC | ZGC | 不分代，着色指针 | JDK 15+ 生产可用 |

### 各回收器详解

#### Serial / Serial Old
- 单线程，GC 时 STW，"Stop The World"
- 适合客户端应用、小堆

#### Parallel Scavenge / Parallel Old
- 多线程并行 GC，目标是**最大吞吐量**（用户代码时间 / 总时间）
- 参数：`-XX:MaxGCPauseMillis`、`-XX:GCTimeRatio`

#### CMS (Concurrent Mark Sweep) — 已在 JDK 14 移除
- 目标：**最低停顿时间**
- 四个阶段：初始标记(STW) → 并发标记 → 重新标记(STW) → 并发清除

| 阶段 | STW? | 说明 |
|------|------|------|
| 初始标记 | 是 | 标记 GC Roots 直接引用的对象，极快 |
| 并发标记 | 否 | 从 Roots 遍历整个对象图（最耗时，与用户线程并发） |
| 重新标记 | 是 | 修正并发标记期间变动的引用（使用写屏障 + 增量更新） |
| 并发清除 | 否 | 清除未标记对象（与用户线程并发） |

- **缺点**：碎片问题（Mark-Sweep 不压缩）、CPU 敏感（并发线程占用 CPU）、浮动垃圾（并发清除阶段新产生的垃圾只能下次 GC 回收）

#### G1 (Garbage-First) — JDK 9+ 默认
- 将堆划分为多个等大 **Region**（1~32MB），每个 Region 可以是 Eden / Survivor / Old / Humongous
- **混合回收**（Mixed GC）：回收部分价值最高的 Region（垃圾最多的优先，Garbage-First 之名由来）

```
┌──────┬──────┬──────┬──────┬──────┬──────┐
│ Eden │ Old  │ Eden │ Free │Surviv│ Humo │
│      │      │      │      │      │ ngous│
└──────┴──────┴──────┴──────┴──────┴──────┘
       ←─── Region ───→
```

| 阶段 | STW? | 说明 |
|------|------|------|
| 初始标记 | 是 | 借助 Minor GC 的 STW 顺便完成 |
| 并发标记 | 否 | 遍历对象图，使用 SATB 快照 |
| 最终标记 | 是 | 处理 SATB 缓冲区中的残留引用 |
| 筛选回收 | 是 | 选择回收价值高的 Region，复制存活对象到空 Region |

#### ZGC — JDK 15+ 生产可用
- **着色指针**（Colored Pointers）：在指针中嵌入 GC 元信息（标记、重映射状态），无需写屏障
- **读屏障**：加载引用时检查指针颜色，自愈（Self-Healing）
- 目标：**亚毫秒级停顿**（< 1ms），且停顿不随堆增大而增加
- 支持 TB 级堆

| 特性 | ZGC |
|------|-----|
| 停顿时间 | < 1ms（通常 0.1~0.2ms） |
| 停顿与堆大小关系 | 无关 |
| 并发阶段 | 标记、转移、重定位全部并发 |
| 指针技术 | 着色指针 + 读屏障 |
| 适用堆大小 | 8MB ~ 16TB |

## Q7: G1 vs CMS 对比

| 对比维度 | CMS | G1 |
|---------|-----|-----|
| 算法 | Mark-Sweep（标记-清除） | Mark-Region-Compact（Region 级复制+压缩） |
| 内存碎片 | **有碎片**，长期运行后需 Full GC 压缩 | **无碎片**，Region 间复制整理 |
| 回收范围 | 整个老年代 | 选择性回收部分 Region（Mixed GC） |
| 停顿可控 | 否，停顿不可预测 | **是**，`-XX:MaxGCPauseMillis` 设定目标 |
| 浮动垃圾 | 有（Concurrent Sweep 阶段产生） | 有但更少（SATB 比 Incremental Update 精确） |
| 内存布局 | 传统分代（连续的新生代 + 老年代） | Region 化化（逻辑分代，物理不连续） |
| 大堆支持 | 差（碎片 + Full GC 风险） | **好**（Region + 可控停顿） |
| 默认启用 | JDK 5~8 可用，JDK 9 被废弃，JDK 14 移除 | JDK 9 默认 |

## Q8: 如何选择垃圾回收器?

| 场景 | 推荐回收器 | 理由 |
|------|-----------|------|
| 单核 / 小堆 (< 200MB) | Serial | 资源有限，无需并行开销 |
| 多核 / 追求吞吐量 / 批处理 | Parallel Scavenge + Parallel Old | 最大化用户代码/总时间比 |
| 多核 / 追求低延迟 / 交互式 | G1 | 停顿可控，JDK 9+ 默认 |
| 超大堆 (> 8GB) / 极低延迟 | ZGC | 亚毫秒停顿，不随堆增大 |
| JDK 8 / 低延迟老项目 | CMS | 兼容性（但注意碎片问题） |

**常用 JVM 参数**：

```bash
# Serial
-XX:+UseSerialGC

# Parallel（JDK 8 默认）
-XX:+UseParallelGC
-XX:MaxGCPauseMillis=200

# G1（JDK 9+ 默认）
-XX:+UseG1GC
-XX:MaxGCPauseMillis=200

# ZGC（JDK 11+）
-XX:+UseZGC
-XX:ZCollectionInterval=0   # 连续 GC 间隔

# 通用调优
-Xms4g -Xmx4g               # 堆大小（建议 Xms == Xmx）
-XX:+PrintGCDetails         # 打印 GC 日志
-XX:+PrintGCDateStamps      # GC 日志加时间戳
```

## 一句话总结

JVM 通过可达性分析从 GC Roots 判定垃圾，基于分代理论（新生代用复制算法、老年代用标记-压缩/清除）将堆分为 Eden+Survivor+Old，对象经多次 Minor GC 后晋升老年代；主流回收器从 Serial → Parallel → CMS → G1 → ZGC 逐步演进，核心趋势是降低停顿、消除碎片、支持更大堆。
