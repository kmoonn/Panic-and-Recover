# 造数Skill设计与难点

## Q: 造数 Skill 怎么设计？有哪些常见难点？

在测试场景里，造数据经常比写测试逻辑还难。因为很多用例不是“直接发请求就能测”，而是依赖一组复杂的前置状态，比如：

- 用户必须是会员且即将过期
- 订单必须是已支付未发货
- 库存刚好不足
- 优惠券在特定活动时段内可领取

所以“造数 Skill”本质上不是简单生成假数据，而是：**根据目标测试场景，稳定地构造出满足约束的业务状态**。

---

## 一、为什么造数要做成 Skill

如果只用普通 Prompt 做造数，常见问题是：
- 输入不规范
- 输出格式不稳定
- 数据约束容易漏掉
- 造完后无法校验是否真的可用
- 多次执行容易互相污染

而做成 Skill 的好处是：

1. **输入结构化**：明确要什么数据
2. **输出结构化**：明确返回哪些结果
3. **约束可复用**：同类测试场景反复调用
4. **更容易接工具**：数据库、接口、脚本可以标准化接入

所以造数特别适合 Skill 这种“有明确输入、明确输出、需要工具协作”的能力形态。

---

## 二、一个完整造数 Skill 的基本结构

参考 Skill 的标准结构，造数 Skill 通常包含：

```text
造数Skill
├── SKILL.md             # 描述能力、输入输出、使用方式
├── references/          # 业务规则、字段约束、表结构说明
├── scripts/             # 调接口、查库、清理数据的脚本
└── evals/               # 验证造出来的数据是否满足预期
```

核心不是目录长什么样，而是下面四件事要清晰：

1. **输入 schema**：我到底要造什么
2. **约束规则**：这些数据必须满足什么条件
3. **执行方式**：通过接口、脚本还是数据库落库
4. **结果校验**：造完后怎么证明数据真的可用

---

## 三、造数 Skill 的输入设计

### 输入一定要结构化

例如不要只写：

```text
帮我造一个可支付订单
```

而应该尽量明确为：

```json
{
  "userType": "member",
  "orderStatus": "UNPAID",
  "productType": "video",
  "inventory": "enough",
  "coupon": {
    "enabled": true,
    "status": "unused"
  }
}
```

### 为什么要这样做

因为“可支付订单”背后可能隐含很多约束：
- 用户必须已实名
- 商品必须上架
- 库存必须充足
- 优惠券必须在有效期内
- 订单金额必须大于 0

如果输入不结构化，Agent 很容易只满足一半条件。

---

## 四、造数 Skill 的输出设计

输出也不能只是“已完成”。

推荐输出至少包含：

```json
{
  "success": true,
  "userId": 1001,
  "orderId": 98765,
  "couponId": 123,
  "evidence": {
    "dbChecked": true,
    "apiChecked": true
  }
}
```

### 为什么输出也要结构化

因为下游测试步骤通常会依赖这些信息：
- 后续接口要用哪个 `orderId`
- UI 场景要登录哪个 `userId`
- 回收清理要清哪些数据

---

## 五、造数 Skill 的核心难点

## 1. 业务约束复杂且隐含

### 问题表现

同样叫“可支付订单”，不同业务下可能要求完全不同：
- 商品类型不同
- 活动状态不同
- 用户身份不同
- 账户余额不同

### 为什么难

很多约束不写在一个地方，而是散落在：
- PRD
- 接口文档
- 代码逻辑
- 数据库表关系
- 历史经验

### 解决思路

- 把高频业务场景沉淀成模板
- 在 references 中补充业务约束说明
- 输入 schema 显式表达关键条件

---

## 2. 关联数据多，单表插入不够

### 问题表现

有些场景不是插一条表记录就行，而是要联动多张表：
- 用户表
- 订单表
- 支付表
- 库存表
- 券表

### 为什么难

如果只造主表，不造依赖表，下游执行时就会失败。

### 解决思路

- 明确实体间依赖关系
- 按依赖顺序造数据
- 造完后查库验证各关联关系是否成立

---

## 3. 幂等性和重复执行问题

### 问题表现

同一个 Skill 多次执行后可能：
- 插入重复数据
- 命中唯一约束
- 污染环境
- 影响其他测试

### 解决思路

- 输入中允许传唯一标识
- 优先复用已有可用数据，而不是每次硬插
- 有副作用的数据操作要支持清理/回滚
- 输出里返回可供清理的关键 id

---

## 4. 环境隔离难

### 问题表现

开发、测试、预发环境规则不同，造数方式也可能不同。

### 为什么难

- 有的环境允许直接写库
- 有的环境只能走接口
- 有的环境表结构不同
- 有的环境依赖服务不完整

### 解决思路

- Skill 明确环境参数
- 不同环境使用不同适配器
- 能走接口就尽量走接口，避免直接写脏数据
- 高风险环境禁止直写库

---

## 5. 造完后不知道是否真的可用

### 问题表现

Skill 返回 success，但实际数据不可用：
- 状态没写对
- 下游查不到
- UI 看不到
- 业务校验过不去

### 解决思路

造数后一定要做验证，至少包括：
- DB 校验：数据是否落到正确表、正确字段
- API 校验：接口查出来的状态是否正确
- 场景校验：是否真的能支撑目标测试步骤

> **关键点**：造数 Skill 不只是“生成”，还必须“自证可用”。

---

## 六、推荐的造数 Skill 设计原则

| 原则 | 说明 |
|------|------|
| **输入结构化** | 约束条件不能只写自然语言 |
| **输出结构化** | 返回关键 ID、状态、证据 |
| **约束显式化** | 会员、状态、库存、时效等写清楚 |
| **优先走业务接口** | 尽量按真实业务路径造数 |
| **支持幂等与清理** | 重复执行不污染环境 |
| **造后必校验** | 不能只返回 success，要验证可用性 |
| **环境可配置** | 不同环境用不同适配器和权限 |

---

## 七、一个简化的造数 Skill 流程

```text
接收输入条件
   ↓
检查是否已有可复用数据
   ↓
如果没有，则按依赖顺序创建数据
   ↓
调用 DB / API / 脚本补齐状态
   ↓
执行校验（DB + API + 场景）
   ↓
返回结构化结果（userId/orderId/...）
   ↓
必要时记录清理信息
```

---

## 八、面试回答模板

> 造数 Skill 的核心不是“随机生成一批数据”，而是根据测试场景稳定构造满足业务约束的状态。所以我会重点设计三块：第一是输入 schema，把用户类型、订单状态、库存、优惠券等条件结构化；第二是执行链路，按依赖顺序通过接口、脚本或数据库把数据造出来；第三是结果校验，不能只返回 success，而要查库、查接口，证明这些数据真的能支撑后续测试。落地难点主要在业务约束隐含、关联数据多、重复执行导致污染，以及不同环境能力不同，所以要特别强调幂等、清理和环境隔离。

## 一句话总结

> 造数 Skill 的本质是“为目标测试场景构造可用业务状态”，关键在于输入输出结构化、业务约束显式化、依赖数据按顺序构造、执行结果可验证，并通过幂等、清理和环境隔离保证可重复使用。
