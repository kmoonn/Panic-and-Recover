# AI 用例生成的质量评估

## Q: 用例生成的 Skill 评估标准是怎样的？怎么保证 AI 生成的用例或 checklist 可靠？

### 五层评估模型

```text
覆盖度 → 有效性 → 准确性 → 采纳率 → 效率
  (核心)   (可执行)  (对不对)  (好不好用) (划不划算)
```

优先级从左到右递减——覆盖度是底线，效率是加分项。

---

## 一、覆盖度 — 最核心

> 生成的用例或 checklist 有没有覆盖到需求里的关键点？

| 评估维度 | 检查方法 |
|---------|---------|
| 正常主流程 | 是否覆盖 PRD 中定义的 Happy Path |
| 异常场景 | 异常输入、权限不足、依赖失败等 |
| 边界值 | 数值上下界、空值、超长字符串 |
| 参数校验 | 必填/选填、类型、枚举范围、组合约束 |
| 风险点 | 高并发、安全、幂等、异常恢复是否覆盖 |

**量化方式**：以 PRD + 接口定义为基准，计算测试资产对需求点的覆盖率。

**圈定范围**：从需求和代码变更**两头**去圈定该覆盖什么——需求侧看 PRD 和接口文档，代码侧看 diff 涉及的分支和异常处理。

---

## 二、有效性 — 可不可执行、能不能发现问题

> 生成的用例或 checklist 需要是可执行的，不能只是“文字描述”。

| 评估点 | 说明 |
|--------|------|
| 数据齐不齐 | 测试数据是否完整（账号、参数、预期值） |
| 前置条件对不对 | 环境依赖、数据准备是否正确 |
| 步骤是否可执行 | 操作路径清不清晰，是否真的能落地 |
| 断言质量 | 断言是否真的校验了业务预期，而非“接口返回 200”这种无意义断言 |
| Checklist 是否有检查价值 | 是不是能帮助发现真实风险，而不只是空泛罗列 |

**有效性看三点**：
1. **能不能跑起来** —— 数据和环境就绪
2. **断言/检查项是否有意义** —— 能不能验证业务预期
3. **能不能发现真实问题** —— 不是写得多，而是查得准

---

## 三、准确性 — 生成内容对不对

> AI 可能“编造”不存在的接口字段、页面元素或业务规则。

| 常见问题 | 示例 |
|---------|------|
| 幻觉字段 | 生成了接口文档中不存在的参数 |
| 逻辑错误 | 正常流程和异常流程的预期结果搞反 |
| 业务误解 | 对业务规则理解有偏差，断言不符合实际预期 |
| 场景错位 | 把后台接口用例写成 UI 交互步骤 |

**应对策略**：
- 与接口文档/PRD 自动对齐，校验字段是否存在
- 人工 review 抽样，确认业务逻辑无误
- 给 AI 更明确的输入上下文和约束模板

---

## 四、采纳率 — 好不好用

> Review 之后能直接采纳多少？需要人工改多少？

| 采纳率等级 | 含义 |
|-----------|------|
| >80% | 高质量，小修即用 |
| 50%-80% | 可用，需补充数据或修正断言 |
| <50% | 质量不足，人工修改成本高 |

### 采纳率怎么细分

可以拆成三档：
- **直接采纳**：几乎不用改
- **修改后采纳**：需要补充、删减、重写部分内容
- **不采纳**：质量太差，人工重写成本更低

### 一个更完整的计算方式

```text
采纳率 = 被采纳的用例/检查项数 ÷ 总生成数
```

如果想更细，可以拆成：

```text
直接采纳率 = 直接采纳数 ÷ 总生成数
修改后采纳率 = 修改后采纳数 ÷ 总生成数
弃用率 = 未采纳数 ÷ 总生成数
```

**提升采纳率的方法**：
- 给 AI 提供更精确的上下文（接口文档、历史用例模板）
- 在 prompt 中约束输出格式和断言规范
- 多轮迭代：先生成骨架，再补充细节

---

## 五、效率 — 划不划算

| 指标 | 计算 |
|------|------|
| 生成速度 | 从需求到测试资产初稿的耗时 |
| 节省比例 | AI 生成 vs 人工编写的工时比 |
| 修后成本 | 采纳 + 修改的总耗时 vs 全人工耗时 |
| 人审成本 | 人工 review 每条资产的平均耗时 |

> 效率是加分项——如果覆盖度和有效性不达标，再快也没意义。

## 六、Checklist 的评估重点

AI 生成 checklist 和生成完整用例有相似点，但也有差异。

### Checklist 更关注什么

| 维度 | 含义 |
|------|------|
| 是否覆盖关键检查维度 | 正常、异常、边界、安全、性能是否都考虑到 |
| 是否可执行 | 检查项不是空话，而是能落地验证 |
| 是否能发现风险 | 不是“看看对不对”这种无效项 |
| 是否复用价值高 | 能否作为后续测试模板长期复用 |

### 常见无效 checklist 特征

- 只有大而空的口号，没有检查动作
- 没有预期结果
- 没有输入条件
- 全是主流程，没有异常和边界
- 与当前需求明显不相关

### Checklist 的有效命中率

这个指标非常适合面试表达。

```text
有效命中率 = 真正有检查价值的 checklist 项数 ÷ checklist 总项数
```

## 七、如何判断 AI 生成内容是否可靠

```text
         ┌──────────────┐
         │   精确上下文   │  ← PRD + 接口文档 + 代码 diff
         └──────┬───────┘
                │
                ▼
         ┌──────────────┐
         │   约束 Prompt  │  ← 格式规范 + 断言模板 + 禁止幻觉指令
         └──────┬───────┘
                │
                ▼
         ┌──────────────┐
         │  多轮迭代生成  │  ← 先骨架后细节，逐步补充
         └──────┬───────┘
                │
                ▼
         ┌──────────────┐
         │  自动校验对齐  │  ← 字段校验 + 接口一致性检查
         └──────┬───────┘
                │
                ▼
         ┌──────────────┐
         │  人工 Review   │  ← 抽样确认 + 采纳率统计
         └──────────────┘
```

### 关键做法

1. **上下文要准**：没有准确 PRD 和接口文档，AI 很容易幻觉
2. **模板要清晰**：输出必须约束格式、步骤、断言、预期
3. **要做自动对齐**：字段存在性、接口参数、必填项都要校验
4. **一定要有人审**：尤其是断言和业务规则部分

---

## 八、面试回答模板

> 我一般会用一个五层模型评估 AI 生成的用例或 checklist：先看覆盖度，确认关键需求点、异常和边界有没有覆盖；再看有效性，判断内容能不能执行、断言和检查项有没有意义；第三看准确性，避免幻觉字段和业务误解；第四看采纳率，包括直接采纳、修改后采纳和弃用比例；最后才看效率，比如节省了多少工时。对于 checklist，我会特别关注“有效命中率”，也就是这些检查项里有多少是真正能发现风险的，而不是空泛描述。为了保证可靠性，通常要结合精确上下文、约束 Prompt、自动校验和人工 review 一起做。

## 一句话总结

> AI 生成测试资产的评估核心是五层模型：覆盖度、有效性、准确性、采纳率、效率；其中 checklist 还要特别关注有效命中率和复用价值，保证它不仅“生成得出来”，还“真的能发现问题”。
