# 提示词增强召回

## 什么是提示词增强召回

用户输入的 Query 通常很短、模糊、缺少上下文，直接拿去做向量检索效果差。**提示词增强召回**（Query Rewriting / Query Expansion）就是在检索前，用 LLM 改写或扩展用户的 Query，使其更适合检索。

```
用户原始 Query："Python 装饰器"
        │
        ▼
  Query 增强（LLM 改写/扩展）
        │
        ▼
增强后 Query："Python 装饰器的用法、原理、带参数装饰器、类装饰器、functools.wraps 的作用"
        │
        ▼
  向量检索 → 召回更全面
```

---

## 核心方法

### 1. Query Rewriting（查询改写）

用 LLM 将模糊/口语化的 Query 改写为更精确、更适合检索的形式。

| 改写类型 | 原始 Query | 改写后 |
|---------|-----------|--------|
| 补全语义 | "怎么防 SQL 注入" | "Java Web 应用防止 SQL 注入攻击的方法：预编译语句、ORM 框架、输入校验" |
| 纠正歧义 | "Java 泛型" | "Java 泛型机制：类型擦除、通配符、泛型方法、泛型与继承" |
| 多角度展开 | "Redis 为什么快" | "Redis 高性能原因：内存存储、单线程模型、IO 多路复用、高效数据结构" |

**Prompt 示例**：

```
你是一个查询改写助手。请将用户的查询改写为更适合文档检索的形式：
1. 补充隐含的上下文和关键词
2. 展开缩写和简称
3. 保留原始意图

用户查询：{query}
改写后查询：
```

### 2. Query Expansion（查询扩展）

生成多个相关子查询，分别检索后合并结果，提高召回率。

```python
# 生成多个子查询
sub_queries = llm.generate(f"""
根据以下问题，生成 3 个不同角度的搜索查询，用于检索相关文档：

原始问题：{query}

搜索查询：
1.""")

# 分别检索
all_docs = []
for sq in sub_queries:
    docs = retriever.retrieve(sq, top_k=5)
    all_docs.extend(docs)

# 去重合并
unique_docs = deduplicate(all_docs)
```

### 3. HyDE（Hypothetical Document Embedding）

**核心思路**：先让 LLM 根据问题生成一个"假想答案"，再用这个假想答案的向量去检索。

```
用户 Query: "RAG 和 Finetuning 的区别"
        │
        ▼
  LLM 生成假想答案（可能不完全正确，但语义相关）
  "RAG 通过检索外部知识增强生成，无需修改模型参数；
   Finetuning 通过在特定数据上训练更新模型参数..."
        │
        ▼
  用假想答案的 Embedding 去检索 → 召回更精准
```

**为什么有效**：假想答案比原始 Query 更接近目标文档的语义空间，向量相似度更高。

```python
from langchain.llms import OpenAI
from langchain.chains import HypotheticalDocumentEmbedder

# HyDE 检索器
hyde_retriever = HypotheticalDocumentEmbedder.from_llm(
    llm=OpenAI(),
    base_embeddings=embeddings,
    prompt="请回答以下问题："
)

# 检索（自动生成假想答案并检索）
docs = hyde_retriever.get_relevant_documents("RAG 和 Finetuning 的区别")
```

### 4. Step-Back Prompting

让 LLM 先将具体问题抽象为更宽泛的概念性问题，检索更广的背景知识：

```
具体问题："为什么 B+ 树比 B 树更适合数据库索引？"
        │
        ▼ Step-Back
抽象问题："B+ 树和 B 树的结构差异是什么？数据库索引的选型标准有哪些？"
        │
        ▼
用抽象问题检索 → 获取更全面的背景知识
        │
        ▼
结合背景知识回答具体问题
```

### 5. Multi-Query Retrieval

同时使用多种改写策略检索，结果融合：

```
原始 Query ──→ 直接检索 ──────────→ 结果集 A
         ├──→ 改写后检索 ─────────→ 结果集 B
         ├──→ HyDE 检索 ──────────→ 结果集 C
         └──→ 子查询分别检索 ─────→ 结果集 D
                                    │
                                    ▼
                          RRF / 加权融合 → 最终结果
```

## 方法对比

| 方法 | 原理 | 优点 | 缺点 | 额外开销 |
|------|------|------|------|---------|
| **Query Rewriting** | LLM 改写 Query | 简单直接，单次 LLM 调用 | 改写可能偏离原意 | 1 次 LLM |
| **Query Expansion** | 生成多个子查询 | 多角度覆盖，召回全面 | 检索次数翻倍 | 1 LLM + N 次检索 |
| **HyDE** | 生成假想答案再检索 | 语义空间更接近目标文档 | 假想答案可能误导 | 1 LLM + 1 次检索 |
| **Step-Back** | 抽象化问题再检索 | 获取更广背景知识 | 可能丢失具体细节 | 1 LLM + 1 次检索 |
| **Multi-Query** | 多策略并行 | 最全面 | 开销最大 | N LLM + N 次检索 |

## 面试高频

### Query 增强一定比直接检索好吗？

不一定。简单事实型查询（如"Python 的 GIL 是什么"）直接检索即可，增强反而可能引入噪声。适合增强的场景：
- 用户 Query 太短/模糊（如"排序算法"）
- 专业术语多，需要展开
- 多角度问题（如"对比 X 和 Y"）

### HyDE 和 Query Rewriting 怎么选？

| 场景 | 推荐 | 原因 |
|------|------|------|
| Query 与文档语义空间差距大 | HyDE | 假想答案更接近文档 |
| Query 只需补全关键词 | Rewriting | 更轻量，延迟更低 |
| 文档库专业性强、术语多 | HyDE | 假想答案包含专业术语 |
| 对延迟敏感 | Rewriting | HyDE 多一次 LLM 生成 |

### 增强后的多路检索结果如何融合？

最常用 **RRF（Reciprocal Rank Fusion）**：

```python
def rrf_merge(result_lists, k=60):
    """多路检索结果融合"""
    scores = {}
    for results in result_lists:
        for rank, doc in enumerate(results):
            scores[doc] = scores.get(doc, 0) + 1.0 / (k + rank + 1)
    return sorted(scores.items(), key=lambda x: -x[1])
```

RRF 不依赖原始分数，只看排名，适合不同检索方式分数不可比的情况。

---

## 一句话总结

> 提示词增强召回通过 LLM 改写/扩展/抽象化用户 Query 提升检索质量，核心方法有 Query Rewriting（改写）、Query Expansion（多子查询）、HyDE（假想答案检索）、Step-Back（抽象化），根据场景选择，多路检索结果常用 RRF 融合。
