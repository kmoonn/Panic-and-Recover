# RAG链路排查与问题定位

## Q: RAG 如何判断生成的回答是否正确？如果效果不好，怎么排查是哪一步出了问题？

回答这类问题，不能只说“看最终答案对不对”，因为 RAG 是一条完整链路：

```text
用户问题 → Query 改写 → Chunk 切分 → Embedding → 检索召回 → ReRank → Prompt 组装 → LLM 生成 → 后处理展示
```

所以判断 RAG 是否做对了，要看两层：

1. **结果层**：最终答案对不对、是否忠实、是否切题
2. **链路层**：如果不对，是 Query、检索、排序、Prompt 还是生成出了问题

---

## 一、先判断“回答是否正确”

### 1. 结果是否切题

问题：用户问的是 A，回答是不是还在答 A，而不是跑偏到 B。

对应指标：
- Answer Relevancy
- 用户主观满意度

### 2. 回答是否忠实于检索内容

问题：答案是不是基于召回内容生成的，有没有“编”。

对应指标：
- Faithfulness

### 3. 检索内容是否覆盖答案所需信息

问题：模型答不出来，是因为没检索到，还是检索到了但没用好。

对应指标：
- Context Recall
- Context Precision

### 4. 回答是否达到业务可用

有时候答案“基本对”，但对业务仍然不可用。

例如：
- 漏掉关键限制条件
- 回答不够完整
- 没给可执行建议

所以除了 RAGAS 类指标，还要看：
- 人工评审
- 任务完成率
- 用户是否继续追问

---

## 二、RAG 排查的总思路

最常见的错误不是“全链路都坏了”，而是某一段先出问题，后面全部被带偏。

所以排查应该遵循：

```text
先确认最终答案问题类型
→ 再判断是检索层问题还是生成层问题
→ 最后下钻到具体组件
```

常见判断方法：

| 现象 | 更可能的问题层 |
|------|---------------|
| 回答完全跑题 | Query 改写 / 检索召回 |
| 回答有依据但不完整 | Chunk 切分 / Recall |
| 检索到了正确文档但答案仍然胡编 | Prompt / Generation |
| 检索结果相关文档很多但排序差 | ReRank |
| 同一问题时好时坏 | Query 改写不稳定 / 检索波动 / Prompt 不稳定 |

---

## 三、按链路拆解排查

## 1. Query 改写阶段

### 这一层做什么

把用户自然语言问题，转成更适合检索的查询表达。

例如：
- 原问题：`怎么判断 RAG 回答对不对？`
- 改写后：`RAG evaluation metrics faithfulness answer relevancy context recall`

### 常见问题

- 改写过度，语义被带偏
- 丢掉原问题中的关键信息
- 关键词扩展不准确
- 多轮对话里上下文引用错误

### 典型现象

- 用户问中文，改写成英文后召回变差
- 用户问“如何排查”，改写后只剩“RAG 指标”
- 同义词扩展把问题引向错误领域

### 怎么查

- 打印原 query 和 rewrite 后 query
- 比较 rewrite 后是否丢掉实体词、限制词、场景词
- 观察不用 rewrite 时结果是否更好

### 优化方向

- 减少过度改写
- 保留原 query + rewrite 双路召回
- 对专有名词和约束词做保护

---

## 2. Chunk 切分阶段

### 这一层做什么

把原文档切成适合 embedding 和检索的小块。

### 常见问题

- chunk 太小：上下文断裂
- chunk 太大：噪音太多
- 切分边界不合理：标题和正文分开、问答拆散
- 表格/代码块被切坏

### 典型现象

- 检索结果命中了主题，但关键答案缺一半
- 多个 chunk 分别包含答案的不同部分，单独看都不完整

### 怎么查

- 把召回的 chunk 原文打印出来看
- 检查关键句是否被切断
- 对比不同 chunk size / overlap 的效果

### 优化方向

- 调整 chunk_size
- 增加 overlap
- 按语义结构切分：标题、段落、Q&A、表格整体保留

---

## 3. Embedding 阶段

### 这一层做什么

把 query 和文档 chunk 编成向量，便于语义检索。

### 常见问题

- embedding 模型不适合领域语料
- 中英文混合效果差
- 术语、缩写、代码词识别差
- query 和文档语言风格差异太大

### 典型现象

- 看起来相关的文档就是召不回来
- 语义很接近的内容排得很后
- 换关键词后结果变化特别大

### 怎么查

- 对比关键词检索 vs 向量检索
- 比较不同 embedding 模型效果
- 针对固定问题查看 TopK 召回结果稳定性

### 优化方向

- 更换更适合领域的 embedding 模型
- 混合检索：BM25 + 向量检索
- 对 query 做术语标准化

---

## 4. 检索召回阶段

### 这一层做什么

从知识库中召回候选文档或 chunk。

### 常见问题

- TopK 太小，正确文档没进候选集
- 召回策略过于依赖某一种检索方式
- 过滤条件过严，误删正确结果

### 典型现象

- Context Recall 低
- 用户问题能在知识库里找到答案，但检索结果没命中
- 一旦调大 TopK，正确答案就出现了

### 怎么查

- 看 TopK 结果中有没有正确 chunk
- 对比 Top5、Top10、Top20 的命中情况
- 检查 metadata filter 是否误过滤

### 优化方向

- 调大 TopK
- 采用混合召回
- 优化 metadata 标注和过滤逻辑

---

## 5. ReRank 阶段

### 这一层做什么

在候选结果里重新排序，把最相关的内容排前面。

### 常见问题

- 召回到了正确文档，但排序靠后
- rerank 模型对业务语义理解不准
- query 与候选文档匹配信号不足

### 典型现象

- Top20 里有对的，但 Top3 里没对的
- 不 rerank 反而更稳定

### 怎么查

- 对比召回前排序与 rerank 后排序
- 查看正确 chunk 在 rerank 前后的名次变化
- 分析 rerank 是否把“关键词多但不关键”的内容排前面

### 优化方向

- 更换 rerank 模型
- 调整 TopK → rerank 的候选集大小
- 给 rerank 输入更多上下文信息

---

## 6. Prompt 组装阶段

### 这一层做什么

把问题、检索上下文、系统指令拼成最终 prompt。

### 常见问题

- 没要求“只能基于上下文回答”
- 上下文太长，关键内容被淹没
- 上下文顺序差，核心 chunk 排后面
- Prompt 没要求引用证据或说明不确定性

### 典型现象

- 正确 chunk 已经召回，但模型还是胡编
- 模型忽略上下文，直接凭参数知识回答
- 相关 chunk 太多时回答变散

### 怎么查

- 打印最终 prompt
- 检查检索内容在 prompt 里的顺序和截断情况
- 对比“有约束 prompt”和“无约束 prompt”的输出差异

### 优化方向

- 明确加入“仅根据提供上下文回答”
- 要求无法确定时明确说不知道
- 控制上下文长度，把高置信 chunk 放前面

---

## 7. LLM 生成阶段

### 这一层做什么

模型基于 prompt 生成最终答案。

### 常见问题

- 温度过高导致自由发挥
- 模型过强依赖参数记忆，不听上下文
- 模型对结构化输出不稳定

### 典型现象

- Faithfulness 低
- 同一输入多次输出差异很大
- 明明上下文里有正确答案，但生成内容偏离

### 怎么查

- 固定 prompt 和上下文，多次运行看稳定性
- 对比不同模型/temperature
- 让模型输出“引用依据”或“逐条证据”看是否能自证

### 优化方向

- 降低 temperature
- 更换更听指令的模型
- 增加引用和结构化约束

---

## 8. 后处理阶段

### 这一层做什么

对模型输出做格式化、截断、拼接、引用渲染等处理。

### 常见问题

- 后处理把关键信息删了
- 引用映射错误
- 多轮拼接时内容错位

### 典型现象

- 原始生成是对的，但最终展示是错的
- 引用编号错乱
- 答案被意外截断

### 怎么查

- 对比模型原始输出与最终展示输出
- 检查引用映射逻辑
- 检查前端渲染是否吞字符或转义异常

---

## 四、如何快速判断是“检索问题”还是“生成问题”

这是面试里最实用的一句话。

### 判断方法

#### 情况 1：检索结果里根本没有正确内容

说明更偏向：
- Query 改写问题
- Chunk 问题
- Embedding 问题
- 召回问题

#### 情况 2：检索结果里已经有正确内容，但答案还是错

说明更偏向：
- ReRank 问题
- Prompt 问题
- 生成问题

> **一句话判断**：先看“对的信息有没有被召回来”，有就是生成层问题，没有就是检索层问题。

---

## 五、推荐的排查顺序

```text
1. 先看最终答案是否切题、忠实、完整
2. 再看召回结果里有没有正确 chunk
3. 有正确 chunk → 查 rerank / prompt / generation
4. 没正确 chunk → 查 query rewrite / chunk / embedding / recall
5. 最后看后处理是否把正确答案弄坏了
```

这是最稳的排查顺序，因为能最快缩小问题范围。

## 六、现象 → 指标 → 原因 → 优化动作速查表

这是最适合面试和排查现场直接使用的一张表。

| 现象 | 优先看什么指标/证据 | 更可能原因 | 优先优化动作 |
|------|------------------|-----------|-------------|
| 回答完全跑题 | Answer Relevancy、rewrite 后 query | Query 改写偏了、召回错了 | 保留原 query、减少过度 rewrite、检查召回 TopK |
| 回答提到的概念相关，但关键结论缺失 | Context Recall、召回 chunk 原文 | Chunk 切分过碎、TopK 太小 | 调大 chunk overlap、提高 TopK |
| 回答看起来流畅，但明显“编”了信息 | Faithfulness、最终 prompt | Prompt 约束弱、模型自由发挥 | 强化“仅基于上下文回答”、降低 temperature |
| 检索结果里有正确文档，但最终答案还是错 | rerank 前后名次、最终 prompt | ReRank 排序差、Prompt 组装差 | 提升 rerank 质量、把高置信 chunk 前置 |
| 同一问题多次回答不稳定 | 多次输出差异、模型参数 | temperature 过高、Prompt 不稳定 | 降低 temperature、固定模板 |
| 热门问题表现好，长尾问题表现差 | Recall 命中率、embedding 质量 | 向量模型领域适配差 | 更换 embedding、加 BM25 混合检索 |
| 多轮对话越问越偏 | rewrite 输入、历史对话拼接 | 上下文拼接错误、历史轮次污染 | 限制历史窗口、重写对话状态管理 |
| 召回结果很多，但噪音很重 | Context Precision、TopK 内容质量 | 召回太宽、filter 不准 | 增加 metadata filter、引入 rerank |
| 原始输出正确，前端展示错误 | 原始生成 vs 最终展示 | 后处理截断、引用映射错 | 检查渲染层和后处理逻辑 |

### 一个面试里很好用的总结句

> 如果正确内容根本没召回到，那通常是检索层问题；如果正确内容已经召回到了但答案还是错，那通常是生成层问题。这个判断可以帮我快速缩小排查范围。

## 七、面试回答模板

> 我判断 RAG 回答是否正确，通常会看四个维度：是否切题、是否忠实于检索内容、检索内容是否覆盖答案所需信息，以及业务上是否可用。如果效果不好，我会先区分是检索层问题还是生成层问题：先看 TopK 召回结果里有没有正确 chunk，如果没有，优先排查 query 改写、chunk 切分、embedding 和召回；如果已经召回到了正确内容，但最终答案还是错，那就重点看 rerank、prompt 和模型生成。这样能把“最终答案错”进一步定位到具体链路环节，而不是只停留在结果层面。

## 一句话总结

> RAG 排查要先判断答案是否切题、忠实、完整，再沿着 Query 改写、Chunk、Embedding、召回、ReRank、Prompt、生成、后处理逐层定位——先看正确内容有没有被召回，是区分检索层问题和生成层问题的关键一步。
