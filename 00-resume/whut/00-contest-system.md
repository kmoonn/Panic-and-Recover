## 0. 项目一句话定位

一个**面向全校的学科竞赛获奖数据管理系统**，**核心业务是"获奖数据登记 → 审核（赛管初审 + 学校终审）→ 汇总导出，供保研/推免等下游用途使用"**：学生/老师提交竞赛获奖信息，经过赛事管理方初审、学校终审，审核通过的获奖数据统一汇总、导出，**供学校保研/推免等场景作为依据**（保送资格的最终认定在下游、不在本系统内计算）。管理员管理竞赛、审核获奖、汇总导出。我做的是**全栈**——从后端（登录鉴权、数据权限、获奖/审核/汇总数据的增删改查、批量导入导出）到前端页面。技术上有三个我重点打磨的点：**Sa-Token 做统一身份认证（SSO）**、**MyBatis 拦截器做动态数据权限**、**SAX 流式做高性能 Excel 读写**。系统上线稳定跑了一年多、服务全校师生量级。

> ⭐ **为什么这个业务定位很关键**：获奖数据是**保研/推免的重要依据**，属于**高利害数据**——数据准不准、审核严不严、有没有越权改别人的获奖，直接影响学生能不能保研。所以这个系统里**审核流的严谨、数据权限的防越权、审核留痕可追溯**不是锦上添花，是**核心诉求**，也正好是我三个技术点的价值所在。
> ⚠️ **诚实边界**：我的系统负责**获奖数据的登记、审核、汇总导出**；至于"这些获奖怎么折算成保研加分/资格"是**下游/学校政策层面的事，不在我系统里计算**——被问到就这么划清，别把别的环节揽成自己做的。

**一句话电梯陈述**：
> "这是我做的一个全校用的学科竞赛获奖管理系统，**核心是把学科竞赛获奖数据登记、审核（赛管初审 + 学校终审），再汇总导出，供保研推免等场景做依据**。我负责全栈开发，重点打磨了三个点：用 **Sa-Token 做统一登录鉴权**、用 **MyBatis 拦截器做动态数据权限**（不同角色/学院只能看和审自己该管的获奖数据，防越权）、用 **SAX 流式解析做高性能 Excel 导入导出**（批量导入获奖名单、导出汇总）。因为数据是保研的重要依据，审核和权限都要求很严、审核还要留痕。系统上线稳定运行一年多，服务全校师生量级。"

**我负责的边界（诚实划界）**
- ✅ **我 own**：这是我**基本独立完成**的项目——从后端（登录鉴权、数据权限、获奖/审核/汇总数据的增删改查、批量导入导出）到前端页面，三个技术点都是我做的。
- ⬜ **诚实说法**：基本一个人做，所以可以放心说"全栈都是我 own",但别把它吹成"扛住海量并发的大型分布式系统"——它是**上线稳定服务全校的高利害业务系统**，价值在**数据准确 + 审核严谨可追溯 + 完整落地**，不在规模；也别把"保送资格认定"揽成我系统算的，我做的是**获奖数据的管理与审核汇总**。

**关联到测开（顺势带出）**
- 这个项目让我**从开发视角理解了高利害数据系统怎么建**——做测开时更知道"哪里容易出问题、该怎么设计更好测"，比如**审核流状态流转、数据权限防越权、批量数据准确性**这些正是测试要重点覆盖、也是这个系统最不能出错的地方。

## 1. 60 秒项目总述稿（STAR，开场必背）

**【背景 S】** 学校学科竞赛获奖数据的**登记、审核，以及汇总供保研/推免等下游使用**，原来靠线下/表格，分散、易错、还难追溯——而这些数据**是学生保研的重要依据**，容不得错也容不得被越权篡改。需要一个**全校统一的线上系统**把"获奖登记 → 审核（赛管初审 + 学校终审）→ 汇总导出"全流程管起来，涉及多角色（学生/老师/赛管/学校管理员），并要处理**大批量获奖名单**的导入导出。

**【任务 T】** 我**基本独立完成全栈开发**，重点解决三个工程问题：统一登录、**多角色数据权限（防越权改别人获奖）**、大批量获奖数据导入导出。

**【行动 A】** 三个关键设计：
① **Sa-Token 统一身份认证**——用 Sa-Token 做登录鉴权和会话管理，**对接学校统一认证（CAS）做单点登录**，学生老师用校园账号直接登录；会话存 **Redis**；
② **MyBatis 拦截器动态数据权限**——用拦截器在 SQL 执行前**自动注入数据权限条件**，让不同角色/学院只能查到、审到自己范围内的获奖数据，**防止越权查看或篡改别人的获奖**，权限逻辑不散落在每个业务查询里；配合**审核状态流转 + 操作留痕**保证审核可追溯；
③ **SAX 流式 Excel 读写**——批量导入获奖名单、导出获奖汇总用 **FastExcel（底层基于 SAX 事件驱动）**逐行解析，边读边处理，避免 POI usermodel 一次性把整个 Excel 读进内存导致 OOM。

**【结果 R】** 系统上线**稳定运行一年多、服务全校师生量级（5 万+）**，把学科竞赛**获奖登记—审核—汇总导出**全流程线上化，多角色数据隔离和大批量数据处理都稳定支撑，保证了获奖数据的**准确、审核可追溯**，为保研/推免等下游提供可靠依据（数字为体感口径，见 Q7）。

## 1.5 端到端主流程（"讲下系统架构/一次请求怎么走"时用）⭐

```
用户（学生/老师/管理员/学院）
    │ 登录
    ▼
① Sa-Token：认证 + 会话/Token + 权限校验（登录态、角色）
    │
    ▼
② 业务请求（查竞赛/获奖/审核/汇总…）
    │
    ▼
③ MyBatis 拦截器：SQL 执行前自动注入"数据权限"过滤条件
   （按角色/学院/本人，拼 WHERE 条件 → 只查到、只审到该管的获奖数据，防越权）
    │
    ▼
④ 业务处理 + 落库（竞赛/获奖登记/审核状态流转+留痕/汇总 CRUD）
    │
    ▼
⑤ 批量数据：FastExcel（SAX）流式导入获奖名单（边读边入库）/ 导出获奖汇总（边查边写）
```

**讲解话术（约 40 秒）**：
> "一次请求先过 **Sa-Token**——校验登录态和角色，鉴权通过才进业务。业务查数据时，**MyBatis 拦截器**会在 SQL 执行前**自动拼上数据权限条件**，比如这个学院的老师只能查到、只能审本学院学生的获奖数据，**防止越权看或改别人的获奖**，权限过滤是统一在拦截器里做的、不用每个查询手写。获奖走**赛管初审 + 学校终审**的状态流转、审核动作留痕可追溯。批量场景比如导入一大批获奖名单或导出汇总，走 **FastExcel（底层 SAX 事件驱动）**——逐行处理，边读边入库、边查边写，不把整个 Excel 塞内存里。核心就是这三层：**统一鉴权、统一数据权限（防越权）、高性能批量数据**——都是围绕'获奖数据不能错、不能被越权改、能追溯'这个诉求，因为它是保研的重要依据。"

## Q4. "这系统核心是获奖数据审核，审核流程怎么设计的？怎么保证获奖数据不被越权改？"⭐⭐（业务核心，必被深挖）

**💡 大白话（自己理解用，不用背）**：这系统最核心的不是报名，是**获奖数据登记 → 赛管初审 → 学校终审 → 汇总导出**，导出的获奖数据供保研/推免等场景做依据（怎么折算成保研资格是**下游/学校政策的事，不在我系统里算**）。因为是保研的重要依据，最怕两件事：**数据被越权改**（别人改我的、我改别人的）、**审核没走完就生效**。所以审核要有明确状态流转 + 留痕，权限要卡死。

**✅ 打磨版答法（背这套）**：
> "这个系统的**核心业务链路是：学生/老师提交学科竞赛获奖 → 赛事管理方初审 → 学校终审 → 审核通过的获奖数据统一汇总、导出**，供学校保研/推免等场景作为依据。因为它是**高利害数据**（保研的重要依据），我在设计上重点保证三点：
> - **审核流的严谨**：获奖记录有明确的**状态流转**（待审核 / 已通过 / 已驳回），要**赛管初审 + 学校终审**两道都过才算数、才进汇总；驳回能说明理由、支持退回修改再提交，也支持**撤回/重走**（改动都重新经审核）；
> - **审核可追溯**：审核动作**留痕**——谁在什么时候把哪条记录审成什么状态都有操作日志，出问题能追溯、也防赖账；
> - **数据不能被越权动**：靠前面说的 **MyBatis 拦截器数据权限**——赛管/学院只能审、只能看自己该管范围的获奖，**不能越权查看或修改别人的获奖**；加上 **Sa-Token 的角色权限**卡住"谁能提交、谁能初审、谁能终审、谁能导出汇总"。
>
> ⚠️ 要划清的边界：我的系统做的是**获奖数据的登记、审核、汇总导出**；**保研加分/资格怎么算是下游、学校政策层面的事，不在我系统里计算**——被问到就这么说，不揽别的环节。整个系统的三个技术点其实都是为这条链路服务的：**Sa-Token 管谁能干什么、拦截器管谁能看/改哪条数据、FastExcel 管大批量获奖名单进出。**"

**⭐ 加分锚点**：能把三个技术点**串到"获奖数据是保研重要依据、高利害"这条业务主线**上（审核状态流转+留痕 + 数据权限防越权 + 批量导入导出），并**主动划清"保送资格认定在下游、不是我系统算的"**——既体现从业务风险倒推技术方案，又体现诚实不揽功。

**追问：审核分几级？状态怎么流转？**
> "是**两级：赛事管理方初审 + 学校终审**。每条获奖记录带状态（待审/通过/驳回），驳回可退回修改重提；要**两级都通过**才进汇总。另外还支持**撤回/重走**——比如提交后在初审前提交人可以撤回修改，或者数据有误时打回、重新走一遍审核流程，保证改动都重新经过审核、不会绕过。"

**追问：怎么防止有人绕过审核直接改成'已通过'或改数据？**
> "三层防护：**接口级**用 Sa-Token 卡角色——只有对应审核角色（赛管/学校）才能调对应审核接口；**数据级**用拦截器——就算是审核方，也只能操作自己权限范围内的记录，改不到别人的；**留痕级**——审核动作有**操作日志**（谁在何时把它审成什么状态），可追溯、可倒查，谁改的赖不掉。"

**追问：这跟测开有什么关系？**
> "这恰恰是**测试最该覆盖的高风险点**——见下一题：审核状态流转的每条路径、越权改获奖数据、批量导入的准确性，都是我做测开时会重点设计用例的地方。"

## Q5. "这三个技术点 / 这套获奖审核业务，测试的时候你会重点测什么？"⭐⭐（测开视角，主动往测开靠，超加分）

**💡 大白话（自己理解用，不用背）**：面测开，要主动把开发经历翻译成"我知道这里怎么测"。三个技术点 + 获奖审核业务各有测试重点。

**✅ 打磨版答法（背这套）**：
> "从测开视角，这个系统**最该重点测的高风险区**正好对应它的核心业务和三个技术点：
> - **审核流状态流转**：这是**获奖数据准不准**的关键——我会把审核建成**状态机**来测：待审→初审通过→终审通过、待审→驳回→重提→通过、以及**非法流转**（比如跳过赛管初审直接终审通过、已终审通过的还能不能被改），保证不会出现'没审完就生效'；再验**审核留痕**是否完整（每次状态变更都有日志）；
> - **数据权限（拦截器）**：**越权测试**的重灾区——重点测**横向越权**（A 学院/赛管账号能不能查/改到不该管的学生获奖）、边界（管理员/普通角色可见范围），因为拦截器一旦漏拼条件就是**获奖数据泄露或被篡改**；
> - **Sa-Token 鉴权**：测**未登录访问、Token 过期、越权调审核/导出接口、踢下线后是否即时失效**；
> - **批量导入（FastExcel）**：测**大文件不 OOM、脏数据/格式错误的容错、部分失败怎么处理（事务/回滚/错误报告）、导入的获奖数据准确性**——导错一条就可能影响某个学生的保研。
>
> 其实正是因为我开发时踩过这些点、又知道这些数据是保研的重要依据，做测开时我更清楚**从哪里下手设计用例、哪里最不能出错**。"

**⭐ 加分锚点**：把**审核流当状态机测、把数据权限当越权测、把批量导入当数据准确性测**，并扣回"错一条影响学生保研"的业务后果——这是测开面试里全栈项目最能加分的答法，体现"我懂开发+懂业务风险所以更会测"。

## Q6. "系统上线后，稳定性/线上问题是怎么保障的？遇到过什么问题？"⭐⭐（工程落地，展示扛线上能力，有真实案例）

**💡 大白话（自己理解用，不用背）**：上线一年多说明它得扛住真实使用。我有一个真实踩过的坑可以讲——**大 Excel 导入把内存撑爆/超时**，正是它逼着我从一次性读改成 FastExcel 流式，这条线索天然和 [`03-contest-excel.md`](./03-contest-excel.md)（SAX 流式）呼应。

**✅ 打磨版答法（背这套）**：
> "上线跑一年多，稳定性主要靠几点：**上线前重点验过越权**（避免学院间数据串）、**报名/出成绩高峰做了缓存**（Redis 缓存热点/竞赛数据、减轻数据库压力）。而**我印象最深的一个真实线上问题，就是大 Excel 导入的内存问题**——"

**⭐⭐ 真实线上案例（现象→定位→根因→修复，必背这一套）**：
> - **现象**：老师**批量导入一份很大的获奖名单**（几千上万行）时，请求**很慢、甚至直接失败/超时**，服务偶发**内存告警**、严重时 OOM；小文件却完全正常。
> - **定位**：我看**报错和内存曲线**——失败集中在大文件、且伴随堆内存飙升，基本锁定是**导入这条链路吃内存**；进一步看代码，用的是 **POI usermodel（`XSSFWorkbook`）一次性把整个 Excel 读进内存**建对象树。
> - **根因**：**一次性全量加载**——文件越大，内存里驻留的对象越多，几万行直接把堆撑爆；本质是**内存模型选错了**，不适合大文件。
> - **修复**：把导入改成 **FastExcel（底层 SAX 事件驱动）流式解析**——**逐行回调、边读边处理**，配合**每约 500 行攒一批批量入库**，内存只保留当前一小批数据。改完后**大文件导入稳定不再 OOM**、速度也上来了。
> - **沉淀**：从此**凡是大批量数据的读写都默认走流式**，不再一次性加载；也让我意识到**性能问题很多时候是'内存模型/数据结构'选错了**，不是加机器能解决的。

**⭐ 加分锚点**：这个案例把 **SAX/FastExcel 选型（详见 [`03-contest-excel.md`](./03-contest-excel.md)）和 Q6（线上稳定性）打通**——不是背概念，是"**真踩过 OOM → 定位到全量加载 → 换流式解决**"的完整闭环，比泛泛说"很稳定"强得多，体现你扛过真实线上、且会从根因上修。

**追问：当时为什么不直接加大 JVM 堆内存就好？**
> "加堆只是**把爆炸点往后推**——文件再大一点还是会 OOM，而且白白占内存、影响其他请求。**根因是一次性加载这个做法本身不 scalable**，换成流式才是**从根上解决**：不管文件多大，内存占用都稳定在一小批的量级。这也是我一贯的习惯——能一次修好就不打补丁。"

**追问：改成流式后，怎么验证真的解决了？**
> "拿**接近生产规模的大文件（几千到上万行）**压测导入，观察**堆内存曲线平稳、不再飙升、无 OOM**，且导入耗时可接受；再验数据**导入准确性**（行数、内容对得上）。作为测开这步我会特别认真——性能改造最怕'跑通了但数据错了'。"
