## 0. 一句话定位

用 **Sa-Token** 做登录鉴权、会话/Token 管理、角色权限校验，并**对接学校统一认证（CAS）做单点登录**——学生老师用校园账号直接登录，走**重定向回调 + Ticket 票据验证**流程、登录后**自动同步并初始化本系统用户身份**；Sa-Token 生成**分布式 Token 维护无状态会话**、Token/会话状态存 **Redis** 多实例共享。选它是因为比 Spring Security 轻、上手快、内置 SSO 对接 CAS 顺。

## 0.5 我的边界

**独立设计实现**：Sa-Token 接入、CAS 对接、Redis 会话、按角色（学生/老师/管理员/学院）的接口级权限控制都是我做的。它同时是审核业务"谁能提交/初审/终审/导出"的接口级卡点（业务串联见索引 §审核业务）。

## 深挖 Q&A ⭐⭐

**Q. "Sa-Token 是怎么用的？为什么不用 Spring Security / JWT 自己撸？"（必被深挖）**

**💡 大白话（自己理解用，不用背）**：Sa-Token 是个轻量的国产权限框架，登录、鉴权、单点登录开箱即用，比 Spring Security 配置简单。我用它管登录态和角色权限。

**✅ 打磨版答法（背这套）**：
> "Sa-Token 是个轻量的权限认证框架，登录、会话/Token 管理、角色/权限校验、单点登录这些开箱即用。我用它做：
> - **登录鉴权**：登录后由 Sa-Token 维护会话/Token，接口通过注解或拦截校验登录态；
> - **角色/权限**：按角色（学生/老师/管理员/学院）做接口级的权限控制；
> - **单点登录**：**对接学校的统一认证（CAS）**——学生老师用校园统一账号登录，不用为这个系统单独注册。流程是标准的 **CAS 重定向 + Ticket 票据校验**：未登录用户被**重定向**到学校 CAS，认证通过后 CAS 带一个 **Ticket（票据）**回调我的系统，我拿 Ticket 反向**向 CAS 验票**、验通过才**自动同步并初始化这个用户在本系统的身份**（首次登录建档、带上角色/部门），再建立 Sa-Token 会话。
>
> 之所以选 Sa-Token 不用 Spring Security：**Spring Security 配置重、学习曲线陡**，这个项目更需要快速落地清晰的登录+角色权限，Sa-Token **上手快、API 直观、够用**，而且它内置的 SSO 模块对接 CAS 也顺。JWT 只是 Token 的一种承载，Sa-Token 也支持——但它还帮我把会话、踢人下线、单点登录这些一起管了，不用我自己攒一套。"

**⭐ 加分锚点**：能说出"Sa-Token vs Spring Security"的取舍（轻量快速 vs 重配置）+ "CAS 重定向+Ticket 验票做真单点登录、验票后自动初始化用户身份" + "分布式 Token 无状态会话、状态放 Redis 共享" + "JWT 只是 Token 载体、Sa-Token 管得更全"，体现你是**按场景选型**、且做过真实的统一认证对接。

**追问：会话存哪？多实例部署怎么共享登录态？**
> "会话/Token 状态存 **Redis**——这样多实例部署时登录态是共享的，用户请求打到哪台机器都不会掉登录；而且改权限、踢人下线能在服务端即时生效。CAS 负责'谁能登录'，Sa-Token + Redis 负责'登录后的会话与权限'，分工清楚。"

**追问：你既说"无状态会话"又说"存 Redis"，不矛盾吗？（必被追）**
> "不矛盾——'无状态'指的是**应用服务本身不在本地内存里存 session**，请求靠携带的**分布式 Token**来识别身份，所以任意一台实例都能处理、能水平扩展；Redis 是**集中存 Token 对应的会话/权限状态**的共享存储，不属于某一台应用实例。所以是'**应用无状态、状态外置到 Redis**'，这正是分布式会话的标准做法。"

**追问：Token 怎么防篡改/过期？**
> "Token 有过期时间、由框架校验有效性；配合 Redis 会话，服务端可控失效（踢下线、改权限即时生效）。"（已确认：**按 Sa-Token 框架默认过期 + Redis 可控失效**做的，无特殊自定义续期逻辑）
