## 0. 一句话定位

**行级数据权限**：同一个查询，不同角色/学院能看到的行不一样。用 **MyBatis 拦截器**在 SQL 执行前**自动注入数据权限 WHERE 条件**，让不同角色/学院只能查到、审到自己该管的**获奖数据**，**防越权改别人的获奖**——权限逻辑不散落在每个业务查询里，收敛到一处。

## 0.5 我的边界

**独立设计实现**：拦截器（拦 `StatementHandler`）、**实体基类扩展权限属性**、**"角色-部门-自定义"3 层权限模型**、5 种权限粒度、字符串拼接注入条件都是我做的。它是审核业务"数据级防越权"的核心（业务串联见索引 §审核业务）；权限来源用户身份取自 Sa-Token（见 [`contest-sso`](./01-contest-sso.md)）。

## 深挖 Q&A ⭐⭐

**Q. "MyBatis 拦截器做数据权限，具体怎么实现的？为什么用拦截器不在业务里写？"（必深挖）**

**💡 大白话**：数据权限 = 不同人查同一张表，能看到的行不一样（比如 A 学院老师只看 A 学院的报名）。如果每个查询都手写 `WHERE 学院=?`，又累又容易漏。我用 MyBatis 拦截器，在 SQL 执行前统一自动拼上这个条件。

**✅ 打磨版答法（背这套）**：
> "数据权限指的是**行级权限**——同一个查询，不同角色能看到的数据范围不同。如果在每个业务 SQL 里手写过滤条件，**又重复又容易漏，漏一个就是越权**。
>
> 所以我用 **MyBatis 的 Interceptor（拦截器）**，拦截 SQL 执行（`StatementHandler`/`Executor` 层），在 SQL 真正执行前**动态改写它**——根据当前登录用户的角色/所属部门，**自动往 SQL 里注入数据权限的 WHERE 条件**。这样：
> - **业务代码不用管数据权限**，查询照常写，权限由拦截器统一织入；
> - **统一、不遗漏**：所有走 MyBatis 的查询都被覆盖，不会因为某个接口忘写过滤而越权；
> - **可配置**：我抽象了**"角色-部门-自定义"3 层权限模型**，支持 **5 种权限粒度**（借鉴若依 `@DataScope`：**全部数据 / 本部门及以下 / 本部门 / 仅本人 / 自定义部门**）——哪个角色是哪种粒度在配置里定义，拦截器运行时按粒度决定拼什么条件，规则调整改配置即可、不用改代码；
> - **无侵入**：需要做数据权限的实体通过**基类扩展权限属性**（部门/创建人等字段），拦截器读这些约定字段来拼条件，业务实体不用逐个改。
>
> 本质是**用 AOP 的思路把'数据权限'这个横切关注点从业务里抽出来**，收敛到一个地方。"

**⭐ 加分锚点**：讲清"行级数据权限 + 拦截器动态改写 SQL + 横切关注点收敛"，并点出"手写过滤易漏=越权风险"——体现你懂**为什么用拦截器**（安全+不重复），不是只会用。

**追问：拦截 MyBatis 哪个对象？怎么改写 SQL？**
> "拦截 `StatementHandler`，在 SQL 执行前拿到原始 SQL，**按当前用户的角色/学院拼上数据权限的 WHERE 条件**再执行。我当时是**字符串层面拼接**条件——实现直接、够用。但我很清楚它的局限：**遇到复杂 SQL（子查询、多表 join、分页 count）字符串拼接容易出错或拼错位置**，所以我把它**限定在需要数据权限的那类查询上、控制 SQL 复杂度**，没有对所有 SQL 无脑拼。"

**⭐ 补充（体现成长）**：如果被追问"这样安全/健壮吗"，诚实说：
> "字符串拼接是当时的实现，能满足这个系统的查询复杂度。如果重做或数据权限要覆盖更复杂的 SQL，**更稳妥的是用 SQL 解析器（如 JSqlParser）规范地插入条件**——它能正确解析 SQL 结构、把条件插到对的地方、不破坏分页和 join 语义。这也是我做完之后意识到的可改进点。"（✅ 诚实 + 展示你知道更优解，比硬说"我用了解析器"更可信）

**追问：怎么知道当前用户是谁、该加什么条件？**
> "从 Sa-Token 拿当前登录用户和角色/部门信息（放在上下文/ThreadLocal），再按该角色配置的**权限粒度**（全部/本部门及以下/本部门/仅本人/自定义部门）决定拼什么 WHERE 条件——拦截器读实体基类上约定的部门/创建人字段来落地这个范围。"

**追问：这样改写 SQL，性能和复杂查询（分页/子查询/join）会不会出问题？**
> "会——这正是字符串拼接方案的软肋，所以我**控制了走数据权限的 SQL 复杂度**、对复杂查询谨慎处理。真要通用化，用 SQL 解析器插条件才是更健壮的做法（见上）。"

## 总结卡（本点）

| 维度 | 一句话 |
|---|---|
| 本质 | 行级数据权限，AOP 思路把横切关注点从业务收敛到拦截器 |
| 拦截点 | `StatementHandler`，SQL 执行前动态注入 WHERE 条件 |
| 实现 | **字符串拼接**（直接够用），限定在需数据权限的查询、控制 SQL 复杂度 |
| 模型 | **"角色-部门-自定义"3 层** + **5 种粒度**（全部/本部门及以下/本部门/仅本人/自定义），**实体基类扩展权限字段**，改配置即调规则 |
| 价值 | 统一不遗漏、**防越权改别人获奖**；数据来源用户身份取自 Sa-Token |
| **红线** | 诚实承认 JSqlParser 是更优解（成长式加分）；字符串拼接软肋主动说清 |
