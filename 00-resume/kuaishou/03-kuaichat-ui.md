## 1. 60 秒项目总述稿（STAR，开场必背）

**【背景 S】** 快聊是移动端产品，核心链路（发消息、营销卡片、潜客留资）每次发版都要回归，痛点有三：一是**耗时**——多机型手工一台台点，一个版本要小半天；二是**易漏**——尤其**机型兼容**问题，测试不可能覆盖所有机型，漏了到线上才暴露；三是**重复**——每版都是同样的链路点一遍，纯体力活。

**【任务 T】** 我负责基于快手内部的 **KRunner** UI 自动化框架，搭建一套**核心链路 UI 自动化巡检体系**，替代发版前的部分人工回归。

**【行动 A】** 关键设计：
① **聚焦核心链路**——不做全量覆盖，只挑**消息发送、营销卡片、潜客留资**这几条"挂了就是大事"的核心链路做巡检（巡检思路，不是全功能自动化）；
② **多机型巡检**——在多机型上跑同一套巡检，专门把**机型兼容**这类人工最容易漏的问题暴露出来；
③ **稳定性治理**——UI 自动化最怕 flaky，做了元素定位、显式等待、失败重试等处理，保证巡检结果可信、不误报（Q3）；
④ **缺陷定位 + 推动修复**——巡检抓出的问题（机型兼容、弹窗层级等 4 类）定位清楚、跟研发推动修掉，并把巡检纳入发版流程。

**【结果 R】** 落地成覆盖快聊核心链路的自动化巡检体系，抓出并推动修复了机型兼容、弹窗层级等 4 类关键交互缺陷；单版本回归**体感**节省约 2-4 小时、回归效率提升约 30%（体感口径，见 Q9），把核心链路回归从人工体力活变成自动出报告。

## Q1. "KRunner 是什么？你基于它做了什么？没重复造轮子吧？"⭐⭐（复用基建，必被问）

**💡 大白话（自己理解用，不用背）**：KRunner 是快手内部**自研**的 UI 自动化框架，靠**标签 + 视觉**来找元素、驱动 App 点点点。它**只管"驱动单机跑用例"，不带调度/多机型编排**——多机型怎么分发、跑在哪，是我自己组织的。我不是造框架，是**用它写快聊的巡检用例**。

**✅ 打磨版答法（背这套）**：
> "KRunner 是快手内部**自研**的 **UI 自动化框架**，特点是**基于标签 + 视觉**做元素定位和操作——既能用控件标签/语义属性定位，也能用视觉方式识别界面元素，然后驱动点击/输入/滑动这些操作。它是个**执行框架、不带调度**，也就是说'在多台机型上怎么分发、怎么编排'不归它管、是我自己组织的。
>
> 我做的**不是造框架，而是基于它搭快聊的核心链路巡检**：设计巡检哪些链路、写巡检脚本、组织多机型跑、定位缺陷。我一贯的做法就是**复用现有基建、只补上业务这层**——框架层公司已经有 KRunner，没必要重造，我的价值在'把快聊核心链路变成可自动巡检的用例 + 组织起多机型巡检'这层。"

**⭐ 加分锚点**：主动说"复用框架、不重造轮子"，和 API Testing Agent 复用 ATE 一个思路——体现成本意识和工程判断力，面试官很吃。

**追问：KRunner 基于标签又基于视觉，这两种定位分别什么时候用？**
> "**标签/控件定位**是首选——稳、快、语义清晰；但移动端有些元素拿不到稳定标签（如自定义绘制的控件、图片化的 UI），这时用**视觉定位**兜底。两者结合能覆盖更多场景，也让定位更稳健（Q3）。"

## Q2. "为什么是'巡检'？和全量 UI 自动化回归有什么区别？"⭐⭐（定位之辨，最能体现测试思维）

**💡 大白话**："巡检"就像保安每天巡楼——只走关键路线看有没有着火，不是把每个房间翻一遍。目标是"核心链路别挂",不是"覆盖所有功能"。

**✅ 打磨版答法（背这套）**：
> "这是我做这套东西时最关键的判断：**我做的是巡检（冒烟/守护核心链路），不是全量 UI 回归**。
> - **全量 UI 自动化的坑**：UI 自动化用例**又贵又脆**——UI 一改就得改脚本，维护成本极高；想覆盖所有功能，最后往往是'维护脚本的时间比它省的还多',ROI 是负的。
> - **巡检的思路**：我只挑**'挂了就是大事'的核心链路**——发消息、营销卡片、潜客留资，把它们守住。这几条是快聊的命脉，任何一条在某个机型上挂了都是线上事故。**用最少的用例守住最关键的链路**，ROI 最高。
>
> 所以定位是'核心链路守护',不是'全功能覆盖'——这是我对 UI 自动化 ROI 的清醒判断。"

**⭐ 加分锚点**：讲清"UI 自动化用例又贵又脆、所以只守核心链路"，体现你懂 UI 自动化的**真实成本和 ROI**，不是盲目追求覆盖率——这是很成熟的测试工程判断。

**追问：那核心链路怎么选出来的？**
> "按**业务重要性 × 出问题的影响面**选：这条链路是不是用户/商家高频用的主路径、挂了是不是直接影响核心业务。消息发送是 IM 的命脉、营销卡片和潜客留资直接关联商业化转化，所以是这三条。"

## Q3. "UI 自动化最大的问题是不稳定（flaky），你怎么保证巡检结果可信？"⭐⭐（UI 自动化最硬的技术点，必被深挖）

**💡 大白话**：UI 脚本经常"假失败"——元素还没加载出来就去点、动画没结束、网络慢一点，就报错，但其实功能是好的。假失败多了大家就不信巡检了。得把假失败摁下去。

**✅ 打磨版答法（背这套）**：
> "UI 自动化最大的敌人就是 **flaky（假失败）**——元素没加载完就操作、动画/网络时序、机型差异，都会让'功能没问题但脚本报错'。假失败一多，巡检就没人信了。我从几个方面治：
> - **显式等待**：关键操作前**等元素真正就绪**（可点击/可见）再操作，不用死等（sleep 固定时间），既稳又不浪费时间；
> - **稳健的元素定位**：优先用**稳定的定位方式**（KRunner 的标签/语义属性），拿不到稳定标签的再用**视觉定位**兜底，少用容易随布局变化而失效的方式（如绝对坐标、深层级路径），降低 UI 微调就挂的概率；
> - **失败重试 + 区分**：跑挂了先自动重试，**区分是环境抖动（重试能过）还是真缺陷（重试仍挂）**，只把重试仍失败的报出来；
> - **失败留证**：失败自动截图 + 存日志，方便快速判断是脚本问题还是真 bug。
>
> 核心目标是**让巡检的'失败'尽量都是真失败**——降低误报率，巡检结果才可信、才有人用。"

**⭐ 加分锚点**：能系统讲出"显式等待 / 稳健定位 / 重试区分 / 失败留证"这套 flaky 治理组合拳，是 UI 自动化里最见功力的部分——比只说"我写了 UI 脚本"深好几层。

**追问：显式等待和 sleep 死等有什么区别？**
> "sleep 是**固定等 N 秒**——等短了元素还没出来就挂、等长了白白浪费时间，且不同机型快慢不一，很难定一个通用值。显式等待是**轮询等某个条件成立**（元素可见/可点击），条件一满足立刻继续，最多等到超时上限。既稳（慢机型也能等到）又快（快机型不空等）。"

**追问：重试会不会把真 bug 也重试'过'了、漏报？**
> "有可能，所以重试只用来**过滤明显的环境抖动**（如偶发的加载超时），次数有限；而且**真缺陷通常是稳定复现的**——重试几次都挂，就判定为真缺陷报出来。重试是为了降误报，不是为了'把失败洗成通过'。"

## Q4. "三条核心链路（消息发送/营销卡片/潜客留资）具体怎么巡检？举个例子。"⭐

**💡 大白话**：以发消息为例——脚本模拟人：进聊天页、输入、点发送、看消息有没有真的出现在对话里。出现了=通过。

**✅ 打磨版答法**：
> "以**消息发送**为例：脚本模拟真实操作——进入聊天会话页 → 输入框输入内容 → 点发送 → **断言消息真的出现在会话列表里、且状态是发送成功**（不是转圈或红叹号）。这一条就覆盖了'能不能正常发消息'这个命脉。
>
> **营销卡片**：巡检卡片能不能正常展示、关键元素（图/文/按钮）在不在、点击跳转对不对；**潜客留资**：巡检留资表单能不能正常填写提交、提交后状态对不对。三条都是'按真实用户路径走一遍 + 断言关键结果'。"

（⚠️ 三条链路的具体巡检步骤/断言点，正式面试就熟悉的那条讲细即可，记不清的讲主干"按真实路径走 + 断言关键控件状态",别硬编 UI 细节。）

**追问：UI 上你怎么断言"成功了"？**
> "断言的是**关键控件的出现与状态**——比如发消息后会话里出现这条消息且无发送失败标记、卡片区域关键元素可见、留资提交后出现成功态。判断'界面上该有的控件在不在、状态对不对'。KRunner 支持标签+视觉两种识别，拿不到稳定标签的元素也能靠视觉确认在不在。"

## Q5. "机型兼容缺陷、弹窗层级缺陷分别是什么？怎么定位的？"⭐⭐（简历点名的两类缺陷，必被问细）

**💡 大白话**：机型兼容=同样的功能在某些手机/系统版本上表现不对（错位、点不动、崩）。弹窗层级=好几个弹窗叠一起，顺序/遮挡乱了，把该点的按钮挡住或点错。

**✅ 打磨版答法（背这套）**：
> "**机型兼容缺陷**：同一套功能在**特定机型/系统版本**上表现异常——比如某机型上布局错位、某个按钮点不到、或特定系统版本上行为不一致。这类是**人工回归最容易漏的**，因为测试不可能人手覆盖所有机型；而我的巡检在**多机型上跑同一套用例**，某个机型挂了、别的机型过了，就能立刻定位到'这是机型相关的问题'。
>
> **弹窗层级缺陷**：多个弹窗/浮层叠加时，**层级或时序乱了**——比如该在最上层的弹窗被别的浮层盖住、或弹窗弹出顺序不对导致该点的按钮点不到。巡检时脚本走到这一步点不到预期元素、或点到了错误元素，就把这类问题暴露出来。
>
> **定位方法**：靠**多机型对比 + 失败截图/日志**——哪个机型挂、挂在哪一步、当时截图长什么样，很快能判断是机型兼容、弹窗层级还是脚本问题，再拿证据推给研发。"

**⭐ 加分锚点**：能讲清"多机型并行跑 → 靠对比定位机型相关问题"这个机制，体现你懂**为什么 UI 自动化在移动端多机型场景下价值最大**——这正是人工回归的盲区。

**追问：4 类缺陷除了这两类，还有哪两类？**
> "另两类是**交互响应异常**和**页面跳转/路由错误**：
> - **交互响应异常**——点击无响应、点击态异常、按钮该可点却点不动这类，用户操作了但界面没给正确反馈；巡检脚本走到这一步'点了但预期结果没出现',就能暴露；
> - **页面跳转/路由错误**——点了某入口跳到错误页、该跳不跳、或返回栈异常；巡检断言'跳转后应到达的目标页元素在不在',跳错了就抓出来。
>
> 加上机型兼容、弹窗层级，正好是这四类核心链路上最影响体验的交互缺陷。"

## Q6. "巡检什么时候触发？怎么纳入发版流程的？"⭐

**✅ 打磨版答法**：
> "主要是**定时跑**——比如每日定时在多机型上把核心链路巡检一遍，持续守护主干，及时发现回归引入的问题；发版前也会跑一轮作为核心链路的把关。定位是'定时守护核心链路 + 发版前把关',把原来发版前人工一台台点核心链路那段，换成自动巡检出报告。"（⚠️ 当前是定时/手动触发为主，若被问"接没接 CI/发版流水线自动卡点"据实说——别把没接的说成强制卡点）

**追问：为什么用定时而不是强绑发版流水线卡点？**
> "定时巡检能**持续**守护主干、不只在发版那一刻才发现问题，反馈更早；而且 UI 巡检有一定耗时和 flaky 风险，做成强制卡点容易因为偶发失败卡住发版。所以定位成'定时守护 + 发版前参考',而不是硬卡点——这也是对巡检可靠性边界的务实判断。"

---

## Q7. "多机型是怎么跑的？真机还是模拟器？"⭐

**✅ 打磨版答法**：
> "跑在**云真机 / 真机机房**上——多台真机并行跑同一套巡检，覆盖主流机型/系统版本。用真机而不是模拟器，是因为**很多机型兼容问题只在真机上才复现**，模拟器测不出来。KRunner 本身只管'在一台机器上驱动 App 跑用例、不带调度',所以**多机型的分发和组织是我自己做的**——选定要覆盖的机型集合、把巡检任务分发到这些真机上跑、再汇总结果。"

**追问：为什么机型覆盖对这个项目特别重要？**
> "因为这个项目**抓的核心缺陷之一就是机型兼容**——它的价值恰恰来自'多真机并行跑'。单机型跑等于放弃了这个项目最大的价值点。所以真机的机型覆盖面直接决定巡检能不能抓到兼容问题。"

---

## Q8. "UI 自动化用例维护成本高，UI 一改脚本就挂，你怎么控制维护成本？"⭐（升华题，主动准备）

**💡 大白话**：UI 老变，脚本容易天天挂。控制成本的办法就是"少而精 + 定位稳 + 好维护"。

**✅ 打磨版答法**：
> "这正是我把它定位成**巡检而非全量回归**的原因（Q2）——**用例少而精，维护面自然小**。具体控制手段：
> - **只守核心链路**：用例数量克制，不追全覆盖，维护量可控；
> - **稳健定位**：优先用稳定的元素定位（id/语义属性），少用易随 UI 变动失效的方式，降低'UI 微调就全挂'的概率；
> - **失败可快速定位**：失败截图+日志，让'到底是 UI 真变了还是真 bug'一眼能判断，减少排查成本。
>
> 本质是**承认 UI 自动化的维护成本客观存在，所以从设计上就控制规模、控制脆弱点**，而不是等它变成维护负担。"

**⭐ 加分锚点**：主动谈"UI 自动化的维护成本 + 我怎么从设计上控制"，是很诚实成熟的工程观——面试官最怕候选人吹 UI 自动化全覆盖却不提维护成本。

## Q9. "单版本省 2-4 小时、回归效率提升约 30%，怎么来的 / 有没有量化？"⭐⭐（简历写了数字，必被追问，务必降级）

> ⚠️ `2-4 小时` 和 `约 30%` 都**写在简历里**，是**体感估算、没做严格对照实验**，被追问必须主动降级。

**✅ 诚实版答法（必背）**：
> "先说清楚，这是**体感估算，没做严格的对照实验**。口径是：以前发版前核心链路要在多台机型上**人工一台台点**——发消息、营销卡片、留资各走一遍，多机型加起来大概要 2-4 小时；现在这几条核心链路交给巡检自动跑、出报告，人只看报告 + 复核失败项，省下的就是这块重复的手工回归时间，体感在单版本 2-4 小时、回归效率三成左右。是团队用下来的体感，不是精确测出来的，所以简历写的是'约'。"

**为什么这么答**：主动说"体感、没做严格实验"反而加分——面试官最反感把估算吹成精确数据。给得出对照口径（人工多机型点 vs 自动巡检+复核），这个数就立得住。

**追问：那 30% 是怎么估的？**
> "省的主要是**核心链路的重复手工回归**这一块——但发版回归里还有很多巡检没覆盖的（新功能、边界、探索性测试），那些还是人工。所以巡检省的是'核心链路回归'这一段，占整体回归的三成左右，不是把回归全自动化了。我不会说这是严格测出来的。"

**⭐ 加分锚点**：主动划清"省的是核心链路回归这一段、不是全部回归"，体现你对自己项目**价值边界**的诚实——比笼统吹"效率提升 30%"可信得多。
