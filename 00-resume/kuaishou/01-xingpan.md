## 0. 项目一句话定位

一个**面向研发团队的 AI 质效分析平台**：把散落在公司各平台/数据库里的**需求、排期、产出**数据打通，围绕**需求风险、QA 排期、团队效能、个人产出**四个维度，用"**先确定性规则算硬指标 → 再 LLM 解释与给建议 → 结构化输出**"的工作流，产出团队排名、风险预警、人力调配建议，通过**网页看板 + 群机器人日报**呈现给 leader / 组长。

**我负责的边界（诚实划界，反而可信）**

- ⬜ **不是我主做**：前端数据可视化看板、底层数据平台/数据库本身（我是消费方，直接查库）。

**关联技术储备（顺势带出）**

## 1. 60 秒项目总述稿（STAR，开场必背）

**【背景 S】** 团队做质效分析全靠 leader 手工跨平台拉需求、排期、产出数据拼 Excel：一是**重复耗时**，二是**数据割裂**——需求、排期、产出散在不同平台，没法交叉分析，三是**缺全局视角**，看不到团队整体负载分布，容易人力错配，四是**发现滞后**，延期/漏测风险往往事后复盘才暴露、没有事前信号。

**【任务 T】** 我负责设计并实现**后端的 AI 质效分析工作流**，把数据打通、围绕需求风险/QA 排期/团队效能/个人产出四个维度自动出分析结论。

**【行动 A】** 关键设计：
① **工作流分层**——"数据查询 → **规则校验（前置算硬指标）** → AI 分析（解释+建议） → 结构化输出",确定性的归规则、语义的归 LLM；
② **稳定 JSON 输出**——借 **Function Calling** 的结构化能力逼 LLM 吐固定 JSON，再用 **Pydantic** 定义 schema 做校验，不合规就**重试重生成**，保证前端看板和日报接口拿到的格式恒定；
③ **策略注册表 + Orchestrator**——每个分析维度封装成一个策略（自带查数+规则+prompt），Orchestrator 按请求挑选调度并汇总，新增维度只需注册、不改主流程；
④ **权限分级**——leader/组长看全量、QA 看部分。

**【结果 R】** 落地成覆盖**整个部门**的质效分析平台，通过网页看板 + 群机器人日报呈现，把原来 leader 手工拉数拼表的工作自动化，并从"事后复盘"前移到"事前风险预警 + 人力调配建议"。（效率提升为体感口径，见 Q9）

## 1.5 端到端主流程（"讲下完整链路 / 画下架构"时用）⭐

```
用户请求（看板点选维度 / 定时触发日报）
    │
    ▼
Orchestrator：解析请求 → 从策略注册表挑出对应分析策略（可多个）
    │
    ├─ 策略1（需求风险）┐
    ├─ 策略2（QA 排期）├─ 每个策略内部：
    ├─ 策略3（团队效能）│    ① 数据查询：直查公司数据平台/数据库拿需求/排期/产出
    └─ 策略4（个人产出）┘    ② 规则校验（前置）：确定性算硬指标——排期天数、是否超期、覆盖阈值…
                             ③ AI 分析：硬指标 + 原始数据喂 LLM → 解释 + 风险判断 + 建议
                             ④ 结构化输出：Function Calling 逼 LLM 吐固定 JSON
                                          → Pydantic schema 校验 → 不合规则重试
    │
    ▼
Orchestrator 汇总各策略结果
    │
    ├─→ 网页看板渲染（排名 / 风险 / 负载分布）
    └─→ 群机器人日报接口（稳定 JSON → 固定格式推送）
```

**讲解话术（约 40 秒）**：
> "入口有两个：用户在看板点选维度，或定时触发日报。请求先到 **Orchestrator**，它从**策略注册表**里挑出对应的分析策略。每个策略内部是一条固定四步：先查数据，再用**确定性规则前置算硬指标**——比如排期多少天、有没有超期、覆盖率够不够，然后把硬指标连同原始数据喂给 **LLM 做解释和建议**，最后用 **Function Calling 逼它吐固定 JSON、Pydantic 校验、不合规就重试**。Orchestrator 把各策略结果汇总，一路给前端看板渲染，一路给群机器人日报接口。核心就是**确定性的归规则、语义的归 AI，输出焊死成稳定 JSON**。"

## Q1. "为什么要规则校验？全交给 AI 分析不行吗？"⭐⭐（核心，最能体现工程判断）

**我的答法（打磨版）**：
> "因为**质效数据里有大量确定性的东西，没必要也不应该交给 AI 猜**。比如'这个需求排期几天''有没有超期''用例覆盖率够不够阈值'——这些是**算出来的、有唯一正确答案**的硬指标，用规则一算就准，交给 AI 反而可能算错、还不可复现。
>
> 所以我把它分层：**确定性的硬指标用规则前置算好，AI 只负责它擅长的部分**——把一堆硬指标'翻译'成人能看懂的解释、判断风险趋势、给出'要不要重排人力'这种建议。这样既保证了硬数据准确，又用上了 AI 的语义总结能力。**这也是我做 AI 工程一直守的原则：确定性的归规则，语义的归 LLM。**"

**加分锚点**：体现你不迷信大模型、有清醒的能力边界认知——面试官很吃"知道什么该用 AI、什么不该"。

**追问：那规则和 AI 的输入输出怎么衔接？**
> "规则算出的硬指标是**结构化的数值/布尔**（超期天数、是否超阈值等），和原始数据一起拼进 prompt 喂给 AI。AI 拿到的是'已经算好的事实 + 原始上下文',它不用做算术，只做解释和建议，出错空间小很多。"

## Q2. "Function Calling 在这里扮演什么角色？"⭐⭐（易被误解，讲准）

**我的答法（打磨版）**：
> "这里我用 Function Calling **不是让 LLM 自主决定调哪个函数去查数据**，而是**借它的结构化能力，逼 LLM 把分析结果吐成固定结构的 JSON**。因为下游有两个硬性消费方——**前端看板要拿稳定 JSON 渲染、群机器人日报接口要固定格式**，格式一乱下游就崩。
>
> 直接让 LLM'请输出 JSON'很不可靠，它可能加解释性文字、Markdown 代码块、字段飘忽。用 Function Calling 定义好函数的参数 schema，相当于给 LLM 一个**强制的结构模具**，它必须按 schema 填参数，输出的结构就稳定可控了。"

**追问：为什么不用 LLM 自主调函数查数（agentic 那套）？**
> "因为查数逻辑是**确定的**——哪个维度查哪张表、算哪些指标，我在策略里写死了，可复现、可测试。没必要让 LLM 现场决定调哪个函数，那样反而引入不确定性。**能用确定性代码的地方就不交给 LLM 发挥**，Function Calling 我只取它'约束输出结构'这一个能力。"

**加分锚点**：能说清"Function Calling 的两种用法（自主调用 vs 结构约束），我用的是后者、且为什么",比只说"我用了 Function Calling"深一层。

## Q3. "Pydantic 怎么保证稳定 JSON？LLM 吐错了怎么办？"⭐⭐（稳定性最硬的深挖点）

> ⚠️ **链路顺序**：规则校验在 **AI 之前**（Q1）；这里 Pydantic 校验的是 **AI 输出的 JSON 结构**，是输出侧的最后一道关，别和前置规则校验混。

**我的答法（打磨版）**：
> "Function Calling 让 LLM **倾向于**吐固定结构，但不能 100% 保证——可能少字段、类型不对、枚举值超范围。所以我用 **Pydantic 定义输出的 schema**，把 LLM 吐出来的 JSON 做一遍**强校验**：字段全不全、类型对不对、枚举合不合法。
>
> **校验不通过就重试**——把'哪里不符合 schema'的错误信息反馈回去，让 LLM 重新生成一版，直到通过或到重试上限。这样交给前端和日报接口的**永远是经过 Pydantic 校验的合法 JSON**，下游可以放心直接渲染、不用做防御性解析。"

**追问：一直重试都不过怎么办？会不会死循环？**
> "有重试上限，不会无限重试。到上限还不过，就走**兜底**——记录这次异常，返回一个结构合法的降级结果（比如标注'该维度分析暂不可用'）,而不是把脏 JSON 甩给前端让它崩。**保证下游拿到的结构永远合法**，是这层的底线。"（✅ 重试上限 + 兜底降级为真实实现）

**追问：为什么用 Pydantic 而不是手写 JSON 校验？**
> "Pydantic 用**声明式的模型定义** schema，校验、类型转换、默认值、报错信息一把梭，比手写一堆 if 判断字段可靠也好维护；而且它的报错信息很结构化，正好能拼回给 LLM 做重试提示。"

## Q4. "策略注册表 + Orchestrator 是怎么设计的？为什么这么做？"⭐⭐（架构亮点，扩展性）

**我的答法（打磨版）**：
> "四个分析维度——需求风险、QA 排期、团队效能、个人产出——它们的**流程骨架是一样的**（查数 → 规则 → AI → 输出），只是**每个维度查哪些数据、算哪些规则、用什么 prompt 不一样**。如果写成一大坨 if-else，加一个维度就要动主流程，很难维护。
>
> 所以我做了**策略注册表 + Orchestrator**：
> - **策略（Strategy）**：一个分析维度封装成一个策略，各自实现自己的'查数 + 规则 + prompt',对外暴露统一接口；
> - **注册表（Registry）**：所有策略注册进去，用维度标识索引；
> - **Orchestrator**：接到请求后，从注册表挑出需要的策略、统一调度执行、汇总结果。
>
> 好处是**扩展性**——新增一个分析维度，只要**实现并注册一个新策略**，Orchestrator 和主流程一行都不用改（开闭原则）；**维护性**——每个策略自洽、互不影响，改一个维度不会波及其他。"

**追问：这用了什么设计模式？**
> "本质是**策略模式 + 注册表**：策略模式把'同一骨架、不同实现'的分析逻辑解耦；注册表 + Orchestrator 承担'选择 + 调度'。所以加维度是'注册新策略',不是'改老代码'。"

**追问：多个策略之间有依赖或共享数据吗？会重复查库吗？**
> "（据实答）策略间相对独立，各自查自己需要的数据。如果有公共数据（比如同一批需求列表被多个维度用），可以在 Orchestrator 层做一次查询、分发给各策略，避免重复查库。"（⚠️ 若实际没做共享优化，就说"当前各策略独立查，公共数据复用是可优化点"，别硬编）

## Q5. "四个维度具体分析什么？举个例子。"⭐

**我的答法（打磨版）**：
> "以**需求风险**为例：输入是团队数据库里的需求数据（排期、进度、关联的用例/缺陷等），规则先算出硬指标——比如**离 deadline 还剩几天、当前进度、是否已超期、测试覆盖够不够**，然后把这些喂给 AI，让它判断**这个需求会不会延期、风险等级、要不要重新安排人力**。
>
> 其他维度类似：**QA 排期**看排期是否合理、有没有过载；**团队效能**、**个人产出**做横向对比、出排名。输出统一是排名 + 风险结论 + AI 建议。"

**追问：数据从哪来？**
> "从公司自己的研发数据平台来，底层是**直接查数据库**拿需求、排期、产出数据。我是数据的消费方，数据平台本身不是我做的。"

## Q6. "权限是怎么做的？"⭐

**我的答法（打磨版）**：
> "做了**分级权限**：leader 和组长能看**全量**——整个团队/部门的排名、负载、个人产出；QA 自己只能看**部分数据**（比如自己相关的部分）。因为个人产出、排名这类数据比较敏感，不能所有人都看全部。"

**追问：怎么实现的？**（若细节记不清，据实答）
> "按角色控制可见的数据范围和维度。"（⚠️ 具体实现若记不清，坦诚说"按角色做数据范围过滤",别硬编框架名）

## Q7. "群机器人日报和网页看板，输出有什么不同？"

**我的答法（打磨版）**：
> "底层是**同一套稳定 JSON**，两个消费方：**网页看板**拿 JSON 做可视化渲染（排名、风险、负载分布图表）；**群机器人日报**是**定时触发**工作流，把 JSON 转成固定格式的消息推到群里。正因为输出是 Pydantic 校验过的稳定结构，同一份数据能同时喂给两个形态的下游而不用各写一套。"

## Q8. "这套工作流最大的技术难点是什么？"⭐（升华题，主动准备）

**我的答法（打磨版）**：
> "最大的难点是**让一个本质不确定的 LLM，产出可被前端和接口直接消费的确定结构**。两个矛盾：一是 LLM 输出天然飘（格式、字段），二是下游要求格式恒定。我的解法是**三道关**：Function Calling 给结构模具、Pydantic 做 schema 强校验、失败重试 + 兜底降级——把不确定性挡在工作流内部，对外永远吐合法 JSON。
>
> 第二个难点是**可扩展**——质效维度会不断加，所以用策略注册表 + Orchestrator，把'加维度'的成本降到'注册一个策略'。这两点合起来，就是把'一次性的 AI 脚本'做成了'可长期维护的分析平台'。"

## Q9. "有没有量化 / 效果？"⭐⭐（务必降级，诚实口径）

> ⚠️ 效率提升类是**体感估算、未做严格对照实验**；采用面按"覆盖整个部门"讲，不编精确人数/需求数。

**我的答法（诚实版）**：
> "采用面上，平台**覆盖了整个部门**的质效分析，网页看板 + 群机器人日报是团队日常在用的。效率上有个**体感**——以前 leader 每个迭代要手工跨平台拉数、拼 Excel，现在自动出报告和日报，省了这块重复劳动；但我**没做严格的对照实验**，所以不会把它说成一个精确的百分比。更重要的价值是**从'事后复盘'前移到'事前风险预警 + 人力调配建议'**,这是手工拉表做不到的。"

**为什么这么答**：主动说"体感、没做严格实验"反而可信；把重点从"省了多少时间"引向"能力质变（预警前移）",比纠结数字更有说服力。

**追问：那你怎么判断它真的有用？**
> "最直接的信号是**它成了团队日常在用的东西**——leader/组长看看板、群里每天收日报。一个内部工具能被日常依赖，本身就说明它解决了真实痛点。"

| **定位** | 面向研发团队的 AI 质效分析平台，我负责后端 AI 分析工作流 |

| **四维度** | 需求风险 / QA 排期 / 团队效能 / 个人产出 |
| **工作流** | 数据查询 → **规则前置算硬指标** → AI 解释+建议 → 结构化输出 |
| **规则 vs AI** | 确定性硬指标归规则（准、可复现），语义解释/建议归 LLM（Q1） |
| **Function Calling** | 取"结构约束"能力逼 LLM 吐固定 JSON，**非**自主调函数查数（Q2） |
| **Pydantic** | schema 强校验 LLM 输出 → 不合规重试 → 兜底降级，对外永远合法 JSON（Q3） |
| **策略注册表+Orchestrator** | 一维度=一策略（查数+规则+prompt），注册即扩展、不改主流程（策略模式，Q4） |
| **输出去向** | 同一套稳定 JSON → 网页看板渲染 + 群机器人日报（Q7） |
| **权限** | leader/组长看全量、QA 看部分，按角色过滤数据范围（Q6） |
| **难点** | 把不确定 LLM 焊成确定结构（三道关）+ 可扩展架构（Q8） |
| **量化** | 覆盖整个部门；效率提升为体感、未做严格实验；价值在"预警前移"（Q9） |
| **红线** | 我 own 后端 AI 工作流；前端看板/数据平台不是我主做，诚实划界 |
