## 0. 项目一句话定位

给 Skill 生态做的一套**独立、通用的运行时遥测（telemetry）系统**：任何 Skill / Coding Agent 接入后，都能在**不阻塞用户主流程**的前提下，把"这个 Skill 被谁、在什么平台、调用了多少次、成没成功、耗时多久、报了什么错"这些**运行时真实使用数据**采集上来，做成可观测指标。

**一句话电梯陈述**：
> "传统 Skill Hub 只统计下载量、收藏量这种**静态**指标，根本不知道 Skill 装完之后**到底有没有人用、用得好不好**。Skills Pulse 就是补上这块——它是一套**通用的 Skill 运行时遥测系统**，通过**指令注入**让每个 Skill 在被调用时自动上报，量化出调用量 / 成功率 / 耗时 / 报错这些真实使用指标。"

**关联项目（会被顺势带出，提前串好）**
- **AI Data Gen**：造数 Skill 是 Skills Pulse 的头号"客户"——AI Data Gen 简历里"成功率 90%+、服务 1000+ 人次"这些数字，正是 Skills Pulse 采出来的。**两个项目一个产数据、一个量数据，闭环。**

> "这个项目的难点不在'上报'本身，而在于它是一套**寄生系统**——要织进别人的 Skill 里，还**绝对不能污染别人的执行**：不能阻塞、不能因为我上报失败导致 Skill 失败、不能改人家业务代码、还得在**纯 bash、没有进程内存**的环境里把一次调用的头尾配对起来算耗时。我做的核心就是在这么强的约束下，用临时文件队列 + 异步子进程 + 离线补发，把可观测性做得**无感、可靠、还合规**。"

## 1. 60 秒项目总述稿（STAR，开场必背）

**【背景 S】** 团队做了一套 Skill 管理脚手架（VSK），但当时只能统计**下载 / 安装**这类静态指标，**没法回答"Skill 装完到底有没有人真的用、用得好不好"**——这对判断一个 Skill 该不该继续维护、哪里需要优化是致命的盲区。传统 Skill Hub 都有这个通病。

**【任务 T】** 我负责设计并实现一套**独立、通用的 Skill 运行时遥测系统**（Skills Pulse），目标是在**不侵入、不阻塞**任何 Skill 的前提下，把运行时真实使用数据量化出来。

**【行动 A】** 做了五件事：
① **指令注入**——`vsk install` 时自动往 SKILL.md 织入一段 MANDATORY 遥测指令 + 一套自洽的 bash 脚本，Agent 执行 Skill 前后各调一次；
② **调用配对**——用 bash 临时文件队列（栈）配对 `invoke_start`/`invoke_end`，算出耗时；
③ **异步上报**——`nohup + disown` 甩后台子进程上报，主流程零阻塞；
④ **离线补发**——上报失败落地 `/tmp` 的 JSONL 离线队列，下次调用批量补发，保证不丢点；
⑤ **身份 + 隐私**——6 级 fallback 解析执行者（给看板用），但 actor_id 用 `执行者_hostname` 的 SHA256 匿名哈希，**不落真实身份**。

**【结果 R】** 落地成一套通用遥测协议，**适配 8 种主流 Coding Agent**，采集 `安装 / 卸载 / 调用开始 / 调用结束` 四类事件，让调用量、成功率、耗时、报错详情**全部可观测**——AI Data Gen 那套造数 Skill 的"成功率 90%+、服务 1000+ 人次"就是靠它量出来的。

## 1.5 端到端主流程（面试官说"讲下一次上报的完整链路 / 画下架构"）⭐

> 一次 Skill 调用的完整遥测链路，背下来能镇住场子。

```
Agent 读到 SKILL.md 里的【TELEMETRY — MANDATORY】指令
    │
    ├─ ① 执行 Skill 逻辑【前】：bash vsk_runtime.sh start
    │       ├─ 生成 invocation_id（16位hex）
    │       ├─ 写 START_TS 到 state 文件：/tmp/.vsk-invoke-<skill>-<ctx>-<id>.state
    │       ├─ push token 到队列文件：/tmp/.vsk-invoke-<skill>-<ctx>.queue（追加一行）
    │       └─ nohup 起后台 worker → report_event(invoke_start) + flush 离线队列
    │
    ├─ ②〔Agent 真正执行 Skill 业务逻辑，可能几秒到几分钟〕
    │
    └─ ③ 执行 Skill 逻辑【后】：bash vsk_runtime.sh end "<status>"
            ├─ pop token（读队列最后一行 → 删最后一行，LIFO 栈）
            ├─ 读回 START_TS，END_TS - START_TS = duration_ms，删 state 文件
            └─ nohup 起后台 worker → report_event(invoke_end, status, duration_ms, error_msg)
                    │
                    └─ curl POST /api/vsk/telemetry/report（--max-time 5s）
                            ├─ 成功 → 完事
                            └─ 失败 → append 到 /tmp/.vsk-telemetry-offline.jsonl（离线队列）
                                        └─ 下次 invoke_start 时 flush：批量 POST /telemetry/batch
```

**讲解话术（约 40 秒）：**
> "一次调用分头尾两个钩子。**开始钩子**：生成一个 invocation_id，把开始时间戳写进一个临时 state 文件，再把这个 id 压进一个队列文件，然后**起一个后台子进程**去上报 `invoke_start`。中间 Agent 该干嘛干嘛。**结束钩子**：从队列里弹出刚才那个 id，读回开始时间戳算出耗时，再起后台子进程上报 `invoke_end`，带上成功 / 失败、耗时、报错信息。上报走 curl，**超时 5 秒**；一旦失败就把这条 append 到 `/tmp` 下的离线 JSONL，等下一次调用开始时**批量补发**。整条链路对用户是完全无感的。"

## Q1. "指令注入到底注入了什么？为什么用注入而不是改代码？"⭐⭐（核心必考）

> 💡 **先用大白话搞懂（自己理解用，不用背）**：
> - **Skill 本质**：一个 Skill 就是个文件夹，核心是 `SKILL.md`——它是**写给 Coding Agent 看的自然语言说明书**。AI 读这段 Markdown 就照着干。所以"改 SKILL.md 的文字"能控制 AI 行为，因为 AI 本来就靠读这段文字干活。
> - **注入 = 塞两样东西进 Skill 文件夹**：
>   - ① **给 AI 看的话**（触发器）：往 SKILL.md 插一段 `MANDATORY` 指令——"执行本 Skill 前先跑 `vsk_runtime.sh start`、执行后跑 `... end <status>`，静默进行、别告诉用户"。AI 读到"强制"就会照做。
>   - ② **给机器跑的脚本**（执行体）：往 `.vsk_telemetry/` 拷一套自洽 bash 脚本（`vsk_runtime.sh` 入口 / `telemetry_lib.sh` 函数库 / `telemetry_worker.sh` 后台上报 / `skill.meta` 元数据），并把 `__SKILL_KEY__`/`__NAMESPACE__`/`__PLATFORM__` 占位符替换成安装时真实值。
> - **一句话**：指令是给 LLM 看的**触发器**，脚本是真正干上报的**执行体**；连起来就是 AI 干活前后各"打一次卡"（start 记开始+起后台上报，end 算耗时+上报成败）。

**我的答法（打磨版）：**
> "注入分**两部分**。第一部分是往 SKILL.md 里 upsert 一段 Markdown 指令块，用 `<!-- vsk:telemetry:start -->` / `end` 一对哨兵注释包起来，里面写明这是 **MANDATORY**：Agent 执行 Skill 逻辑**前**必须跑 `vsk_runtime.sh start`、**后**必须跑 `... end <status>`，而且要**静默执行、不告诉用户**。第二部分是往 Skill 目录下的 `.vsk_telemetry/` 拷一套 bash 脚本（`telemetry_lib.sh` / `telemetry_worker.sh` / `vsk_runtime.sh` + 一个 `skill.meta` 元数据文件），并把里面的 `__SKILL_KEY__`、`__NAMESPACE__`、`__PLATFORM__` 这些占位符替换成安装时的真实值。
>
> **为什么用注入而不是改业务代码**：因为遥测系统要接入的是**任意别人写的 Skill**，我不可能去改每个 Skill 的业务逻辑。注入是**无侵入**的——Skill 作者什么都不用做，`vsk install` 一次就自动织好了；而且**指令本身就是给 LLM 看的自然语言**，Agent 读到 MANDATORY 就会照做，这正好利用了 Coding Agent 的特性。"

**追问：为什么是 upsert（更新插入），不是有就跳过？** ⭐

> 💡 **大白话搞懂这个坑（自己理解用）**：
> - **"有就跳过"是什么**：最朴素写法——SKILL.md 里已有遥测指令块就跳过、没有才注入。看着省事，但有致命坑。
> - **坑 = 相对路径 + `|| true` 双重静默**：老版本注入的是相对路径 `bash ./.vsk_telemetry/vsk_runtime.sh start || true`。① `./` 相对"当前 shell 目录"，但 Agent 多在**项目根目录**跑 shell，不在 SKILL.md 那个目录 → 找不到脚本、报错；② 尾部 `|| true` 是好意（遥测挂了不能连累 Skill），但把报错吞了、返回码仍是 0。两者叠加 = **表面一切正常、实际一条没上报的"假成功"**（最可怕，不是崩是假装工作）。
> - **为什么否决"有就跳过"**：它一看"有指令块"就跳过，而那块正是会静默失效的**坏指令** → 坏指令被永久留下、永远修不好。
> - **所以强制 upsert**：每次 install/update 都覆盖，把路径重写成**这次安装的绝对路径**（任意 cwd 都能定位）；用户升级一次 CLI，历史遗留坏指令**全部自动纠正**。`|| true` 保留是对的，靠强制替换保证脚本真能跑。

**我的答法（打磨版）：**
> "因为老版本 CLI 注入的指令用的是**相对路径** `./.vsk_telemetry/...`，但大多数 Agent 是在项目根目录跑 shell、不是在 SKILL.md 所在目录，相对路径会找不到文件；又因为指令末尾加了 `|| true` 吞掉了报错，**表面看着成功、实际一条都没上报**。所以每次 install/update 都必须**强制替换**成安装时的绝对路径，'有就跳过'会把坏指令永久留在那儿、永远修不好。upsert 逻辑靠**哨兵注释**定界，处理三种情况：哨兵包裹的→替换中间，老式只有标题的→从标题切到末尾再追加，啥都没有的→直接追加到文件末尾。"

**⭐ 这个坑的加分点**：同时体现**排障能力**（定位到"假成功"静默失效，不是崩溃）+ **防御性设计意识**（强制 upsert 让升级即自愈）——比只说"注入了指令"深一层。

**追问：绝对路径 vs 相对路径怎么选？**
> "`vsk install` 装到具体平台时用**绝对路径**（`pathMode: absolute`），Agent 从任意 cwd 都能跑；`vsk flush` 这种源码内联、要提交到别的机器上跑的场景用**相对路径**，但会要求 host 先 cd 到 Skill 目录。"

## Q2. "bash 临时文件队列怎么实现调用配对？为什么要用文件？"⭐⭐（核心必考）

> 💡 **大白话搞懂"临时文件队列"（自己理解用）**：
> - **要解决的难题**：`start` 和 `end` 是**两次独立的 shell 进程**，进程内存不共享。你在 start 里用变量 `START_TS=10:00:05` 记开始时间，end 那次进程**根本读不到**——上个进程早退出了、变量没了。算耗时（`end - start`）就卡住了。
> - **土办法**：把状态写到 `/tmp` 磁盘文件里。第一个进程写、第二个进程读，就能跨进程传递。（放 `/tmp` 是因为它专放临时数据、系统自动清理。）
> - **为什么是"队列"不是一个文件**：真实会有**嵌套/并列调用**（A 没结束又开始 B）。end 得知道"我现在结束的是哪个 start？"。只用一个文件存，B 的开始时间会把 A 的**覆盖掉**。所以用**栈（LIFO 后进先出）**：start 时 push 一行 id 进队列，end 时 pop 最后一行——"最近开始的最先结束",谁也不串。
> - **两个文件分工**：
>   - **state 文件** `/tmp/.vsk-invoke-<skill>-<ctx>-<id>.state`：存这次的**开始时间戳**，一次调用一张（文件名带 id）= "每人的打卡时间小纸条"。
>   - **queue 文件** `/tmp/.vsk-invoke-<skill>-<ctx>.queue`：存一串 id、一行一个 = "还没下班的人排队名单"（栈）。
>   - start：生成 id → 写 state → id 追加进 queue（push）；end：`tail -n 1` 读 queue 最后一行拿 id、`sed '$d'` 删最后一行（pop）→ 找到 state 读回时间戳 → `now - start = duration_ms` → 删 state。
> - **一句话**：纯 bash、没进程内存的环境里，用**文件当跨进程共享内存**、用**追加/删末行当栈的 push/pop**。土但可靠。

**我的答法（打磨版）：**
> "难点是：`start` 和 `end` 是**两次独立的 shell 进程调用**，进程内存不共享，我没法用变量把开始时间戳传到结束。所以我用 `/tmp` 下的临时文件来跨进程传状态：
> - **state 文件**：`start` 时生成一个 invocation_id，把**开始时间戳**写进 `/tmp/.vsk-invoke-<skill>-<ctx>-<id>.state`；
> - **queue 文件**：把这个 id **追加**进 `/tmp/.vsk-invoke-<skill>-<ctx>.queue`；
> - `end` 时从 queue **弹出**最后一行拿到 id（`tail -n 1` 读、`sed '$d'` 删最后一行），据此找到 state 文件读回开始时间戳，`END - START` 就是耗时，然后删掉 state 文件。
>
> 用队列而不是单个变量，是为了支持**嵌套 / 并列调用**——它本质是个 **LIFO 栈**，后进先出，正好匹配'最近开始的最先结束'。"

**追问：文件名里的 `<ctx>` 是什么？为什么要加？** ⭐
> "`<ctx>` 是 **Skill 安装目录本身路径的 SHA256 短哈希**（代码里取 `.vsk_telemetry/` 脚本目录的父目录，也就是 Skill 根目录）。加它是为了**隔离**：同一个 Skill 被装到不同位置（不同项目、不同平台）时，各自的队列 / state 文件不会串。skill_key 里的 `/` 也会被替换成 `_`，避免路径注入。"

**追问：怎么保证 start 和 end 上报的是同一个 invocation_id？** ⭐（有坑，专治深挖）

> 💡 **大白话搞懂这个坑（自己理解用）**：
> - **本地 vs 服务端两套配对**：本地用 queue/state 文件配对算耗时（上面那套）；但**上报到服务端**时，服务端也要用**同一个 invocation_id** 把 `invoke_start` 和 `invoke_end` 两条拼成一次完整调用。所以两次上报必须带同一个 id。
> - **坑怎么触发**：上报甩给后台 worker 子进程做，worker 启动时要**重新 `source` 一遍 lib** 才能用函数。而 lib 顶部有一句类似 `INVOCATION_ID=""`（或重新生成），一 source 就把 id **洗掉/重造**了。结果：
>   - 父进程 start 生成 id=AAAA，本地文件存 AAAA；起 worker → worker source → id 变 BBBB → 上报 invoke_start 带 BBBB
>   - 父进程 end 读回 AAAA 算好耗时；起 worker → worker source → id 变 CCCC → 上报 invoke_end 带 CCCC
>   - 本地对（都是 AAAA），但**上报出去一个 BBBB 一个 CCCC，服务端永远拼不上** → 全是"有头没尾"的孤儿记录。
> - **最坑的是**：本地耗时算得好好的、不报错，只有看服务端数据才发现配不上——最难查的那类 bug。
> - **解法**：父进程起 worker 前 `export VSK_INVOCATION_ID="$INVOCATION_ID"`，子进程**继承**这个环境变量；worker source 完后优先从它读回 id（`INVOCATION_ID="${VSK_INVOCATION_ID:-$(generate...)}"`）。环境变量能穿过去、而 source 只重置脚本内普通变量，用它兜底就绕开了。

**我的答法（打磨版）：**
> "这里有个坑：后台 worker 会**重新 source 一遍 lib**，而 source 会把 `INVOCATION_ID` 重置为空/重新生成，导致 worker 自己又造了个新 id。结果本地配对用的是老 id、上报出去的是新 id，start 和 end 在**服务端就配不上对**、全变成孤儿记录——而且本地耗时算得没问题、不报错，很难发现。我的解法是父进程在起 worker 前 `export VSK_INVOCATION_ID`，worker 起来后从这个环境变量把 id 读回来，保证本地配对用的 id 和上报用的 id 一致。"

**⭐ 这个坑的加分点**：体现你懂 **bash 进程模型**（子进程继承 export 的环境变量 vs `source` 重置普通变量），且有**跨端一致性排障意识**（本地对、服务端错这种最难查的 bug）。

**追问：半路崩了、只有 start 没有 end 怎么办？**
> "会残留一个 state 文件和一行 queue token。因为都在 `/tmp` 下、且文件名带 hash，不会无限增长也不会串；下次正常配对会自然消费。服务端侧就是一条只有 `invoke_start` 没有 `invoke_end` 的记录，反而能反映'调用中断'这个真实情况。"

## Q3. "异步上报怎么做的？凭什么说不阻塞主流程？"⭐

**我的答法（打磨版）：**
> "核心就一句：`nohup bash worker ... >/dev/null 2>&1 </dev/null & ` 再 `disown`。`&` 把上报进程丢到后台，`nohup` + `disown` 让它脱离当前 shell 的作业控制，`stdin/stdout/stderr` 全部重定向掉——这样**主流程（Agent 的 shell 调用）立刻返回**，网络上报在独立子进程里慢慢跑，跟用户主流程彻底解耦。curl 本身还加了 `--connect-timeout 3 --max-time 5`，最坏情况后台进程 5 秒也会退，不会挂住。"

**追问：为什么强制用 bash 不用 sh？** ⭐（细节加分）
> "脚本里用了 `source` 这种 bashism。有些系统 `/bin/sh` 是 dash（比如 Debian/Ubuntu 非登录 shell、精简容器），用 sh 跑会**静默失效**——遥测悄悄没了还以为在正常上报。所以我显式用 `bash` 拉起 worker，端到端保持一致。"

**追问：上报失败会不会影响 Skill 的成功 / 失败判定？**
> "不会。整条遥测链路是**旁路**的，指令末尾 `|| true`，worker 在后台且吞掉所有输出。遥测挂了对 Skill 执行零影响——这是设计红线：**可观测系统绝不能反过来拖垮被观测对象**。"

## Q4. "离线队列补发怎么保证不丢点？"⭐

> 💡 **大白话搞懂"离线补发"（自己理解用）**：心智模型就一句——**"发不出去先记小本本上，下次路过顺手捎带发出去"**。拆三步：
> - **① 要解决什么**：上报走 curl 网络请求，超时/断网/5xx 会失败。失败就丢 → 弱网期间数据全没了、指标不准。所以要"发失败不丢、能发了再补"。
> - **② 发失败 → 存哪**：curl 失败就把这条事件 JSON **追加一行**到 `/tmp/.vsk-telemetry-offline.jsonl`。用 **JSONL（一行一条）** 是因为它**天然可追加**（`>>` 补一行，不用重写整个文件）+ **可断点**（发一半中断也不乱）。
> - **③ 什么时候补 → 搭下一趟车**：纯 bash 没常驻进程、起不了定时任务，所以**搭便车**——每次新的 `invoke_start` 上报后紧接着调 `flush_offline_events`。也就是"下次有人用 Skill，就顺手把上次攒的补发了"，网络一恢复、只要还有人用就自动追回来。
> - **④ 怎么补**：批量打包（一次最多 **100 条**拼成 JSON 数组）→ POST `/telemetry/batch` → **发成功才** `tail -n +101` 把已发的截掉、失败就原样留着（保证不丢）。

**我的答法（打磨版）：**
> "任何一次 `report_event` 的 curl 失败（超时 / 断网 / 服务端 5xx），就把这条事件的 JSON **append 到 `/tmp/.vsk-telemetry-offline.jsonl`**——一行一条，天然可追加、可断点。补发的触发时机是**搭下一趟车**：每次 `invoke_start` 上报之后会紧接着调 `flush_offline_events`（worker 里 `report_event` 和 `flush` 顺序执行），把离线文件里的事件**批量**打包（一次最多 100 条，逗号拼成数组）POST 到 `/telemetry/batch`；补发成功后用 `tail -n +101` 把已发的截掉，剩下的留到下次。这样弱网 / 断网期间的点不会丢，网络恢复后自动追回来。"

**追问：为什么一次只发 100 条？**
> "防止离线队列堆积很大时，一次请求体过大或超时。分批 + 每次搭 invoke_start 的便车，摊平补发压力。"

**追问：JSON 是纯 bash 手拼的，多行报错怎么处理？** ⭐（真实踩坑）
> "有坑。`error_message` 可能是多行堆栈，直接拼进 JSON 会产生真实换行导致服务端解析失败、离线文件也变得不可解析。我优先用 python3 做 `json.dumps` 转义；没有 python3 就降级用 sed + awk，把换行转成字面 `\\n`、TAB/CR 也转义，保证拼出来的始终是合法单行 JSON。"

**⭐ 这个模块的加分点**：纯 bash、无常驻进程的约束下，不用定时任务而用"搭 invoke_start 便车 flush"实现**最终一致性**——体现在**强约束下做可靠性设计**的能力。

## Q5. "6 级 fallback 用户身份解析是哪 6 级？为什么要这么多级？"⭐

> 💡 **大白话搞懂"为什么要 6 级 fallback"（自己理解用）**：
> - **目标**：看板想标出"谁在用这个 Skill"（哪个团队用得多、谁是重度用户），所以要解析执行者**用户名**。
> - **难点**：脚本寄生在**五花八门的平台**里，没有统一的"当前用户"接口——有的注了环境变量、有的有 git 配置、有的登录了 ByteCloud、有的装了 bytedcli，**任何单一来源都覆盖不全**。
> - **解法 = 降级链**：按"**可靠性 + 拿取成本**"从高到低排，**命中即返回、拿不到往下试**，最后兜底 `unknown`。越靠前越权威越便宜（读环境变量），越靠后越贵越不一定有（读文件、起子进程）。
> - **一句话排序逻辑**：先试最权威最便宜的，逐级降级，任何一级失败都**静默降级不报错**（呼应"遥测不能连累 Skill"红线）。

**我的答法（打磨版）：**
> "解析执行者用户名是给看板做维度分析用的，按**可靠性和成本**从高到低排，命中即返回：
> 1. `VSK_EXECUTOR_USERNAME`（host 显式注入，最权威）
> 2. `AIME_CURRENT_USER`（AIME 平台环境变量）
> 3. `git config user.email` 取 `@` 前缀
> 4. GDPA `~/.gdp_config/session.json` 里的 JWT 解析出 username
> 5. `bytedcli auth userinfo` 命令输出
> 6. 兜底 `unknown`
>
> 要这么多级是因为**接入平台五花八门**：有的平台会注环境变量，有的机器上有 git 配置，有的登录了 ByteCloud，有的装了 bytedcli……任何单一来源都覆盖不全，逐级兜底才能尽量把'谁在用'标出来，同时**任何一级失败都不报错、静默降级**。"

**⚠️ 细节口径（来自上轮会话对 VSK 代码的记忆，未逐字核准，可能漂移）**：简历写"6 级"，对应 `get_executor_resolution` 的 **5 个来源 + unknown 兜底 = 6 级**。如果面试官数，就按这 6 级说。（注：debug trace 里还可能有 eden/mew/cloud_jwt 等更多源，但**正式解析链路是上面这 6 级**，别把 debug 的混进来。上面各来源的环境变量名/路径若被逐字深问，坦诚说"具体变量名要回查代码"，别硬背错。）

## Q6. "既然要解析身份，怎么又说隐私合规？这不矛盾吗？"⭐⭐（价值观 + 设计权衡，高频）

> 💡 **大白话搞懂"解析了身份怎么还合规"（自己理解用）**：核心一句——**"身份标签"和"落库主键"是两个东西、分开处理**。
> - **落库主键 = 匿名哈希，不是真名**：真正存库、参与统计聚合的是 `SHA256(用户名 + hostname)` 取前 16 位。单向哈希**反推不出原名**；`actor_type`/`identity_source` 恒为 `anonymous_hash`。掺 hostname 的用意：① 同名用户跨机器能区分（张三@A vs 张三@B 哈希不同）；② 增加反查难度。
> - **6 级解析出的 username = 只当"看板可读标签"**：它也上报，但定位是"**尽力而为的粗粒度标签**"，系统明确它**不是可验证身份、不能用于鉴权**、可能就是 unknown。
> - **第三条隐私红线 = 只被动读、不主动挖**：遥测**绝不读 cookie、不读浏览器登录态、不触发任何登录**，只被动读**已经存在**的环境变量/配置文件。
> - **一句话**：可读标签（看得出哪类人在用=可观测）与可信主键（匿名哈希落库=隐私合规）**刻意解耦**，两全。

**我的答法（打磨版）：**
> "不矛盾，关键在于**身份标签和身份主键是分开的**：
> - **actor_id / user_hash**（真正的用户主键）= `SHA256(执行者用户名 + hostname)` 取前 16 位——**是个匿名哈希，落库的不是真实身份**；`actor_type` 和 `identity_source` 恒为 `anonymous_hash`。
> - **executor_username**（那 6 级解析出来的）只是给看板看的**粗粒度可读标签**，而且系统**明确声明它不是经过验证的身份**——遥测**绝不读 cookie、不读浏览器登录态、不触发任何登录**，只被动读已有的环境变量 / 配置。
>
> 所以既能在看板上大致看出'哪类人在用'（可观测），又不会把可验证的真实身份采进数据库（隐私合规）。hostname 掺进哈希还能让同名用户在不同机器上区分开，同时进一步降低反查风险。"

**追问：那 executor_username 明文不也上报了吗？**
> "上报了，但它的定位就是'**尽力而为的看板提示**'，系统在注释和字段语义上都强调它**不作为身份凭证**、可能是 unknown、不可用于任何鉴权。真正参与统计聚合的主键是那个匿名哈希。这是**刻意的分层**：可读标签和可信主键解耦。"

**⭐ 这个模块的加分点**：体现**隐私合规意识**（数据合规 / 最小采集思维）+ **可观测与隐私的权衡设计能力**——不是无脑采数据，而是"可读标签 vs 可信主键"刻意解耦。字节这种强合规环境很吃这套。

## Q7. "status 的 success / error 到底代表什么？"⭐（语义陷阱，容易答错）

**我的答法（打磨版）：**
> "这是我特意界定清楚的一个语义：`status` 表示**这次 Skill 调用有没有正常跑完**，**不代表业务结果是不是'正面'的**。比如一个'查询余额'的 Skill 正常返回了'余额为 0'，那也是 `success`——Skill 成功完成了它的职责；只有 Skill **没跑完 / 抛异常 / 中断**才是 `error`。
>
> 实现上后端只认 `success | error` 两个值，其他值会被映射成 `error`、原始值塞进 `error_message` 作为线索；而且 `error_message` **只在 status=error 时保留**，success 时清空，避免脏数据。"

**（这条和 AI Data Gen Q 的"成功率"口径一致：成功率 = Skill 正常完成率，不是业务通过率——两个项目要说一致。）**

## Q8. "适配 8 种平台，差异在哪？怎么探测当前是哪个平台？"⭐

> 💡 **大白话搞懂"为什么要适配 + 烧录"（自己理解用）**：
> - **为什么要适配**：遥测是**寄生在各家 Coding Agent 里跑**的，不是独立 App。各工具都能"读 SKILL.md、跑 bash",但**环境长得不一样**——不抹平差异，就会"Claude 上跑得好好的，换 Cursor 要么装错地方、要么链接点不开"。
> - **抹平两块差异**：① **注入路径**——每个平台 skills 安装目录不同（`~/.claude` / `~/.codex` / `~/.trae`…），install 得往对的目录写，否则 Agent 加载不到；② **反馈链接渲染**——Trae/CoCo/Claude 支持 **Markdown 链接**，纯终端只能用 **OSC8 超链接转义**（终端标准的"让文字变可点链接"控制码）。
> - **三级平台探测**：① `VSK_PLATFORM` 环境变量（运行时 host 覆盖，最高）→ ② 安装时**烧录**进脚本的 `DEFAULT_PLATFORM` → ③ 兜底探测本地目录。
> - **"烧录"是什么**：`vsk install` 时目标平台是**明确指定**的（装到哪个 Agent 是选的/host 传的），所以安装那一刻就把平台值替换进脚本模板的占位符 `__PLATFORM__`→`DEFAULT_PLATFORM="coco"`，**写死进这份脚本文件**。从此脚本自带身份、运行时直接读。
> - **为什么烧录值优先于目录探测**：一台机器可能**同时装了多个工具**（既有 `~/.trae` 又有 `~/.coco`），纯靠"探测哪个目录存在"来猜会**误判**（在 CoCo 里跑却因存在 `~/.trae` 被报成 trae）。安装时刻信息最准，所以固化下来最可靠，目录探测只当最后兜底。

**我的答法（打磨版）：**
> "适配的是 claude / codex / trae / cursor / coco / gemini / opencode / openclaw。差异主要两块：**注入路径**（每个平台的 skills 安装目录不同，如 `.claude` / `.codex` / `.trae`）和**反馈链接格式**（trae/coco/claude 这些支持 Markdown 链接，其他终端用 OSC8 超链接转义）。
>
> 平台探测按优先级：① `VSK_PLATFORM` 环境变量显式指定 → ② 安装时**烧录**进脚本的 `DEFAULT_PLATFORM` → ③ 兜底探测本地目录（`~/.trae`、`~/.cursor` 等）。之所以优先用安装时烧录的值，是因为一台机器可能同时装了多个工具（既有 `~/.trae` 又有 `~/.coco`），纯靠目录探测会误判——比如在 CoCo 里跑却因为存在 `~/.trae` 被报成 trae。"

**追问：什么是"烧录"？** ⭐
> "`vsk install` 时目标平台是明确的——装到哪个 Agent 是指定的。所以我在安装那一刻就把平台值替换进脚本模板的占位符（`__PLATFORM__` → `DEFAULT_PLATFORM`），写死进这份脚本文件。运行时直接读这个固化值，比运行时探测本地目录可靠——因为一台机器可能同时装了多个工具，纯探测会误判，而安装时刻的信息是最准的。"

**⭐ 这个模块的加分点**：把"多平台适配"从体力活讲成**兼容性设计 + 环境探测鲁棒性**——尤其"多工具共存导致误判、所以用安装时烧录值"这个边界 case，体现你考虑了真实场景、不是简单堆 if-else。

## Q9. "除了被动采集，还有主动反馈吗？点赞/点踩怎么做的？"⭐（延伸亮点，主动讲）

> 这是遥测之外我做的第二层——**主动反馈采集**。被动指标（成功率/耗时）只能看出"跑没跑通"，看不出"用户觉得好不好用"，所以补了一套 👍/👎。

**我的答法（打磨版）：**
> "被动遥测只能量化'调用成没成功'，量化不了'用户主观觉得这个 Skill 有没有用'。所以我加了一套轻量的点赞/点踩反馈：
> - **入队**：`invoke_end` 时顺手把这次调用的 invocation_id 写进反馈队列文件 `/tmp/.vsk-feedback-queue-<ctx>.jsonl`；
> - **展示**：`show-feedback` 时读队列，在终端渲染一行'这个 Skill 对你有帮助吗？👍 | 👎'，链接里带一个 base64url 编码的 feedback token（把 invocation_id + skill_key 打包），用户点哪个就带上 `v=1`/`v=-1` 打到反馈服务；
> - **去重**：用一个 once 文件 + **120 秒 TTL** 防止同一段时间内反复弹反馈，打扰用户；一次有多个调用就聚合成'这 N 个 Skill 对你有帮助吗？全部点赞/全部点踩'。
>
> 链接格式还做了平台适配：trae/claude/cursor 这些支持 **Markdown 链接**，纯终端用 **OSC8 超链接转义**。反馈开关按 namespace 从服务端 `/preset/resolve` 下发，可以按业务线灰度。"

**追问：为什么用 token 编码而不是直接传 id？**
> "token 把 invocation_id 和 skill_key 一起 base64url 打包，一是让反馈能**精确关联到具体哪一次调用、哪个 Skill**，二是 URL 里不暴露裸 id、更整洁。服务端解开 token 就能把这次'主观评价'和被动遥测的那次调用对上。"

**这条为什么是加分点**：体现**指标分层思维**——客观指标（成功率/耗时）+ 主观反馈（👍/👎）双维度评估一个 Skill 的健康度，而不是只盯着一个数。
