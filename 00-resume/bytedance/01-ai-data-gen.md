## 0.6 Skill 造数方法的三轮演进（⭐⭐ 王炸素材：证明项目真实性 + 工程驱动力）

> 面试官最想听、又最难编的就是"迭代演进史"——它证明你是**自己驱动把一件事越做越好**，而不是接活照做。三轮之间是清晰的**痛点驱动**逻辑，讲的时候一定要把"为什么要进化到下一轮"说清楚。

| 轮次 | 方法 | 痛点 / 为什么进化 |
|---|---|---|
| **第 1 轮** | 平台**浏览器抓包** → 手动把 HTTP 请求转成 RPC | 极麻烦、纯手工、HTTP→RPC 转换易错、无法规模化（**已淘汰**）|
| **第 2 轮**（现为辅） | 让 **AI 基于 IDL + 业务代码分析**自动生成 Skill | 摆脱抓包，效率大增；但**静态分析可能和线上真实调用不符**——真实的参数默认值、调用序列拿不准。**现用作参数验证的交叉校验源** |
| **第 3 轮**（现为主）⭐ | 部署独立 **PPE 泳道环境**，部署所需 PSM，**基于时间范围内的真实日志**编排 Skill | 用**真实流量日志**还原真实调用链路和参数——线上真实发生过的，天生正确、可复现 |

**串讲话术（背下来，约 40 秒）：**
> "这套 Skill 的造数方法我迭代了三轮：**第一轮**最原始，靠在平台上浏览器抓包，再手动把 HTTP 请求转成 RPC，非常麻烦也容易错；**第二轮**我让 AI 直接基于接口的 IDL 和业务代码去分析、自动生成 Skill，效率高了很多，但静态分析拿不准线上真实的参数和调用顺序；**第三轮**我干脆部署了一个独立的 PPE 泳道、把需要的 PSM 都部署上去，然后**基于一段时间范围内的真实调用日志来编排 Skill**——因为日志是线上真实发生过的，还原出来的链路和参数天生就是对的、可复现的。"

**这条演进线证明了 3 件事（讲的时候心里有数）：**
1. **工程驱动力**：手工 → 半自动（AI 分析）→ 数据驱动（真实日志），一条标准的效率进化路径。
2. **数据可信的根因**：第 3 轮用真实日志编排，直接回答了"怎么保证参数对、链路对"——**日志是线上真实流量，天生正确**（比 AI 猜、比静态分析都可信）。
3. **硬核动手能力** ⭐：会自己**搭 PPE 泳道、部署 PSM**——这是很多测开候选人不具备的环境搭建能力，测开面试官很看重。

**⭐ 必备追问应对**："既然第 3 轮最好，前两轮还用吗？三种并存还是只用第 3 种？"
> "**以第 3 轮（PPE 泳道真实日志编排）为主**——它还原的链路和参数来自线上真实流量，最准；**辅以第 2 轮（IDL + 业务代码静态分析）做参数验证**——用接口的静态契约定义交叉校验日志里解析出来的参数对不对。**一个来自运行时真实数据、一个来自静态契约定义，两者相互印证**，比只信任单一来源更可靠。第 1 轮抓包已经淘汰了。"

**⭐ 这个答法的加分点**：体现"**多源交叉验证、不轻信单一数据源**"的质量思维——运行时数据 + 静态契约相互印证，正是测开该有的严谨。

## 1. 60 秒项目总述稿（STAR，开场必背）

**【背景 S】** 我在字节 TikTok One 做测试开发，负责三方创意业务的质量保障。当时有两个核心痛点：
① **效率**——测试要覆盖账号、合作、审核、投稿、达人 5 大业务模块，很多场景需要长链路的复杂测试数据（如一条完整链路要从创建测试账号 → 合作 → 达人接单 → 投稿上传视频一路串起来），人工造数耗时且易错；
② **知识壁垒（更关键）**——微服务架构下，每个研发只维护自己的 PSM，对上下游接口的必填参数、依赖顺序、校验规则并不了解，而一条完整测试数据天然是跨多个 PSM 的长链路，**没有人能独立、正确地造出来**。

**【任务 T】** 我负责在 AI Testing 场景下，把这套跨模块的造数能力**自动化、原子化、可复用**地沉淀下来——本质是**把散落在各研发脑子里的造数 know-how 产品化**。

**【行动 A】** 做了三件事：① 把造数拆成 **40+ 原子化 Skill**（一个业务动作一个），每个只干一件最小粒度的事；② 设计 **Prompt 触发 + Skill 匹配 + 流程编排**，让长链路自动把多个原子 Skill 串起来；③ 用**三级参数确定机制（默认静默值 / 约定必填值 / 可选参数）+ 前后置校验**保证参数填得对、数据造得准。

**【结果 R】** 从四个维度看效果：**采用度**——服务 1000+ 人次；**质量**——造数成功率 90%+；**效率**——一条完整长链路从人工 10min+ 降到 5min 内、提效约一半；**覆盖**——36+ Skill 覆盖账号到达人 5 大模块全链路。

## 1.5 端到端主流程（面试官说"讲下一次造数的完整流程 / 画下架构"时用）⭐

> 这是开场后的第二张王牌。能顺畅串讲一条 main flow，比零散答问更能证明"我真的设计了这套系统"。

**一次造数的完整链路（按顺序串讲）：**

```
用户 prompt（一句业务描述，如"造一条从账号到达人上传视频的完整链路"）
  │
  ▼
① coding agent 全量加载所有 Skill（名称 + 简短描述）
  │
  ▼
② 匹配：agent 按 prompt 选出要用的 Skill（选中后才展开读参数/步骤细节 = 渐进式加载）
  │
  ▼
③ 编排：agent 规划长链路顺序（账号 → 合作 → 达人接单 → 投稿上传视频）
  │
  ▼
④ 逐个执行：每个 Skill 用 bam-query 发真实 RPC；上一步输出（accountID）作下一步入参
  │
  ▼
⑤ 每步后置校验：读接口回查关键业务字段；不符 → 中断链路、抛明确错误（失败即止）
  │
  ▼
⑥ Skills Pulse 全程埋点上报：调用量 / 成功率 / 耗时 / 报错（异步 + 离线补发）
  │
  ▼
⑦ 返回造数结果（新建返 ID / 修改返成功状态）
```

**串讲金句（30 秒版）**：
> "用户一句话进来，coding agent 先全量读所有 Skill 的名称描述、匹配出要用哪些，再现场规划长链路顺序；然后逐个 Skill 用 bam-query 发真实 RPC，上一步的输出喂给下一步；**每步都做后置校验，不对就立即中断**；全程 Skills Pulse 埋点上报成功率和耗时；最后把造数结果返回。**关键设计是——执行交给通用 agent，但每一步的业务约束和校验都由我写在 Skill 里，保证结果可信可复现。**"

**这条流程分别踩中哪些考点（方便面试时顺势展开）：**
- ①② → Q1 Skill 形态 + Q2 全量加载/匹配
- ③ → Q2 编排 + Q2-d 不确定性兜底
- ④ → bam-query 真实链路（Q8 护城河）
- ⑤ → Q4 数据正确性
- ⑥ → Q3 成功率口径 + Skills Pulse

## 2. Q1 · Skill 的形态与管理

**面试官会问**：所谓"原子化 Skill"到底是什么？是脚本、函数还是 prompt？36 个怎么管理？一个 Skill 的输入输出是什么？

**我的答法（打磨版，约 40 秒）**
- 每个 Skill 本质是一个**结构化的 prompt 模板**，固化了该业务操作对应的 RPC 元信息（PSM、method、必填参数、参数类型约束）。
- 底层复用团队已有的 **bam-query 能力**真正发起 RPC，不重复造轮子。
- 所有 Skill 统一托管在类似 **SkillHub 的线上平台**，支持从 **git 仓库自动同步最新版本**，避免定义散落、版本不一致。
- **输入** = 一段业务操作描述；**输出** = 造数结果（新建返回实体 ID，修改返回成功状态）。

**⭐ 加分锚点（真实踩坑护城河 + 三级参数机制）**
> 为保证 agent 拼出的请求正确、提高造数成功率，我在 Skill 模板里设计了**三级参数确定机制**，把"参数该怎么填"从源头规定死，而不是靠 agent 现场猜：
> - **① 默认静默值**：有合理默认的参数预置好，用户不用管、agent 也不用问，静默填入（降低交互成本、避免 agent 乱填）。
> - **② 约定必填值**：业务强制必填的参数（如 `brandID`）明确标记必填，缺了就不放行——**这是我踩坑沉淀的**：某些创意投放接口 `brandID` 漏传会报特定错误码（如 38002001）。
> - **③ 可选参数**：用户想覆盖时可显式传，不传走默认。
>
> 另外还固化了**参数类型约束**——比如一批 ID 字段必须是 **i64 而非字符串**，类型错会直接报 `need I64 type but got STRING`，这也做进了模板校验。

**⭐ 这套机制回答了两个高频追问**：
- "怎么保证 agent 不漏填/填错参数？" → 三级机制从源头约束，不靠猜。
- "怎么提高成功率？" → 默认值兜底 + 必填拦截 + 类型约束 + 后置校验，多层保证。

**可能被继续追**
- "prompt + LLM 怎么保证 RPC 一定对？" → 引到 Q2-d 的兜底 + 上面的参数约束。
- "一句描述就能造数，LLM 怎么知道调哪个、填什么？" → 引到 Q2。

## 3. Q2 · Skill 匹配与流程编排（必考）

> **架构前提**：Skill 全量加载给 coding agent，匹配和编排都是 **agent 运行时自主完成的**（不是我写代码做路由）。我的抓手是把 Skill 的名称、描述、参数约束写清楚，让 agent 选得准、串得对。

**面试官会问**：一段业务描述进来后，(a) 怎么匹配到正确的 Skill？(b) 长链路串接顺序谁定？(c) 上一步输出怎么喂给下一步？

**我的答法（打磨版）**
- **(a) 匹配**：36+ 个 Skill **全量加载**，coding agent 根据用户 prompt 去**匹配 Skill 的名称和描述**，自主选出该用哪个。选得准的前提是 **Skill 命名和描述区分度足够高**——这是我写 Skill 时重点保证的。
- **(b) 编排**：长链路由 **agent 现场规划**——比如"造一个能直接投放的完整账号"，agent 规划出账号 → 授权 → 合作 → 投稿的顺序。
- **(c) 数据传递**：agent 根据上下游接口的出入参传递数据，**上一步的输出（如 accountID）作为下一步的入参**。

**⭐ 必备追问应对："全量加载 36+ Skill，token 会爆吗？Skill 太多会选错吗？"**
> "全量加载的只是每个 Skill 的**名称 + 简短描述**，token 占用可控；真正大的内容（参数细节、调用步骤、校验规则）是 agent **选中某个 Skill 后才展开读**的——本质是渐进式加载（progressive disclosure）。降低选错率主要靠**把 Skill 命名和描述的区分度写高**。Skill 规模继续涨（100+）后，我会引入**向量粗筛 + agent 精选的两级匹配**（见 Q7）。"

**可能被继续追** → 进入 Q2-d（灵魂追问：agent 规划不确定性怎么兜底）。

## 4. Q2-d · 如何兜底 agent 规划的不确定性（⭐ 测开灵魂）

**面试官潜台词**：你是做测试的，一个本身不稳定（agent 现场规划）的造数系统，你凭什么保证造出来的数据可信？

**我的答法（4 层兜底，完整背）**
1. **事前——收窄 agent 自由度**：Skill 模板通过**三级参数确定机制**（默认静默值 / 约定必填值 / 可选参数）+ 类型约束 + 前置依赖，给 agent 划护栏，让它没法乱填乱串——参数怎么填是模板规定的，不靠 agent 猜。
2. **事中——每步校验，失败即止**：每个原子 Skill 执行完校验返回是否符合预期（合法 ID、正确状态码），**不过就中断链路并抛明确错误**，不让脏数据往下游传、避免错误累积。（真实坑：brandID 漏传、i64 类型错都沉淀成校验规则。）
3. **事后——可观测 + 兜底重试**：这就是 **Skills Pulse** 做的——统计每个 Skill 的调用量、成功率、耗时、报错详情，失败 case 有报错能快速定位；**离线队列补发**保证上报数据不丢。
4. **收敛——高频链路固化模板**：对高频关键长链路，不完全依赖 agent 每次现场规划，把验证过的编排路径**沉淀成相对固定的流程模板**，只在末端参数上让 agent 灵活填充——**用确定性换稳定性**。

**⭐ 杀伤力**：把 AI Data Gen / Skills Pulse / 踩过的坑串成一个**完整质量闭环**，正是测开面试官最想看的"质量思维"。

**压缩记忆锚点（时间不够时）**
> 事前用 Skill 模板约束参数 → 事中每步校验失败即止 → 事后靠 Skills Pulse 观测成功率 + 重试补发 → 高频链路固化成模板降低不确定性。

## 5. Q3 · 成功率数字口径（测开最爱挖）

**面试官会问**：成功率 90%+、服务 1000+ 人次——(a) 90% 的分母是什么？(b) 失败的 10% 是哪几类？(c) "成功 / 失败"怎么定义，重试后成功算哪种？

**我的答法（打磨版）**
- **(a) 分母 = Skill 调用总次数**（不是 1000+ 人次里的人，别答混）。
- **(c) 统计的是最终成功率**：一次造数请求，**重试后拿到正确结果就算成功**。系统健康度上，Skills Pulse 里也能单独看**首次调用成功率**和**重试率**，重试率高的 Skill 就是我优先优化的对象。
- **(b) 失败约 10% 两类**：① **权限问题**——测试身份缺对应业务的操作权限；此时系统不是干报错，而是**返回权限申请链接、引导用户去申请，并等待审核通过后再继续**，做成了闭环而不是死路。② **参数校验没过**——必填缺失或类型不对。都能在 Skills Pulse 的报错详情里快速归因。

**⭐ 加分锚点**：口径要自洽——明确区分"单次成功率 vs 最终成功率"，并顺势体现"**用数据驱动优化**"（重试率高的优先优化）。

**易错点**
- 不要把"调用次数"和"人次"混为一个分母。
- "权限问题"别停在词面——要能答清是**测试身份缺某业务操作权限**，且系统**返回申请链接、引导申请、等审核通过**（是闭环处理，不是干报错）。

## 6. Q4 · 造出的数据怎么保证"业务上正确"（⭐ 压轴，区分度最高）

**面试官会问**：(a) 接口调用成功、返回了 ID，但这个数据业务上真可用吗？怎么防"接口成功、业务残缺"的脏数据？(b) 数据造错了会导致测试结论不可信，你怎么防？(c) AI 造数 vs 手写 SQL 直插库 / 固定 mock，正确性上谁更可信？

**我的答法（完整口径，直接背）**
- **(a) 前置 + 后置校验**：前置确认是**测试账号、测试环境**（防污染生产）；后置在造数完成后**用读接口回查**，不只确认 ID 存在，还**校验关键业务字段符合预期**（如账号状态是可投放的）。
- **(c) 走接口比直插库更可信** ⭐（注意：不是"一样"）：走接口造数经过系统**完整的业务校验链路**，不会造出接口逻辑永远不会产生的非法数据；直插库虽快但**绕过校验**，容易埋下"脏数据测出假结论"的坑。这也是本方案的价值之一。
- **(b) 数据可追溯** ⭐：每条造出的数据记录了它是**哪个 Skill、什么参数**造的；测试结果异常时能快速回溯是"**被测功能的 bug**"还是"**造数本身造错了**"，把两类原因分离开。（区分"数据的错 vs 功能的错"是资深测开的分水岭。）

**易错点**
- **c 千万别答"可信度一样"**——这题恰恰是你方案优于传统做法的亮点，答"一样"等于把亮点抹平。

## 7. Q5 · 异常与稳定性（⭐ 测开视角，深水区）

> **架构前提（重要）**：造数不是"我写代码调 LLM API 拿 JSON 再发请求"，而是**用 coding agent（如 Claude Code）调用我写的 Skill 来完成**。职责划分：coding agent 负责理解描述、匹配 Skill、规划长链路、实际执行工具调用并解析结果；我的 Skill（prompt 模板）负责告诉 agent"调哪个接口、必填什么参数、怎么用 bam-query、执行完怎么校验"；bam-query 负责真正发 RPC。
> 所以"LLM 输出格式不合法、JSON 解析失败"这类底层问题由 agent 框架运行时自己扛，**不是我写代码兜底的**；我的稳定性保障重心是**把 Skill 的指令和校验规则写得足够明确，让 agent 不容易做错**。

**面试官会问**：这套系统的不稳定因素有哪些？(a) agent 理解 / 规划出错怎么办？(b) 下游 RPC 超时限流时重试会不会造成重试风暴？(c) 造数造到一半失败，前面的数据怎么办？

**参考答法（按实际调整）**
- **(a) agent 理解 / 规划出错**（选错 Skill、串错顺序、漏一步）：靠**把 Skill 描述写得足够清晰、约束足够明确**来降低概率——固化必填参数、类型约束、前置依赖（呼应 Q1、Q2-d 事前收窄 agent 自由度）；执行完每步用 Skill 里写的**后置校验**兜底（呼应 Q4），结果不对就中断、不往下造。
- **(b) 防重试风暴**：重试**分错误类型**——4xx 参数错**不重试**（重试也没用），只有 5xx / 超时才重试；重试**限次数 + 指数退避 + 抖动**，避免同时重试把下游打挂；遇限流则退避等待。
- **(c) 半成品脏数据**：长链路造到一半失败（账号建好、合作失败）会留半成品。测试数据场景**不强求分布式事务回滚**——① 失败即止，不继续往下造、避免错误累积；② 每步产出资源**可追溯**（哪个 Skill、什么参数、产出什么 ID），失败能定位断点；③ **测试环境本身有自动清理机制**，半成品数据会被定期回收，所以不需要我额外做补偿删除。

**⭐ 加分锚点 0（体现工程判断）**：主动点破"这是测试环境，本身会自动清理，所以我没有过度设计补偿/回滚——**在测试场景做生产级的事务回滚是过度设计**"。分得清场景边界本身就是加分项。

**⭐ 加分锚点 1**：主动点破"测试数据对一致性要求没生产高，重点是**可追溯 + 可清理**"，体现你分得清"生产级严谨"和"测试场景的合理取舍"。

**⭐ 加分锚点 2（反向问题，必备）**：若被问"既然 agent 执行，你的核心工作量是什么？"——
> "执行交给了 agent，我的核心价值集中在**把每个业务操作的造数知识写成 agent 能准确理解和执行的 Skill**：调哪个接口、必填哪些参数、类型约束、依赖顺序、执行后怎么校验。**agent 是通用的，但它不懂 TikTok One 的业务；我做的就是把业务 know-how 翻译成 agent 能执行的确定性指令**——这正是外部工具复制不了的地方。"

## 8. Q6 · 并发与资源隔离（高频考点，但本项目要先澄清前提）

> **架构前提（关键，先说清）**：这套造数是**测试同学在本地用自己的 coding agent 调用 Skill**——每个人在自己的机器、用自己的身份跑，**本质是单人单会话，不存在多人共用一个服务实例并发抢资源的场景**。所以传统的"并发控制/资源锁"在这里不是核心问题。

**面试官会问**：多人同时造数会不会冲突？有没有做并发控制？

**我的答法（据实）**
- **先澄清前提**："我这套是**本地化、单人使用**的——每个测试同学用自己的 agent、自己的身份在本地调 Skill，不是一个中心化服务被多人并发调用。所以**天然没有多人抢同一资源的并发问题**。"
- **数据天然隔离**：不同人用不同测试身份/环境造数，**数据按身份维度天然隔离**，互不影响。
- **如果被追问"那假如要做成平台化、多人共用呢？"**（考延展思维）：那时才需要考虑并发——我会按 **session/用户维度隔离资源**（每次造新的、不复用固定资源），对稀缺共享资源再引入**资源池 + 分布式锁**。但当前形态下这属于过度设计。

**⭐ 加分锚点**：不硬凑"我做了并发控制"，而是**先澄清使用形态、说明为什么不需要**，再给出"若平台化该怎么做"的延展——比编一个用不上的锁方案更能体现判断力。

## 9. Q7 · 如果重构会改哪里（⭐ 考架构反思，几乎必问）

**面试官会问**：回头看，如果重做一版你会改哪？（答"没什么可改"是大忌——说明没反思。）

**参考答法（挑 1–2 个真实反思点讲）**
1. **编排过度依赖 agent 现场规划** → 稳定性和可复现性差。重做会**把高频长链路固化成 DAG / 流程模板**，agent 只负责末端参数填充和异常兜底，用确定性换稳定性（其实上线后我已经在往这个方向收敛）。
2. **Skill 匹配是全量加载 + agent 硬匹配** → Skill 涨到 100+ 后 token 和选错率都会上升。重做会引入**向量粗筛 → agent 精选的两级匹配**，并按 5 大业务模块**分组分层**，先选模块再选 Skill。
3. **可观测接得晚**（Skills Pulse 是后补的）→ 早期定位失败靠翻日志。重做会**一开始就内建埋点**，Skill 从第一版就上报调用 / 成功率 / 耗时，并扩展"选错 / 选不到 Skill"的匹配质量指标。
4. **Skill 定义与真实接口可能漂移** → 接口改了但 Skill 模板没跟上会静默失败。重做会加**契约校验**：Skill 上线前自动校验它声明的参数定义与真实接口一致（把踩过的 brandID / i64 坑做成自动化拦截）。

**⭐ 加分锚点**：讲反思时带出"我已经在往哪个方向改进"，比只吐槽更能体现主动性。

## 10. Q8 · 护城河与最大难点（收尾必问，要有"钩子"答案）

**面试官会问**：(a) 和直接用 ChatGPT / Cursor 生成测试数据比，核心壁垒在哪？换个人一周能复制吗？(b) 一句话：这个项目最大的技术难点是什么？

**参考答法**
- **(a) 壁垒（不在"调 LLM"，在沉淀）**：
  1. **业务 know-how 沉淀（核心）**——微服务下每个研发只懂自己的 PSM，跨上下游的长链路造数**没人能独立完成**；我把 5 大业务模块的领域知识（有哪些接口、必填什么参数、依赖顺序、校验规则）固化进 36+ Skill，**相当于把散落在各研发脑子里的专家造数能力产品化了**。这是踩坑 + 摸清全链路才有的，外部工具没有。
  2. **打通真实内网 RPC 链路 + 真实日志编排**——复用内部 bam-query 调真实接口，外部 ChatGPT / Cursor **根本调不到内网接口**，只能编假数据；而且我的 Skill 是**基于 PPE 泳道真实调用日志**编排出来的（见 0.6 第 3 轮演进），链路和参数天生正确，这更不是外部工具能做到的。
  3. **配套质量闭环**——Skills Pulse 可观测 + 前后置校验 + 参数约束规则。
  > 结论：换个人一周**复制不了**，难在业务知识沉淀和链路打通，不在 LLM 调用本身。
- **(b) 最大难点（钩子答案，背熟）**：把**非确定性的 LLM 规划，约束成可信、可复现的测试数据产出**——即"事前约束参数、事中校验失败即止、事后可观测 + 重试"这套质量闭环。这也是**测试开发**和"随便写个造数脚本"的本质区别。
