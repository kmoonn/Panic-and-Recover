## 0. 项目一句话定位

一个**从"用例设计"到"执行验证"打通的接口测试 Agent**：提测前用 **PRD 生成用例 checklist 初稿**供评审，提测后用 **MR 代码改动做增量查漏**；再由 Agent **自主补齐测试数据 → 编排用例经内部 ATE 平台发起调用 → 基于 IDL/PRD 生成断言 → 失败自动重试 → 出测试报告**。把"读需求 → 翻代码 → 写 checklist → 备数据 → 跑接口 → 判定"这条人工链路端到端自动化。

**一句话电梯陈述**：
> "接口测试从设计到执行都很耗人。我做的 API Testing Agent 干了两段：前半段**贴着真实测试流程分两阶段**生成 checklist——提测前 PRD 出初稿走评审、提测后 MR 查漏补缺；后半段让 **Agent 自主把 checklist 变成真的能跑的接口测试**——自己补数据、编排用例、发请求、生成断言、失败重试，最后出报告。"

**关联项目（顺势带出，闭环）**
- **AI Data Gen**：执行阶段三种数据源之一的"造数 Skill"就是它——Agent 补数据时直接调造数 Skill。**一个定"测什么"、一个供"拿什么测"。**
- **内部 ATE 平台**：接口自动化执行的载体，Agent 通过其配套 Skill 写用例、发请求（**复用现有基建，不重造轮子**）。
- **业务知识库 RAG**：呼应我对 RAG / 知识库的技术储备。

## 1. 60 秒项目总述稿（STAR，开场必背）

**【背景 S】** 接口测试从设计到执行都很重：测试要读 PRD 判断该测什么、提测后翻 MR 看代码实际改了什么、手写接口 checklist、凑测试数据，再一条条去 ATE 平台配用例、发请求、写断言、看结果。整条链路重复、耗时、强依赖个人经验，新人容易漏测。

**【任务 T】** 我在团队里负责设计并实现一个把这条链路端到端自动化的 API Testing Agent，核心是**PRD 与 MR 双驱动的 checklist 生成机制 + Agent 自主执行闭环**。

**【行动 A】** 关键设计：
① **两阶段生成**——提测前用 PRD 生成用例 checklist 初稿供**评审**；提测后用 MR 代码改动对已评审 checklist 做**增量查漏**（符合"评审必须在提测前"的真实流程）；
② **MR 确定性解析**——写解析层调 GitLab API 拿结构化 changes，提取改动的**接口/函数/字段**，只把相关改动喂模型；
③ **执行闭环**——Agent **自主**从 Mock/日志检索/造数 Skill 补齐测试数据 → 编排用例经 **ATE 平台**发起调用 → 基于 **IDL/PRD/业务代码**生成断言 → **失败自动重试** → 出测试报告；
④ **知识库 RAG + review 闭环**——业务文档检索补充规则/历史缺陷；输出 md+html，评审意见经 html 评论喂回 AI 完善。

**【结果 R】** 测试准备与执行耗时体感缩短约 40%（人工小半天的设计+执行，压缩到工具生成初稿 + review 补充 + 自动跑）。

## 1.5 端到端主流程（"讲下完整流程 / 画下架构"时用）⭐

```
【阶段一 · 提测前，只有 PRD】
  PRD 链接 ──→ CLI 解析 PRD ──→ RAG 检索业务规则/历史缺陷 ──→ 生成用例 checklist 初稿
                                                                    │
                                                            输出 md + html
                                                                    │
                                                      html review（测试/评审人评论）
                                                                    │
                                                      评论喂回 AI ──→ 完善 checklist（可多轮）
                                                                    │
                                                            ✅ 定稿参加用例评审

【阶段二 · 提测后，有了 MR】
  MR 链接 ──→ 解析层调 GitLab API 拿结构化 changes ──→ 提取改动接口/函数/字段
                                                            │
              已评审 checklist ＋ 变更集 ──→ 增量校正：
                                              ① MR 改了但用例没覆盖 → 补
                                              ② MR 引入的重构/隐藏改动 → 列为变更风险点
                                              ③ 代码级覆盖度查漏
                                                            │
                                                    ✅ 定稿 checklist（该测什么已确定）

【阶段三 · 执行闭环，Agent 自主把 checklist 跑成真接口测试】
  定稿 checklist
       │
       ├─→ 逐条自主补数据：Mock / 日志检索 / 造数 Skill（按用例场景选）
       │
       ├─→ 编排用例：经 ATE 平台配套 Skill 写接口用例、组织入参
       │
       ├─→ 发起调用：ATE 平台真实发请求
       │
       ├─→ 生成断言：基于 IDL（契约）+ PRD（预期）+ 业务代码（实现）交叉推断
       │
       ├─→ 判定结果 ──失败──→ 自动重试（区分环境抖动 vs 真实失败）
       │                              │
       │                        重试仍失败 → 记为缺陷候选
       │
       └─→ 汇总输出测试报告（通过/失败/未覆盖）
```

**讲解话术（约 60 秒）**：
> "分三阶段，对齐研发节奏。**提测前**只有 PRD，CLI 解析 PRD、结合知识库 RAG 检索业务规则和历史缺陷，生成一份用例 checklist 初稿，输出 md 和 html 两版；测试可以在 html 上直接评论，评论喂回 AI 多轮完善，定稿后拿去参加用例评审。**提测后**有了 MR，我的解析层调 GitLab API 拿到结构化改动、提取出改了哪些接口和字段，再拿这个变更集去和已评审的 checklist 比对——补上代码改了但用例没覆盖的点，把重构、隐藏字段这类改动单列成变更风险点。**checklist 定稿后进入执行阶段**：Agent 逐条用例自主补数据——Mock、日志检索或造数 Skill 里选——再经内部 ATE 平台的配套 Skill 编排用例、真实发请求，断言用 IDL、PRD、业务代码交叉生成，跑失败了自动重试、区分是环境抖动还是真实缺陷，最后汇总成测试报告。这样从'该测什么'到'真的跑完'整条链路是通的。"

## Q1. "为什么是两阶段？直接 PRD+MR 一起喂不行吗？"⭐⭐（核心，最能体现懂测试流程）

**我的答法（打磨版）**：
> "这正是我这个项目最关键的设计点，来自一个真实的流程约束：**用例评审必须在提测前完成，但代码 MR 是提测之后才有的**。如果我做成'PRD+MR 一起喂、一把生成',那在评审阶段根本没有 MR，工具就用不上；等有了 MR 再生成，评审早过了。
>
> 所以我把它拆成两阶段、对齐研发节奏：
> - **提测前**只有 PRD，生成用例 checklist 初稿，去走用例评审——这是测试流程里雷打不动的前置环节；
> - **提测后**有了 MR，再用代码实际改动去给已评审的 checklist **查漏补缺**、标出变更风险点。
>
> 这样'双驱动'不是把两份输入一锅煮，而是**在正确的时间点用正确的输入**——PRD 解决'该测什么'，MR 解决'代码到底动了什么、有没有漏测'。"

**加分锚点**：这体现你懂**真实测试流程节奏**（评审前置）、且有**变更聚焦/风险驱动**的测试思维，不是纯做 AI 工具的。

**追问：那提测后阶段和'提测前初稿'什么关系？会推翻重来吗？**
> "不推翻。提测后是**增量校正**，输入是'已评审的 checklist + MR 变更集'，只做三件事：补 MR 改了而用例没覆盖的点、把重构/隐藏改动单列为变更风险点、做代码级覆盖度查漏。评审过的东西是基线，MR 只负责让它对齐真实代码改动。"

## Q2. "MR 是代码 diff，你怎么解析成模型能用的输入？"⭐⭐（核心，硬工程亮点）

**我的答法（打磨版）**：
> "我写了**解析层**做确定性解析，没有把裸 diff 丢给 LLM。具体是**调 GitLab 的 MR API 拿结构化的 changes**（比 raw diff 文本干净），从里面解析出本次改动的**文件、接口、函数、字段**这些结构化信息。大 MR 的时候，按'与 PRD 功能点相关'做过滤分组，只把相关改动喂给模型，**控制上下文规模**。"

**⭐ 为什么用代码解析而不是 LLM 提取（必背，测开核心判断力）**：
> "因为 **MR 改动是测试的事实依据，不能有幻觉空间**。让 LLM 去'提取代码改了啥'，它可能漏、可能编，而这直接决定测试覆盖对不对。所以变更提取这一步我用**确定性的代码解析**保证准确，LLM 只负责它真正擅长的部分——把'改了哪些接口'翻译成'该测哪些用例'的语义生成。**该用确定性代码的地方用代码，该用 LLM 的地方用 LLM**，这是我做 AI 测试工具时一直守的原则。"

**追问：大 MR 几百个文件怎么办？**
> "两层控制：一是解析层先做**结构化过滤**，只保留接口/字段级的实质改动，剔除格式、注释、lock 文件这类噪声；二是按**与 PRD 功能点的相关性**分组，优先喂相关改动。本质是**上下文工程**——不是塞得越多越好，是喂得越准越好。"

**追问：怎么判断改动'和某个 PRD 功能点相关'？**
> "靠接口/字段名做关联——PRD 功能点会落到具体接口，MR 改动也解析出接口，两边按接口维度对齐。"（⚠️ 若细节记不清，就说"按接口维度关联"，别硬编算法）

## Q3. "业务知识库 RAG 怎么设计的？"⭐

**我的答法（打磨版）**：
> "知识库是**文档形态**，内容是业务规则和**历史缺陷模式**。设计上：
> - **切块**：按**接口维度**和**缺陷案例条目**切，不是整篇文档塞——保证召回的粒度和'一个接口/一个缺陷'对齐；
> - **检索 query**：用从 **PRD 和 MR 里提取出的接口名、业务关键词**当 query 去召回，而不是拿整篇 PRD 检索——query 越聚焦召回越准；
> - **拼装**：召回的业务规则和历史缺陷拼进生成 prompt，让 checklist 带上业务约束和'过去这里踩过什么坑'。"

**追问："历史缺陷模式"具体是什么？** ⭐（呼应简历原词）
> "是**过往 bug 单沉淀成的结构化条目**——把线上/测试发现过的缺陷提炼成'现象 + 触发条件 + 关联接口'，存进知识库。生成 checklist 时，如果这次改动命中了某个接口的历史缺陷，就会把对应的测试点带出来，**相当于把团队踩过的坑资产化、不再重复漏测**。"

**加分锚点**："把缺陷经验资产化"是很成熟的质量思维，体现你不只做工具、还想着沉淀团队资产。

**追问：为什么用 RAG 不把知识库全塞进 prompt？**
> "知识库会越攒越大，全塞既超上下文又稀释重点。RAG 只召回和本次改动相关的规则/缺陷，**又准又省 token**。"

## Q4. "三种测试数据源怎么选？分别什么场景？"⭐

**我的答法（打磨版）**：
> "checklist 定了'测什么'，还得有数据才能真跑，我接了三种，按场景选：
> - **Mock**：下游依赖不稳定、或要构造特定返回（异常、边界）时，直接 mock 掉依赖；
> - **日志检索**：需要贴近真实的数据时，从日志里检索真实发生过的请求/参数——**真实、可复现**；
> - **造数 Skill**：需要在环境里真造一条数据（如新建一个账号/订单）时，调 AI Data Gen 那套造数 Skill。
>
> 三者覆盖'伪造依赖 / 复用真实 / 真造数据'三类需求。"

**加分锚点**：造数 Skill 直接把 **AI Data Gen 项目串进来**，两个项目形成闭环——面试官会觉得你的工作是成体系的，不是零散的。

**追问：三种数据可信度一样吗？**
> "定位不同：日志检索来自真实流量，最贴近生产；造数 Skill 是本地真实构造；Mock 是人为构造、可控但不真实。按测试目的选——要覆盖异常路径用 Mock，要验证真实链路用日志/造数。"

## Q5. "html review 闭环是干嘛的？为什么要 human-in-the-loop？"⭐

**我的答法（打磨版）**：
> "AI 生成的 checklist 初稿不可能一次到位，尤其要拿去**用例评审**。所以我输出 **md + html 两版**：md 给归档/流水线用，html 是给人 review 的——测试或评审人可以直接在 html 上评论（哪个点漏了、哪个不该测、粒度不对），这些评论再**喂回 AI 做多轮完善**。
>
> 之所以要人在环，是因为**测试 checklist 的最终责任人是测试，不是 AI**。AI 负责把初稿做到 80 分、省掉重复劳动，人负责把关到 100 分，评审意见还能反过来喂回去让下一版更好。这个闭环正好卡在'提测前评审'这个阶段最有用。"

**加分锚点**："AI 出初稿、人把关定稿"体现你对 AI 能力边界的清醒认知——不迷信 AI 全自动。

## Q6. "测试准备与执行耗时缩短约 40%，怎么来的 / 有没有量化？"⭐⭐（简历写了数字，必被追问，务必降级）

> ⚠️ **40% 写在简历里**（"测试准备与执行耗时缩短约 40%"）。它是**体感估算、没做严格对照实验**，被追问时必须主动降级，别硬撑成精确数据。

**我的答法（诚实版，必背）**：
> "先说清楚，这是个**体感估算，没做严格的对照实验**。口径是：人工走完一次接口测试的准备加执行——读 PRD、提测后翻 MR 看代码改了啥、手写 checklist、凑数据，再去 ATE 平台一条条配用例、发请求、写断言、看结果——大概要小半天；用工具后，生成 checklist 初稿 + 人 review 补充，执行交给 Agent 自主补数据、编排、发请求、判定，人只做复核，整体大致省了四成左右。是团队日常用下来的体感，不是精确测出来的，所以简历里我用的是'约 40%'而不是精确值。"

**为什么这么答**：
> 数字最招追问。**主动说"体感估算、没做严格实验，所以写的是约 40%"反而加分**——面试官最反感把估算吹成精确数据。坦诚 + 给得出对照口径（人工小半天 vs 工具生成+review+Agent 执行），这个数就立得住。

**追问：那你怎么知道是四成不是两成？**
> "省的主要是两段最耗人的：**准备侧**——翻 MR 定位改动 + 从零写 checklist，现在解析层自动出改动、AI 出初稿只需补充；**执行侧**——以前在 ATE 上一条条手工配用例、造数据、写断言，现在 Agent 自主编排。这两段是全流程里最花时间的，所以体感在四成上下。但我不会说这是严格测出来的。"

## Q7. "叫 Agent，它到底'自主'在哪？和固定流水线脚本区别是什么？"⭐⭐（名实之辨，必被问）

**我的答法（打磨版）**：
> "区别在于**是不是每步都要人写死**。固定流水线是'把 checklist 手动翻成一堆脚本、每个用例的数据、入参、断言都预先写好、按顺序跑'——改一个接口就要改一批脚本。我这个是 **Agent 拿着定稿 checklist，自己决定每一步怎么做**：
> - **自主补数据**：看这条用例需要什么数据，自己判断该 Mock、该从日志捞、还是该调造数 Skill 真造；
> - **自主编排用例**：调 ATE 平台的配套 Skill 把用例组织出来、拼好入参；
> - **自主生成断言**：读 IDL/PRD/业务代码推断这个接口该断言什么；
> - **自主处理失败**：跑挂了自己重试、判断是环境问题还是真缺陷。
>
> 也就是说，人给的是**'测什么'的 checklist**，Agent 补的是**'怎么测、拿什么测、怎么判定'的执行细节**——这部分传统上要测试一条条手工做，现在交给 Agent 在 checklist 约束下自主完成。这也是它叫 Agent 而不是脚本的原因。"

**⭐ 边界的诚实划法（防止被追问'那它完全无人值守？'）**：
> "不是全自动无人值守。**checklist 是人评审定稿的**（提测前那道关），执行阶段 Agent 自主，但**断言是否合理、失败是真缺陷还是用例问题，最终还是人复核**。我把它定位成'把测试从体力活里解放出来'，不是'取代测试判断'。"

**加分锚点**：既讲清 Agent 的自主性（对比脚本），又主动划出人的责任边界——比只吹"全自动"可信得多。

---

## Q8. "断言你怎么自动生成？IDL/PRD/业务代码三个来源分别管什么？"⭐⭐（执行闭环最硬的技术点）

**我的答法（打磨版）**：
> "断言最怕两件事：漏断言（跑通就算过）和错断言（断错了预期）。我用**三个来源交叉**来兜：
> - **IDL 管'结构与契约'**：响应字段、类型、必填、枚举取值范围——保证返回结构合法、字段类型对；
> - **PRD 管'业务预期'**：这个功能预期的结果是什么（比如'提交后状态应变为待审核'）——保证业务语义对；
> - **业务代码管'实现细节与边界'**：实际的校验逻辑、错误码、默认值——补 PRD 说不到的实现层断言。
>
> 三者是**互补**的：光看 IDL 只能断'结构合法'但断不了'业务对不对'；光看 PRD 断不了具体错误码和边界；所以交叉生成才能既覆盖契约、又覆盖业务、又覆盖实现。"

**追问：这么生成的断言会不会也有幻觉、断错？**
> "会，所以我不把它当'最终真理'。断言是 **Agent 生成、人复核**的——尤其业务语义类断言，评审时会看。而且**结构/类型这类硬断言来自 IDL，是确定的、不会幻觉**；容易出错的是业务语义断言，那部分正好是留给人把关的。**又是那个原则：确定的部分（IDL 结构）交给确定来源，模糊的部分（业务语义）AI 生成 + 人复核。**"

**追问：断言跑挂了，怎么区分是'用例/断言写错了'还是'真有 bug'？**
> "这正是要人复核的地方。Agent 侧先做**能自动区分的**——比如超时、连接失败、5xx 这类先归为环境/依赖问题、自动重试；重试仍失败、且是业务字段不符，才记为**缺陷候选**丢给人看。人再判断是断言本身不合理，还是真缺陷。"

## Q9. "执行是接内部 ATE 平台，你具体做了什么？没有重复造轮子吧？"⭐

**我的答法（打磨版）**：
> "没有重造，**执行引擎就是复用团队的 ATE 接口自动化平台**——它本来就能配接口用例、发请求、管理环境。我做的是**让 Agent 会用它**：ATE 有配套的 Skill，我编排 Agent 去调这些 Skill 把 checklist 里的用例落成 ATE 上真实能跑的用例、组织入参、发起调用、拿回结果。
>
> 所以我的价值不在'又写了个测试执行器'，而在**把'人在 ATE 上一条条配用例'这段体力活，变成 Agent 自主编排**——数据我来补、用例我来编排、断言我来生成，ATE 负责它擅长的发请求和环境管理。**复用现有基建、只补上 AI 编排这层**，是我一贯的做法（Skills Pulse、造数 Skill 也都是接现有体系，不另起炉灶）。"

**加分锚点**：主动说"复用基建、不重造轮子"，体现工程判断力和成本意识——面试官很吃这套。

## 7. 总结卡（考前 5 分钟扫一眼）

| 维度 | 一句话 |
|---|---|
| **定位** | 从"用例设计"到"执行验证"打通的接口测试 Agent：PRD/MR 双驱动生成 + Agent 自主执行闭环 |
| **核心亮点** | ① 发现"评审前置 vs MR 后置"矛盾→**两阶段渐进生成**；② **Agent 自主执行闭环**（补数据/编排/断言/重试） |
| **双驱动** | PRD=该测什么（提测前）；MR=代码实际改了什么（提测后查漏） |
| **MR 解析** | 写代码解析层，调 GitLab API 拿结构化 changes，提取接口/函数/字段（**确定性，不用 LLM 提**） |
| **LLM 边界** | 确定性的用代码（变更提取、IDL 结构断言），语义生成的用 LLM（改动→用例、业务断言）+ 人复核 |
| **执行闭环** | Agent 自主：补数据→经 ATE 编排用例发请求→IDL/PRD/代码生成断言→失败重试→出报告（Q7-Q9） |
| **Agent 自主性** | 人给"测什么"(checklist)，Agent 补"怎么测/拿什么测/怎么判定"；断言与失败判定人复核（Q7） |
| **断言三来源** | IDL=结构契约 / PRD=业务预期 / 业务代码=实现边界，交叉生成（Q8） |
| **ATE 复用** | 执行引擎复用团队 ATE 平台，我只补 AI 编排层，不重造轮子（Q9） |
| **三数据源** | Mock（造依赖）/ 日志检索（复用真实）/ 造数 Skill（真造，接 AI Data Gen）——**已写进简历** |
| **RAG** | 文档按接口/缺陷案例切块，用接口名/业务词当 query 召回业务规则 + 历史缺陷（Q3） |
| **历史缺陷模式** | 过往 bug 单沉淀成"现象+触发条件+关联接口"条目，缺陷经验资产化 |
| **review 闭环** | md+html 双版本，html 评论喂回 AI 完善（human-in-the-loop）——**已写进简历** |
| **40%** | **体感估算**，覆盖"准备+执行"；被追问才降级说"没做严格对照实验"（Q6） |
| **红线** | 团队项目，我 own"双驱动生成 + 执行闭环编排 + MR 解析"；ATE 平台是团队基建，我做的是编排它 |
