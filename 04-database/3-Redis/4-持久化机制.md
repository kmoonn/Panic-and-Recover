# 持久化机制

## Redis 为什么需要持久化？

Redis 是纯内存数据库，数据存储在内存中，一旦服务器重启或宕机，内存中的数据就会丢失。持久化机制将内存数据保存到磁盘，保证数据在重启后可以恢复。

## 两种持久化方式

| 对比项 | RDB | AOF |
|---|---|---|
| 全称 | Redis Database | Append Only File |
| 方式 | 定时快照（二进制文件） | 追加写命令（文本文件） |
| 触发方式 | save / bgsave / 自动配置 | 每次写操作追加 |
| 文件 | dump.rdb | appendonly.aof |
| 数据安全性 | 可能丢两次快照间的数据 | 最多丢 1 秒数据（everysec） |
| 文件大小 | 小（二进制压缩） | 大（文本，可重写压缩） |
| 恢复速度 | 快 | 慢 |
| 性能影响 | bgsave 时 fork 子进程，COW | 每次写操作追加日志 |

## RDB（快照持久化）

### 工作原理

RDB 通过 fork 子进程，利用**写时复制（Copy-On-Write, COW）** 生成内存快照：

```
主进程
  │
  ├── fork() ──→ 子进程
  │                │
  │    主进程继续处理写请求    子进程将内存数据写入 dump.rdb
  │    (COW: 修改的页复制)    (读取的是 fork 时的内存快照)
  │                │
  │                └── 完成后退出
  │
  └── 替换旧 RDB 文件
```

### 触发方式

| 方式 | 命令/配置 | 说明 |
|---|---|---|
| save | `SAVE` | 同步阻塞主进程，生产环境禁用 |
| bgsave | `BGSAVE` | fork 子进程后台执行，推荐 |
| 自动触发 | `save 900 1` | 900 秒内至少 1 个 key 变化则触发 |
| | `save 300 10` | 300 秒内至少 10 个 key 变化 |
| | `save 60 10000` | 60 秒内至少 10000 个 key 变化 |

### 优点

1. **文件小**：二进制压缩，紧凑
2. **恢复快**：直接加载二进制文件，远快于 AOF
3. **对主进程影响小**：bgsave 由子进程完成，主进程继续服务
4. **适合备份**：定期生成快照，方便灾备

### 缺点

1. **可能丢数据**：两次快照之间的数据变更会丢失
2. **fork 耗时**：数据量大时 fork 子进程可能耗时较长
3. **不适合实时性要求高的场景**

## AOF（追加日志持久化）

### 工作原理

AOF 将每条**写命令**追加到 AOF 文件末尾：

```
客户端发送写命令 → Redis 执行 → 命令追加到 AOF 缓冲区 → fsync 到磁盘
```

### 同步策略（appendfsync）

| 策略 | 行为 | 数据安全性 | 性能 |
|---|---|---|---|
| always | 每次写操作都 fsync | 最高，最多丢 0 条 | 最差 |
| everysec | 每秒 fsync 一次 | 较高，最多丢 1 秒数据 | 折中（**默认推荐**） |
| no | 由 OS 决定何时 fsync | 最低，可能丢较多数据 | 最好 |

### AOF 重写（Rewrite）

AOF 文件会越来越大，Redis 提供**重写机制**压缩文件：

```sql
-- 手动触发
BGREWRITEAOF

-- 自动触发
auto-aof-rewrite-percentage 100   -- AOF 文件大小比上次重写后增长 100%
auto-aof-rewrite-min-size 64mb    -- AOF 文件最小 64MB 才触发重写
```

重写原理：fork 子进程，遍历 Redis 当前数据状态，用**最少的命令**重写 AOF 文件（合并冗余命令、删除过期 key 等）。

### 优点

1. **数据更安全**：最多丢 1 秒数据（everysec 模式）
2. **可读性好**：AOF 是文本格式，可人工查看和修复
3. **可恢复性更强**：即使文件损坏，可用 redis-check-aof 修复

### 缺点

1. **文件大**：记录每条写命令，比 RDB 大很多
2. **恢复慢**：需要重放所有写命令
3. **性能开销**：每次写操作都要写磁盘

## RDB vs AOF 详细对比

| 对比项 | RDB | AOF |
|---|---|---|
| 持久化方式 | 快照（二进制） | 追加写命令（文本） |
| 数据安全性 | 可能丢数分钟数据 | 最多丢 1 秒 |
| 文件大小 | 小 | 大（重写后缩小） |
| 恢复速度 | 快（直接加载） | 慢（重放命令） |
| 系统资源占用 | fork 时 CPU/内存 | 写操作频繁 fsync |
| 适用场景 | 备份、灾备 | 数据安全要求高 |
| 优先级 | 低（同时开启时 AOF 优先） | 高 |

> Redis 重启时，如果 RDB 和 AOF 都开启，**优先使用 AOF 恢复数据**，因为 AOF 数据更完整。

## 混合持久化（Redis 4.0+）

Redis 4.0 引入**混合持久化**，结合 RDB 和 AOF 的优点：

```
AOF 重写后的文件结构：

┌──────────────────────────────┐
│  前半段：RDB 格式（二进制）   │  ← 全量数据，恢复快
├──────────────────────────────┤
│  后半段：AOF 格式（增量命令） │  ← RDB 之后的增量写命令
└──────────────────────────────┘
```

```sql
-- 开启混合持久化
aof-use-rdb-preamble yes   -- 默认 yes（Redis 4.0+）
```

优势：兼顾恢复速度和数据安全性，重写时前半段用 RDB 格式（体积小、恢复快），后半段用 AOF 格式（增量数据安全）。

## 配置建议

| 场景 | 推荐配置 |
|---|---|
| 数据安全要求高 | AOF（everysec） + RDB（定时备份） |
| 允许丢失数分钟数据 | 仅 RDB |
| 兼顾安全和恢复速度 | 混合持久化（AOF + RDB preamble） |
| 纯缓存场景 | 可关闭持久化 |

## 面试高频问题

### Q: RDB 和 AOF 怎么选？

- **数据安全要求高**：用 AOF（everysec），最多丢 1 秒数据
- **追求恢复速度**：用 RDB，恢复远快于 AOF
- **最佳实践**：两者同时开启，AOF 保证数据安全，RDB 用于备份和快速恢复
- **Redis 4.0+**：推荐开启混合持久化

### Q: RDB 的 bgsave 是怎么工作的？

1. 主进程调用 fork() 创建子进程
2. 子进程利用 COW（写时复制）机制读取 fork 时的内存快照
3. 子进程将数据写入临时 RDB 文件
4. 写完后替换旧的 dump.rdb 文件
5. 主进程在此期间继续处理请求，修改的内存页会复制一份

### Q: AOF 的 everysec 模式会丢数据吗？

极端情况下会。everysec 模式每秒 fsync 一次，如果 Redis 在两次 fsync 之间宕机，最多丢失 1 秒的数据。

## 一句话总结

Redis 持久化有 RDB（快照，恢复快但可能丢数据）和 AOF（追加日志，数据安全但恢复慢），Redis 4.0+ 推荐混合持久化兼顾两者优势；生产环境建议同时开启 RDB 和 AOF，AOF 保证数据安全，RDB 用于备份和快速恢复。
