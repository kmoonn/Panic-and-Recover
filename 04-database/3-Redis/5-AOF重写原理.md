# AOF 重写原理

## Q：为什么需要 AOF 重写？

AOF(Append Only File) 持久化通过追加写命令来记录数据状态。随着时间推移：

```
# AOF 文件内容（未重写）
SET counter 1
INCR counter        → counter=2
INCR counter        → counter=3
INCR counter        → counter=4
DEL temp_key
SET name "张三"
SET name "李四"      → 最终 name="李四"
```

- 文件越来越大，占用磁盘空间
- 恢复时需要逐条执行所有命令，恢复速度慢
- 实际上很多命令是冗余的（如对同一 key 的多次 SET 只需保留最后一次）

**AOF 重写就是压缩 AOF 文件，用最少的命令记录当前数据库状态。**

---

## Q：AOF 重写的原理？

AOF 重写**不是读取旧的 AOF 文件来分析压缩**，而是**直接读取当前数据库状态**，用一条命令代替多条历史命令。

### 对比

```
旧 AOF（6条命令）：           重写后（2条命令）：
SET counter 1                 SET counter 4
INCR counter                  SET name "李四"
INCR counter
INCR counter
SET name "张三"
SET name "李四"
```

### 原理

1. 主进程 fork 子进程
2. 子进程遍历当前数据库中的每个 key
3. 根据 key 的类型和当前值，生成一条写入命令
4. 将命令写入新的 AOF 文件

> 对于集合类数据（如 Hash 有很多字段），为避免单条命令过大，会拆分为多条命令（每条最多 64 个元素）。

## Q：AOF 重写的详细流程？

```
                    ┌──────────────────────────┐
                    │  主进程接收到 BGREWRITEAOF  │
                    │  或触发自动重写             │
                    └────────────┬─────────────┘
                                 │
                    ┌────────────▼─────────────┐
                    │  fork 子进程               │
                    │  子进程继承数据库快照        │
                    └────────────┬─────────────┘
                                 │
                 ┌───────────────┴───────────────┐
                 │                               │
        ┌────────▼────────┐            ┌─────────▼─────────┐
        │  子进程           │            │  主进程继续处理      │
        │  遍历数据库生成   │            │  新的写命令：        │
        │  新 AOF 文件      │            │  1. 写入旧 AOF      │
        │                   │            │  2. 写入 AOF 重写    │
        │                   │            │     缓冲区          │
        └────────┬─────────┘            └─────────┬──────────┘
                 │                                   │
        ┌────────▼─────────┐                        │
        │  子进程完成重写    │                        │
        │  通知主进程        │                        │
        └────────┬─────────┘                        │
                 │                                   │
                 └───────────────┬───────────────────┘
                                 │
                    ┌────────────▼─────────────┐
                    │  主进程将 AOF 重写缓冲区    │
                    │  中的命令追加到新 AOF 文件  │
                    └────────────┬─────────────┘
                                 │
                    ┌────────────▼─────────────┐
                    │  用新 AOF 文件替换旧 AOF   │
                    └──────────────────────────┘
```

### 关键步骤说明

1. **fork 子进程**：利用写时复制(COW)，子进程获取 fork 时刻的数据库快照
2. **子进程重写**：遍历快照数据，生成新 AOF 文件（此时主进程不阻塞）
3. **主进程继续服务**：新写命令同时写入旧 AOF 和 AOF 重写缓冲区
4. **子进程完成**：主进程将重写缓冲区追加到新 AOF 文件
5. **原子替换**：用新 AOF 文件替换旧 AOF 文件（rename 系统调用，原子操作）

---

## Q：AOF 重写期间的写入不会丢失？

不会丢失，原因：

1. fork 时的数据：子进程通过 COW 获取了 fork 时刻的完整快照
2. fork 后的新写入：
   - 主进程将新写命令写入**旧 AOF 文件**（保证崩溃恢复安全）
   - 同时写入**AOF 重写缓冲区**（保证这些命令最终进入新 AOF）
3. 子进程完成后，主进程将重写缓冲区追加到新 AOF
4. 最终新 AOF = fork 时刻的数据快照 + fork 后的新写入

> 任何一个时刻的写入，要么在旧 AOF 中，要么在新 AOF 中，不会丢失。

## Q：AOF 重写的触发方式？

### 手动触发

```bash
BGREWRITEAOF    # 后台异步重写，不阻塞主进程
```

### 自动触发

由 `redis.conf` 中两个参数控制：

| 参数 | 默认值 | 说明 |
|---|---|---|
| `auto-aof-rewrite-percentage` | 100 | AOF 文件大小比上次重写后增长的百分比 |
| `auto-aof-rewrite-min-size` | 64MB | AOF 文件最小大小，低于此值不触发重写 |

触发条件：**AOF 文件大小 >= auto-aof-rewrite-min-size 且 增长率 >= auto-aof-rewrite-percentage**

```
示例：
上次重写后 AOF 大小 = 100MB
当前 AOF 大小 = 220MB
增长率 = (220 - 100) / 100 = 120% > 100%
且 220MB > 64MB
→ 触发自动重写
```

## Q：AOF 重写的注意事项？

### fork 的 COW 开销

- fork 子进程时，操作系统通过 COW(Copy-On-Write) 机制共享内存页
- 重写期间主进程的写操作会触发页复制，占用额外内存
- 如果 Redis 占用内存很大（如 10GB），fork 可能很慢，且 COW 可能占用大量内存
- 建议：单实例 Redis 内存不超过 10GB，避免 fork 开销过大

### 重写期间的性能

- fork 本身是一个耗时操作（与内存大小相关）
- 子进程写新 AOF 文件会消耗磁盘 IO
- 主进程同时写旧 AOF 和重写缓冲区，IO 负载增加

> 一句话总结：AOF 重写通过 fork 子进程直接读取当前数据库状态来生成压缩后的新 AOF 文件，重写期间主进程的新写入同时记录到旧 AOF 和重写缓冲区，子进程完成后将缓冲区追加到新 AOF 再原子替换，保证数据不丢失。
