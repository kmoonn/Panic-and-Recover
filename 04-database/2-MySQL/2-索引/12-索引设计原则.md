# 索引设计原则

## Q: 什么样的索引才是好的索引？

一个“好索引”不是建得越多越好，而是要满足三个目标：

1. **让高频查询更快**
2. **让排序、分页、分组更稳定**
3. **不要给写入和维护带来过高成本**

所以判断一个索引好不好，核心看的是：**命中率、选择性、查询收益、维护成本、是否贴合真实业务 SQL**。

---

## 一、索引设计的核心原则

### 1. 先看查询，再建索引

索引一定要围绕真实 SQL 来设计，而不是凭感觉建。

错误做法：
- 每个字段都加索引
- 看到慢就随便补一个单列索引
- 不分析 where / order by / group by 就直接建联合索引

正确做法：
- 先看高频 SQL
- 再看过滤条件、排序条件、分页方式
- 最后确定索引列和顺序

> **口诀**：先看查询，再建索引；索引服务 SQL，不是字段摆设。

### 2. 优先给高频查询建索引

并不是所有字段都值得建索引。

适合优先建索引的字段：
- 高频 `where` 条件字段
- 高频 `join` 关联字段
- 高频 `order by` / `group by` 字段
- 业务唯一性字段

不适合优先建索引的字段：
- 很少参与查询的字段
- 只在展示中出现、从不用于过滤的字段
- 更新特别频繁但查询收益很小的字段

### 3. 选择性高的字段更适合建索引

**选择性**可以理解为：字段值能把数据区分开的能力。

例如：
- 用户 id：选择性高
- 手机号：选择性高
- 性别：选择性低
- 是否删除：选择性低

选择性越高，索引过滤效果通常越好。

```text
选择性 = 不同值个数 / 总行数
```

所以：
- 高选择性字段更适合单列索引
- 低选择性字段如果必须放进联合索引，通常不建议放在最前面

---

## 二、联合索引设计原则

### 1. 最左前缀原则

联合索引 `(a, b, c)` 能命中的前提是从最左边开始使用。

可命中：
- `where a = ?`
- `where a = ? and b = ?`
- `where a = ? and b = ? and c = ?`

不能充分命中：
- `where b = ?`
- `where c = ?`
- 跳过最左列直接用后面的列

所以联合索引列顺序非常重要。

### 2. 等值条件在前，范围条件在后

这是非常高频的面试点。

例如 SQL：

```sql
select * from orders
where user_id = 1001
  and status = 1
  and create_time > '2026-01-01'
order by create_time desc;
```

更合理的联合索引往往是：

```sql
(user_id, status, create_time)
```

原因：
- `user_id`、`status` 是等值过滤
- `create_time` 是范围查询
- 范围列后面的索引利用率通常会下降

### 3. 排序字段要和过滤字段协同设计

如果 SQL 里既有过滤又有排序，就要一起考虑。

例如：

```sql
select * from orders
where user_id = ?
order by create_time desc
limit 20;
```

适合的索引：

```sql
(user_id, create_time)
```

这样既能过滤，又有机会避免 `filesort`。

### 4. 分页场景要特别重视索引顺序

深分页常见问题：

```sql
select * from orders
order by create_time desc
limit 100000, 20;
```

如果没有合适索引，MySQL 需要扫描大量数据再丢弃。

优化思路：
- 排序字段上有索引
- 优先用“条件分页/游标分页/主键分页”替代深分页
- 联合索引优先覆盖过滤条件 + 排序字段

## 三、覆盖索引意识

### 什么是覆盖索引

查询所需的列都能直接从索引里拿到，不需要回表。

例如：

```sql
select user_id, status
from orders
where user_id = 1001;
```

如果索引就是 `(user_id, status)`，就可能直接走覆盖索引。

### 为什么覆盖索引好

好处：
- 减少回表
- 减少随机 IO
- 提升查询速度

所以设计索引时，要有意识地思考：
- 这个高频查询能不能变成覆盖索引
- 能不能避免 `select *`

> **经验**：好索引不只是“能命中”，还要尽量“少回表”。

---

## 四、避免冗余索引和重复索引

### 冗余索引

例如已经有：

```sql
(a, b, c)
```

通常再建：

```sql
(a)
```

很多场景就是冗余的，因为最左前缀已经能覆盖。

### 重复索引

例如：

```sql
index idx_user_id (user_id)
index idx_user_id2 (user_id)
```

这就是重复索引。

### 为什么要避免

索引不是免费的，代价包括：
- 占磁盘空间
- 插入变慢
- 更新变慢
- 删除变慢
- 优化器选择更复杂

所以：
- 索引数量不是越多越好
- 一个字段被多个相似索引重复覆盖，要及时清理

## 五、哪些字段要慎建索引

| 字段类型 | 原因 |
|---------|------|
| **低区分度字段** | 如性别、布尔标志，过滤能力差 |
| **更新频繁字段** | 每次更新都要维护索引，写入成本高 |
| **长文本字段** | 索引占用大，维护成本高 |
| **很少查询的字段** | 查询收益不明显 |
| **函数计算后才参与查询的字段** | 容易导致索引失效 |

如果确实要查长文本，通常考虑：
- 前缀索引
- 倒排索引/搜索引擎
- 把检索型需求交给 Elasticsearch 等系统

## 六、好索引的判断标准

可以从这 6 个维度判断一个索引是不是“好索引”。

| 判断维度 | 好索引的表现 |
|---------|-------------|
| **是否命中高频 SQL** | 高频查询能稳定使用到它 |
| **过滤效果是否好** | 扫描行数明显下降 |
| **是否帮助排序/分页/分组** | 避免 `filesort`、`temporary` |
| **是否减少回表** | 能形成覆盖索引或减少随机 IO |
| **维护成本是否可接受** | 不会明显拖慢写入 |
| **是否冗余** | 不和其他索引重复、冲突 |

---

## 七、结合 EXPLAIN 判断索引好不好

索引不是建完就算完，要结合 `EXPLAIN` 看效果。

重点看这些字段：

| 字段 | 关注点 |
|------|--------|
| `type` | 至少不要是 `ALL` |
| `key` | 是否真的用了你设计的索引 |
| `rows` | 扫描行数是否明显下降 |
| `Extra` | 是否出现 `Using filesort`、`Using temporary` |

如果一个索引建了以后：
- `key` 没用到
- `rows` 还是很大
- 还在 `filesort`

那它大概率不是一个“好索引”。

---

## 八、面试回答模板

> 我理解的好索引，不是建得多，而是能真正服务高频 SQL。设计时我会先看真实查询，再决定索引列；高选择性字段优先，联合索引遵循最左前缀，一般等值条件在前、范围条件在后；如果 SQL 里有排序和分页，还要把 `order by` 一起考虑，尽量避免 `filesort`。另外我会关注覆盖索引，尽量减少回表。最后还要避免冗余索引和低区分度字段乱建索引，因为索引本身也会增加写入成本。建完以后要结合 `EXPLAIN` 看 `key`、`rows` 和 `Extra`，验证它是不是真的带来了收益。

## 一句话总结

> 好索引的本质是：围绕高频 SQL 设计，优先高选择性字段，联合索引遵循最左前缀和“等值在前、范围在后”，尽量兼顾排序分页与覆盖索引，同时避免冗余索引和高维护成本。
