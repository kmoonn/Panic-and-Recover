# B+树

## Q：B+树的结构特点？

B+树是 B-Tree 的变体，是 MySQL InnoDB 引擎索引的**核心数据结构**。

### 核心特点

1. **非叶子节点只存键值（索引）**，不存储数据，仅用于索引路由
2. **所有数据都存在叶子节点**，非叶子节点只起"目录"作用
3. **叶子节点形成有序双向链表**，支持高效的范围查询和顺序遍历
4. **每个节点对应一个页(Page)**，InnoDB 默认页大小 16KB
5. **树的层级低**，通常 3~4 层即可存储千万级数据

### 结构图示

```
            [30|60]                 ← 非叶子节点（只存键值）
           /   |    \
      [10|20] [40|50] [70|80|90]   ← 非叶子节点（只存键值）
      /   \    /   \    /  |  \
   [数据]↔[数据]↔[数据]↔[数据]↔[数据]↔[数据]  ← 叶子节点（存数据+双向链表）
```

## Q：B+树与 B-Tree 的对比？

| 对比维度 | B-Tree | B+树 |
|---|---|---|
| **节点数据位置** | 每个节点都存键值+数据 | 非叶子节点只存键值，数据只在叶子节点 |
| **范围查询** | 需要中序遍历整棵树 | 叶子节点有链表，直接沿链表顺序遍历 |
| **树的高度** | 相对较高（节点存数据，单页存放的键更少） | 更矮（非叶子节点不存数据，单页存放更多键） |
| **磁盘 IO 次数** | 较多 | 较少（树更矮） |
| **查询稳定性** | 数据可能在非叶子节点命中，路径长度不等 | 所有查询都走到叶子节点，路径长度相同 |
| **全表扫描** | 需遍历所有节点 | 只需遍历叶子链表 |
| **叶节点链表** | 无 | 有双向链表 |

## Q：为什么 MySQL 用 B+树而不用 B-树？

### 1. 范围查询友好

- 数据库中范围查询（`WHERE id BETWEEN 10 AND 100`）非常频繁
- B+树叶子节点有双向链表，范围查询只需定位起点后沿链表遍历
- B-树需要中序遍历，每一步都可能涉及磁盘 IO

### 2. IO 次数更少

- 非叶子节点不存数据，单个页能容纳更多键值
- 以 16KB 页为例：若键+指针占 12 字节，一个页可容纳约 1365 个指针
- 3 层 B+树可存储：1365 * 1365 * 16 ≈ **2980 万条记录**
- 同等层数 B-树因节点存数据，能容纳的键远少于此

### 3. 查询性能稳定

- B+树所有数据都在叶子层，每次查询都要走到叶子，路径长度相同
- B-树数据可能在中间节点就命中，查询时间不稳定

## Q：B+树与 Hash 索引的对比？

| 对比维度 | B+树 | Hash 索引 |
|---|---|---|
| **等值查询** | O(log n) | O(1)，更快 |
| **范围查询** | 支持（链表遍历） | 不支持 |
| **排序** | 支持（有序） | 不支持（Hash 无序） |
| **最左前缀匹配** | 支持 | 不支持 |
| **模糊查询** | 支持（LIKE 'abc%'） | 不支持 |
| **存储** | 有序存储 | 无序存储 |
| **适用场景** | 通用场景 | 仅等值查询（如 Memory 引擎） |

> InnoDB 的自适应哈希索引(AHI)是对 B+树的补充，对频繁查询的页自动建 Hash 索引。

## Q：为什么不用红黑树或跳表？

### vs 红黑树

| 对比维度 | B+树 | 红黑树 |
|---|---|---|
| **树的高度** | 3~4 层（百万/千万级数据） | 可能 20+ 层（二叉树，高度 = log₂n） |
| **磁盘 IO** | 3~4 次 | 20+ 次 |
| **数据局部性** | 节点大小=页大小，一次 IO 读一页 | 节点小且分散，一次 IO 一个节点 |
| **适用存储** | 磁盘 | 内存 |

红黑树是二叉树，在数据量大时树高过大，每层可能产生一次磁盘 IO，性能不可接受。

### vs 跳表

| 对比维度 | B+树 | 跳表 |
|---|---|---|
| **查询复杂度** | O(log n)，稳定 | O(log n)，概率性 |
| **磁盘友好度** | 节点=页，IO 高效 | 节点小且分散，IO 不友好 |
| **实现复杂度** | 较复杂 | 简单 |
| **适用场景** | 磁盘存储 | 内存存储（Redis ZSet 用跳表） |

跳表适合内存场景（如 Redis），但节点分散不利用磁盘顺序读取，不适合磁盘索引。

## Q：B+树在 InnoDB 中的体现？

### 页(Page)结构

InnoDB 中 B+树的每个节点就是一个**页**，默认大小 16KB：

```
┌─────────────────────────────────────────┐
│              页结构 (16KB)                │
├─────────────────────────────────────────┤
│  File Header（页头信息：页号、前后页指针）  │
├─────────────────────────────────────────┤
│  Page Header（页内状态：记录数、槽位数等） │
├─────────────────────────────────────────┤
│  Infimum + Supremum（最小/最大虚拟记录）   │
├─────────────────────────────────────────┤
│  User Records（用户数据记录，有序排列）     │
├─────────────────────────────────────────┤
│  Free Space（空闲空间）                    │
├─────────────────────────────────────────┤
│  Page Directory（页目录，二分查找加速）     │
├─────────────────────────────────────────┤
│  File Trailer（校验信息）                  │
└─────────────────────────────────────────┘
```

### 页目录(Page Directory)

- 将页内的记录分组，每组最后一条记录的地址偏移量存入页目录
- 查找时先在页目录中**二分查找**定位到组，再在组内**线性查找**
- 将页内查找从 O(n) 优化到 O(log n)

### 页间双向链表

- 每个页的 File Header 中存有 `FIL_PAGE_PREV` 和 `FIL_PAGE_NEXT`
- 同一层的相邻页通过双向链表连接
- 叶子层的双向链表支撑范围查询和顺序扫描

### 查找过程

1. 从根页开始，在页目录中二分查找定位到具体记录
2. 比较键值，决定进入哪个子页（通过记录中的页指针）
3. 重复上述过程直到叶子页
4. 在叶子页中找到目标数据或沿链表继续遍历

> 一句话总结：B+树是 MySQL 索引的核心数据结构，非叶子节点只存键值、叶子节点存数据并形成双向链表，相比 B-树有更少的磁盘 IO、更好的范围查询支持和更稳定的查询性能，3~4 层即可存储千万级数据。
