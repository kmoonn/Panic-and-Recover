# EXPLAIN

## Q: MySQL 的 `EXPLAIN` 是什么？面试里应该怎么看？

`EXPLAIN` 是 MySQL 优化 SQL 的核心命令，用来查看一条 SQL 的**执行计划**。

它回答的不是“SQL 语法对不对”，而是：
- 会先查哪张表
- 会不会走索引
- 预计扫多少行
- 有没有额外排序
- 有没有临时表

所以面试里如果被问到 `EXPLAIN`，重点不是把所有字段死背下来，而是要能说出：**我会用哪些字段快速判断这条 SQL 好不好，慢在哪里，应该往哪个方向优化。**

---

## 一、先记结论：看 `EXPLAIN` 的固定顺序

面试里最实用的回答顺序是：

```text
先看 type
再看 key
再看 rows
最后看 Extra
```

原因：
- `type` 决定访问方式，最能说明是不是全表扫描
- `key` 决定有没有真正命中索引
- `rows` 决定扫描量大不大
- `Extra` 决定有没有额外排序、临时表、覆盖索引等信息

如果只能记四个字段，就记这四个。

---

## 二、EXPLAIN 常见字段

| 字段 | 含义 | 面试关注点 |
|------|------|-----------|
| `id` | 查询执行顺序编号 | 看子查询、联合查询的执行顺序 |
| `select_type` | 查询类型 | 区分简单查询、子查询、派生表、UNION |
| `table` | 当前访问的表 | 看多表 join 时每一步查哪张表 |
| `type` | 访问类型 | 核心字段，判断是否全表扫描 |
| `possible_keys` | 可能使用的索引 | 候选索引 |
| `key` | 实际使用的索引 | 是否真的命中了期望索引 |
| `key_len` | 使用的索引长度 | 判断联合索引利用是否充分 |
| `ref` | 索引匹配对象 | 常量还是某列 |
| `rows` | 预估扫描行数 | 越小越好 |
| `filtered` | 过滤比例 | 过滤效果参考 |
| `Extra` | 补充信息 | 看覆盖索引、排序、临时表等 |

---

## 三、重点字段详解

## 1. `type` —— 访问类型，最先看

`type` 表示 MySQL 访问表的方式，性能通常从好到差大致是：

```text
system > const > eq_ref > ref > range > index > ALL
```

### 常见取值解释

| type | 含义 | 说明 |
|------|------|------|
| `const` / `system` | 常量级访问 | 主键或唯一索引精确命中，通常最好 |
| `eq_ref` | 唯一索引关联 | 多表 join 时按主键/唯一键匹配 |
| `ref` | 普通索引等值匹配 | 常见且不错 |
| `range` | 范围查询 | 如 `> < between in` |
| `index` | 全索引扫描 | 比 `ALL` 好，但通常还不理想 |
| `ALL` | 全表扫描 | 最差，优先优化 |

### 面试回答重点

> 我看 `EXPLAIN` 会先看 `type`，因为它最直接反映访问方式。如果是 `ALL`，说明全表扫描，一般就是高风险 SQL；至少希望到 `range`，更理想是 `ref` 或更好。

---

## 2. `key` —— 实际使用的索引

`possible_keys` 只是“可能会用”，`key` 才是“实际用了哪个索引”。

### 重点判断

- `key = NULL`：没走索引
- `key = 某索引名`：说明命中了这个索引

### 面试回答重点

> `possible_keys` 只是候选，不代表真的用到；真正判断索引是否生效，要看 `key`。如果 `key` 是 NULL，说明没走索引，通常就要继续排查索引失效、条件设计或者数据分布问题。

---

## 3. `rows` —— 预估扫描行数

`rows` 表示 MySQL 估算这条 SQL 需要扫描多少行数据。

### 怎么看

- 数值越小越好
- 如果查询结果只要几十条，但 `rows` 很大，说明过滤效率不高
- 即使走了索引，`rows` 很大也不代表真的快

### 面试回答重点

> 一条 SQL 好不好，不只是看有没有走索引，还要看扫描量大不大。`rows` 很大说明虽然可能用了索引，但过滤效果不好，仍然可能慢。

---

## 4. `Extra` —— 额外优化信号

`Extra` 是非常有价值的补充信息。

### 常见取值

| Extra | 含义 | 面试判断 |
|-------|------|----------|
| `Using index` | 使用覆盖索引 | 好信号，通常表示不需要回表 |
| `Using where` | 结果还需要继续过滤 | 常见，不一定有问题 |
| `Using filesort` | 额外排序 | 风险较高，说明没用上索引排序 |
| `Using temporary` | 使用临时表 | 风险较高，常见于不合理的 `group by` / `order by` |
| `Using join buffer` | join 未充分利用索引 | 关联查询性能风险 |

### 重点理解

#### `Using index`
通常是好事，说明查询列都能从索引里拿到，形成覆盖索引。

#### `Using filesort`
不是说真的用文件排序，而是 MySQL 做了额外排序操作，通常说明：
- `order by` 没走索引
- 排序字段和过滤字段的联合索引没设计好

#### `Using temporary`
通常说明：
- `group by`
- `distinct`
- 排序分组逻辑不够友好

面试里如果看到 `filesort` 或 `temporary`，一般要往：
- 索引设计
- 排序字段顺序
- SQL 改写

这些方向回答。

## 四、其他常见字段怎么理解

### `id`

- `id` 越大，通常越先执行
- `id` 相同，通常按从上到下顺序执行
- 多层子查询、多表关联时很有用

### `select_type`

常见值：
- `SIMPLE`：简单查询
- `SUBQUERY`：子查询
- `DERIVED`：派生表，通常是 `from` 中的子查询
- `UNION`：联合查询

面试里主要用它判断：这条 SQL 是否复杂，有没有子查询、临时派生结果。

### `key_len`

`key_len` 表示索引使用长度。

作用：
- 判断联合索引是否被充分利用
- 判断只用到了联合索引前几列，还是更多列

### `ref`

表示索引列和谁做比较：
- 常量 `const`
- 某张表的某一列

多表关联时可以帮助判断 join 方式。

## 五、怎么用 EXPLAIN 判断 SQL 好坏

可以直接按下面这套标准判断：

| 判断点 | 理想状态 |
|-------|----------|
| `type` | 不要是 `ALL`，最好 `range/ref` 及以上 |
| `key` | 不为 `NULL` |
| `rows` | 越小越好 |
| `Extra` | 尽量有 `Using index`，避免 `Using filesort`、`Using temporary` |

### 一套面试常用话术

> 我一般会先看 `type`，避免全表扫描；再看 `key` 确认是否真正命中索引；然后看 `rows` 判断扫描量；最后看 `Extra`，重点关注有没有 `Using filesort` 和 `Using temporary`。如果这几个字段都比较健康，这条 SQL 通常不会太差。

## 六、一个简单例子

```sql
EXPLAIN
SELECT user_id, status
FROM orders
WHERE user_id = 1001
ORDER BY create_time DESC
LIMIT 20;
```

假设结果里看到：

- `type = ref`
- `key = idx_user_id_create_time`
- `rows = 20`
- `Extra = Using index`

说明：
- 走了索引
- 扫描量不大
- 可能形成覆盖索引
- 排序也比较友好

如果结果变成：

- `type = ALL`
- `key = NULL`
- `rows = 1000000`
- `Extra = Using filesort`

那就说明：
- 全表扫描
- 没用索引
- 扫描量很大
- 还做了额外排序

这是典型需要优化的 SQL。

## 七、面试高频追问

### 1. `possible_keys` 和 `key` 的区别？

- `possible_keys`：理论上可能使用的索引
- `key`：实际使用的索引

所以真正判断是否走索引，看 `key`。

### 2. `Using filesort` 一定很差吗？

不一定绝对差，但通常说明排序没借助索引完成。数据量小时问题可能不大，数据量一大就容易成为瓶颈。

### 3. `rows` 是真实值吗？

不是，是优化器估算值，但非常有参考意义。

### 4. `type = index` 和 `type = ALL` 区别？

- `index`：扫描整棵索引树
- `ALL`：扫描整张表

`index` 一般比 `ALL` 好，但仍然不代表足够优秀。

---

## 八、面试回答模板

> `EXPLAIN` 是我分析 SQL 执行计划最常用的工具。面试里我会重点看四个字段：先看 `type`，判断是不是全表扫描；再看 `key`，确认有没有真正命中索引；然后看 `rows`，判断扫描量大不大；最后看 `Extra`，重点关注 `Using index`、`Using filesort` 和 `Using temporary`。如果 `type` 是 `ALL`、`key` 是 NULL、`rows` 很大，或者 `Extra` 出现 `filesort`、`temporary`，我就会继续从索引设计、SQL 改写、排序分页优化这些方向排查。

## 一句话总结

> `EXPLAIN` 的核心不是背字段，而是形成固定分析顺序：先看 `type`，再看 `key`，再看 `rows`，最后看 `Extra`，从而快速判断 SQL 是否走索引、扫描量是否过大，以及有没有额外排序或临时表风险。
