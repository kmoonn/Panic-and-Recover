# 生产者-消费者模式

## 什么是生产者-消费者模式？

生产者-消费者模式（Producer-Consumer Pattern）通过一个缓冲区（队列）解耦生产者和消费者。生产者将数据放入缓冲区，消费者从缓冲区取出数据处理，二者不直接交互。

**核心思想**：用队列作为缓冲区，将"生产数据"与"消费数据"解耦。

```
Producer → [Buffer/Queue] → Consumer
```

| 组件 | 职责 |
|------|------|
| 生产者（Producer） | 产生数据，放入缓冲区 |
| 缓冲区（Buffer/Queue） | 存储数据的队列，解耦生产与消费 |
| 消费者（Consumer） | 从缓冲区取出数据并处理 |

---

## 解决的问题

| 问题 | 说明 | 示例 |
|------|------|------|
| **解耦** | 生产者和消费者不直接依赖，各自独立变化 | 订单系统与库存系统 |
| **异步** | 生产者无需等消费者处理完，放入队列即返回 | 异步发邮件、发短信 |
| **削峰** | 突发大量请求时缓冲区吸收峰值，消费者按自身速率消费 | 秒杀请求写入队列，后端逐步消费 |

---

## Java 实现方式

| 方式 | 说明 | 推荐度 |
|------|------|--------|
| wait/notify + synchronized | 最基础，手动控制等待与通知，必须用 `while` 防虚假唤醒 | 理解用 |
| **BlockingQueue** | 内部已实现等待/通知，无需手动同步 | **✅ 推荐** |
| Lock + Condition | 比 synchronized 更灵活，支持多条件变量精确唤醒 | 高级场景 |
| Disruptor | 无锁环形缓冲区，CAS 保证线程安全，预分配内存避免 GC | 超低延迟场景 |

### 常用 BlockingQueue

| 阻塞队列 | 特点 |
|---------|------|
| `ArrayBlockingQueue` | 有界，底层数组，创建时指定容量 |
| `LinkedBlockingQueue` | 可有界可无界，底层链表 |
| `PriorityBlockingQueue` | 无界，按优先级排序 |
| `SynchronousQueue` | 容量为 0，生产者直接交付给消费者 |

### wait/notify 为什么必须用 while 不能用 if？

虚假唤醒（Spurious Wakeup）——线程可能在没有收到 notify 的情况下被唤醒。用 `if` 判断会导致条件不满足时继续执行出错，用 `while` 会重新检查条件，安全。

## 面试高频

### 生产者-消费者模式与消息队列的关系

| 维度 | 生产者-消费者模式 | 消息队列 |
|------|-----------------|---------|
| 范围 | 进程内线程间通信 | 分布式系统间通信 |
| 存储 | 内存队列 | 持久化存储（磁盘） |
| 可靠性 | 进程崩溃数据丢失 | 持久化保证不丢消息 |
| 典型实现 | BlockingQueue | Kafka / RabbitMQ / RocketMQ |

**关系**：消息队列是生产者-消费者模式在分布式场景的扩展实现。

### 缓冲区满了怎么办

| 策略 | 说明 | 适用场景 |
|------|------|---------|
| 阻塞等待 | 生产者阻塞直到有空间 | 不允许丢数据 |
| 丢弃数据 | 直接丢弃新数据或旧数据 | 实时性优先（如监控日志） |
| 扩容 | 动态增加缓冲区容量 | 内存充足 |
| 降级 | 拒绝请求并返回错误 | 保护系统（如限流） |

### 与观察者模式的区别

| 维度 | 生产者-消费者模式 | 观察者模式 |
|------|-----------------|-----------|
| 核心目的 | 解耦生产与消费的**速率** | 一对多通知**状态变化** |
| 中间件 | 有缓冲区（队列） | 无缓冲区，直接通知 |
| 耦合度 | 生产者和消费者完全不知道对方 | Subject 知道所有 Observer |
| 数据处理 | 消费者主动拉取 | 观察者被动接收通知 |

---

## 一句话总结

生产者-消费者模式通过缓冲区解耦生产与消费，解决解耦、异步、削峰三大问题，Java 推荐用 BlockingQueue 实现，消息队列是其分布式场景的扩展，与观察者模式的本质区别在于有缓冲区和速率解耦。

## 八股速记

**问：生产者-消费者模式（阻塞队列 / 线程池）？**

> 这是简历设计模式行明确列出的一项，且极高频（几乎必考并发），务必能讲清。

- **定义**：生产者产出数据放进**共享缓冲区（队列）**，消费者从队列取出处理，**两者不直接通信、靠队列解耦**——一种经典的并发协作模式。
- **为什么用**：① **解耦**：生产/消费速率不同也能各干各的；② **削峰/缓冲**：突发流量先入队，消费者匀速处理；③ **复用线程**：配合线程池，避免频繁创建销毁线程。
- **核心机制（关键）**：缓冲区用**阻塞队列（BlockingQueue）**——队列**满时生产者阻塞**、**空时消费者阻塞**，由队列内部帮你处理好线程等待/唤醒，不用自己写 `wait/notify`。
- **Java 落地**：`BlockingQueue`（`ArrayBlockingQueue`/`LinkedBlockingQueue`）+ 线程池（`ThreadPoolExecutor` 内部就是"任务队列 + 工作线程"的生产者-消费者）。**Python 落地**：`queue.Queue`（线程）/ `asyncio.Queue`（协程）。

**⭐ 加分/易错**：
- **本质是"用队列解耦 + 用阻塞处理协调"**。手写版容易踩坑（`wait` 要放 `while` 循环里防**虚假唤醒**、要在同步块里 `notify`），所以生产上**直接用 BlockingQueue** 更稳——能说出这点是加分。
- 和**观察者模式/MQ 区分**：观察者是同步"一变全知"；MQ 是**跨进程/分布式**的生产者-消费者进阶版；本模式指**进程内多线程**协作。三者是"同一思想、不同尺度"。
- **线程池参数**呼应：核心/最大线程数、队列容量、拒绝策略——本质就是在调这个"生产者-消费者"系统的缓冲与背压（可交叉回线程 / Spring）。
