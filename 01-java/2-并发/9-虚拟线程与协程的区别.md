# 虚拟线程与协程的区别

## 协程是什么

协程是**用户态的暂停/恢复机制**，由协程库或语言运行时调度，而不是操作系统调度。程序自己决定什么时候暂停、什么时候继续。

**没有内核态切换**，成本极低，一个进程里可以跑成千上万个协程。但它**不能抢占 CPU**，如果一个协程不主动让出执行权，别人就只能干瞪眼。所以协程非常适合 **I/O 密集型**任务，不适合纯计算。

典型实现：Go goroutine、Python asyncio、Kotlin coroutine、C++20 co_await。

```kotlin
// Kotlin 协程
launch {
    val data = fetchData()  // 暂停点（suspend point）
    show(data)              // 恢复后继续
}
```

## 虚拟线程是什么

虚拟线程（Virtual Thread）是 Java 21 (Project Loom) 引入的**轻量级线程**，由 JVM 而非 OS 内核调度。创建和切换开销接近协程，但 API 完全兼容传统 `Thread`。

```java
// 创建虚拟线程
Thread vt = Thread.startVirtualThread(() -> {
    System.out.println("hello from virtual thread");
});

// 或用 ExecutorService
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    executor.submit(() -> fetchFromDB());
    executor.submit(() -> callRemoteAPI());
}
```

## 核心区别

| 维度 | 虚拟线程（Java Loom） | 协程（goroutine/asyncio/coroutine） |
|---|---|---|
| **抽象层级** | 线程（Thread API） | 函数级暂停/恢复（suspend function） |
| **API 兼容** | ✅ 完全兼容 Thread / Runnable / ExecutorService | ❌ 需用 `suspend`/`async`/`launch` 等新 API |
| **调度方式** | JVM 调度，IO 时自动 unmount 从载体线程剥离 | 运行时调度，suspend point 处暂停 |
| **与现有代码兼容** | ✅ 旧代码几乎不改，换 Executor 即可 | ❌ 需改写为 suspend/async 风格 |
| **调用栈** | 完整调用栈（可调试、可打印堆栈） | 无/有损调用栈（调试困难） |
| **颜色问题** | 无"函数颜色"问题（同步/异步函数签名相同） | 有"函数颜色"（suspend 函数只能被 suspend 调用） |
| **阻塞操作** | 自动处理：`BlockingOp` → unmount → 完成后 remount | 需显式用非阻塞 API（如 `aiohttp` 而非 `requests`） |
| **实现语言** | Java 21+ | Go / Kotlin / Python / Rust / C++20 |

## "函数颜色"问题

这是虚拟线程最大的优势——**消灭了函数颜色问题**：

```java
// 虚拟线程：同步写法，JVM 自动处理阻塞
String fetch() {
    return httpClient.get(url);  // 阻塞调用，JVM 自动 unmount
}

// 虚拟线程中直接调用，无需改任何代码
Thread.startVirtualThread(() -> {
    String data = fetch();  // 阻塞时自动让出载体线程
    process(data);
});
```

```kotlin
// 协程：必须用 suspend 函数，普通函数不行
suspend fun fetch(): String {
    return httpClient.get(url)  // 必须 suspend
}

// 普通函数不能调用 suspend 函数！
fun normalFunc() {
    fetch()  // ❌ 编译错误！
}
```

> **虚拟线程 = 用同步的代码写法，获得异步的性能。** 不需要 `suspend`、`async`、`await` 等关键字，也不需要将整个调用链改造为异步风格。

## 阻塞操作的处理

| | 虚拟线程 | 协程 |
|---|---|---|
| 阻塞 IO（如 `InputStream.read()`） | JVM 自动 unmount，载体线程释放 | ❌ 会阻塞整个线程，必须用非阻塞 API |
| 非阻塞 IO（如 NIO / epoll） | 也能用，但不必须 | ✅ 这才是协程的正确搭配 |
| `Thread.sleep()` | 自动 unmount | `delay()`（suspend 版） |
| `synchronized` 块 | Java 21+ 会 pin 住载体线程（不 unmount） | 不适用 |

## 性能对比

```
场景：10,000 个并发 HTTP 请求

平台线程（线程池 200）：  ~50s（线程不够，大量排队）
虚拟线程：              ~5s（每个请求一个虚拟线程，IO 时自动让出）
协程（asyncio/kotlin）：~5s（类似，但需改写为 async 风格）
```

虚拟线程和协程性能接近，但虚拟线程**不需要改代码**。

## 什么时候用虚拟线程

| 场景 | 推荐 |
|---|---|
| Java 项目，IO 密集型高并发 | ✅ 虚拟线程（改 Executor 即可，代码几乎不动） |
| 已有大量同步代码，不想改造 | ✅ 虚拟线程 |
| CPU 密集型任务 | ❌ 用平台线程 / ForkJoinPool |
| 非 Java 语言 | ❌ 用该语言的协程（goroutine/asyncio/coroutine） |
| `synchronized` 频繁的代码 | ⚠️ 会 pin 住，先用 `ReentrantLock` 替换 |

## 一句话总结

> 虚拟线程 = 用**同步代码写法**获得**异步性能**，API 兼容 Thread，消灭函数颜色问题；协程 = **显式暂停/恢复**，需要 `suspend`/`async` 改写调用链。两者性能接近，虚拟线程的代价是旧代码改动更少。
