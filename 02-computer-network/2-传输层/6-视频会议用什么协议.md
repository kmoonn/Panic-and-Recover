# 视频会议用什么协议

## Q: 视频会议为什么用 UDP 而不是 TCP？

| 对比项 | TCP | UDP |
|--------|-----|-----|
| 可靠性 | 可靠（重传丢失包） | 不可靠（不重传） |
| 延迟 | 高（丢包重传等代，累积延迟越来越大） | 低（丢包就丢，不重传） |
| 有序性 | 严格有序（前面包不到，后面包卡住） | 无序（每个包独立） |
| 拥塞控制 | 有（丢包时降速，视频会卡顿/降质） | 无（不主动降速） |
| 适合场景 | 文件传输、网页、API 请求 | 实时音视频、游戏、直播 |

### 实时音视频为什么不能容忍重传？

```
时间轴：
t=0ms   发送视频帧1
t=20ms  发送视频帧2
t=33ms  发送视频帧3
         ↓ 帧1 丢失！
t=40ms  TCP：等待重传帧1...帧2帧3都在缓冲区排队（队头阻塞！）
t=80ms  TCP：重传帧1到达 → 播放帧1 → 播放帧2 → 播放帧3
         → 用户感受到 80ms 的卡顿！

UDP：帧1丢了就丢了，继续播放帧2帧3
     → 用户看到瞬间花屏/跳帧，但整体流畅
     → 对于 30fps 视频，丢1帧只影响 33ms，人眼几乎无感
```

> **核心原则**：实时音视频中，**低延迟 > 可靠性**。晚到的帧已经"过期"了，重传毫无意义。

## Q: WebRTC 使用了哪些协议？

**WebRTC**（Web Real-Time Communication）：浏览器内置的实时音视频通信框架。

### WebRTC 协议栈

```
┌─────────────────────────────────────────┐
│          Application Layer              │
│  SDP (Session Description Protocol)     │  ← 信令（协商能力）
├─────────────────────────────────────────┤
│  DTLS (Datagram TLS)                    │  ← 加密密钥协商
├──────────┬──────────┬───────────────────┤
│  SRTP    │  SRTCP   │  SCTP/DataChannel │  ← 安全媒体 + 数据通道
├──────────┴──────────┴───────────────────┤
│  UDP                                    │  ← 传输层
├─────────────────────────────────────────┤
│  ICE / STUN / TURN                      │  ← NAT 穿透
├─────────────────────────────────────────┤
│  IP                                     │
└─────────────────────────────────────────┘
```

### 各协议职责

| 协议 | 层级 | 职责 |
|------|------|------|
| **RTP** | 应用 | 实时传输音视频数据（承载媒体流） |
| **RTCP** | 应用 | RTP 控制协议（反馈质量报告：丢包率、抖动、延迟） |
| **SRTP** | 应用 | Secure RTP = RTP + DTLS 加密（防窃听/篡改） |
| **SRTCP** | 应用 | Secure RTCP = RTCP + 加密 |
| **SCTP** | 应用 | DataChannel 数据通道（可靠/不可靠皆可的文本/文件传输） |
| **DTLS** | 安全 | 基于 UDP 的 TLS，用于 SRTP 密钥协商 |
| **ICE** | NAT穿透 | 交互式连通建立，综合 STUN/TURN 找最优路径 |
| **STUN** | NAT穿透 | 让客户端发现自己的公网 IP:Port |
| **TURN** | NAT穿透 | STUN 失败时的中继服务器（兜底） |
| **SDP** | 信令 | 描述媒体能力（编码格式、分辨率、Payload Type） |

## Q: RTP/RTCP/SRTP 分别是什么？

### RTP（Real-time Transport Protocol）

- 承载实时音视频**数据**的协议
- 基于 UDP，每个 RTP 包含：

```
┌──────────────────────────────────────────┐
│  Payload Type (7bit)  │  序列号 (16bit)  │
│  时间戳 (32bit)       │  SSRC (32bit)    │
│  Payload (音视频数据)                     │
└──────────────────────────────────────────┘
```

| 字段 | 作用 |
|------|------|
| Payload Type | 标识编码格式（如 H.264=96, Opus=111） |
| 序列号 | 检测丢包、排序（接收端用） |
| 时间戳 | 同步音视频、计算抖动 |
| SSRC | 标识媒体源（区分多路流） |

### RTCP（RTP Control Protocol）

- RTP 的**控制伴侣协议**，定期发送质量报告

| 报文类型 | 作用 |
|---------|------|
| SR（Sender Report） | 发送方报告：已发包数、字节数 |
| RR（Receiver Report） | 接收方报告：**丢包率、抖动、延迟** |
| SDES | 源描述（CNAME 等） |
| BYE | 结束会话 |

> 接收方通过 RR 反馈丢包率，发送方可据此**动态调整编码码率**（自适应码率）。

### SRTP（Secure RTP）

- RTP + 加密 + 认证
- 加密算法：AES-CTR
- 认证：HMAC-SHA1
- 密钥通过 DTLS 握手协商
- WebRTC 中**所有媒体必须走 SRTP**（强制加密）

## Q: NAT 穿透怎么解决？ICE/STUN/TURN

由于两端通常在 NAT/防火墙后面，无法直接建立 P2P 连接，需要 NAT 穿透。

### STUN（Session Traversal Utilities for NAT）

```
内网客户端 ──────► STUN 服务器 ──────► 返回公网 IP:Port

1. 客户端向 STUN 服务器发 Binding Request
2. STUN 服务器看到源地址是 NAT 映射后的公网 IP:Port
3. 返回给客户端："你的公网地址是 203.0.113.5:12345"
4. 客户端将此地址通过信令告诉对方
```

### TURN（Traversal Using Relays around NAT）

```
当对称 NAT / 防火墙阻止 P2P 时：

客户端A ◄──── TURN 中继服务器 ────► 客户端B
              所有数据经 TURN 转发

缺点：延迟增加、服务器带宽成本高
作为最后兜底方案
```

### ICE（Interactive Connectivity Establishment）

ICE 是**框架**，按优先级尝试所有候选路径：

```
ICE 候选地址类型（优先级从高到低）：
1. Host Candidate   - 本地网卡地址（同局域网直连）
2. Server Reflexive - STUN 获取的公网地址（P2P 穿 NAT）
3. Relay Candidate  - TURN 中继地址（兜底转发）

ICE 流程：
1. 收集所有候选地址
2. 通过信令交换候选地址（SDP Offer/Answer）
3. 连通性检查（逐对尝试）
4. 选择最优可用路径
```

## Q: 为什么不全部走 TCP？什么情况下会降级到 TCP？

### 理想情况：UDP 直连

```
Client A ────── UDP/SRTP ────── Client B
              低延迟、低开销
```

### 需要降级 TCP 的场景

| 场景 | 原因 | 解决方案 |
|------|------|---------|
| 企业防火墙只允许 443/TCP 出站 | UDP 被完全封锁 | TURN over TLS/TCP 中继 |
| 极严格 NAT（对称 NAT 双向） | P2P 穿透失败 | TURN 中继 |
| 代理服务器不支持 UDP | HTTP Proxy 只转 TCP | TURN TCP 中继 |

### TURN 降级流程

```
1. ICE 先尝试 UDP 直连 → 失败
2. ICE 尝试 STUN 穿 NAT → 失败
3. ICE 尝试 TURN/UDP → 失败（UDP 被封锁）
4. ICE 降级到 TURN/TCP → 成功（走 TCP 中继）
   → 延迟增加，但至少能通
```

> **代价**：TCP TURN 中继增加延迟（2次中继跳 + TCP 重传），视频质量下降，但保证可用性。

## Q: 视频会议信令用什么协议？

**信令**（Signaling）：通话建立前的"握手"过程，用于交换能力、地址、密钥。

| 方案 | 协议 | 说明 |
|------|------|------|
| **传统 VoIP** | SIP（Session Initiation Protocol） | 电信标准，复杂，适合与电话网互通 |
| **WebRTC** | 自定义（通常基于 WebSocket + JSON/SDP） | WebRTC 本身不规定信令协议，常用 WS 传 SDP |

### WebRTC 信令流程

```
Client A            信令服务器            Client B
  │                    │                    │
  │── 1. SDP Offer ──►│── 2. SDP Offer ──►│
  │                    │                    │
  │◄── 4. SDP Answer ─│◄── 3. SDP Answer ─│
  │                    │                    │
  │── 5. ICE Candidate ──►│── 6. ICE Candidate ──►│
  │◄── 8. ICE Candidate ──│◄── 7. ICE Candidate ──│
  │                    │                    │
  │═════════════ P2P SRTP 直连 ═════════════│
```

- **SDP Offer**：A 的媒体能力（编码、分辨率、ICE 候选）
- **SDP Answer**：B 的媒体能力回应
- **ICE Candidate**：双方交换网络地址，尝试连通

## Q: SCTP 和 DataChannel 是什么？

WebRTC 除了音视频（SRTP），还支持**数据通道**（DataChannel）：

| 对比项 | DataChannel (SCTP) | WebSocket |
|--------|-------------------|-----------|
| 传输层 | SCTP over DTLS over UDP | TCP |
| 延迟 | 低（UDP 基础） | 较高（TCP） |
| 可靠性 | 可配置（可靠/不可靠/部分可靠） | 可靠（TCP） |
| 有序性 | 可配置（有序/无序） | 有序 |
| 连接 | P2P 直连 | 需要经过服务器 |

```javascript
// WebRTC DataChannel 示例
const pc = new RTCPeerConnection();

// 创建数据通道
const dc = pc.createDataChannel("chat", {
    ordered: false,        // 无序交付（更低延迟）
    maxRetransmits: 0      // 不重传（类似 UDP）
});

dc.onopen = () => dc.send("Hello!");
dc.onmessage = (e) => console.log("收到:", e.data);
```

> 适用场景：实时游戏数据、文件传输、聊天消息、屏幕共享控制指令。

## 一句话总结

视频会议用 UDP 传输音视频因为低延迟优先于可靠性（晚到的帧已过期），WebRTC 协议栈用 UDP + SRTP（加密媒体）+ SCTP（数据通道）+ DTLS（密钥协商）+ ICE/STUN/TURN（NAT 穿透），防火墙封锁 UDP 时降级走 TURN over TCP 中继（牺牲延迟保可用），信令通常用 WebSocket 交换 SDP 完成能力协商和连接建立。
