# 触发器

## Q：什么是触发器？

触发器(Trigger)是一种**与表关联的特殊存储过程**，当对表执行特定的 INSERT / UPDATE / DELETE 操作时，触发器会自动执行，无需手动调用。

- 由事件驱动，不能被显式调用
- 与某张表绑定，只有对该表执行指定操作时才会触发
- 可用于数据校验、审计日志、级联更新等

---

## Q：触发时机与触发事件？

### 触发时机

| 时机 | 说明 |
|---|---|
| `BEFORE` | 在触发事件**之前**执行（可用于数据校验、修改新值） |
| `AFTER` | 在触发事件**之后**执行（可用于审计日志、级联操作） |

### 触发事件

| 事件 | 说明 |
|---|---|
| `INSERT` | 插入数据时触发 |
| `UPDATE` | 更新数据时触发 |
| `DELETE` | 删除数据时触发 |

组合后共有 6 种触发器：BEFORE INSERT、AFTER INSERT、BEFORE UPDATE、AFTER UPDATE、BEFORE DELETE、AFTER DELETE。

---

## Q：NEW 和 OLD 关键字是什么？

在触发器内部，可以通过 `NEW` 和 `OLD` 访问行数据：

| 关键字 | INSERT | UPDATE | DELETE |
|---|---|---|---|
| `NEW` | 新插入的行数据（可修改） | 修改后的行数据（BEFORE 中可修改） | 不可用 |
| `OLD` | 不可用 | 修改前的行数据（只读） | 被删除的行数据（只读） |

- **BEFORE 触发器中**可以修改 `NEW` 的值（如自动填充创建时间）
- **AFTER 触发器中**`NEW` 和 `OLD` 均为只读

---

## Q：创建触发器的语法？

```sql
CREATE TRIGGER trigger_name
{BEFORE | AFTER} {INSERT | UPDATE | DELETE}
ON table_name
FOR EACH ROW
BEGIN
    -- 触发逻辑
END;
```

### 示例：插入前自动填充创建时间

```sql
DELIMITER //

CREATE TRIGGER before_user_insert
BEFORE INSERT ON users
FOR EACH ROW
BEGIN
    SET NEW.create_time = NOW();
END //

DELIMITER ;
```

### 示例：删除后记录审计日志

```sql
DELIMITER //

CREATE TRIGGER after_user_delete
AFTER DELETE ON users
FOR EACH ROW
BEGIN
    INSERT INTO audit_log(table_name, action, old_data, operate_time)
    VALUES ('users', 'DELETE', OLD.id, NOW());
END //

DELIMITER ;
```

### 删除触发器

```sql
DROP TRIGGER IF EXISTS trigger_name;
```

## Q：触发器的使用场景？

| 场景 | 说明 | 示例 |
|---|---|---|
| **数据校验** | BEFORE 触发器中校验数据合法性 | 订单金额不能为负 |
| **审计日志** | AFTER 触发器中记录操作历史 | 记录谁在什么时间修改了什么数据 |
| **级联更新** | 一张表的数据变化时同步更新另一张表 | 修改部门名称时同步更新员工表的部门名 |
| **自动填充** | BEFORE 触发器中自动计算或填充字段 | 自动设置更新时间、生成编号 |

## Q：触发器的缺点？

| 缺点 | 说明 |
|---|---|
| **隐式执行** | 触发器自动运行，开发人员可能不知道它的存在，难以定位问题 |
| **调试困难** | 触发器无法断点调试，出错时排查成本高 |
| **性能影响** | 每行数据操作都会触发，大批量操作时性能影响显著 |
| **级联触发** | 触发器中的操作可能触发另一个触发器，形成链式反应甚至死循环 |
| **业务逻辑耦合** | 将业务逻辑放入数据库层，与应用层逻辑分散，维护困难 |
| **数据库负担** | 增加数据库的计算压力，不利于扩展 |

---

## Q：面试中关于触发器的观点？

**一般不推荐使用触发器，推荐在应用层处理**，理由如下：

1. **隐式行为不可控**：触发器对应用透明，排查问题时容易被忽略
2. **违反关注点分离**：业务逻辑应集中在应用层，数据库应专注于存储
3. **影响可维护性**：触发器逻辑分散在数据库中，不纳入代码版本管理
4. **性能风险**：特别是行级触发器，批量操作时每行都触发，性能难以预估
5. **替代方案**：审计日志可在应用层通过 AOP/拦截器实现；数据校验可在 Service 层完成；级联更新可通过应用逻辑或消息队列实现

> 如果确实需要触发器，建议：仅用于简单的数据一致性问题，避免复杂业务逻辑，并做好文档记录。

> 一句话总结：触发器是与表关联的自动执行存储过程，在 INSERT/UPDATE/DELETE 时触发，常用于数据校验和审计日志，但因隐式执行、调试困难和性能问题，一般不推荐使用，建议在应用层替代。
