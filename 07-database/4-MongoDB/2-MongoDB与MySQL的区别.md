# MongoDB 与 MySQL 的区别

## Q：MongoDB 和 MySQL 有什么区别？

| 对比维度 | MongoDB | MySQL |
|---|---|---|
| **数据模型** | 文档型（BSON），支持嵌套和数组 | 关系型（行列表结构），需范式化 |
| **Schema** | Schema-Free，文档结构灵活，可随时增减字段 | 固定 Schema，需 ALTER TABLE 修改表结构 |
| **查询语言** | MongoDB Query Language（JSON 风格） | SQL（结构化查询语言） |
| **事务** | 4.0+ 支持多文档事务（但跨分片事务有限制） | 完善的 ACID 事务支持 |
| **JOIN** | `$lookup`（性能有限，不推荐频繁使用） | 原生支持各种 JOIN |
| **扩展方式** | 水平扩展为主（分片 Sharding） | 垂直扩展为主（读写分离、分库分表需中间件） |
| **索引** | B-Tree、哈希、文本、地理空间等 | B+Tree 为主，FULLTEXT、SPATIAL 等 |
| **存储** | BSON 文档，单文档上限 16MB | 行存储，支持多种存储引擎（InnoDB、MyISAM） |
| **一致性** | 默认最终一致性，可调读写关注级别 | 强一致性 |
| **性能** | 高写入吞吐、嵌套文档减少 JOIN | 复杂查询优化成熟、索引体系完善 |
| **数据关联** | 鼓励嵌套文档（反范式），减少关联 | 鼓励范式化，通过 JOIN 关联 |
| **适用数据** | 半结构化/非结构化、层次化数据 | 结构化数据，关系明确 |
| **成熟度** | 2009 年发布，生态完善 | 1995 年发布，极为成熟 |

---

## Q：何时选择 MongoDB？

- **数据模型多变**：需求迭代快，字段频繁变更，不想频繁改表
- **高写入场景**：日志采集、物联网数据、实时埋点
- **文档型数据**：数据天然具有层次结构（如订单含多个商品），嵌套存储避免 JOIN
- **水平扩展需求**：数据量大到单机无法承载，需要分片
- **快速原型**：初创项目，业务模型未定型
- **地理位置应用**：LBS 类应用，利用 2dsphere 索引

---

## Q：何时选择 MySQL？

- **强事务需求**：金融、支付等对数据一致性要求极高的场景
- **复杂关联查询**：多表 JOIN 频繁的业务（如 ERP、CRM）
- **数据模型稳定**：表结构很少变化，关系清晰
- **成熟的生态**：需要丰富的运维工具、监控方案、人才储备
- **严格合规**：某些行业监管要求使用关系型数据库
- **读多写少**：配合读写分离和缓存，MySQL 的读性能很强

---

## Q：能否混合使用？

可以。常见架构：

- **核心业务用 MySQL**：订单、账户等需要事务和强一致性的数据
- **辅助业务用 MongoDB**：用户画像、日志、配置、内容管理等

> 一句话总结：MongoDB 适合数据灵活、高写入、需水平扩展的场景，MySQL 适合强事务、复杂关联、数据模型稳定的场景，两者常搭配使用各取所长。
