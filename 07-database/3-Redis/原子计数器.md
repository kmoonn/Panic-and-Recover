# Redis 原子计数器

用 Redis 实现跨进程/跨机器的原子计数，是限流、库存、点赞、发号等场景的常用手段。

## 为什么能保证原子

Redis 命令**单线程串行执行**，`INCR`/`DECR` 这类命令天然原子，多个客户端并发调用不会丢更新——不需要额外加锁（对比：MySQL 要 `UPDATE ... SET n=n+1` 或行锁，成本高）。

## 核心命令

| 命令 | 说明 |
|---|---|
| `INCR key` | +1，key 不存在时按 0 起算 |
| `DECR key` | -1 |
| `INCRBY key n` | +n（n 可负） |
| `INCRBYFLOAT key f` | 浮点自增（如金额） |
| `HINCRBY key field n` | Hash 字段自增（一个 key 存多个计数器） |

> `INCR` 返回自增后的值，可"自增 + 拿结果"一步到位，天然适合发号/限流判断。

## 典型场景

| 场景 | 做法 |
|---|---|
| 接口限流 | `INCR` 计数 + 首次 `EXPIRE` 设窗口，超阈值拒绝 |
| 全局发号/订单号 | `INCR` 保证唯一递增 ID |
| 点赞/浏览量 | `INCR` 累加，异步落库 |
| 秒杀扣库存 | `DECR` 后判断是否 < 0，防超卖 |

## ⭐ 加分/易错

- **计数 + 过期要原子**：限流场景若 `INCR` 后单独 `EXPIRE`，第一条命令后进程崩溃会导致 key 永不过期。应在返回值 `==1`（首次）时才设过期，或用 **Lua 脚本**把"自增+判断+设过期"打包成原子操作。
- **扣库存判断非原子**：`DECR` 是原子的，但"先 `GET` 判断再 `DECR`"不是——高并发会超卖。正确做法是先 `DECR`，再判断返回值是否 < 0，负数则回补 `INCR` 并拒绝；更严谨用 Lua。
- **区别于分布式锁**：计数器解决的是"原子累加"，不是"互斥临界区"。要保护一段复杂逻辑仍需[分布式锁](分布式锁.md)。

## 一句话总结

> Redis 单线程让 INCR/DECR 天然原子，是限流/发号/库存的利器；但"计数+过期""判断+扣减"这类组合操作要用 Lua 脚本兜住原子性，否则仍有并发漏洞。
