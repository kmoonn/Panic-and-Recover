# 缓存机制

## Q：缓存的基本模式有哪些？

### 1. Cache-Aside（旁路缓存）

最常用的缓存模式，应用代码同时管理缓存和数据库。

```
读流程：                          写流程：
1. 先读缓存                       1. 先更新数据库
2. 缓存命中 → 返回                2. 再删除缓存
3. 缓存未命中 → 读数据库 →        （而非更新缓存，因为更新缓存可能
   写入缓存 → 返回                  在并发场景下导致数据不一致）
```

- 优点：简单，缓存和数据库解耦
- 缺点：首次请求必 miss；缓存失效时有一定延迟

### 2. Read-Through（读穿透）

应用只与缓存交互，缓存未命中时由**缓存层自动从数据库加载**。

```
读流程：
1. 应用读缓存
2. 缓存命中 → 返回
3. 缓存未命中 → 缓存组件自动读数据库 → 写入缓存 → 返回

写流程：由应用直接更新数据库 + 删除缓存
```

- 优点：应用代码更简洁，不需要关心缓存加载逻辑
- 缺点：缓存组件需要支持自动加载（如 Guava Cache、Caffeine）

### 3. Write-Through（写穿透）

应用只写缓存，由**缓存层同步写入数据库**。

```
写流程：
1. 应用写缓存
2. 缓存组件同步写数据库
3. 返回成功

读流程：同 Read-Through
```

- 优点：缓存和数据库始终一致
- 缺点：写入延迟 = 写缓存 + 写数据库

### 4. Write-Behind（异步写回/Write-Behind Caching）

应用只写缓存，由缓存层**异步批量写入数据库**。

```
写流程：
1. 应用写缓存 → 立即返回
2. 缓存组件异步/批量写入数据库

读流程：同 Read-Through
```

- 优点：写入极快（只写缓存），可批量合并写入
- 缺点：数据可能丢失（缓存宕机时未持久化的数据丢失）

### 对比总结

| 模式 | 读 | 写 | 一致性 | 复杂度 | 适用场景 |
|---|---|---|---|---|---|
| **Cache-Aside** | 应用管理 | 应用管理 | 最终一致 | 低 | 通用场景，最常用 |
| **Read-Through** | 缓存自动加载 | 应用管理 | 最终一致 | 中 | 读多写少，简化应用代码 |
| **Write-Through** | 缓存自动加载 | 缓存同步写DB | 强一致 | 中 | 一致性要求高 |
| **Write-Behind** | 缓存自动加载 | 缓存异步写DB | 最终一致 | 高 | 写入频繁，允许少量丢失 |

## Q：缓存与数据库一致性如何保证？

### 先删缓存 vs 先更新数据库？

| 方案 | 流程 | 问题 |
|---|---|---|
| **先删缓存，再更新DB** | 删缓存 → 更新DB | 并发时：删缓存后、更新DB前，另一请求读DB旧值写回缓存 → 不一致 |
| **先更新DB，再删缓存（推荐）** | 更新DB → 删缓存 | 极端并发时：读请求在DB更新前读旧值、DB更新后缓存才被删 → 短暂不一致，概率低 |

> 推荐使用**先更新数据库再删缓存**（Cache-Aside 标准做法），不一致概率更低。

### 延迟双删

解决"先删缓存再更新DB"的不一致问题：

```
1. 删除缓存
2. 更新数据库
3. 休眠一段时间（如 500ms，大于一次读请求的耗时）
4. 再次删除缓存
```

- 休眠期间可能有脏数据入缓存，但第二次删除后保证最终一致
- 缺点：休眠导致写请求延迟增大

### 其他保障方案

| 方案 | 说明 |
|---|---|
| **基于 binlog 异步同步** | 监听 MySQL binlog，变更时异步更新/删除缓存，可靠性高 |
| **设置较短的 TTL** | 即使删除失败，缓存也会过期，保证最终一致 |
| **分布式锁** | 写操作时加锁，保证读写串行化，性能差 |

## Q：缓存过期策略有哪些？

### 主动过期(TTL)

- 设置 `EXPIRE` 或在 SET 时指定过期时间
- Redis 采用**惰性删除 + 定期删除**：
  - 惰性删除：访问 key 时检查是否过期，过期则删除
  - 定期删除：每 100ms 随机抽查一批 key，过期则删除

### 被动淘汰(内存淘汰策略)

当 Redis 内存使用超过 `maxmemory` 时，触发内存淘汰策略：

| 策略 | 说明 |
|---|---|
| **noeviction** | 不淘汰，写入返回错误（默认策略） |
| **allkeys-lru** | 从所有 key 中淘汰最近最少使用的 |
| **volatile-lru** | 从设置了过期时间的 key 中淘汰最近最少使用的 |
| **allkeys-random** | 从所有 key 中随机淘汰 |
| **volatile-random** | 从设置了过期时间的 key 中随机淘汰 |
| **volatile-ttl** | 从设置了过期时间的 key 中淘汰 TTL 最短的 |
| **allkeys-lfu** | 从所有 key 中淘汰使用频率最低的（Redis 4.0+） |
| **volatile-lfu** | 从设置了过期时间的 key 中淘汰使用频率最低的（Redis 4.0+） |

### 如何选择？

| 场景 | 推荐策略 |
|---|---|
| 通用缓存 | **allkeys-lru** |
| 有冷热数据区分 | **allkeys-lfu** |
| 部分数据必须保留（如配置） | **volatile-lru**（将必须保留的 key 不设过期） |
| 无明显访问特征 | **allkeys-random** |

## Q：多级缓存架构是怎样的？

```
┌───────────────┐
│    客户端      │
└───────┬───────┘
        │ 请求
        ▼
┌───────────────┐
│   CDN 缓存     │  ← 静态资源缓存
└───────┬───────┘
        │
        ▼
┌───────────────┐
│   Nginx 缓存   │  ← 本地代理缓存
└───────┬───────┘
        │
        ▼
┌───────────────┐
│  应用本地缓存   │  ← 如 Guava Cache / Caffeine
│  (L1 Cache)   │  ← 特点：速度快、容量小、进程内
└───────┬───────┘
        │ miss
        ▼
┌───────────────┐
│  分布式缓存     │  ← 如 Redis Cluster
│  (L2 Cache)   │  ← 特点：容量大、可共享、网络开销
└───────┬───────┘
        │ miss
        ▼
┌───────────────┐
│   数据库       │  ← MySQL
└───────────────┘
```

### 各级缓存对比

| 级别 | 示例 | 延迟 | 容量 | 一致性 | 共享性 |
|---|---|---|---|---|---|
| **L1 本地缓存** | Caffeine、Guava | ns 级 | MB 级 | 最弱（各节点独立） | 不共享 |
| **L2 分布式缓存** | Redis | ms 级 | GB 级 | 较弱 | 共享 |
| **数据库** | MySQL | 10ms+ | TB 级 | 最强 | 共享 |

### 多级缓存的问题

| 问题 | 解决方案 |
|---|---|
| **本地缓存不一致** | 设置短 TTL + 消息广播通知各节点失效 |
| **缓存穿透到 DB** | 布隆过滤器 + 空值缓存 |
| **缓存雪崩** | 过期时间加随机值 + 多级缓存互为兜底 |
| **热点 key** | 本地缓存优先 + 热点探测 |

> 一句话总结：缓存常用 Cache-Aside 模式（先更新DB再删缓存），通过 TTL + 内存淘汰策略管理缓存生命周期，生产环境常采用本地缓存 → 分布式缓存 → 数据库的多级架构，每级以延迟换容量，互为兜底保障可用性。
