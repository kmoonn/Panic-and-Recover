# Redis 底层实现

## 面试Q&A

### Q1: Redis 五种基本数据类型的底层实现概览？

| 数据类型 | 底层编码（小数据量） | 底层编码（大数据量） | 转换阈值 |
|---------|-------------------|-------------------|---------|
| String | SDS | SDS | — |
| List | quicklist（ziplist + list） | quicklist | — |
| Hash | ziplist | hashtable | 元素数 > 512 或单值 > 64字节 |
| Set | intset | hashtable | 元素数 > 512 |
| ZSet | ziplist | skiplist + hashtable | 元素数 > 128 或单值 > 64字节 |

> 阈值可通过 `redis.conf` 调整：`hash-max-ziplist-entries`、`hash-max-ziplist-value` 等。

### Q2: String → SDS（Simple Dynamic String）

Redis 没有直接用 C 字符串（`\0` 结尾的字符数组），而是自己实现了 **SDS**。

```c
// SDS 结构（Redis 5+ 多种 sdshdr，这里以 sdshdr8 为例）
struct sdshdr8 {
    uint8_t  len;    // 已使用长度（buf中已存字符数）
    uint8_t  alloc;  // 总分配空间（不包括头部和\0）
    unsigned char flags; // 类型标志（sdshdr5/8/16/32/64）
    char     buf[];  // 实际数据，以'\0'结尾
};
```

**SDS vs C 字符串**：

| 对比维度 | C 字符串 | SDS |
|---------|---------|-----|
| 获取长度 | O(n) 遍历到 `\0` | **O(1)** 直接读 `len` |
| 二进制安全 | 否（`\0` 是结束标志） | **是**（用 `len` 判断长度，不限内容） |
| 缓冲区溢出 | 易溢出（不检查空间） | **自动扩容**（修改前检查并扩容） |
| 内存重分配 | 修改必重分配 | **空间预分配 + 惰性释放** |
| 兼容C函数 | — | 是（buf 仍以 `\0` 结尾） |

**空间预分配策略**：
- `len < 1MB`：分配 `2 * len` 空间（翻倍）
- `len >= 1MB`：分配 `len + 1MB` 空间

**惰性释放（lazy free）**：
- 缩短字符串时不立即释放内存，用 `free` 字段记录可用空间
- 真正释放需手动调用 `sdsfree`

### Q3: List → quicklist

Redis 3.2+ 使用 **quicklist** 替代旧版 ziplist 和 linkedlist。

```
quicklist = 双向链表，每个节点是一个 ziplist

  ┌─────────┐    ┌─────────┐    ┌─────────┐
  │ ziplist1 │ ←→ │ ziplist2 │ ←→ │ ziplist3 │
  │ [a,b,c]  │    │ [d,e,f]  │    │ [g,h]   │
  └─────────┘4─┘    └─────────┘    └─────────┘
```

**设计思想**：
- **ziplist**：连续内存，紧凑，缓存友好，但连锁更新问题
- **linkedlist**：无连锁更新，但每个节点额外开销大（prev/next指针 + 内存碎片）
- **quicklist**：两者折中，每个节点是一个小 ziplist，兼顾内存和性能

```c
// quicklist 节点
typedef struct quicklistNode {
    struct quicklistNode *prev;
    struct quicklistNode *next;
    unsigned char *zl;       // 指向 ziplist
    unsigned int sz;         // ziplist 占用字节数
    unsigned int count;      // ziplist 中元素个数
    ...
} quicklistNode;
```

> Redis 7.0+ 进一步引入 **listpack** 替代 ziplist，解决连锁更新问题。

### Q4: Hash → ziplist / hashtable

**小数据量（ziplist）**：
```
ziplist 中存储: [field1, value1, field2, value2, field3, value3, ...]
                紧凑连续内存，省空间
```

**大数据量（hashtable）**：
```c
// Redis 的字典结构
typedef struct dict {
    dictType *type;        // 类型特定函数
    void *privdata;        // 私有数据
    dictht ht[2];          // 两个哈希表！用于渐进式rehash
    long rehashidx;        // rehash进度，-1表示未在rehash
    int16_t pauserehash;   // rehash暂停标志
} dict;

typedef struct dictht {
    dictEntry **table;     // 哈希表数组（桶数组）
    unsigned long size;    // 哈希表大小（总是 2^n）
    unsigned long sizemask;// size - 1，用于计算索引
    unsigned long used;    // 已有节点数
} dictht;
```

**渐进式 Rehash**：
- Hash 扩容时不能一次性迁移所有数据（会阻塞服务）
- Redis 维护**两个哈希表 `ht[0]` 和 `ht[1]`**
- 每次对字典执行增删改查操作时，**顺便迁移 `ht[0]` 中一个桶的所有节点到 `ht[1]`**
- 查找时**同时查 `ht[0]` 和 `ht[1]`**
- 新增只往 `ht[1]` 写
- 迁移完成后，`ht[0]` 指向 `ht[1]`，`ht[1]` 重置

```
扩容触发条件：
- 负载因子 = used / size
- 未在执行 BGSAVE/BGREWRITEAOF 时：负载因子 >= 1 → 扩容
- 正在执行持久化时：负载因子 >= 5 → 扩容
缩容条件：负载因子 < 0.1 → 缩容
```

### Q5: Set → intset / hashtable

**intset（所有元素都是整数 + 元素数少）**：
```c
typedef struct intset {
    uint32_t encoding;  // 编码方式: int16 / int32 / int64
    uint32_t length;    // 元素个数
    int8_t contents[];  // 有序整数数组（实际类型由encoding决定）
} intset;
```

- 有序数组，查找 O(logN)（二分）
- 自动升级编码（插入超范围整数时 int16 → int32 → int64）
- 内存紧凑

**hashtable（有非整数元素 或 元素数多）**：
- 与 Hash 类似，value 都存 `null`

### Q6: ZSet → ziplist / skiplist + hashtable

**小数据量（ziplist）**：
```
ziplist: [member1, score1, member2, score2, ...]
         按score有序存储
```

**大数据量（skiplist + hashtable）**：
```c
typedef struct zset {
    dict *dict;              // hashtable: member → score，O(1)查找
    zskiplist *zsl;          // skiplist: 按score有序，O(logN)范围查询
} zset;

// 跳表节点
typedef struct zskiplistNode {
    sds ele;                 // 成员
    double score;            // 分值
    struct zskiplistNode *backward; // 后退指针
    struct zskiplistLevel {
        zskiplistNode *forward;     // 前进指针
        unsigned long span;        // 跨度（用于计算排名）
    } level[];              // 多层指针
} zskiplistNode;
```

**为什么用两种结构**：
- **hashtable**：O(1) 查找元素是否存在、获取 score（`ZSCORE`）
- **skiplist**：O(logN) 范围查询、排名（`ZRANGEBYSCORE`、`ZRANK`）
- 两者共享同一组元素节点（通过指针），不重复存储

### Q7: 跳表（Skiplist）详解

```
跳表 = 有序链表 + 多层索引

Level 4:  1 ────────────────────────────── 50
Level 3:  1 ──────────── 20 ────────────── 50
Level 2:  1 ────── 10 ── 20 ────── 30 ──── 50
Level 1:  1 ── 5 ── 10 ── 15 ── 20 ── 30 ── 40 ── 50

查找 30: Level2: 1→20→30 命中，只需3步（链表需6步）
```

- **随机层数**：每个节点插入时随机决定层数，概率 P=0.25，最大 32 层
- **查找 O(logN)**：每层跳过约一半节点
- **插入 O(logN)**：找到位置 + 随机层数 + 修改指针
- **删除 O(logN)**：查找 + 修改指针
- **范围查询 O(logN + M)**：定位起点后沿底层链表遍历 M 个元素

### Q8: 为什么 ZSet 用跳表而不用红黑树？

| 对比维度 | 跳表（Skiplist） | 红黑树（RB-Tree） |
|---------|----------------|-----------------|
| 查找 | O(logN) | O(logN) |
| 插入/删除 | O(logN) | O(logN) |
| 范围查询 | **O(logN + M)**：找到起点后沿链表遍历 | O(logN + M)：需要中序遍历，实现复杂 |
| 实现复杂度 | **简单**（概率平衡，无需旋转） | 复杂（左旋、右旋、变色） |
| 内存占用 | 每节点平均 1.33 个指针（P=0.25） | 每节点 2~3 个指针 + 颜色位 |
| 并发友好 | **好**（锁粒度细，无需旋转调整） | 差（插入/删除可能触发旋转，影响范围大） |
| 修改指针数 | 插入/删除只修改局部指针 | 可能触发多次旋转 |

> Redis 作者 antirez 的原话：*"Skip lists are a simpler data structure, and their implementation is easier to understand and maintain compared to balanced trees."*

### Q9: Redis 7.0 的 listpack 是什么？

**listpack 是 ziplist 的替代**，解决了 ziplist 的**连锁更新问题**：

- **ziplist 问题**：每个 entry 存储 `prevlen`（前一个元素长度），修改一个元素可能导致后续所有 entry 的 `prevlen` 字段大小变化，引发连锁更新（cascade update），最坏 O(N^2)
- **listpack 改进**：每个 entry 存储**自身总长度**而非前一个元素长度，删除/修改不影响其他 entry

```
ziplist entry:  [prevlen] [encoding] [data]
listpack entry: [encoding] [data] [backlen(自身总长度)]  ← 不依赖前一个元素
```

---

## 一句话总结

**Redis底层用SDS替代C字符串(O(1)长度+二进制安全)，List用quicklist(ziplist+链表)，Hash/Set小数据用ziplist/intset大数据用hashtable(渐进式rehash)，ZSet用skiplist+hashtable(跳表范围查询+哈希O(1)查找)，跳表比红黑树实现简单且范围查询更方便。**
