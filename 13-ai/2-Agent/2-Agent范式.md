# Agent 范式

## 什么是 Agent 范式

Agent 范式是 LLM Agent 执行任务的**架构模式**，定义了"感知→规划→行动→反馈"的组织方式。不同范式在规划深度、工具调用方式、自修正能力上有本质区别。

---

## 四大主流范式

### 1. 反射范式（ReAct）

最经典的 Agent 范式，交替执行 Reasoning（推理）和 Acting（行动）。

```
用户：北京今天的天气适合户外运动吗？

Thought: 我需要查询北京今天的天气
Action: weather_api(city="北京")
Observation: 晴，28°C，湿度 45%，PM2.5=35

Thought: 天气晴朗、温度适宜、空气质量优，适合户外运动
Answer: 北京今天天气晴朗，28°C，空气质量优，非常适合户外运动。
```

**循环**：`Thought → Action → Observation → Thought → ...`

| 特点 | 说明 |
|------|------|
| 优点 | 简单直观，可追踪推理过程 |
| 缺点 | 线性执行，无全局规划，长链容易偏移 |
| 适用 | 简单工具调用、单步推理 |

### 2. 规划范式（Plan-and-Execute）

先规划完整任务链，再逐步执行。将"想"和"做"分离。

```
用户：帮我写一篇关于 RAG 的技术博客并发布

[规划阶段]
Plan:
  1. 搜索 RAG 最新技术资料
  2. 整理大纲和关键要点
  3. 撰写博客正文
  4. 校对和排版
  5. 发布到博客平台

[执行阶段]
Step 1: search("RAG technology 2024") → 获取资料
Step 2: outline(topics=["RAG原理", "优化技巧", "实战案例"]) → 生成大纲
Step 3: write_blog(outline) → 生成正文
Step 4: proofread(blog) → 修正错误
Step 5: publish(blog, platform="medium") → 发布
```

| 特点 | 说明 |
|------|------|
| 优点 | 全局视角，步骤有依赖关系时效果好 |
| 缺点 | 规划可能不合理，执行中无法灵活调整 |
| 适用 | 多步骤复杂任务、有依赖关系的子任务 |

### 3. 反思范式（Reflexion）

在 ReAct 基础上加入**自我反思**，执行后评估结果，失败时重新规划。

```
用户：用 Python 实现一个 LRU 缓存

[第 1 轮尝试]
Action: write_code("LRU Cache")
Observation: 测试失败 - get() 方法返回 None

[反思]
Evaluation: 代码中 get 方法未正确更新访问顺序
Insight: 需要在 get 时将节点移到链表头部

[第 2 轮尝试]（带反思记忆）
Action: revise_code(fix="get时移动节点到头部")
Observation: 测试通过 ✓
```

**核心循环**：`Act → Evaluate → Reflect → Re-Act`

| 特点 | 说明 |
|------|------|
| 优点 | 能从失败中学习，自我修正 |
| 缺点 | 反思本身可能不准确，多轮重试开销大 |
| 适用 | 需要试错的任务（编程、调试、推理） |

### 4. 多智能体范式（Multi-Agent）

多个 Agent 协作，各司其职。

```
用户：开发一个用户登录功能

┌─────────────┐
│  Planner    │ ← 规划任务分解
│  Agent      │
└──────┬──────┘
       │ 分配子任务
       ▼
┌──────────┐  ┌──────────┐  ┌──────────┐
│ Coder    │  │ Reviewer │  │ Tester   │
│ Agent    │  │ Agent    │  │ Agent    │
└────┬─────┘  └────┬─────┘  └────┬─────┘
     │             │             │
     │  代码 ──→   │  审查 ──→   │  测试
     │             │             │
     └─────────────┴─────────────┘
                   │
                   ▼
              最终输出
```

| 角色 | 职责 |
|------|------|
| Planner Agent | 任务分解、分配、进度管理 |
| Coder Agent | 编写代码 |
| Reviewer Agent | 代码审查、质量把关 |
| Tester Agent | 编写和执行测试 |

| 特点 | 说明 |
|------|------|
| 优点 | 专业化分工，并行效率高 |
| 缺点 | 通信开销大，协调复杂 |
| 适用 | 大型复杂任务、需要多角色协作 |

## 范式对比总表

| 维度 | ReAct | Plan-and-Execute | Reflexion | Multi-Agent |
|------|-------|-----------------|-----------|-------------|
| **规划方式** | 逐步推理 | 先规划后执行 | 逐步+反思 | 分布式协作 |
| **自修正** | 无 | 需重新规划 | ✅ 反思机制 | 角色间互审 |
| **全局视野** | 弱 | 强 | 中 | 强（分工视角） |
| **复杂度** | 低 | 中 | 中 | 高 |
| **Token 消耗** | 低 | 中 | 高 | 很高 |
| **可追踪性** | 强 | 中 | 强 | 弱（分散） |
| **适用任务** | 简单工具调用 | 多步骤任务 | 需试错的任务 | 大型复杂项目 |

## 如何选择范式

```
任务简单？
  └─ 是 → ReAct
  └─ 否 → 需要试错？
              └─ 是 → Reflexion
              └─ 否 → 子任务有依赖？
                          └─ 是 → Plan-and-Execute
                          └─ 否 → 需要多角色协作？
                                      └─ 是 → Multi-Agent
                                      └─ 否 → ReAct
```

**实践经验**：
- 大多数场景 **ReAct 就够用**，不要过度设计
- Plan-and-Execute 适合步骤>5 的长链任务
- Reflexion 适合代码生成等"生成-验证"循环
- Multi-Agent 是最后手段，协调成本常被低估

## 面试高频

### ReAct 和 Chain-of-Thought（CoT）的区别？

| 维度 | CoT | ReAct |
|------|-----|-------|
| 核心思想 | 只推理，不行动 | 推理+行动交替 |
| 工具调用 | 无 | 有 |
| 外部信息 | 不获取 | 通过 Action 获取 |
| 适用 | 纯推理任务 | 需要外部信息的任务 |

### Plan-and-Execute 中执行失败怎么办？

1. **局部重试**：单个步骤失败，重试该步骤（最多 N 次）
2. **Replan**：步骤失败后重新规划后续步骤
3. **降级**：跳过失败步骤，用替代方案继续

### Multi-Agent 的协调模式有哪些？

| 模式 | 说明 | 示例 |
|------|------|------|
| 主从式 | 一个主 Agent 分配任务 | Planner 分配给 Worker |
| 管道式 | 流水线依次传递 | Coder → Reviewer → Tester |
| 讨论式 | 多 Agent 辩论达成共识 | 两个 Reviewer 辩论后决策 |
| 黑板式 | 共享状态空间，各 Agent 读写 | 共享代码仓库 |

---

## 一句话总结

> Agent 四大范式：ReAct（推理-行动交替，最通用）、Plan-and-Execute（先规划后执行，适合长链任务）、Reflexion（加入反思自修正，适合试错场景）、Multi-Agent（多角色协作，适合大型项目），选择时从简单范式开始，按需升级。
