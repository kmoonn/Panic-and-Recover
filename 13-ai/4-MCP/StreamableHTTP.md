# StreamableHTTP

> 一句话总结：Streamable HTTP 用单一 `/mcp` 端点 + 无状态设计替代 SSE 长连接，TCP 连接数降 90%+，是 MCP 传输层当前最佳实践。

---

## 为什么替代 SSE？

| 维度 | HTTP+SSE（旧） | Streamable HTTP（新） |
|------|----------------|----------------------|
| 端点 | `/sse` + `/message` 两个 | 单一 `/mcp` 端点 |
| 连接模型 | 每客户端一个长连接 | 无状态，每次请求独立 POST |
| 流式支持 | 固定 SSE 流 | 按需：可返回 JSON 或升级为 SSE 流 |
| 并发能力 | >1000 连接时成功率骤降 | TCP 连接数降 90%+，高并发仅 SSE 1/4 耗时 |
| 网关友好 | SSE 难穿透代理/网关 | HTTP 头透传 JSON-RPC 字段，网关可路由监控 |

## 协议版本演进

| 版本 | 核心变更 |
|------|---------|
| 2025-03 | 首次引入 Streamable HTTP，替代 SSE |
| 2025-11 | 增加 `Mcp-Session-Id` 头支持会话恢复 |
| 2026-07 | **破坏性变更**：移除协议级会话和 Session-Id，改为无状态设计 |

---

## 为什么 2026 版移除会话？

无状态设计的优势：
- **水平扩展更简单**：任意实例可处理任意请求，无需会话亲和
- **网关/CDN 友好**：标准 HTTP 语义，无需特殊长连接支持
- **故障恢复**：无会话状态需要恢复

代价：服务端需自行管理业务级状态（如通过外部 Redis），协议层不再兜底。

---

## 面试高频问题

**Q：Streamable HTTP 为什么替代 SSE？**
A：三点优势：(1) 单一 `/mcp` 端点简化部署；(2) 无状态设计天然支持水平扩展和负载均衡；(3) 性能提升——TCP 连接数降 90%+，高并发场景执行时间仅为 SSE 的 1/4。

**Q：2026 版为什么移除会话？**
A：无状态设计让任意实例可处理任意请求（无需会话亲和），网关/CDN 天然友好，故障无需恢复状态。代价是业务级状态需服务端自行管理。
