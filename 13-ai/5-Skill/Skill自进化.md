# Skill 自进化

> 一句话总结：Skill 自进化 = 用「运行时反馈」驱动「Skill 自动改进」的闭环——采集调用数据（成功率/耗时/报错/误命中）→ 发现问题 Skill → 沉淀新规则/新 Skill/修描述 → 回归验证上线，让 Skill 越用越准，而不是写死后一成不变。

## 什么是自进化

普通 Skill 一次写死、静态不变；**自进化**指 Skill 能根据真实使用反馈**自动或半自动地迭代自己**——描述、参数校验、编排路径、甚至新 Skill 的诞生，都由数据驱动而非人工拍脑袋。

核心是一个闭环：

```
采集反馈 → 发现问题 → 生成改进 → 回归验证 → 上线 → （回到采集）
```

## 四个进化维度

| 维度 | 进化什么 | 触发信号 |
|---|---|---|
| **描述/触发词** | 收窄或改写 description、triggers | 线上误命中率高、该命中没命中（见[命中与冲突消解](Skill命中与冲突消解.md)） |
| **参数/校验规则** | 把踩过的坑固化成前后置校验 | 某参数漏传/类型错反复报错 |
| **编排路径** | 高频长链路固化成模板/DAG | agent 现场规划不稳定、可复现性差 |
| **Skill 集合本身** | 自动生成 / 拆分 / 合并 / 淘汰 Skill | 覆盖不到的新场景、长期零调用的僵尸 Skill |

## 怎么做（进化引擎）

### 1. 反馈采集（进化的燃料）

没有数据就没有进化。要采：客观指标（**调用量、成功率、耗时、报错详情**）+ 主观反馈（**👍/👎**）+ 匹配质量（**选错/选不到**）。这正是遥测系统（如 Skills Pulse）的价值——[渐进式披露](渐进式披露机制.md)只解决"怎么选"，遥测才解决"选得好不好"。

### 2. 问题定位

- 成功率低的 Skill → 参数或依赖有坑；
- 误命中高的 Skill → 描述/触发词太泛；
- 报错聚类 → 共性坑（如某接口 `brandID` 漏传报固定错误码）→ 可固化成校验规则；
- 长期零调用 → 僵尸 Skill，考虑淘汰。

### 3. 生成改进（半自动 / 自动）

- **踩坑沉淀**：把高频报错固化成 Skill 的前后置校验规则，下次同类错误直接拦截。
- **描述自优化**：用 LLM 根据误命中样本重写 description，缩小语义边界（类似 [Prompt 自动化优化](../6-Prompt/Prompt自动化优化.md)的思路）。
- **数据驱动重建**：不再靠人工/静态分析写 Skill，而是**基于真实调用日志**还原真实链路与参数自动编排——线上真实发生过的天生正确、可复现。
- **契约校验防漂移**：Skill 上线前自动校验其声明的参数与真实接口一致，接口改了自动告警，避免"接口变了 Skill 没跟上"的静默失效。

### 4. 回归验证（进化的安全带）

改完不能直接上线。用 **evals 数据集**（输入 + 期望包含/不包含）跑回归，确认改进没引入新问题，再灰度放量。这是自进化区别于"乱改"的关键——**每次进化都要可验证**。

## 演进范式：手工 → 半自动 → 数据驱动

一条 Skill 造数能力的典型进化路径：

| 阶段 | 做法 | 局限 |
|---|---|---|
| 手工 | 人肉抓包、手动转换、手写 Skill | 易错、不可规模化 |
| 半自动 | AI 基于接口定义/代码**静态分析**生成 Skill | 静态分析和线上真实调用可能不符 |
| 数据驱动 | 基于**真实流量日志**编排 Skill，指标反哺持续迭代 | 需要遥测 + 日志基建，但最可信 |

> 越往后越"自进化"：从"人改"到"数据改"。

## 面试高频问题

**Q：Skill 自进化怎么做？**
A：本质是"运行时反馈驱动 Skill 迭代"的闭环——先用遥测采成功率/耗时/报错/误命中数据，定位问题 Skill，再针对性改进（踩坑沉淀成校验规则、误命中样本重写描述、真实日志重编排、契约校验防漂移），最后用 evals 回归验证再灰度上线。关键是每次进化都可度量、可验证，而不是拍脑袋改。

**Q：怎么保证进化是"变好"而不是"改坏"？**
A：靠 evals 回归 + 灰度。每个 Skill 有期望输入输出的评估集，改动先跑回归确认不劣化，再小流量灰度观察线上指标，正常才全量。

## 一句话总结

> Skill 自进化 = 遥测采反馈 → 定位问题 → 数据驱动改进（沉淀校验/重写描述/日志重编排/契约防漂移）→ evals 回归灰度上线的闭环，让 Skill 从"写死"变成"越用越准"。
