# Skill 命中与冲突消解

> 一句话总结：Skill 多了必然出现"描述重叠、边界模糊"，靠 description 精准划边界 + triggers 差异化 + 单一职责拆分 + 分层/命名空间管理 + 冲突时二次澄清，避免相似 Skill 互相误命中。

当 Skill 数量从几个涨到几十上百个（如项目里的 40+ 造数 Skill），最大的问题不是"能不能做"，而是**该命中的没命中、不该命中的乱命中**。

## 为什么会误命中

Skill 选择本质是 **LLM 用 query 去匹配各 Skill 的 name + description**（见[渐进式披露机制](渐进式披露机制.md)：只加载索引层做匹配）。误命中根源：

- **描述重叠**：两个 Skill 的 description 语义太接近（"造账号数据" vs "生成用户信息"）。
- **粒度不一**：一个大而全的 Skill 和几个细粒度 Skill 职责交叉。
- **触发词太泛**：triggers 里放了"帮我""处理""数据"这类高频泛词，谁都能命中。
- **缺少负向边界**：description 只说"能做什么"，没说"不做什么"。

## 治理手段

### 1. description 精准划边界（最关键）

匹配主要看 description，所以它要**同时说清"做什么"和"不做什么/什么时候用"**。

- ✅ "造**审核**场景数据，用于审核流程测试；不负责账号/投稿造数（走对应 Skill）"
- ❌ "生成测试数据"（太泛，和所有造数 Skill 撞）

### 2. triggers 差异化

- 覆盖**业务专有名词**而非通用词（账号/合作/审核/投稿/达人，而不是"数据""测试"）。
- 3~5 个精准词，宁缺毋滥；泛词（"帮我""生成"）一律不放。

### 3. 单一职责，避免交叉

一个 Skill 只做一件事。"造账号并审核"应拆成两个——职责一交叉，描述必然重叠，必然抢命中。

### 4. 分层 / 命名空间管理

- 按业务域分组（账号域 / 内容域 / 交易域），先选域再选具体 Skill，缩小候选集。
- name 用命名空间前缀（`account-create`、`content-audit`）体现归属，降低跨域误命中。

### 5. 冲突时二次澄清

多个 Skill 打平难分时，不硬猜——让 Agent **反问澄清**（"你要造账号数据还是达人数据？"），或按优先级/更具体者优先。

### 6. 线上度量反哺

采集每个 Skill 的**命中量、误触率、成功率**（项目里 Skills Pulse 做的事），发现某 Skill 频繁被误命中 → 回头收窄它的 description/triggers。

## 与简历项目的关联

| 手段 | 项目实践 |
|---|---|
| description 划边界 | 40+ 造数 Skill 每个描述锚定具体业务模块，互不重叠 |
| triggers 差异化 | 触发词用模块名（账号/合作/审核/投稿/达人）而非"造数" |
| 单一职责 | 每个 Skill 只造一类数据，不做"造账号+审核"混合 |
| 线上度量 | Skills Pulse 采集调用量/成功率/耗时，反查误命中 Skill |

## 面试高频问题

**Q：Skill 多了怎么防止相似 Skill 误命中？**
A：核心是 description 精准划边界（说清做什么 + 不做什么），配合 triggers 用业务专名差异化、单一职责拆分避免交叉、按业务域分层/命名空间缩小候选、冲突时二次澄清，最后用线上命中率/误触率度量反哺收窄描述。

**Q：Skill 选择是怎么发生的？**
A：渐进式披露——先只加载所有 Skill 的 name+description 索引层，LLM 拿 query 做语义匹配选中后，才展开该 Skill 的参数和步骤。所以描述质量直接决定命中准确率。

## 一句话总结

> 相似 Skill 误命中的根源是描述重叠 + 触发词太泛；治理靠 description 划清正负边界、triggers 用业务专名、单一职责拆分、分层命名空间、冲突二次澄清，并用线上命中度量持续收窄。
