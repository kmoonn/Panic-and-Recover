# Skill结构

> 一句话总结：Skill = Frontmatter（元数据+触发词）+ Prompt 模板（核心指令）+ 工具绑定 + I/O Schema，遵循单一职责、工具最小化原则，与 MCP 是"菜谱与厨具"的关系。

---

## 标准结构

```
Skill/
├── SKILL.md          ← 元数据 + Prompt 模板（核心）
├── references/       ← 参考文档（可选）
├── scripts/          ← 脚本工具（可选）
└── evals/            ← 评估数据（可选）
```

---

## SKILL.md 四部分

### 1. Frontmatter（元数据）

| 字段 | 必填 | 说明 | 示例 |
|------|------|------|------|
| `name` | ✅ | 唯一标识，小写+连字符 | `code-review` |
| `description` | ✅ | 一句话描述，用于触发匹配 | "代码审查，检查安全性和规范性" |
| `triggers` | ❌ | 触发关键词列表 | `代码审查 / code review / review code` |

### 2. Prompt 模板（指令区）

核心指令，定义 Skill 要做什么、按什么步骤、输出什么格式。

**设计原则**：
- 指令清晰简短，不超过上下文的 10%
- 先定义角色，再给步骤，最后指定输出格式

### 3. 工具绑定

声明式指定需要的工具，执行时自动注入。**只声明必要的工具**——声明 20 个但只用 3 个会分散模型注意力。

### 4. I/O Schema

| 作用 | 说明 |
|------|------|
| Input Schema | 校验输入参数类型和格式，非法输入直接拒绝 |
| Output Schema | 约束输出格式，便于下游消费和自动化验证 |

---

## 参考文档（references/）

为 Skill 提供知识补充，不影响 Prompt 但需要时可查阅。

**用途**：当用户问题涉及具体规范时，Agent 查阅参考文档获取细节，不必把所有内容塞进 Prompt。

---

## 脚本工具（scripts/）

Skill 自带脚本，扩展 Agent 能力边界。特点：
- 脚本由 Agent 调用执行，不是手动运行
- 需有明确的输入/输出接口
- 错误处理要完善（Agent 可能传非法参数）

---

## 评估数据（evals/）

验证 Skill 执行效果：定义输入 + 期望包含/不包含的内容，用于回归测试和 Skill 质量卡点。

---

## 设计原则

| 原则 | 说明 | 反例 |
|------|------|------|
| **单一职责** | 一个 Skill 只做一件事 | "代码审查并部署" |
| **Prompt 精炼** | 指令清晰简短，< 上下文 10% | 3000 字的 Prompt 模板 |
| **工具最小化** | 只声明必要的工具 | 声明 20 个工具但只用 3 个 |
| **输入明确** | 明确输入参数和格式 | 模糊的"传入相关信息" |
| **输出结构化** | 指定输出格式，便于下游消费 | 自由文本输出 |
| **可评估** | 有 evals 数据验证效果 | 无法判断执行是否正确 |

## Skill 与 MCP 的分工

```
┌──────────────────────────────────────┐
│            Skill 层                   │
│  定义"做什么"：审查代码 / 部署服务     │
│  Prompt + 工具选择 + I/O 约束         │
├──────────────────────────────────────┤
│            MCP 层                     │
│  提供"怎么做"：read_file / kubectl    │
│  原子级工具 + 通信协议                │
└──────────────────────────────────────┘
```

| 维度 | Skill | MCP Tool |
|------|-------|----------|
| 粒度 | 任务级（代码审查） | 操作级（读取文件） |
| 包含 Prompt | 是 | 否 |
| 可组合 | Skill 可链式调用 | Tool 被组合使用 |
| 类比 | 菜谱（做什么菜） | 厨具（锅碗瓢盆） |

## 与简历项目的关联

| 结构要素 | 项目关联 |
|---------|---------|
| 单一职责 | AI Data Gen 的 40+ 造数 Skill 每个只做一件事：造账号、造合作、造审核……不混合 |
| 工具绑定 | API Testing Agent 的 Skill 绑定三种工具：Mock 生成、日志检索、造数 Skill |
| I/O Schema | 造数 Skill 的三级参数确定机制（必填→默认→LLM 推断），本质是 Input Schema 的分层 |
| evals 评估 | Skills Pulse 采集调用量/成功率/耗时，本质是对 Skill 执行效果的线上 evals |
| 链式组合 | 字节 AI Testing 工具链：造数→遥测→测试 三 Skill 闭环 |
| triggers 设计 | 造数 Skill 的触发词：覆盖业务模块名（账号/合作/审核/投稿/达人） |

## 面试高频问题

**Q：Skill 的标准结构是什么？**
A：四部分——Frontmatter（name+description+triggers）、Prompt 模板（核心指令）、工具绑定（声明式依赖）、I/O Schema（输入校验+输出约束）。遵循单一职责、Prompt 精炼、工具最小化原则。

**Q：Skill 和 MCP Tool 的分工？**
A：Skill 是任务级，定义"做什么"（含 Prompt + 工具选择 + I/O 约束）；MCP Tool 是操作级，提供"怎么做"（原子级工具 + 通信协议）。Skill 调用 MCP 工具完成具体操作，MCP 不知道自己在被哪个 Skill 使用。类比：菜谱与厨具。

**Q：多个 Skill 如何组合？**
A：三种方式——链式（A→B 顺序执行）、条件式（A 的结果决定是否执行 B）、并行式（A 和 B 同时执行后合并）。

**Q：Skill 的 triggers 怎么设计？**
A：覆盖中英文关键词 + 同义词，3~5 个最佳，不要太泛（"帮我"不放），避免误触发。

---

## 一句话总结

Skill = 元数据 + Prompt 模板 + 工具绑定 + I/O Schema，遵循单一职责/工具最小化，与 MCP 是"菜谱与厨具"关系——Skill 定义做什么菜，MCP 提供锅碗瓢盆。
