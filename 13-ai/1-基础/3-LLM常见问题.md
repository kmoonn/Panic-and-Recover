# LLM 常见问答

## Q: 大模型的"幻觉"是什么？怎么缓解？

### 什么是幻觉？

幻觉（Hallucination）是指大模型生成**看似合理但实际错误**的内容，包括虚构事实、编造引用、张冠李戴等。模型并非故意说谎，而是因为其本质是**基于概率预测下一个 Token**，并不具备真正的知识验证能力。

### 幻觉的类型

| 类型 | 说明 | 示例 |
|------|------|------|
| 事实性幻觉 | 编造不存在的事实 | "爱因斯坦于 1968 年获得诺贝尔奖"（实际 1921 年） |
| 引用幻觉 | 虚构不存在的论文/书籍 | "根据 Smith 等人 2023 年的研究..."（该论文不存在） |
| 推理幻觉 | 逻辑推理出错 | 数学题中间步骤错误但答案恰好正确 |

### 缓解方法

| 方法 | 说明 |
|------|------|
| RAG（检索增强生成） | 让模型先检索真实文档，基于文档内容回答 |
| 提示工程 | 要求模型"仅根据已知信息回答，不知道就说不知道" |
| 多模型交叉验证 | 用多个模型交叉检验答案 |
| 事实校验后处理 | 对输出进行自动化事实核查 |
| Fine-tuning | 用高质量数据微调，减少编造倾向 |

## Q: Token 是什么？为什么 LLM 按 Token 计费？

### 什么是 Token？

Token 是 LLM 处理文本的**最小单位**，介于字符和词之间。不同语言的分词方式不同：

```
英文："Hello world" → ["Hello", " world"] → 2 个 Token
中文："你好世界" → ["你好", "世界"] → 2~4 个 Token（取决于分词器）
代码："def foo():" → ["def", " foo", "()"] → 3~5 个 Token
```

- 约略估算：1 个英文单词 ≈ 1.3 个 Token，1 个中文字 ≈ 1.5~2 个 Token
- 不同模型的分词器不同（如 GPT 用 BPE，Claude 也有自己的分词器）

### 为什么按 Token 计费？

| 原因 | 说明 |
|------|------|
| 计算量与 Token 数成正比 | 注意力机制的计算复杂度是 O(n^2)（n 为 Token 数） |
| 输入和输出成本不同 | 输入（Prompt）需要缓存，输出需要逐个生成，输出成本更高 |
| 统一度量 | 按字符计费不公平（中文信息密度高，字符多但 Token 少） |

典型的计费格式：`输入 $x / 1M Token，输出 $y / 1M Token`

## Q: Temperature 参数的作用？

Temperature 控制 LLM 生成的**随机性/创造性**，影响采样概率分布的平滑程度：

```
原始概率：  [0.7, 0.2, 0.1]

Temperature=0.1（几乎贪心）：[0.97, 0.02, 0.01]  → 几乎总选最高概率
Temperature=1.0（默认）：    [0.7,  0.2,  0.1]   → 保持原始分布
Temperature=2.0（高度随机）：[0.41, 0.33, 0.26]  → 概率趋近均匀
```

| Temperature 值 | 行为 | 适用场景 |
|---------------|------|---------|
| 0 ~ 0.3 | 确定性强，输出稳定 | 代码生成、事实问答、数据提取 |
| 0.3 ~ 0.7 | 平衡创造性和准确性 | 日常对话、文本改写 |
| 0.7 ~ 1.0 | 创造性强，输出多样 | 创意写作、头脑风暴 |
| > 1.0 | 高度随机，可能不连贯 | 实验性用途 |

> **面试要点**：Temperature=0 不等于完全确定性（仍有浮点精度影响），但实际可视为确定性输出。

## Q: 大模型为什么有上下文窗口限制？

### 什么是上下文窗口？

上下文窗口（Context Window）是模型单次能处理的**最大 Token 数**，包括输入和输出：

```
输入 Prompt + 模型输出 ≤ 上下文窗口大小
```

### 限制的原因

| 原因 | 说明 |
|------|------|
| **注意力机制的计算复杂度** | 标准 Self-Attention 计算量为 O(n^2)，序列翻倍计算量翻四倍 |
| **显存占用** | KV Cache 随序列长度线性增长，长序列需要巨大显存 |
| **训练数据限制** | 模型在训练时见过的最大序列长度决定了其外推能力 |
| **长距离依赖衰减** | 即使技术允许，模型对超长上下文中间部分的信息也会"遗忘"（Lost in the Middle） |

### 各模型上下文窗口参考

| 模型 | 上下文窗口 |
|------|-----------|
| GPT-4o | 128K Token |
| Claude 3.5 Sonnet | 200K Token |
| Gemini 1.5 Pro | 1M Token |

### 超出上下文的处理方式

- **截断**：丢弃最早的内容
- **滑动窗口**：保留最近 N 个 Token
- **摘要压缩**：对历史对话进行摘要
- **RAG**：只检索相关片段放入上下文

## Q: Fine-tuning 和 RAG 的区别？

| 对比维度 | Fine-tuning | RAG |
|---------|-------------|-----|
| **原理** | 用额外数据调整模型参数 | 检索相关文档放入 Prompt 供模型参考 |
| **知识更新** | 需重新训练 | 实时更新知识库即可 |
| **成本** | 高（需 GPU 训练） | 低（只需向量数据库 + 检索） |
| **效果** | 改变模型行为和风格 | 不改变模型，仅补充知识 |
| **可解释性** | 低（参数变化不可解释） | 高（可追溯引用来源） |
| **幻觉风险** | 仍然存在 | 大幅降低（基于真实文档） |
| **适用场景** | 风格适配、领域专业化 | 知识问答、文档检索、实时信息 |

### 什么时候用 Fine-tuning？什么时候用 RAG？

```
需要改变模型的"行为方式"（语气、格式、风格） → Fine-tuning
需要让模型"知道新知识"（最新数据、私有文档） → RAG
两者都需要 → 先 RAG 保证知识准确，再 Fine-tuning 调整风格
```

## Q: 什么是 Embedding？为什么检索需要它？

### 什么是 Embedding？

Embedding（嵌入）是将文本等非结构化数据映射为**高维向量**（通常 768~3072 维）的技术。语义相近的文本，在向量空间中距离也相近。

```
"猫"     → [0.12, -0.34, 0.56, ..., 0.78]   ┐
"小猫"   → [0.11, -0.33, 0.55, ..., 0.77]   ├── 语义相近，向量距离近
"猫咪"   → [0.13, -0.35, 0.57, ..., 0.79]   ┘

"汽车"   → [0.91, 0.22, -0.45, ..., -0.33]  ← 语义不同，向量距离远
```

### 为什么检索需要 Embedding？

| 对比 | 关键词检索 | 向量检索（Embedding） |
|------|-----------|---------------------|
| 匹配方式 | 精确匹配关键词 | 语义相似度匹配 |
| "手机" 能匹配 "电话" | 不能 | 能 |
| "如何减肥" 能匹配 "瘦身方法" | 不能 | 能 |
| 对同义词/近义词 | 无能为力 | 天然支持 |
| 对错别字/表述差异 | 容易漏检 | 具有容错性 |

### RAG 中的 Embedding 流程

```
1. 离线阶段：
   文档 → 分块 → Embedding 模型 → 向量 → 存入向量数据库

2. 查询阶段：
   用户问题 → Embedding 模型 → 查询向量
   → 向量数据库检索 Top-K 相似文档
   → 将检索结果 + 问题一起送入 LLM 生成答案
```

### 常见 Embedding 模型

| 模型 | 维度 | 特点 |
|------|------|------|
| OpenAI text-embedding-3-small | 1536 | 通用效果好 |
| BGE（BAAI） | 768/1024 | 中文效果优秀 |
| GTE（Alibaba） | 768/1024 | 中英文兼顾 |
| Cohere Embed v3 | 1024 | 多语言支持好 |

## 一句话总结

大模型面试核心问答：幻觉是概率预测的固有缺陷，RAG 是最有效的缓解手段；Token 是模型的处理单位，Temperature 控制随机性，上下文窗口受计算复杂度限制；Fine-tuning 改行为，RAG 补知识；Embedding 将语义映射为向量，是实现语义检索的基础。
