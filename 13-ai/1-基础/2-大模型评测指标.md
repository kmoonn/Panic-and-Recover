# 大模型评测指标

## 为什么评测重要

大模型能力多样（生成、推理、代码、对话），没有统一评测就无法：
- 对比不同模型的能力差异
- 验证微调/对齐是否有效
- 评估模型在特定任务上的可靠性

---

## 评测体系分类

```
大模型评测
├── 通用能力评测（通用基准）
│   ├── 语言理解（MMLU, C-Eval）
│   ├── 推理能力（GSM8K, ARC）
│   ├── 代码能力（HumanEval, MBPP）
│   └── 长文本（LongBench）
├── 对齐评测（安全与偏好）
│   ├── 安全性（TruthfulQA, SafetyBench）
│   └── 人类偏好（MT-Bench, AlpacaEval）
└── 生成质量指标（算法指标）
    ├── 自动指标（BLEU, ROUGE, Perplexity）
    └── LLM-as-Judge
```

## 一、通用能力评测基准

### 语言理解

| 基准 | 内容 | 评估方式 | 特点 |
|------|------|---------|------|
| **MMLU** | 57 个学科的多选题 | 准确率 | 英文通用能力标杆 |
| **C-Eval** | 52 个学科中文多选题 | 准确率 | 中文能力基准 |
| **CMMLU** | 67 个学科中文多选题 | 准确率 | 中文更全面 |
| **HellaSwag** | 常识推理完形填空 | 准确率 | 测试常识推理 |

### 数学推理

| 基准 | 内容 | 评估方式 | 特点 |
|------|------|---------|------|
| **GSM8K** | 8500 道小学数学题 | 准确率 | 推理能力基础测试 |
| **MATH** | 竞赛级数学题 | 准确率 | 高难度数学推理 |
| **ARC** | 科学推理题 | 准确率 | 分 Easy/Challenge 两级 |

### 代码生成

| 基准 | 内容 | 评估方式 | 特点 |
|------|------|---------|------|
| **HumanEval** | 164 道 Python 编程题 | Pass@k | 代码能力标杆 |
| **MBPP** | 974 道入门编程题 | Pass@k | 更基础的代码测试 |
| **SWE-bench** | 真实 GitHub Issue 修复 | 解决率 | 实际工程能力 |

### 长文本

| 基准 | 内容 | 评估方式 | 特点 |
|------|------|---------|------|
| **LongBench** | 多任务长文本理解 | 准确率/F1 | 最全面的长文本基准 |
| **Needle in Haystack** | 在长文本中找特定信息 | 召回率 | 测试大海捞针能力 |

## 二、对齐与安全评测

### 安全性

| 基准 | 内容 | 评估方式 |
|------|------|---------|
| **TruthfulQA** | 测试模型是否会输出常见误解 | 真实率 + 信息量 |
| **SafetyBench** | 多维度安全测试 | 不安全率 |
| **ToxiGen** | 有害内容生成检测 | 有害率 |

### 人类偏好

| 基准 | 内容 | 评估方式 |
|------|------|---------|
| **MT-Bench** | 多轮对话质量 | GPT-4 评分（1-10 分） |
| **AlpacaEval** | 指令遵循质量 | 胜率（vs 参考模型） |
| **Chatbot Arena** | 人类盲评 PK | ELO 积分排名 |

> **Chatbot Arena** 是目前公信度最高的评测——真实用户匿名 PK，ELO 积分排序。

## 三、生成质量算法指标

### BLEU

**用途**：评估生成文本与参考文本的 n-gram 重合度，主要用于翻译。

```
BLEU = BP × exp(Σ w_n × log(p_n))

p_n: n-gram 精度（1-gram, 2-gram, 3-gram, 4-gram）
BP: 惩罚短译文的 Brevity Penalty
w_n: 各阶权重（通常均匀 1/4）
```

| 特点 | 说明 |
|------|------|
| 优点 | 计算快，可复现 |
| 缺点 | 只看字面重合，不理解语义；对生成式任务不适用 |

### ROUGE

**用途**：评估生成文本对参考文本的召回率，主要用于摘要。

| 变体 | 含义 |
|------|------|
| **ROUGE-1** | 单词召回率 |
| **ROUGE-2** | bigram 召回率 |
| **ROUGE-L** | 最长公共子序列召回率 |

```python
from rouge_score import rouge_scorer

scorer = rouge_scorer.RougeScorer(['rouge1', 'rouge2', 'rougeL'])
scores = scorer.score(
    "RAG 通过检索增强生成",
    "检索增强生成是 RAG 的核心思想"
)
# {'rouge1': PrecisionRecallF1(...), ...}
```

### Perplexity（困惑度）

**用途**：衡量模型对文本的预测不确定性，越低越好。

```
PPL = exp(-1/N × Σ log P(w_i | w_<i))

P(w_i | w_<i): 模型对第 i 个 token 的预测概率
```

| PPL 值 | 含义 |
|--------|------|
| < 20 | 模型对文本很确定，文本流畅 |
| 20~50 | 中等，有一定不确定性 |
| > 100 | 模型很困惑，文本可能不通顺 |

### LLM-as-Judge

用强模型（如 GPT-4）评判弱模型输出，适合开放性任务。

```python
JUDGE_PROMPT = """
请从以下维度评估回答质量（1-10分）：
1. 准确性：信息是否正确
2. 完整性：是否充分回答了问题
3. 清晰度：表达是否清晰有条理

问题：{question}
回答：{answer}
参考答案：{reference}

评分和理由：
"""
```

| 优点 | 缺点 |
|------|------|
| 评估开放性任务 | Judge 模型自身有偏差 |
| 可自定义评估维度 | 成本高 |
| 接近人类判断 | 可复现性差 |

## 四、指标选择指南

| 任务类型 | 推荐指标 | 说明 |
|---------|---------|------|
| 分类/选择题 | Accuracy | 简单直接 |
| 翻译 | BLEU | n-gram 匹配 |
| 摘要 | ROUGE-L | 召回率导向 |
| 代码生成 | Pass@k | 功能正确性 |
| 开放式问答 | LLM-as-Judge | 语义质量 |
| RAG | RAGAS（Faithfulness 等） | 检索+生成联合评估 |
| 对话质量 | MT-Bench / Arena ELO | 多轮对话综合评估 |

## 面试高频

### BLEU 和 ROUGE 的区别？

| 维度 | BLEU | ROUGE |
|------|------|-------|
| 关注点 | 精度（生成中有多少在参考中） | 召回率（参考中有多少在生成中） |
| 适用场景 | 翻译（不能多翻） | 摘要（不能漏要点） |
| 方向 | 生成 → 参考 | 参考 → 生成 |

### Pass@k 是什么？

代码生成指标，k 次采样中至少有一次通过测试的概率：

```
Pass@k = 1 - C(n-c, k) / C(n, k)

n: 总采样次数
c: 通过测试的次数
k: 取前 k 个结果
```

Pass@1 更严格（一次通过），Pass@100 更宽松（百次中通过一次）。

### 为什么 Chatbot Arena 的公信度高？

| 特点 | 说明 |
|------|------|
| 真实用户 | 不是研究者自评 |
| 匿名 PK | 不知道是哪个模型，消除品牌偏见 |
| 大规模 | 数十万场 PK |
| ELO 积分 | 棋类评级系统，跨对手可比较 |
| 持续更新 | 新模型随时加入 |

## 八股速记

### Q10. 模型评测指标 / 采样参数 ⭐ B

**答（要点式）**：
- **采样参数**：`temperature`（越高越随机/有创意，越低越确定，评测/抽取类任务调低）、`top_p`（核采样，只从累积概率 top_p 的候选里选）、`max_tokens`（输出上限）。
- **生成质量指标**：BLEU / ROUGE（比对参考答案的 n-gram 重合，偏机器翻译/摘要）；语义相似度；**LLM-as-Judge**（用更强的模型当裁判打分，主流做法）。
- **RAG 专项指标**：**检索**看召回率/命中率、**生成**看忠实度（Faithfulness，答案是否忠于资料）、答案相关性。

**⭐ 加分/易错**：传统 BLEU/ROUGE 对开放式生成不敏感，现在多用 **LLM-as-Judge + 人工抽检** 结合；但 LLM 裁判本身有偏差，需固定 prompt/多次采样降噪。

### Q13. 大模型评测：Benchmark / 评测数据集 / 基准指标 ⭐⭐

> 同为 AI 测开 JD 核心（"模型基准评测 Benchmark、测试数据集搭建、大模型测试资产库：评测数据集/基准指标"）。Q12 是"测哪些维度"，**Q13 是"用什么标准尺子量、怎么攒这把尺子"**。

**答（要点式）**：
- **Benchmark（基准评测）**：业界**标准化的评测数据集 + 打分方法**，让不同模型在同一把尺子上比。常见：**MMLU**（多学科知识）、**C-Eval/CMMLU**（中文）、**GSM8K**（数学推理）、**HumanEval**（代码）、**MT-Bench**（多轮对话）。作用是**横向选型 + 纵向看迭代有没有退化**。
- **评测数据集怎么搭**（测开真正要 own 的）：
  - **来源**：真实线上 query 采样（最贴业务）+ 人工构造边界/对抗 case + 已知缺陷沉淀；
  - **分层**：按业务场景 / 难度 / 维度（准确/安全/鲁棒）分层，保证覆盖不偏科；
  - **标注**：给标准答案或评分标准（rubric），多人标 + 对齐（算标注一致性）；
  - **防泄漏**（⭐易被追）：评测集**不能进训练数据**，否则"考题泄题"分数虚高——要和训练集隔离、定期换新题。
- **基准指标怎么定**：先定"什么算好"，再定阈值。生成类=准确率/忠实度/安全通过率；检索类=召回率/命中率（呼应 RAG 分层）；对话=多轮一致性通过率；性能=TTFT/吞吐/P99。**关键是定一条基线（baseline），每次迭代对比涨跌**。
- **测试资产库（JD 的"资产库"）**：把 评测数据集 + 专项用例 + 评测脚本 + 基准指标 沉淀成**可复用、可回归**的资产——模型/prompt 一改就跑全套，实现"质量可量化、可追溯"。

**⭐ 加分/易错**：
- **评测集防泄漏**是最容易被追的深度点——能主动说"评测集要和训练数据隔离、防止刷分"就显专业。
- **LLM-as-Judge 的坑**：用强模型当裁判省人力，但裁判有偏差（位置偏好、啰嗦偏好），要**固定 prompt + 多次采样 + 人工抽检校准**（呼应 Q10）。
- **别把 Benchmark 分数当业务表现**——公开 Benchmark 高 ≠ 你的业务场景好，最终要用**自建业务评测集**兜底。
- **扣回我的经验**：RAG 项目就是自建标注问答对做评测集、跑检索/生成分层指标、改 prompt 后回归看涨跌（`ceec/00-rag-platform.md`）——这套正是 JD 要的"评测数据集 + 基准指标 + 回归"。

---

## 一句话总结

> 大模型评测分三层：通用能力用基准测试（MMLU/GSM8K/HumanEval）、对齐安全用偏好评测（Arena/MT-Bench）、生成质量用算法指标（BLEU/ROUGE/Perplexity）或 LLM-as-Judge，选择指标要看任务类型——分类看 Accuracy，翻译看 BLEU，摘要看 ROUGE，代码看 Pass@k，开放问答用 LLM-as-Judge。
