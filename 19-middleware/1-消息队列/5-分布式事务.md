# 分布式事务

## Q: 什么是分布式事务？

**分布式事务**是指跨多个服务或数据库的事务操作，需要保证这些操作要么全部成功，要么全部回滚，以维持数据一致性。

在微服务架构下，一个业务操作往往涉及多个服务：
```
用户下单 → 订单服务(创建订单) + 库存服务(扣减库存) + 支付服务(扣款)
```
每个服务有独立的数据库，本地事务无法保证跨服务的一致性，因此需要分布式事务方案。

---

## Q: CAP 定理和 BASE 理论是什么？

### CAP 定理

分布式系统无法同时满足以下三者，最多同时满足两个：

| 属性 | 说明 |
|------|------|
| **C（Consistency）** | 一致性：所有节点在同一时刻看到相同的数据 |
| **A（Availability）** | 可用性：每个请求都能在有限时间内收到非错误响应 |
| **P（Partition Tolerance）** | 分区容错：网络分区时系统仍能运行 |

> 实际中网络分区不可避免（P 必选），所以分布式系统实质上在 **CP** 和 **AP** 之间选择。

```
CP：保证一致性，牺牲可用性（如 ZooKeeper、Etcd）
AP：保证可用性，牺牲强一致性（如 Eureka、Cassandra）
```

### BASE 理论

BASE 是 CAP 中 AP 方向的实践总结：

| 原则 | 说明 |
|------|------|
| **BA（Basically Available）** | 基本可用：允许响应时间增加或功能降级 |
| **S（Soft State）** | 软状态：允许中间状态存在 |
| **E（Eventually Consistent）** | 最终一致性：一段时间后数据达到一致 |

> 面试观点：**大多数业务场景不需要强一致性**，追求最终一致性即可，这是分布式事务方案选型的核心思想。

## Q: 分布式事务有哪些常见解决方案？

### 1. 2PC（两阶段提交）

```
┌──────────┐         ┌──────────┐         ┌──────────┐
│Coordinator│───────▶│Resource 1│         │Resource 2│
│ (协调者)   │◀───────│ (参与者)  │         │ (参与者)  │
└──────────┘         └──────────┘         └──────────┘

阶段一（Prepare / 准备）：
  协调者 → 所有参与者："准备提交"
  参与者执行事务但不提交，锁定资源 → 回复 Yes/No

阶段二（Commit / Rollback）：
  所有参与者回复 Yes → 协调者发送 Commit
  任一参与者回复 No → 协调者发送 Rollback
```

| 优点 | 缺点 |
|------|------|
| 实现相对简单 | **同步阻塞**：准备阶段锁定资源，其他事务等待 |
| 强一致性 | **单点故障**：协调者宕机则参与者永久阻塞 |
| | **数据不一致**：第二阶段网络异常可能导致部分提交部分回滚 |

### 2. 3PC（三阶段提交）

```
阶段一（CanCommit）：
  协调者 → 参与者："能否提交？"（轻量询问，不锁资源）

阶段二（PreCommit）：
  所有参与者回复 Yes → 协调者发送 PreCommit
  参与者执行事务但不提交，锁定资源

阶段三（DoCommit）：
  协调者发送 Commit 或 Rollback
  超时未收到指令 → 参与者默认提交（减少阻塞）
```

| 优点 | 缺点 |
|------|------|
| 增加超时机制，减少阻塞 | 仍可能出现数据不一致 |
| CanCommit 阶段不锁资源 | 实现更复杂，网络开销更大 |
| | 本质问题（网络分区下的不一致）未根本解决 |

### 3. TCC（Try-Confirm-Cancel）

**业务层面的两阶段提交**，由业务代码实现三个操作：

```
Try：    预留资源（冻结库存、冻结金额）
Confirm：确认执行（扣减冻结的库存/金额）
Cancel：  取消执行（释放冻结的资源）

示例：下单扣库存
  Try：    库存服务冻结 10 件商品（可用库存 -10，冻结库存 +10）
  Confirm：确认扣减（冻结库存 -10）
  Cancel： 释放冻结（可用库存 +10，冻结库存 -10）
```

| 优点 | 缺点 |
|------|------|
| 无资源长期锁定（Try 阶段快速完成） | **业务侵入性强**，每个操作需实现三个方法 |
| 最终一致性 | 需考虑 Confirm/Cancel 的幂等性 |
| 灵活性高 | 空回滚、幂等、悬挂等问题需额外处理 |

### 4. Saga 模式

将长事务拆分为多个本地事务，每个本地事务有对应的补偿操作：

```
正向执行：              补偿回滚：
T1(创建订单)           C1(取消订单)
T2(扣减库存)           C2(恢复库存)
T3(扣款)      ← 失败   C3(退款)

执行流程：
T1 → T2 → T3(失败) → C2 → C1（逆序补偿）
```

两种编排方式：

| 方式 | 说明 | 优点 | 缺点 |
|------|------|------|------|
| **编排式（Choreography）** | 事件驱动，每个服务监听事件触发下一步 | 简单、松耦合 | 难以跟踪流程、循环依赖风险 |
| **控制式（Orchestration）** | 中心协调器控制流程 | 流程清晰、易监控 | 协调器有单点风险 |

### 5. 本地消息表

利用本地事务 + 消息表实现最终一致性：

```
1. 业务操作与消息插入在同一本地事务中
   ┌─────────────────────────────────┐
   │ BEGIN;                          │
   │ INSERT INTO order (...) VALUES  │ ← 业务操作
   │ INSERT INTO msg_table (...)     │ ← 消息记录
   │ COMMIT;                         │
   └─────────────────────────────────┘

2. 后台定时任务扫描消息表，发送到 MQ

3. 下游服务消费消息，处理成功后回调确认

4. 消息状态更新为已发送
```

| 优点 | 缺点 |
|------|------|
| 实现简单，无侵入 | 与业务系统耦合（消息表在业务库中） |
| 利用本地事务保证一致性 | 定时轮询有延迟 |
| 无需额外中间件 | 消息表需定期清理 |

### 6. MQ 事务消息

以 RocketMQ 半消息方案为例：

```
1. Producer 发送半消息（Half Message）→ Broker
   半消息：对 Consumer 不可见，暂存于 Broker

2. Broker 返回发送成功 → 执行本地事务

3. 根据本地事务结果：
   Commit → 半消息对 Consumer 可见，正常消费
   Rollback → 半消息被删除，Consumer 不会收到

4. 网络异常未收到确认 → Broker 回查本地事务状态
```

```java
// RocketMQ 事务消息示例
TransactionMQProducer producer = new TransactionMQProducer("order-group");
producer.setTransactionListener(new TransactionListener() {
    // 执行本地事务
    @Override
    public LocalTransactionState executeLocalTransaction(Message msg, Object arg) {
        try {
            createOrder();  // 本地事务
            return LocalTransactionState.COMMIT_MESSAGE;
        } catch (Exception e) {
            return LocalTransactionState.ROLLBACK_MESSAGE;
        }
    }
    // 回查本地事务状态
    @Override
    public LocalTransactionState checkLocalTransaction(MessageExt msg) {
        boolean exists = checkOrderExists(msg);
        return exists ? LocalTransactionState.COMMIT_MESSAGE
                      : LocalTransactionState.ROLLBACK_MESSAGE;
    }
});
```

| 优点 | 缺点 |
|------|------|
| 对业务侵入性较低 | 依赖特定 MQ（如 RocketMQ） |
| 无需本地消息表 | Broker 需支持半消息机制 |
| 最终一致性 | 事务回查增加复杂度 |

## Q: 各方案如何对比？

| 方案 | 一致性 | 性能 | 侵入性 | 复杂度 | 适用场景 |
|------|--------|------|--------|--------|---------|
| **2PC** | 强一致 | 低（同步阻塞） | 低 | 低 | 数据库层面跨库事务 |
| **3PC** | 强一致 | 低 | 低 | 中 | 理论改进，实际少用 |
| **TCC** | 最终一致 | 高 | 高（三个方法） | 高 | 资金/库存等一致性要求高的业务 |
| **Saga** | 最终一致 | 高 | 中 | 中 | 长流程业务编排 |
| **本地消息表** | 最终一致 | 中 | 中（消息表） | 低 | 中小规模、已有 MQ |
| **MQ 事务消息** | 最终一致 | 高 | 低 | 中 | 使用 RocketMQ 的系统 |

## Q: Seata 框架是什么？

**Seata** 是阿里开源的分布式事务框架，提供四种事务模式：

| 模式 | 原理 | 侵入性 | 适用场景 |
|------|------|--------|---------|
| **AT 模式** | 自动拦截 SQL，生成前后镜像（undo log），自动回滚 | 低（只需加 `@GlobalTransactional` 注解） | 大多数业务场景（推荐） |
| **TCC 模式** | 业务实现 Try/Confirm/Cancel 三个方法 | 高 | 需要自定义资源预留的场景 |
| **Saga 模式** | 长事务编排，每个步骤定义补偿操作 | 中 | 长流程、第三方服务参与 |
| **XA 模式** | 数据库 XA 协议，两阶段提交 | 低 | 支持XA协议的数据库 |

### AT 模式工作流程

```
1. TM 向 TC 注册全局事务
2. RM1 执行分支事务：
   - 拦截 SQL，查询修改前数据（前镜像）
   - 执行业务 SQL
   - 查询修改后数据（后镜像）
   - 生成 undo log 并与业务 SQL 在同一本地事务提交
3. RM2 执行分支事务（同上）
4. TM 通知 TC 提交/回滚
   - 提交：异步删除 undo log
   - 回滚：根据 undo log 反向补偿
```

```
关键组件：
  TC（Transaction Coordinator）：事务协调者，维护全局事务状态
  TM（Transaction Manager）：事务管理器，定义全局事务边界
  RM（Resource Manager）：资源管理器，管理分支事务
```

---

## 一句话总结

分布式事务方案从强一致（2PC/3PC）到最终一致性（TCC/Saga/本地消息表/MQ事务消息）演变，大多数业务场景追求最终一致性即可；Seata 框架的 AT 模式是低侵入的通用方案。
