# 高并发

## 是什么

高并发指系统在**同一时间段内收到大量请求**，需要保证快速响应、数据正确、系统不崩溃。

核心指标：

| 指标 | 含义 |
|---|---|
| QPS | 每秒查询数（Query Per Second） |
| TPS | 每秒事务数（Transaction Per Second） |
| 并发数 | 同时活跃的请求数 |
| 响应时间 | 平均/ P99 响应延迟 |
| 吞吐量 | 单位时间处理的数据量 |

## 高并发三板斧

从宏观到微观，三板斧：**缓存、异步、拆分**。

### 1. 缓存——减少 DB 压力

```
请求 → 缓存命中？→ 返回
              ↓ 未命中
           查 DB → 写缓存 → 返回
```

| 层 | 方案 |
|---|---|
| 本地缓存 | Guava Cache、Caffeine |
| 分布式缓存 | Redis Cluster |
| CDN 缓存 | 静态资源边缘缓存 |

### 2. 异步——削峰填谷

同步调用的请求会阻塞线程，异步让线程立即释放：

| 方案 | 适用场景 |
|---|---|
| 消息队列（MQ） | 写操作异步化、削峰填谷 |
| 异步线程池 | 计算密集型任务异步执行 |
| 响应式编程 | WebFlux / CompletableFuture |

```
用户下单 → 写 MQ → 立即返回"下单中"
                        ↓
                    消费者异步处理 → 扣库存 → 通知结果
```

### 3. 拆分——分而治之

| 拆分维度 | 方案 |
|---|---|
| 水平拆分 | 分库分表（ShardingSphere）、数据分片 |
| 垂直拆分 | 微服务拆分，各服务独立扩容 |
| 读写分离 | 主库写、从库读 |

## 其他关键手段

### 限流

防止突发流量打崩系统：

| 算法 | 特点 |
|---|---|
| 固定窗口 | 简单，但有临界突刺 |
| 滑动窗口 | 平滑，无突刺 |
| 令牌桶 | 允许突发，最常用 |
| 漏桶 | 严格匀速 |

### 降级

系统压力过大时**主动丢弃非核心功能**，保核心链路：

- 页面降级：返回静态兜底页
- 接口降级：返回缓存数据 / 默认值
- 功能降级：关闭推荐、评论等非核心功能

### 熔断

连续失败达到阈值时**自动断开调用链**，避免级联崩溃：

```
Closed（正常）→ 失败率超阈值 → Open（熔断，直接拒绝）
                                    ↓ 等待超时
                              Half-Open（试探放少量请求）
                                    ↓ 成功 → Closed
                                    ↓ 失败 → Open
```

实现：Hystrix / Sentinel / Resilience4j

### 连接池化

避免每次请求新建连接的开销：

- 数据库连接池：HikariCP / Druid
- HTTP 连接池：Apache HttpClient / OkHttp
- Redis 连接池：Lettuce / Jedis

## 高并发架构演进

```
单机 → 垂直拆分（微服务）→ 水平扩展（集群+负载均衡）
                              → 引入缓存
                              → 读写分离
                              → 分库分表
                              → 引入 MQ 削峰
                              → CDN + 网关限流
```

## 总结

| 层级 | 手段 | 解决的问题 |
|---|---|---|
| 接入层 | CDN、网关限流、负载均衡 | 流量分发与控制 |
| 应用层 | 异步（MQ/线程池）、缓存、连接池 | 减少阻塞与重复计算 |
| 数据层 | 读写分离、分库分表 | 数据库瓶颈 |
| 容灾层 | 降级、熔断、超时重试 | 防止级联崩溃 |

## 一句话总结

> 高并发三板斧：缓存减压力、异步削峰、拆分治之，辅以限流降级熔断保系统稳定。
